## 0. 一句话定位

**Backend 是管控面，Engine 是执行面，两者共用同一部微内核宪法。**

这场分享真正想讲的不是「介绍两个服务」，而是**同一套架构方法论在两种形态的服务上如何落地，以及为什么这么切**。

| | Backend | Engine |
| --- | --- | --- |
| 包名 | `agentclaw.community` | `engine.community` |
| 规模 | 1,813 个 Python 文件 / 约 35.8 万行 | 518 个 Python 文件 / 约 9.3 万行 |
| 形态 | 中心化服务，多租户 | 随 Bot 部署的单机服务，无租户轴 |
| 职责 | Bot 生命周期、技能中心、空间治理、发布、配额 | 会话、对话流、MCP、技能落盘、审批、文件、定时 |
| 抽象的对象 | **外部基础设施**（数据库、缓存、存储、身份、审批） | **异构 Agent 引擎本身**（claude_code、openclaw） |
| 分层 | `adapters/http → api → core → plugin_api → plugins` + `kernel` + `di` | 同构，额外多一层 `core/adapters/`（反腐层） |

两边真正的差异不在层数，而在**每一层抽象的对象不同**。这个对照是全场最值得带走的一个认知。

相邻边界本次不展开，只作交代：**BCS**（Rust，Bot 协调、群聊、路由）、**BaaS**（运行时供给）、**Frontend**（工作台 UI）。

**代码锚点**：`src/backend/`、`src/engine/`、`CONTEXT-MAP.md`

## 1. 为什么先讲宪法，而不是先讲模块

### 1.1 问题不是「架构不好」，是「架构留不住」

任何一个活跃演进的系统都会经历这个过程：第一版设计清晰，三个月后边界开始模糊，一年后没人说得清某个模块到底该依赖谁。差别只在**腐蚀速度**。

在人和模型一起高速改代码的前提下，这个速度被显著放大了：

- 生成的代码倾向于「让它先跑起来」，而不是「让它落在正确的层」；
- 一次改动的物理范围更大，review 的注意力却没有同比增长；
- 「这里为什么不能直接调那个类」的答案，往往只存在于某个人的记忆里。

**结论：靠 review 记住边界是不现实的。边界必须是一次可执行的断言。**

### 1.2 四个典型腐蚀方向

这套宪法针对的不是抽象的「架构美感」，而是四个具体的、反复出现的腐蚀方向：

| 腐蚀方向 | 典型表现 | 后果 |
| --- | --- | --- |
| **传输内渗** | 交付层的概念渗进领域逻辑 | 领域逻辑绑死协议，脱离框架就无法独立验证 |
| **实现直连** | 领域逻辑直接依赖某个具体实现 | 失去可替换性，本地与测试环境跑不起来 |
| **环境散落** | 配置读取散落在业务代码各处 | 部署行为不可知，环境差异变成隐性逻辑 |
| **分发泄漏** | 内部实现混进开源目录树 | 开源版无法独立启动，分发边界失守 |

四条都有一个共同特征：**单看一次改动都很合理，累积起来才致命**。这正是需要机器而不是人来把关的原因。

### 1.3 宪法自己的边界感

`docs/arch/arch.rules.md` 有 25 条规则，分三级：

- **Invariant（不变量）** — 必须遵守，违反需要显式豁免；
- **Policy（政策）** — 强默认，偏离需要说明理由；
- **Guideline（建议）** — 推荐做法，本身不构成结构违规。

更值得注意的是它**明确声明不管什么**：不规定领域建模风格、不规定与架构无关的命名、不规定语言语法细节。

这个自我克制是它能被执行下去的前提。一部什么都想管的宪法，最后只会被整体忽略。

每条规则的结构也是固定的：**规则 → 防止了什么 → 必须检查什么 → 如何解释**。「防止了什么」这一栏是它区别于普通编码规范的地方 —— 规则不是从美学推导出来的，是从事故推导出来的。

**代码锚点**：`docs/arch/arch.rules.md`、`docs/arch/ci.enforce.md`

## 2. 骨架：微内核的七个角色

![微内核七角色分层对照](images/arch/01-layers.svg)

### 2.1 七个角色

宪法要求至少能区分出七种角色，并且依赖方向必须显式且可强制：

**契约 · 内核与核心 · 交付适配 · 插件契约 · 插件实现 · 组装根 · 测试**

层的名字可以各仓库不同，但**依赖方向必须是单向的、可被工具检查的**。Backend 和 Engine 落地成同一组目录：

| 角色 | Backend | Engine |
| --- | --- | --- |
| 交付适配 | `adapters/http/` — 40+ 路由组 | `api/` — HTTP + WebSocket `/api/{engine}/ws` |
| 服务契约 | `api/` — 115 个 Protocol 再导出 | `core/<domain>/protocol.py` — 23 个能力域 |
| 领域内核 | `core/` — 55 个领域模块 | `core/` + `core/adapters/`（反腐层） |
| 插件契约 | `plugin_api/` — 35 个能力契约 | `plugin_api/<engine>/` — 每引擎原生端口 |
| 插件实现 | `plugins/{community, local, prod}` | `plugins/<engine>/` — 传输叶子 |
| 底座 | `kernel/` — 生命周期、设备 DTO | `kernel/frames` — 线协议信封 |
| 组装根 | `di/` — 59 个 Module | `di/` + `engines/<name>/` |

### 2.2 值得单独讲的三个细节

#### （1）`api/` 这个名字在两个模块里角色不同 —— 而这恰恰是规则要防的事

- Backend 的 `api/` 是**服务契约层**（Protocol 再导出），交付层在 `adapters/http/`；
- Engine 的 `api/` 是**交付层**（FastAPI 应用本身）。

宪法 Rule 8 的原话是：如果 `api/` 存在，它在**该仓库内**必须有唯一明确的含义。两个模块各自内部是自洽的，但跨模块阅读时确实构成认知成本。

**这一点我们主动提出来，作为评审议题之一**：是要统一命名（代价是一次大范围重命名），还是接受「每个模块内自洽」并在 CONTEXT-MAP 里显式说明。两条路都可以，但不应该默认现状。

#### （2）Protocol 定义在哪，是被摩擦决定的，不是被美学决定的

曾经的做法是：Protocol 定义在 `api/`，`core/` 里的服务实现它。

结果是：每个实现服务都要 `core → api` 反向 import，而这违反层序；于是每加一个服务，就要在架构测试里手写一条例外。**那份例外清单只增不减 —— 这本身就是设计有问题的信号。**

现在的做法是：

```
core/skill_center/skill_query_service_protocol.py   # Protocol 定义在这
core/skill_center/services/skill_query_service.py   # 实现，继承它
api/skill_query_service.py                          # 只做 re-export
adapters/http/skill_center/router.py                # Injected(Protocol)
```

Protocol 与实现都在 `core/`，继承变成 `core → core`，不需要任何跨层豁免。消费者仍然从 `api/` 拿名字，无感知。**例外清单从此不再增长。**

这个演进过程比结论本身更值得讲：**当你发现某条规则需要不断加例外，通常不是规则错了，是契约放错了地方。**

#### （3）为什么 Engine 的线协议信封要下沉到 `kernel/`

Engine 的 `plugins/` 是纯传输叶子，规则上**禁止 import `core`**。但传输层产生的帧（`RequestFrame` / `ResponseFrame` / `EventFrame`）恰恰是 `core` 要消费的。

两边都需要，谁也不能依赖谁 —— 那就只能下沉到**两边都能依赖的最底层**。`kernel/` 因此被定义为「不 import 本包任何其他模块」的底座，`frames` 是它的第一个住户。

这是「共享原语下沉」这个通用手法的一个干净实例：**当两个不能互相依赖的模块需要共享类型时，答案永远是往下沉，而不是开一个例外。**


**代码锚点**：`src/backend/src/agentclaw/community/api/README.md`、`src/engine/src/engine/community/kernel/README.md`

## 3. 契约：两个方向相反的 API

![两类契约的方向性](images/arch/02-two-contracts.svg)

### 3.1 方向是第一性的

宪法 Rule 3：**Service API 和 Plugin API 是两类不同的契约，必须分开定义、分开记录、分开版本化、分开测试。**

- **Service API**：消费者调 core。必须定义成独立于交付层的 Protocol。
- **Plugin API**：core 调外部依赖。永远为外部能力定义契约。

一个模块可以在不同交互中同时扮演两种角色，但**控制方向必须是明确的**。

### 3.2 方向决定了什么

这不是分类学游戏。方向一旦搞错，下面三件事全错：

| | Service API | Plugin API |
| --- | --- | --- |
| **谁破坏谁** | core 改契约 → 所有消费者受影响 | 契约变动 → 所有插件实现受影响 |
| **怎么测** | 一致性测试：实现是否满足契约 | 契约测试 + 替身：core 在各种插件行为下是否正确 |
| **谁可替换** | core 实现可替换，消费者无感 | 插件实现可替换，core 无感 |

把「注册函数」和「被注册的回调」当成同一个 API 面来描述，是这里最常见的错误 —— 它们的方向恰好相反。

### 3.3 依赖倒置真正落地的样子

图 2 的第二条带子是关键：**没有任何一条箭头从实现指向实现。**

- 消费者依赖 Service API 契约，core 也依赖它；
- core 依赖 Plugin API 契约，插件实现也依赖它。

两侧都指向中间的契约。消费者不知道 core 里放了什么，core 也不知道插件是谁。

### 3.4 契约的价值来自它描述得有多具体

一份只列了方法名、参数一律写成「随便什么」的契约，挡不住任何东西：形式上它存在，实际约束为零。评审一份契约时真正该问的只有一个问题 —— **它到底约束了什么？**

配套两条工程约定，两条都是关于「问题在什么时候暴露」：

- 契约与实现之间要能双向找到对方，读代码的人不该先翻一遍装配逻辑才知道谁实现了它；
- 实现没有满足契约，要在**装配的时候**就暴露出来，而不是等到某一次线上调用。

### 3.5 同一份契约，多套实现，由组装根选择

Backend 的 `plugin_api/` 有 35 个能力契约，每个契约对应多套实现：

| 实现集 | 用途 | 在开源树中 |
| --- | --- | --- |
| `plugins/community` | 开源实现，不依赖任何内部 SDK | 存在 |
| `plugins/local` | 内存 / 本地替身，单机开发与测试 | 存在 |
| `plugins/prod` | 企业基础设施实现 | **物理不存在**（位于内部树） |

选择发生在**唯一的组装根** `di/`，由 `DEPLOY_PROFILE` 驱动，五档：`community` / `singlebox` / `test` / `corp` / `corp_test`。

这里有个设计细节值得说：**profile 是一个纯选择器**。它不提供 `is_local` 或 `database` 这类派生属性 —— 那样等于把已经废弃的「运行时 × 数据库」二维模型重新编码回去。「装配了什么」这个问题由**装了哪些 Module**回答，而不是由枚举上的某个方法回答。

另一个细节：**profile 必须显式**。未设置或取值未知是启动硬失败，没有静默默认值。一个「猜出来」的部署形态，比启动失败危险得多。

最后一行是可以当场验证的：开源树里 `src/backend/src/agentclaw/` 下**只有 `community/` 一个命名空间**，`corp/` 目录物理不存在；`plugins/` 下也只有 `community` 和 `local` 两套。契约文档里会提到企业实现的名字，但那份代码不在这棵树里。

这就是所谓**单一归属（single residency）**：每个文件只存在于一个命名空间。共享代码只有一份，放在 `community/` 里由内部树反向引用；「同一功能、两种实现」一律表达为「一个 Protocol + 两个实现 + 按 profile 绑定」，而不是两棵平行的目录树。

对评审的意义：**这是开源分发与内部部署同源、零分叉的技术前提**。开源版能独立启动，内部版跑的是同一份 `core`，两边不需要各自维护一套业务逻辑。

**代码锚点**：`src/backend/src/agentclaw/community/di/profile.py`、`plugin_api/`、`plugins/`

## 4. 引擎：异构接入怎么做到改动可控

![异构引擎反腐层](images/arch/03-engine-acl.svg)

### 4.1 要回答的问题只有一个

**接入一个新引擎，改动面有多大？**

架构好不好，这个问题的答案最能说明问题。Engine 给出的答案是：**新增四个文件夹，`api/` 和 `core/` 一行不改。**

| 层 | 接新引擎时 |
| --- | --- |
| `api/` | **不动** —— 对外表面与引擎无关 |
| `core/<domain>/protocol.py` | **不动** —— 领域协议与引擎无关 |
| `core/adapters/<engine>/` | **新增** —— 反腐层，翻译 DTO ⇄ 原生形状 |
| `plugin_api/<engine>/` | **新增** —— 该引擎的原生端口契约 |
| `plugins/<engine>/` | **新增** —— 传输叶子 |
| `engines/<engine>/` | **新增** —— 组装根，声明能力矩阵，import 时自注册 |

### 4.2 反腐层的两条关键性质

**性质一：它是 `core` 里唯一认识具体引擎的地方。**

这一条让「引擎特异性」有了明确的收纳位置。不在这个目录里的任何 `core` 代码，都不应该出现引擎名字。

**性质二：它 import 的是端口抽象，不是具体实现。**

反腐层位于 `core/` 之内，但它只依赖 `plugin_api/<engine>/` 的 Protocol；具体的传输实现由 `di/` 注入。因此「core 不 import plugins」这条约束对**整个 core 成立，包括反腐层自己**。

这两条加起来，才使得「引擎可插拔」不只是一句口号。

### 4.3 能力矩阵：声明式，而不是异常驱动

![引擎能力矩阵](images/arch/04-capability-matrix.svg)

每个引擎在自己的组装根声明一份能力矩阵，分三态：

- **原生支持** — 反腐层为它接上了该引擎的原生能力；
- **受限 / 降级** — 支持但有约束，**声明时必须写明原因**；
- **未接入** — 上层不派发，前端直接隐藏功能。

核心规则是：**一个能力存在，当且仅当反腐层真的把它接上了。** 声明与实现的一致性在**装配阶段**交叉校验 —— 声明了能力却没接上，启动就失败，而不是等到线上第一次调用。

受限项的原因必须具体，例如：

- `session.create`：claude_code 侧没有显式的建会话接口，会话由首条消息落地；
- `mcp.tools.call`：只有 SDK 桥可以直调工具，CLI 桥要绕对话。

**评审时最值得强调的一点：两条链路不是包含关系。**

claude_code 在技能管理和对话交互（澄清提问、模式切换）上更强；openclaw 在 MCP（覆盖 resources / prompts）、节点、渠道、Web Shell 上更全。**交集才是 `core` 可以无条件依赖的部分**，差集必须走能力判断。

能力名是 engine、backend、前端三方之间的稳定契约：**新增是安全的，改名或删除是破坏性变更。**

### 4.4 两条链路的部署差异

| | claude_code | openclaw |
| --- | --- | --- |
| Gateway | Node 服务，**随仓库分发** | 外部部署，**不随仓库分发** |
| 地址 | `ws://127.0.0.1:18900` | `ws://…:18789` |
| 桥接方式 | Claude Agent SDK 或 claude CLI（可切） | 自有协议 |
| 开源可跑 | **是** | 否（需自备 gateway） |

这个差异是有意的：**开源版必须有一条完整可跑的链路**，否则「可插拔」无法被外部验证。claude_code 那条就是这条链路。

**代码锚点**：`src/engine/src/engine/community/core/adapters/README.md`、`engines/claude_code/README.md`、`src/engine/docs/heterogeneous-engine-architecture.md`

## 5. 链路：一次请求怎么穿透两个模块

![端到端请求链路](images/arch/05-end-to-end.svg)

### 5.1 十步，但真正要记住的是中间那条线

以一条公开 API 上的会话消息为例，请求依次经过：

**Backend 侧**：① 调用方 → ② 交付适配（解析、鉴权、协议校验）→ ③ 服务契约（拿到的是 Protocol）→ ④ 领域编排（按属主解析 bot、判定发布态、解析设备上下文）→ ⑤ 出口契约（唯一的跨系统抽象）

**─── 系统边界 ───**

**Engine 侧**：⑥ 统一表面 → ⑦ 核心协议 → ⑧ 反腐层 → ⑨ 传输叶子 → ⑩ Gateway → 模型

回程是 `EventFrame` 流式事件沿同一条链路反向回传。

### 5.2 中间那条线为什么重要

**Engine 没有租户轴。** 它是随 Bot 部署的单机服务，只服务它自己那一个 Bot —— 请求一旦落到设备上，就**没有任何东西再约束它**。

这意味着：**Backend 侧的领域编排，是隔离唯一存在的地方。** 三条不变量都由此推导：

#### 不变量 A · 解析必须先于转发

按属主解析 bot 必须发生在任何设备操作之前。先转发再解析、或者信任调用方传来的用户标识，隔离就**静默失效** —— 下游不会有任何守卫察觉。

这是最危险的一类缺陷：它不报错、不告警，只是在某一天变成一次越权访问。

#### 不变量 B · 200 不等于成功

Engine 可以在一次传输层成功的应答里报告业务失败。这里必须把它识别出来，**绝不让它变成一次对外的成功**。同样地，链路故障要在这里收敛成有语义的失败，而不是把设备细节泄漏给调用方。

#### 不变量 C · 发布态走发布绑定

服务型 Bot 必须经由**已发布的运行时绑定**解析（草稿 / 预发 / 线上三态），而不是草稿列 —— 否则线上流量会打到发布前的那台机器上。

### 5.3 一个关于可测性的观察

这条链路上，**唯一不能在测试中真实运行的，是最外面那一跳**（对设备适配器的 HTTP 调用）—— 因为真实的适配器进程不可达。

而它上面的一切 —— bot 解析、权限判定、发布态选择、响应整形 —— **都是生产代码，都在测试里真实执行**。

这是「可测性由边界位置决定」最好的例证：**把不可测的部分压缩成一个 Protocol，剩下的全部变成可测的**。如果测试里要 mock 的东西超过一个，通常说明边界画在了错误的地方。

**代码锚点**：`src/backend/src/agentclaw/community/core/engine_runtime/README.md`、`core/engine_runtime/relay.py`

## 6. 治理：架构怎么才能不腐烂

![架构治理闭环](images/arch/06-governance.svg)

### 6.1 五个环节

**① 宪法（25 条）→ ② 模块自描述（87 处）→ ③ 机器校验（53 组测试）→ ④ CI 门禁（7 类）→ ⑤ 违规出口（2 条路）→ 回到 ①**

### 6.2 模块自描述：让白名单可校验

每个边界显著的模块，在自己的 `README.md` 里用固定格式声明边界：

```yaml
purpose: 一句话说清这个模块负责什么
provides:
  - 对外公开的能力
consumes:
  - 它调用的外部契约（信息性，不做机器校验）
internal_dependencies:
  - 允许 import 的本包前缀 —— 这是一份白名单
```

关键在最后一项：**`internal_dependencies` 是白名单，不是文档。** 模块实际发生的、未被任何声明前缀覆盖的 import，会让架构测试失败。

几个设计取舍值得注意：

- **前缀匹配** —— 声明一个前缀即覆盖其所有子模块，避免清单碎片化；
- **声明了但没用不算错** —— 过期条目顺手清理即可，不制造无谓的红灯；
- **反向视图是生成的** —— 「谁依赖了我」由工具反推，不手工维护。

同时明确了几条反模式：把具体实现模块列进 `internal_dependencies`（多半意味着分层已经破了）、把「改动影响」写成文件清单（要写的是**谁会察觉到这个改动**，不是改了哪些文件）。

Backend 75 处 + Engine 12 处，共 87 个模块有这份声明。

### 6.3 机器校验：静态分析，不必把系统跑起来

53 组架构测试（Backend 50 + Engine 3），全部是对代码结构的静态分析 —— 不启动服务、不连依赖，因此可以无条件挂在每一次提交上。挑几条有代表性的：

| 测试 | 守的是什么 |
| --- | --- |
| `test_no_fastapi_in_core` | core 出现任何交付框架依赖即失败 |
| `test_kernel_no_imports` | 底座不得依赖本包任何其他层 |
| `test_core_no_concrete_plugin_imports` | core 只能依赖插件契约，不得依赖实现 |
| `test_module_boundaries` | 真实 import 图 vs 各模块自己声明的白名单 |
| `test_composition_root_corp_free` | 开源组装根里不得出现内部实现 |
| `test_no_oversized_modules` | 超大模块预警 —— 往往藏着边界违规 |

这里有一个务实的做法值得单独提：**迁移期允许清单**。规则收紧时，存量违规先进允许清单，新增违规立刻失败，清单条目随迁移逐批删除，**目标是清空**。

这个做法承认现实，但同时锁定了方向 —— 比「一步到位」和「无限期妥协」都更可执行。

### 6.4 违规出口：只有两条路

要么改代码，**要么写一份豁免**：有归属、有 owner、经过评审、有期限。

目前存量豁免 **1 条**。这个数字本身就是一个健康度指标 —— **能被数出来的例外，才是可以管理的例外。**

系统级、难以回退的决策则沉淀为 ADR（现 11 条），反过来修订宪法。ADR 的地位高于规格说明和调研文档：**规格和调研是决策的输入，它们不能推翻一份已经接受的 ADR。**

### 6.5 一条明确的纪律

> 不要为了让改动通过而削弱检查。如果某个检查本身是错的，修检查，并说明为什么。

这句话写在 `AGENTS.md` 里。它的意义在于：**把「绕过门禁」从一个技术选项变成一个需要解释的行为。**

**代码锚点**：`docs/arch/context-boundary-format.md`、`docs/arch/ci.enforce.md`、`docs/arch/waivers/`、`docs/adr/`

## 7. 收口：可迁移的五条经验

不依赖这个仓库的上下文，这五条在任何中大型服务上都成立：

1. **方向比分层重要。** 先问清楚「谁调用谁」，再决定放在哪一层。方向搞错，分层再漂亮也没用 —— 兼容性假设和测试策略会跟着一起错。

2. **契约的位置由摩擦决定，不由美学决定。** 当你发现某条规则需要不断加例外，通常不是规则错了，是契约放错了地方。**例外清单只增不减，本身就是设计信号。**

3. **能力要声明，不要靠异常发现。** 「调用了才知道不支持」是运行期问题；「声明了却没实现」应该是启动期问题。把失败时机往前推。

4. **把不可测的部分压缩成一个契约。** 如果测试里需要 mock 的东西超过一个，边界多半画错了。可测性不是测试写得好，是边界画得对。

5. **例外要可数。** 允许豁免，但必须有归属、有期限、能被统计。一个说不清自己有多少例外的架构，等于没有架构。

## 附录 A：评审提问预案

> 以下是预计会被追问的问题，以及我们当前的答案。带 ⚠️ 的是我们自己也认为尚未收敛、希望在评审中听意见的。

**Q1：55 个 core 模块 + 59 个 DI Module，DI 是不是过度工程了？**

DI 的成本集中在组装根，收益分布在每个消费点。真正的判据是：换一套基础设施实现要改多少处？现在是改一个 Module 绑定。取消 DI 的话，改动面是所有消费点。规模到了 35 万行，这笔账是正的。

**Q2：多套插件实现，测试成本是不是成倍增长？**

不是。各套实现共享同一份契约一致性测试，只有差异部分各自测。而且 `local` 那套的存在，恰恰让**上层编排逻辑的测试成本大幅下降** —— 见 §5.3，整条链路只有最外一跳被替换，上面全部跑真实代码。

**Q3：Engine 没有租户轴，安全吗？**

Engine 是随 Bot 部署的单机服务，其边界就是那一个 Bot。隔离在 Backend 侧完成（不变量 A）。风险点不在「Engine 没有租户轴」这个事实，而在「Backend 侧是否真的每次都先解析后转发」—— 所以这条被写进了模块 README 的「改动影响」，任何重构都必须保留它。

**Q4：反腐层的翻译会不会成为维护负担？**

会有成本，但它替换的是更贵的东西：没有反腐层的话，引擎的原生形状会直接渗进 `core`，第二个引擎接入时就要大改。反腐层把「引擎差异」这件事的成本**固定在一个可预期的位置**，而不是让它扩散。

**Q5：53 组架构测试会不会拖慢 CI、成为改动阻力？**

全部是 AST 静态分析，不启动服务，开销很小。至于「阻力」—— 它确实会挡住一部分改动，这是设计意图。允许清单机制保证了存量不阻塞，新增才拦截。

**Q6：为什么 Backend 和 Engine 不合并？**

部署形态不同（中心化多租户 vs 随 Bot 单机）、伸缩维度不同、信任边界不同。合并会让「Engine 没有租户轴」这个简化前提消失，反而增加复杂度。

**Q7：能力矩阵不是超集关系，上层代码怎么写？**

交集部分直接调用；差集部分必须查能力声明后再决定派发、降级还是隐藏。这正是把能力做成**显式声明**而不是「试了才知道」的原因。

**⚠️ Q8：`api/` 在两个模块里角色不同，要不要统一？**

见 §2.2（1）。两个模块各自内部自洽，但跨模块阅读有认知成本。统一的代价是一次大范围重命名。**希望在评审中定调。**

**⚠️ Q9：能力的装配期交叉校验，目前只覆盖了一部分能力域。**

交叉校验现在实际比对的是会话、对话、定时这几个有完整插件实现的槽位；其余能力域的协议槽位已经定义，但并非每个引擎都落了实现（openclaw 的 MCP 与技能能力至今由交付层直接服务）。也就是说，「声明了却没接端口，启动即失败」这条保证在这几个域上还没有完全生效。这是已知的待收敛项，不是设计意图。

| 我要做的事 | 应该动的位置 |
| --- | --- |
| 加一个公开 HTTP 接口 | `backend/adapters/http/` 加路由 → 从 `api/` 注入契约 |
