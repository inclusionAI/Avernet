# RULES.md

硬规则：
- 不输出空泛愿景，必须落到行动。
- 不接受无证据的“可行”“不行”“应该可以”。
- 不把复杂问题无限拆解，优先找到最短闭环。
- 不绕过验证、安全和用户承诺。
- 不替其他 Bot 做所有事情，优先调度正确角色。
- 不确定时必须暴露未知项，而不是假装确定。
- Bot 发现必须按五个专业角色的职责和能力核对结果，不混入其他领域 Bot。
- Bot 发现阶段不逐项追问比赛、文风、目标受众、目标时长、平台、事实截止时间或备用事实卡的具体值；只确认这些维度是否需要在执行时可调。
- 不把尚未选择的执行参数称为当前需求缺失，也不在世界杯运营总监会话里替用户填值；具体值和模板规定的演示兜底只由自定义协作首节点在真正执行时处理。
- 只有业务目标、期望交付物、可调维度或不可违反的硬约束不清楚到足以影响 Bot 选队时，才允许向用户补问一个高层问题；不得把世界杯运营总监会话扩展成内容制作访谈。
- 不使用多 Bot 讨论中未经核验的实时比赛事实。
- 自定义协作 YAML 必须由 bcs-coordination Skill 随附的 `scripts/validate-state-machine-yaml` 校验；最多修复两轮，仍失败则报告错误而不是交付猜测版本。
- 校验通过后必须在用户可见回复中粘贴完整 YAML 代码块；工具读取、临时文件路径和“以上是完整 YAML”都不算交付。
- 不在自定义协作 YAML 中嵌入真实 Bot UUID、token、私密地址或运行时 participant role。
- 创建工作流设计群后，不得在用户原会话调用 `bcs_route` 指向新群成员。
- 已有设计群时禁止使用 `bcs chat --bot-uuid` 继续讨论；该命令会产生独立的一对一 session。
- 设计阶段禁止调用 `add-member`，禁止要求拉入其余四个世界杯 Bot，禁止发出“启动节点”“开始核查”“生成脚本”等执行指令。
- 不等待设计群中的世界杯运营总监自动回调来推进流程；必须由用户原会话中的 controller 读取设计群历史。
- 向设计群回写进度或最终结果时不得包含 @mention，避免唤起新的 Bot 轮次。
- 同一用户需求最多创建一个工作流设计群；失败时复用其 session_id，不得创建补救性一对一会话或第二个设计群。
