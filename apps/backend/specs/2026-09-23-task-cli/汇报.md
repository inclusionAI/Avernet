# task-cli 与分布式接力执行：设计汇报稿

> 目标设计，不代表当前代码已经实现。详细合同以 [task-cli 设计](design.md)、[端到端接力设计](end-to-end-relay-design.md) 和 [Bot S1–S6 函数式协议](../2026-09-16-distributed-relay-execution/bot-s1-s8-functional-contract.md) 为准。

## 1. 汇报结论

用户通过 `task-cli` 输入一句话目标，在同一会话内澄清并确认 `TaskSpec`。**确认只冻结规格**；随后 CLI 用 `session_id` 请求 `/start`，Backend 构造内部 `TaskInfoRequest` 并调用 `TaskService.execute()` 创建正式任务和根节点，返回 `TaskOpResult(task_id, node_id)`，根节点满足 `task_id == node_id`。若确认后进程中断，`resume` 只读恢复，用户可选择继续创建，不重复确认。

每一棒 Bot 从指令取得 `task_id/node_id`，在 S1 从 Task Module 拉取权威 `TaskContext`，执行后写入节点事实。本棒依据根任务规格和已完成节点产出本地推理任务级 `task_gaps: list[str]`，再按“**缺什么 → 下一棒做什么 → 谁来做 → 真正交接**”完成接力。任务级 gaps 不落图；节点级验收 `gap_items` 仍保存在节点运行事实中。

```text
task-cli 输入 → START/CONTINUE 澄清 → CONFIRM 冻结 TaskSpec
             → CLI POST /start {session_id} → Backend 构造 TaskInfoRequest
             → TaskService.execute → TaskOpResult
             → 首棒启动指令(task_id, node_id) → Bot S1 拉取 TaskContext
             → S2 缺口 → S3 能力 → S4a 执行 → S4b 上报执行事实
             → S5.1 更新缺口 → S5.2 规划下一棒 → S5.3 搜索候选
             → S5.4 决定执行者 → S5.5 一次上报规划与选人结果
             → Skill S6 调 /dispatch，Backend 投递下一棒指令 → 下一棒 S1，直至收口
```

## 2. 用户动线：发起、澄清、确认、查询

### 2.1 用户可见命令

```bash
task-cli "<一句话任务目标>"
task-cli "<一句话任务目标>" @<bot-ref> bot
task-cli "<一句话任务目标>" @<group-ref> group
task-cli resume <session-id>
task-cli get <task-id>
```

Human 未显式指定目标时，按“用户同名且可运行的 Bot → 用户配置的 default Bot → 按目标匹配能力 → 可访问 Bot 中随机选择”解析；没有可用 Bot 时提示创建或启用。选中的稳定 Bot ID 写入 intake 结果，后续澄清不重新抽取。显式 `@bot/@group` 必须校验可见性与发起权限。Bot 身份发起时默认使用自身；第一版不通过命令显式指向其他 Bot/Group。

`task-cli resume <session-id>` 是跨进程恢复入口。正常交互中 CLI 自动持有 `session_id`；补充、确认、取消均在会话内操作，不另设 `reply/select-task/select-target/confirm/cancel` 子命令。`task-cli get` 查询正式任务图谱，不参与澄清。

### 2.2 一次澄清会话

| 用户/CLI 动作 | 内部 `TaskIntakeAction` | 服务端处理 | 返回 |
| --- | --- | --- | --- |
| 输入一句话目标 | `START` | 解析目标；Skill 识别初始 `TaskSpec`、缺项和追问；生成 `session_id` | `TaskIntakeResult(CLARIFYING)` |
| 在会话内补充信息 | `CONTINUE` | 基于已保存规格修订 `TaskSpec`；保持验收项稳定 ID；重算完整性 | 更新后的 `TaskIntakeResult(CLARIFYING)` |
| 跨进程恢复 | `RESUME` | 校验会话所有权，只读已保存结果 | 原 `TaskIntakeResult` |
| 点击确认卡 | `CONFIRM` | 要求完整 `TaskSpec`；冻结结果，不创建任务 | `TaskIntakeResult(CONFIRMED)` |
| 点击取消 | `CANCEL` | 终止澄清，不创建任务 | `TaskIntakeResult(CANCELLED)` |

只有 `CLARIFYING/CONFIRMED/CANCELLED` 三种状态。`CLARIFYING + TaskSpec 完整` 即展示确认卡，不另设 `READY_FOR_CONFIRMATION`。暂不支持“一次输入拆成多个任务候选”的选择状态。

### 2.3 澄清输入、上下文与结果

```python
@dataclass(frozen=True)
class TaskIntakeCommand:
    action: TaskIntakeAction  # START | RESUME | CONTINUE | CONFIRM | CANCEL
    message: str | None = None
    requested_target: IntakeTarget | None = None

@dataclass(frozen=True)
class TaskIntakeContext:
    session_id: str | None
    owner_user_id: str
    source_type: TaskSourceType
    caller_bot_id: str | None = None

@dataclass
class TaskIntakeResult:
    session_id: str
    owner_user_id: str
    source_type: TaskSourceType
    status: TaskIntakeStatus  # CLARIFYING | CONFIRMED | CANCELLED
    target: IntakeTarget | None = None
    task_spec: TaskSpec | None = None
    missing_fields: list[str] = field(default_factory=list)
    questions: list[str] = field(default_factory=list)
    create_time_ms: int = 0
    update_time_ms: int = 0

class TaskService:
    async def intake(
        self, command: TaskIntakeCommand, context: TaskIntakeContext,
    ) -> TaskIntakeResult: ...
```

`TaskIntakeCommand` 只表达本次用户动作；`TaskIntakeContext` 由 Adapter 从认证身份、调用来源和会话控制信息构造，用户无需填写。`session_id` 在 `START` 时由服务端生成，后续动作沿用。`TaskIntakeResult` 是唯一 intake 持久化状态和所有动作的直接返回对象，不含 `task_id/node_id`。

`TaskSpec` 是确认前后共用的业务规格，至少明确 `goal.objective`、交付物、`goal.acceptances` 和约束是否存在；用户明确“无约束”可表示为空列表。验收项首次生成时分配稳定 ID。`owner_user_id/source_type/target` 由系统解析或校验，不由 Skill 擅自填写。

### 2.4 HTTP 与正式任务创建

```http
POST /api/v1/collaboration/tasks/intake
```

- 请求体：`TaskIntakeCommand`；`session_id` 属于会话控制信息，认证和调用事实由 Adapter 组装为 `TaskIntakeContext`。
- 响应 `data`：`TaskIntakeResult`，包括 `CONFIRM`；不定义同构 DTO，也不返回任务 ID。
- 设计尚未指定 `session_id` 在 HTTP 层的具体承载位置，实施时须在 Service API 合同中定稿。

确认后走独立 HTTP 创建链路；CLI 不构造 `TaskInfoRequest`：

```python
confirmed_result: TaskIntakeResult = await task_service.intake(confirm_command, context)
# CLI 随后 POST /api/v1/collaboration/tasks/start
# 请求体：{"session_id": confirmed_result.session_id}

# Backend 应用层处理该请求：
session_id: str = body["session_id"]
result: TaskIntakeResult = load_and_validate_confirmed_intake(session_id)
request: TaskInfoRequest = build_task_info_request(result)
created: TaskOpResult = await task_service.execute(request)
assert created.task_id == created.node_id  # Relay 唯一根节点
```

`build_task_info_request` 读取已确认 `TaskSpec`、结果中的 owner/source/target，并由服务端策略补齐 `owner_bot_id`、`execution_config`（含会话关联与冻结的 `initial_target`）。Group 目标映射出的 manager Bot 只是归属 Bot；根节点仍以 Group ID 作为首棒执行者。`source_type` 记录发起来源，不代替目标类型。不重新调用 LLM 改写规格。正式创建继续复用 `TaskService.execute()`，不新增同构的 Service `start()`；按 `session_id` 的内部唯一关联处理确认后重试，返回同一任务标识。HTTP `/start` 只是确认后的会话提交入口，服务端应用层负责转换，Adapter 不承担业务策略。

## 3. 执行领域对象：事实、推理和上报分离

| 对象 | 关键内容 | 作用与归属 |
| --- | --- | --- |
| `TaskContext` | `task_id`、`node_id`、根/当前规格、仅前序 `all_done_output`、本棒已接纳的可选执行 patch/规划结果 | Task Module 从图谱即时投影；S1 获取，不持久化对象或在派发消息中复制权威快照 |
| `task_gaps: list[str]` | 尚未满足的根任务验收缺口 | S2/S5.1 在 Bot 本地推理；不作为图谱或 `TaskContext` 字段 |
| `BotCapability` | Bot 身份、已激活 Skill、可用工具 | S3 的真实能力输入；不写任务图谱 |
| `CapabilityMatchResult` | `ACCEPTED/DECLINED`、`actual_goal` 或失败原因 | S3 本地决策，传给 S4a |
| `TaskNodePatch` | `actual_goal`、`output_patch`、`actual_goal_acceptance_result`、执行决策/异常 | S4a 产出；S4b 上报后写入当前节点运行事实 |
| 未落图 `TaskNode` | 下一棒 `task_spec`，逐步填入 `run_info.assignee/run_mode` | S5.2 初始化，S5.4 填执行者，S5.5 一次上报；`node_id/status/node_run_graph` 由 Backend 补齐 |
| `BotCandidate` / `SearchResult` | 搜索候选 / 本地选择结果 | S5.3/S5.4 使用；不单独写图或再次上报 |
| `TaskReportCommand` / `TaskReportResult` | 统一事件命令 / 接纳与迁移结果 | S4b、S5.5 共用 `TaskService.report()`，不是每步新造返回类 |

`TaskNode.run_info.acceptance_result.gap_items` 是**节点级验收事实**，照常保留；不保存的是跨节点重算的**任务级** `task_gaps`。`TaskContext.all_done_output` 严格只投影本棒之前的已接纳前序事实，本棒即使已上报也不纳入；本棒事实由可选 `accepted_execution_patch` 单独投影，S5.1 只追加一次。已接纳的规划结果由 `accepted_plan_report` 投影，恢复时可取回原 `target_node_id`，不重做 LLM 规划。

```python
@dataclass(frozen=True)
class TaskReportCommand:
    task_id: str
    node_id: str
    event_id: str
    relay_token: str
    event_type: TaskReportEventType  # EXECUTION_RESULT | PLAN_RESULT
    event: TaskNodePatch | TaskNode | None
    progress_reason: str = ""
    failure_reason: str | None = None
    task_acceptance_result: AcceptanceResult | None = None

@dataclass(frozen=True)
class TaskReportResult:
    status: TaskReportStatus  # APPLIED | PROCESSING
    target_node_id: str | None = None
    task_completed: bool = False
    task_hung: bool = False
    bbs_publish_pending: bool = False  # 仅表示发布意图已持久化
```

`EXECUTION_RESULT` 的 `event` 为 `TaskNodePatch`。`PLAN_RESULT` 的 `event` 为已填执行者的未落图 `TaskNode`，或在任务收口/规划失败时为 `None`。Backend 首派前生成 `relay_token`，同一 `node_id` 重试时轮换；Bot 原样携带当前代次值。Bot 调用层生成 `event_id` 并在同一事件的 HTTP 重试时复用；两者都不是 Bot 身份凭证。Bot 不传 `dispatch_id`、图谱版本或自报身份。旧执行持旧代次迟到上报被拒；同节点重试时 S1 只投影当前尝试的接纳阶段。`PROCESSING` 不推进到下一步。

## 4. 每一棒执行：输入 → 处理 → 输出

| 步骤          | 输入 | 处理与执行方式 | 输出 | Task API |
|-------------| --- | --- | --- | --- |
| S1：获取上下文    | `task_id`、`node_id`：首棒与后续棒均来自 Runner 指令，恢复来自持久记录 | Bot Runtime 拉取本节点上下文；Task Module 投影根规格、当前规格和已接纳事实 | `TaskContext` | `GET /api/v1/collaboration/tasks/{task_id}/nodes/{node_id}/context` |
| S2：计算缺口     | `TaskContext` | Skill 比较根任务验收项和 `all_done_output`，推理本棒执行前的任务级 gaps | `task_gaps: list[str]` | 无 |
| S3：能力匹配     | `current_task_spec: TaskSpec`、`task_gaps`、`BotCapability` | Skill 判断当前 Bot 是否能覆盖节点目标，并裁剪 `actual_goal` | `CapabilityMatchResult` | 无 |
| S4a：执行当前节点  | `TaskContext`、`CapabilityMatchResult` | Bot 仅执行接受的 `actual_goal`，形成本节点业务产出和逐项验收；拒绝时不调用业务工具 | `TaskNodePatch`，关键字段 `output_patch`、`actual_goal_acceptance_result` | 无 |
| S4b：上报执行    | `TaskNodePatch` | Runtime 转为 `TaskReportCommand(EXECUTION_RESULT)`；Backend 接纳并写当前节点事实 | `execution_report: TaskReportResult` | `POST /api/v1/collaboration/tasks/callback/report` |
| S5.1：更新缺口   | `TaskContext`、`TaskNodePatch` | Skill 合并历史与本棒事实，重算根任务 gaps；无缺口时生成根任务验收 | `task_gaps: list[str]`、`task_acceptance_result: AcceptanceResult \| None` | 无 |
| S5.2：规划下一棒  | `TaskContext`、`task_gaps`、`TaskNodePatch` | 有缺口时初始化**一个**未落图 `TaskNode`；无缺口返回 `None`；规划不了则抛 `PlanningUnavailable` | `next_node: TaskNode \| None` | 无 |
| S5.3：搜索候选   | `TaskContext`、`next_node` | Runtime 用 `next_node.task_spec.goal.objective` 搜索；`task_context.node_id` 只标记当前棒搜索轨迹 | `candidates: list[BotCandidate]` | `POST /api/v1/collaboration/tasks/search` |
| S5.4：决定执行者  | `next_node`、`candidates` | Skill 本地决定单 Bot、协作群或 MISS，填同一未落图节点的执行信息；不落图 | 已填执行者的 `next_node: TaskNode` | 无 |
| S5.5：统一上报规划 | `TaskReportCommand(PLAN_RESULT)`；由根任务验收、已填执行者的节点、或规划失败三选一构造 | Runtime 只上报一次；Backend 原子收口或创建唯一后继、写选人决策和待投递意图 | `planning_report: TaskReportResult` | `POST /api/v1/collaboration/tasks/callback/report` |
| S6：实际交接     | 后继棒：`task_id`、`planning_report.target_node_id`；首棒/恢复：待投递意图。Backend 据此读取权威 `next_node: TaskNode` | Skill 调 HTTP；Adapter 校验身份并调用 `TaskDispatcher.dispatch(next_node)`，接力策略内部调用 Runner 投递；后台消费者复用该派发逻辑 | `dispatched_node: TaskNode`；成功表示投递通道接纳，下一棒进入 S1 | `POST /api/v1/collaboration/tasks/dispatch` → `TaskDispatcher.dispatch(next_node)` |

S4a 的 `output_patch` 是当前 `actual_goal` 的业务交付，例如 `{"result": "根因分析及证据"}`；`actual_goal_acceptance_result` 是对该目标验收项的逐项结论，包含 `done_items/gap_items`。两者先存在本棒 `TaskNodePatch`，只有 S4b 接纳后才成为图谱事实。S5.1 的 `task_acceptance_result` 则验收**根任务**，不能与节点级验收混用。

### 4.1 S5.5 的三种互斥结果

```text
task_gaps == []，根任务验收非空
  → PLAN_RESULT(event=None, task_acceptance_result=根任务验收)
  → Backend 将任务收口；不创建下一棒，不进入 S6

task_gaps != []，S5.4 得到已填执行者的 next_node
  → PLAN_RESULT(event=next_node)
  → Backend 创建唯一目标节点；HIT 记录待投递意图，Skill 调 S6 HTTP 派发；MISS/BBS 发布招募，不进入 S6

task_gaps != []，S5.2 抛 PlanningUnavailable
  → PLAN_RESULT(event=None, failure_reason=非空原因)
  → Backend 进入 HUNG/待干预；不能误判为完成
```

S5.3 搜索故障由 Runtime 重试，不伪装成 S5.2 规划失败。Backend 对同一逻辑 `PLAN_RESULT` 的重试返回原 `target_node_id`，同键不同内容返回冲突。

## 5. S6：统一派发与可恢复交接

S5.4 已在 Bot 本地决定执行者，S5.5 已将决策随规划节点一次接纳。后继棒 Skill 在 S6 调用 `/dispatch`，Backend **不再选人**，只让被选中的下一棒真正收到任务指令；首棒和失败恢复由后台消费者触发同一 Dispatcher。

```python
# 后继棒 Skill 调用 HTTP，只提交 task_id、target_node_id。
# 首棒与失败恢复由 Backend 消费待投递意图触发同一逻辑。
next_node = await task_graph_service.get_node(task_id, target_node_id)
dispatched_node = await task_dispatcher.dispatch(next_node)
# 策略内部调用 TaskRunner.start_run(next_node)。成功仅表示通道接纳，
# 不表示节点执行完成；失败由 Backend 保留待投递意图并重试。
```

HTTP Adapter 与 Backend 消费者都先从图谱读取权威节点，再调用同一个 Dispatcher；由 Dispatcher 内部认领以 `(task_id, target_node_id)` 唯一标识的 `PENDING` 投递意图：

```text
TaskDispatcher.dispatch(next_node) -> dispatched_node
  # S6 唯一直接派发接口；按 runtime_profile 加载 relay_handoff 策略
  → Dispatcher 校验可信调用身份与节点状态、认领意图
  → 策略校验已落图执行者
  → 策略内部调用 TaskRunner.start_run(next_node)
  → 生成接力 Prompt，向 assignee Bot/协作群投递 task_id + node_id
下一棒 S1 → GET 节点级 context API
```

指令可以含执行提示，但不携带权威 `TaskContext` 快照。`dispatch(next_node)` 成功返回 `TaskNode` 只表示内部 Runner 已获投递通道接纳，**不表示下一棒完成**；Runner 返回 `False` 或抛错时策略必须使 `dispatch` 失败。Bot 在 S5.5 后立即崩溃也不丢接力，Backend 扫描待投递意图补发；HTTP 请求与后台消费者进入同一 Dispatcher，只能认领同一逻辑交接。已投递重试返回权威节点，投递中返回可重试的处理中响应。至少一次投递下消费端按目标节点去重，不能承诺外部业务副作用恰好一次。目标 Relay 链路复用 Bot 可调用的 `/dispatch`，但不增加 `TaskService.dispatch_task` 包装方法。

### 5.1 模式隔离与策略装配

任务创建时将 `orchestration_mode` 和 `runtime_profile` 策略标识冻结到执行图；profile 不是策略实例。组合根在进程启动时实例化白名单策略并注册，Dispatcher/Runner 入口按 `(orchestration_mode, strategy_name)` 查表，不在方法内写模式分支。

```yaml
# 中心化模式：保留框架规划、选人和执行
orchestration_mode: centralized
runtime_profile:
  planner_strategy: default
  dispatcher_strategy: default
  runner_strategy: default

# 分布式接力：Bot 自行规划与选人；统一派发/执行入口加载 Relay 策略
orchestration_mode: relay
runtime_profile:
  dispatcher_strategy: relay_handoff
  runner_strategy: relay_prompt
```

统一 `dispatch(node)` 的成功语义是“指令已被投递通道接纳”。中心化 Dispatcher 的 `default` 策略保留搜索/选人，但需把原先外置的 Runner 调用纳入策略以符合该语义；Relay `relay_handoff` 策略只校验 S5.5 已持久化的 `assignee`、`run_mode` 和节点状态，不重复搜索或改派，然后在内部调用 Runner。Relay `relay_prompt` Runner 策略生成“从 S1 拉取上下文、执行本棒至 S5.5”的指令并真正投递。Relay **省略** `planner_strategy`，既不设 `null`，也不填 `default`，不调用中心化 `TaskPlanner`。配置解析器必须按模式校验；策略缺失时显式失败，不回退中心化实现。当前解析器给缺省 planner 补 `default`，实施时须同步迁移。

## 6. 具体推演：支付失败率峰值复盘

以下是**目标流程示例**，用于解释两棒接力，并非声称当前版本可直接运行。

1. 用户输入 `task-cli "复盘昨晚支付失败率峰值，给出根因、影响范围和处置建议"`。默认目标解析为 `bot-payment-diagnosis`。Intake Skill 生成含 `ac1` 影响范围、`ac2` 根因证据、`ac3` 处置建议的 `TaskSpec`。如有缺项，CLI 持续展示追问；规格完整后展示确认卡。
2. 用户点击确认。`TaskService.intake(CONFIRM)` 返回 `TaskIntakeResult(CONFIRMED)`，**尚无** `task_id`。创建链路调用 `build_task_info_request(result)` 和 `TaskService.execute(request)`，得到 `TaskOpResult(task_id="task-pay-001", node_id="task-pay-001")`。
3. `start` 同事务提交 `TaskInfo`、图谱根节点、`session_id` 唯一创建关联及待投递意图；Backend S6 直接调用 `TaskDispatcher.dispatch(root_node)`，接力派发策略内部经 Runner 向 `bot-payment-diagnosis` 投递根节点标识。Bot 在 S1 调节点级 API 取得根 `TaskContext`。S2 发现 `ac1/ac2/ac3` 均未覆盖；S3 判定自己能承担 `ac1/ac2`，形成 `actual_goal`。
4. 首棒 S4a 产出影响范围和根因证据，并逐项验收；S4b 以 `EXECUTION_RESULT(TaskNodePatch)` 上报。S5.1 合并本棒事实后得 `task_gaps=["缺少处置建议"]`。S5.2 初始化目标为 `ac3` 的未落图 `TaskNode`；S5.3 搜索候选；S5.4 选定 `bot-incident-response`，写入 `run_info.assignee/run_mode`。
5. 首棒 S5.5 一次上报 `PLAN_RESULT(event=next_node)`。Backend 创建 `node-pay-002`、写依赖与执行者决策、登记投递意图，并返回 `TaskReportResult(target_node_id="node-pay-002")`。首棒 Skill 调 S6 `/dispatch`；Backend 经 Relay Dispatcher 校验、内部 Runner 发送包含 `task-pay-001/node-pay-002` 的指令。
6. `bot-incident-response` 在 S1 拉取 `node-pay-002` 的 `TaskContext`。历史 `all_done_output` 包含首棒已接纳的产出，但不含首棒内存里的 `task_gaps`。第二棒完成 `ac3` 并上报节点事实；S5.1 重算得到 `task_gaps=[]` 和根任务验收结果；S5.5 上报收口 `PLAN_RESULT`。Backend 将整体任务置为 `DONE`，第二棒不执行 S6。

## 7. 实施差距与待确认事项

| 优先级 | 目标合同与当前实现差距 | 不处理的后果 |
| --- | --- | --- |
| P0 | `start` 同事务提交 `TaskInfo`、图谱根节点、`session_id` 唯一关联和投递意图；Backend 消费者调用 `TaskDispatcher.dispatch(root_node)` 并处理重试 | 响应丢失后重复建任务，或根节点已创建但第一棒未收到指令 |
| P0 | 实现节点级 `TaskContext` API，首棒、后续棒和 harness 恢复一律调用；`TaskOpResult` 增加 `node_id`，`TaskInfoRequest.task_spec` 统一为 `TaskSpec` | 上下文来源分叉，首棒无法可靠取得根节点规格 |
| P0 | 同节点 harness 重试使用服务端 attempt 与可信 Runner 会话绑定；`exec_error` 后原子开启新尝试，Runtime 自动传递绑定，S1 仅投影当前尝试的接纳事实 | 已接纳失败结果永久阻断重试，或旧会话迟到上报覆盖新尝试 |
| P1 | 将 Intake 的 `TaskIntakeCommand + TaskIntakeContext → TaskIntakeResult` 与独立 `start` 落地，并确定 `session_id` 的 HTTP 承载位置 | 确认与创建混杂，恢复及契约不稳定 |
| P1 | 将统一上报迁移为 `TaskReportCommand → TaskReportResult`；`PLAN_RESULT` 一次提交未落图节点和执行者，覆盖完成、HUNG、BBS 三分支 | 重复建节点、两次上报之间断点、异常误收口 |
| P1 | Relay 首版 S5.4 不支持 `HIT_GROUP`；动态组群须有唯一协调 Bot；S5.5 从冻结配置校验 `max_rounds`；BBS 只报告发布意图，S6 投递中返回可重试错误 | 不可达的选群分支、无限接力、意图误报为已发布或投递中误报成功 |
| P1 | 动态建群、BBS 发布与接力指令各以目标节点 ID 关联稳定外部操作键或原结果对账；BCS 无此能力时暂不开放动态建群 | 响应丢失或进程崩溃后重复建群、重复发布或重复启动下一棒 |
| P1 | S5.5 原子登记投递意图；Skill S6 调 `/dispatch`，Adapter 读取权威节点并调用 `dispatch(next_node)`；接力派发策略内部调用 Runner，后台消费者恢复失败投递 | Bot 崩溃丢接力、Relay 意外落入中心化逻辑，或派发成功却未实际投递 |
| P1 | 补齐接口合同、配置校验、状态迁移、重复投递和首棒启动的测试 | 文档看似闭环，运行时仍有不一致和重复副作用风险 |

本稿中 `start`、节点级 context、统一 report 领域对象、一次规划上报和按 profile 选择 Relay 策略均为**目标协议**；汇报时应与现有实现严格区分。
