# 工作流优化：精简产品方案与实施交接

日期：2026-10-15。状态：产品方向已确认；本文为实现依据，尚未完成新方案实现。

本文取代 [旧发布方案](2026-10-14-workflow-repair-release-flow.md) 中的 Bot 发布主流程、单独确认候选、手工确认修复效果及默认操作步骤。旧文档中的精确候选、安全校验、完整 Pack、幂等与恢复要求继续保留。新方案不代表已合并或已上线。

## 1. 目标与范围

用户能判断先修什么，看懂真实修改，只做一次明确的发布决策；系统负责分析、去重、发布状态核对和效果观察。

主流程只有：**生成优化草稿 → 审阅并确认发布 → 自动验证效果**。

- 手动分析、手动选择与自动分析、自动草稿共用同一套问题清单和任务。
- 不增加独立的“确认候选”“进入候选确认”“手动标记已修复”必经步骤。
- 灰度可选、默认关闭；没有真实版本分流能力就不开放入口，也不阻塞首批交付。
- 不新增自动发布、自动回滚、任意业务测试运行；不扩展为通用编排平台。
- 复用现有任务、发布历史、配置与权限体系，新增持久化必须先证明现有模型无法承载，不预设一批新表。

## 2. 页面与优先级

保留三个用户视角：问题、优化任务、效果。它们是同一流程的视图，不是三轮确认。

### 问题：先修什么

- 问题卡片有明确间隔与边界；首屏显示影响程度及依据、近 24 小时/7 天受影响运行数、频率、趋势、最近出现时间、方案及处理状态。
- 频率按同一时间窗内去重运行计算。区分“相关运行总量”“已分析量”“发现问题量”；分析不全时只能称已分析样本命中率，不能假称全量发生率。
- 时间按运行实际发生时间，不按分析完成时间。重试分析与迟到分析不重复累计同一运行。
- 没有可靠严重性来源显示“待评估”；不能把旧适配器填充的 medium 当成真实判断。排序展示可解释依据，未知不等于低风险。
- 默认优先高影响，再结合近期频率、恶化趋势和时效排序，用户可切换排序；没有历史对照就不显示虚假趋势。
- 建议展示覆盖问题、证据、修改范围、风险与冲突；优先推荐依据充分且改动小的可用方案，不能按文案、建议数量或列表位置自动全选。
- 按问题分页，服务端排序/筛选后分页；总数、页码与当前筛选口径一致。当前页带轻量建议摘要，详情按需读取；保留已访问页缓存，不能先渲染空问题再突然插入建议。

用户可在列表跨页选择问题，不必逐个打开抽屉等建议加载。选择代表修复目标，不代表接受全部方案。互斥方案在列表内取舍，无冲突方案可组合；缺方案的问题明确提供补充分析入口。

底部只有“已选 N 个问题 / 预计修改范围”和“生成优化草稿”；补充要求可选。详情、复制等次要操作使用紧凑链接或图标，保留提示和可访问名称。

### 优化任务：这些修改能否发布

- 自动/手动只是来源标签，共用状态、版本和恢复入口。
- 默认逐行 Diff：增删行、行号、文件统计、上下文折叠和变更定位；覆盖完整 Pack，不只 YAML。默认展示 Git 查看/比较链接，SHA 等技术信息折叠。
- 一个状态只有一个突出主操作：待审阅为“发布此版本”，生成失败为“重试生成”，发布未知为“核对发布状态”。不要求取消任务才能重试。
- 发布按钮打开一次确认面板，说明版本、修改范围、工作流影响范围及未覆盖风险；不再要求先独立确认候选，再重复确认发布。
- 服务端可复用内部审阅凭据，但界面不暴露第二个审批步骤。没有有效授权和候选校验不能执行副作用。
- 改范围或拒绝部分修改时生成新候选并重新检查；不能只取消勾选而发布仍包含全部修改的旧 commit。
- 问题原因未聚合时展示可用单次诊断与证据；聚合失败、无数据、加载失败分别说明，不能只留空白。

### 效果：系统判断，不依赖用户补操作

- 实际生效后自动进入观察，不以生成、打 tag 或确认成功替代生效。
- 只统计本次生效版本、真实执行相关节点且可判定的运行；旧版本迟到日志、未走相关分支和未知版本样本不用于结论。
- 无样本、样本不足、分析缺失、缺验证规则均显示“观察中”及原因，不默认为有效，也不重复生成已应用的修改。
- 已有明确验证规则的问题自动判断；规则记录版本、适用节点/签名、观察窗口、最小有效样本和通过条件，结论保留证据。规则阈值是实施时需测试的工程策略，不是用户已确认的固定业务数字。
- 主观业务质量没有验证器时不自动宣称修复；人工纠错入口可保留，但不是完成流程的要求。
- 新版本明确复现原问题时自动进入待优化并关联上一轮；无效方案基于新证据调整，不能原样无限重试。已修复后复发创建新问题阶段，不改写旧验证记录。

## 3. 自动与手动共存

每工作流只暴露“自动分析”开关；开启后可选“自动生成优化草稿”，并设置每日执行时间。手动分析/选择始终可用；自动草稿不能在自动分析关闭时独立生效。首次未配置默认关闭，已有配置迁移不得静默改变用户选择。

- 使用现有 OB 应用配置体系，不新增环境变量；时区明确为 Asia/Shanghai。自动分析既有事件触发能力不等于已有每日优化调度器，接入前要核对并统一设置语义。
- 分析增量运行，合并历史未处理项；不每天重新传全部历史日志。没有有效新增或实质变化，不生成空任务或相同候选。
- 同一修复范围已在生成、审阅或发布中则复用；其他独立问题不必等待。用户仅勾选但未提交不占用全局范围，提交时重新校验。
- 候选冻结基线、建议内容版本、证据截止点与范围；新证据更新问题视图，但不能偷偷改变正在审阅的候选。
- 自动和手动竞争用同一事务占用与幂等机制；定时重跑、重启、重试不能重复创建任务或发布。
- 生成前再次检查开关、权限、范围、冲突与当前部署版本；限制单轮数量、输入大小、成本和重试次数。无法安全取舍的方案留给用户。
- 关闭开关停止新自动派发，不自动取消已派发任务、不丢弃结果、不撤销发布；运行中的任务继续核对状态。错过多日调度合并处理，不补发多份相同任务。
- 每日分析通知新增重点问题，自动草稿通知可审阅候选；相同任务/版本不重复通知。通知失败重试通知，不能重建任务。Owner 和权限按当前工作流重新解析，不能沿用失效卡片授权。

## 4. 跨轮范围规则

待优化清单持续存在，任务只是冻结的本轮快照。按具体修复项及内容版本记账，不以整个问题、勾选状态或 AI 改写文案作为完成依据。

| 情况 | 后续行为 |
| --- | --- |
| 新问题、未选择、本次不采用、生成失败、发布明确失败 | 保留可优化资格；按当前基线重新校验适用性 |
| 正在生成或等待审阅 | 保留未处理事实，复用任务，不每日复制 |
| 已确认但未生效 | 仍未修复；确认不能把建议移出待处理范围 |
| 发布中或结果不确定 | 核对已有请求，不能盲目重发或算完成 |
| 实际 changed 项已生效 | 移出重复生成范围，进入效果观察 |
| 未选择、unresolved 或未应用的部分 | 继续保留，不能因同一任务其他项成功而消失 |
| AI 声称 not_needed | 核实当前版本确已满足后才排除，不能只相信文字结论 |
| 验证有效 | 同一问题阶段/同一修改不再带入 |
| 无效、复发、回滚或人工发布改变现状 | 重新检查当前版本和证据，必要时纳入新一轮 |
| 暂缓/明确忽略 | 遵守期限和范围；重大新证据或范围变化时重新提示 |

同一修改的新分析补充到既有证据，不创建重复建议。同一字段的替代方案在一项生效后重新判断，不能继续携带不适用的旧补丁。

例：首轮有 A/B/C，仅 A/B 进入候选。A/B 生效后下轮处理 C 和新增 D，A/B 只观察效果；未采用或明确失败则 A/B 仍可进入下一轮；仍待审阅则保留原候选，C/D 留在独立待优化范围，可按占用规则另行处理但不能偷偷并入原候选；仅 A 生效则 B/C/D 保留。

## 5. 发布边界：服务端发布完整 Pack

- Avernet 公共模块拥有产品状态、发布/验证契约、权限要求、UI 与公共持久化逻辑；不能引入内部执行通道依赖。
- OCB Host 使用现有 Git 凭证和发布能力发布精确候选，不再通过目标 Bot 的 shell/chat 执行发布。主流程移除 Bot 选择和 nodeBinary/entryPath 前置条件。
- ClawMind 保持对精确部署版本及完整 Pack 的消费/物化；是否需要配套修改由实际运行时契约证明，不预设无改动，也不恢复远程发布入口依赖。
- TaskGuard/AIS 负责生成候选和报告，不承担线上发布。
- 发布按当前工作流/实际环境的既有部署作用域生效。现有 workflow_id 粒度激活不是单 Bot 灰度，界面不得声称仅影响所选 Bot。
- 服务端核对发布权限、冻结 commit/Pack/checks、完整 Diff、冲突、当前基线；候选或基线变化需重新检查/审阅，不能自动套用旧授权。
- 推工作流分支和不可变部署 tag、提交部署历史/生效指针是不同阶段，不宣称 Git 与 DB 存在一个跨系统事务。阶段记录、幂等请求和基线 CAS 支持核对恢复；Git 成功但激活失败仍不是整体成功。
- 发布后新运行必须能取得正确完整 Pack；必要时复用或补齐运行时能力。回滚是独立授权操作，取消任务不回滚。
- 保留旧任务和历史审计。旧 Bot 发布仍在执行或未知时先核对，不能迁移时再发一次；不把旧确认静默迁移为新作用域发布授权。

## 6. 实施顺序与验收

**第一批：可用的人工闭环。** 问题优先级/频率及列表选择 → 清晰 Diff → 单次发布确认 → 服务端精确发布与恢复 → 自动效果观察/验证。已有能力优先复用，不把全部 UI 推倒重写。

**第二批：自动化复用闭环。** 开关/调度 → 增量分析与跨轮范围 → 自动草稿 → Owner 通知与去重。灰度不作为两批的前置条件；真实分流能力是后续独立扩展。

最小验收场景：

1. 24 小时/7 天去重统计、覆盖率、相关运行分母和未知严重性正确；不能用累计次数伪装发生率；问题分页、筛选、缓存与跨页选择一致。
2. 列表直接选择多个问题，互斥方案可取舍；不必逐项进抽屉；缺失原因有证据回退。
3. 深处变更、多文件、脚本/资源、二进制/截断有明确表现；缺少完整检查或必要审阅内容阻止发布。
4. 一次确认后发布精确候选，主流程不选 Bot、不配置 Bot 路径；完整 Pack 可被新运行取得，授权和基线冲突有效阻止副作用。
5. 双击/并发不重复发布；超时先核对；Git 成功但 DB 失败可恢复；失败可重试而无需取消。
6. 无人点击“已修复”时，有验证规则和足量证据仍能自动完成；无运行/不可判定不假成功；旧版本日志不误复发；明确复发能重新优化。
7. 自动/手动命中同一范围复用，独立范围可继续；关闭开关、任务重启、通知重试不重复派发；待审阅候选不会被每日刷新篡改。
8. A/B/C/D 跨轮示例、部分 changed、not_needed、复发/回滚和暂缓逐一覆盖；未应用项不丢失，已应用项不重复修改。

验收使用受影响模块测试、类型/边界检查、真实本地 Git/DB 集成及浏览器全流程。外部 AIS、生产发布/运行时未验证时单列缺口；本地通过、PR、合并、宿主部署、生产效果分别报告。
