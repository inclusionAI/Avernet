# 邀请码准入门禁设计

> 状态：草案
> 日期：2026-09-05
> 范围：新增 6 位随机邀请码能力，用于限制 human 用户在绑定邀请码后才能使用平台功能。内部支持批量初始化邀请码；OpenAPI 暴露匿名领取、绑定邀请码和查询当前用户绑定状态。

## 1. 背景

当前平台的 OpenAPI 能力面向已认证用户开放，但缺少一层“邀请制准入”控制。现在需要新增邀请码功能：

- 邀请码由 6 位随机数字 + 字母组成；
- 先由 BCS 内部接口批量初始化邀请码；
- 用户通过邀请码完成一次性绑定；
- 一个邀请码只能绑定一个用户；
- 一个用户最多绑定一个邀请码；
- 提供 OpenAPI 接口判断“当前用户是否已绑定邀请码”；
- 后续平台功能的访问门禁应依赖这一绑定状态。

## 2. 设计目标

1. **深模块**：邀请码生成、去重、绑定、状态查询、门禁判断集中在一个独立模块内。
2. **最小开放面**：
   - 内部只暴露批量初始化能力；
   - OpenAPI 暴露匿名单码领取、绑定和自查，不暴露任意用户查询或邀请码列表。
3. **不可枚举**：不提供可批量查询的邀请码列表，不暴露任意用户绑定状态，不返回多余的码存在性细节。
4. **可作为统一准入门禁**：未来平台功能入口可以统一复用“是否已绑定邀请码”的判断。

## 3. 模块切分

建议新增独立模块：

- `bcs_service_api::application::invite_code`
- `services/bcs-invite-code`（或同等命名的实现 crate）
- `bcs_service_api::port::repo::InviteCodeRepo`

### 为什么独立

邀请码不是好友关系，也不是 bot 关系，更不是注册流程的一部分。它是一个独立的准入门禁能力，适合单独建模：

- 生成邀请码
- 落库
- 绑定用户
- 查询当前用户绑定状态
- 门禁校验

这样可以保证接口小、实现深、测试集中。

## 4. 邀请码模型

### 4.1 编码规则

- 长度：6
- 字符集：`0-9A-Z`
- 形式：随机大写字母数字串，例如 `A1B2C3`
- 生成必须使用安全随机源

### 4.2 存储规则

不建议明文存储邀请码。

建议存储：

- `code_hash`：对明文邀请码做 HMAC-SHA256 或等价带密钥哈希
- `code_hint`：可选，仅用于排障定位，例如后 2 位或后 4 位
- `bound_user_id`：绑定的用户 id，未绑定时为 `NULL`
- `bound_at`：绑定时间
- `status`：`active / bound / disabled`

### 4.3 唯一约束

- `code_hash` 唯一
- `bound_user_id` 唯一（一个用户只能绑定一个邀请码）

## 5. 数据表建议

建议新增单表即可起步：`bcs_invite_codes`

字段建议：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 主键 |
| `env` | varchar | 环境标记 |
| `code_hash` | varchar | 邀请码哈希，唯一 |
| `code_hint` | varchar | 可选，排障用 |
| `status` | varchar | `active/bound/disabled` |
| `bound_user_id` | varchar nullable | 绑定用户 |
| `bound_at` | datetime nullable | 绑定时间 |
| `created_by` | varchar nullable | 内部初始化来源 |
| `gmt_create` | datetime | 创建时间 |
| `gmt_modified` | datetime | 修改时间 |

如果后续需要记录批次、发放来源、导入任务 id，可以再补 `batch_id`，但第一版不必强制引入。

## 6. 服务接口设计

### 6.1 内部接口：批量初始化邀请码

仅 BCS 内部使用，不进入 OpenAPI 对外面。

#### 建议接口

```http
POST /internal/v1/invite-codes/init
```

#### 请求

```json
{
  "count": 100
}
```

#### 返回

```json
{
  "codes": ["A1B2C3", "Q7M9K2"]
}
```

#### 行为

- 按请求数量生成邀请码；
- 生成后立即落库；
- 遇到碰撞自动重试，直到补足数量；
- 仅内部管理员、运维或后台任务可调用；
- 明文邀请码只在该接口响应中出现一次。

### 6.2 OpenAPI：匿名领取邀请码

#### 接口

```http
POST /openapi/v1/collaboration/invite-codes/claim
```

#### 规则

- 不要求登录，不读取 `Principal`，也不经过邀请码准入门禁；
- 仅当配置 `invite.public_claim_enabled = true` 时开放，默认关闭；
- 公共领取总量由 `invite.public_claim_max_count` 控制，默认 1000；达到上限后返回 `429` 和 `invite_code_claim_limit_reached`；
- 每次请求生成并持久化一个新的有效邀请码；
- 明文邀请码只在本次响应中返回，响应携带 `Cache-Control: no-store` 和 `Pragma: no-cache`；
- 当前版本不引入活动 token、按时间窗口限流或验证码。

#### 返回

```json
{
  "code": 20000,
  "message": "OK",
  "data": {
    "invite_code": "A1B2C3"
  },
  "request_id": "..."
}
```

建议将公共二维码指向一个独立领取页面，而不是直接指向此有副作用的 `POST` 接口。用户扫描二维码访问领取页面，页面服务端调用本接口并展示邀请码。

### 6.3 OpenAPI：绑定邀请码

#### 建议接口

```http
POST /openapi/v1/collaboration/invite-codes/bind
```

#### 请求

```json
{
  "code": "A1B2C3"
}
```

#### 规则

- 使用 `AuthenticatedCaller` 识别当前用户，不允许客户端传 `user_id`；
- 只能绑定当前调用者；
- 当前用户如果已经绑定过邀请码：返回冲突；
- 同一个邀请码如果已被其他用户绑定：返回冲突；
- 同一个用户重复绑定同一个邀请码，可按幂等成功处理；
- 绑定写库必须原子化。

#### 返回

```json
{
  "bound": true
}
```

### 6.4 OpenAPI：查询当前用户是否已绑定邀请码

#### 建议接口

```http
GET /openapi/v1/collaboration/invite-codes/me
```

#### 返回

```json
{
  "bound": true,
  "bound_at": "2026-09-05T10:00:00Z"
}
```

#### 规则

- 仅查询当前调用者；
- 不开放任意 `user_id` 参数；
- 未绑定时返回 `bound=false`；
- 该接口用于前端/调用方在进入平台功能前判断当前状态。

## 7. 平台准入门禁

邀请码绑定状态应作为平台功能入口的统一门禁。

### 建议门禁规则

- 对 **human** 调用者：必须已绑定邀请码，才能访问受保护的平台功能；
- 对 **bot / 服务调用者**：默认不受邀请码门禁影响，避免影响现有自动化和内部调用链；
- `bind` 和 `me` 接口本身必须允许未绑定用户访问，否则无法完成绑定流程；
- `claim` 挂载在匿名路由树中，不要求 Principal；关闭开关时返回 404。

### 建议拒绝方式

- 未绑定用户访问受保护功能时：返回 `403 Forbidden`；
- 可附带统一错误码，例如 `invite_code_required`；
- 不要返回用户是否接近命中邀请码、是否存在其他绑定的额外信息。

## 8. 错误语义

### 绑定接口

| 场景 | 建议 HTTP | 建议错误码 |
|---|---|---|
| 未认证 | 401 | `unauthenticated` |
| 参数非法 | 400 | `invalid_request` |
| 当前用户已绑定其他邀请码 | 409 | `invite_code_already_bound` |
| 邀请码不可用（不存在 / 已绑定 / 已禁用） | 409 | `invite_code_unavailable` |
| 非 human 调用者 | 403 | `invite_code_not_applicable` |

### 查询接口

| 场景 | 建议 HTTP | 建议错误码 |
|---|---|---|
| 未认证 | 401 | `unauthenticated` |
| 成功 | 200 | `OK` |

### 门禁拒绝

| 场景 | 建议 HTTP | 建议错误码 |
|---|---|---|
| human 未绑定邀请码 | 403 | `invite_code_required` |

## 9. 服务接口建议

建议在应用层提供一个最小接口：

- `init_codes(count) -> Vec<String>`
- `claim_public_invite_code() -> String`
- `bind_code(caller, code) -> BindResult`
- `has_bound_code(caller) -> BindingState`

如果需要更强的分层，可以将内部初始化放到单独的 admin service，但第一版不必拆太细。

## 10. 事务与并发

绑定流程必须在事务内完成，避免竞态：

1. 锁定邀请码记录；
2. 检查当前用户是否已绑定；
3. 检查邀请码是否可用；
4. 写入绑定结果；
5. 提交事务。

并发下应保证：

- 不会出现一个邀请码绑定到多个用户；
- 不会出现一个用户绑定多个邀请码；
- 重试请求不会破坏唯一性。

## 11. 安全与风控

1. **不明文落库**：避免数据库泄露后直接批量撞码。
2. **限流**：绑定接口应按用户和 IP 做限流。
3. **统一失败语义**：邀请码无效和已使用尽量不要暴露过多区分信息。
4. **内部初始化隔离**：初始化接口只允许内部身份或后台任务调用。

## 12. 验证策略

建议覆盖以下测试：

- 初始化指定数量的邀请码，数量正确且唯一；
- 邀请码长度与字符集符合规则；
- 同一码只能绑定一个用户；
- 同一用户只能绑定一个邀请码；
- `me` 接口能正确返回绑定状态；
- 未绑定 human 调用受保护功能被拒绝；
- `bind` 和 `me` 不会被门禁拦截；
- `claim` 无认证可访问，关闭 `invite.public_claim_enabled` 后返回 404；
- `claim` 每次仅生成一个已持久化的邀请码，并返回禁止缓存响应头。

## 13. 范围边界

本 spec 只定义“邀请码准入门禁”。不包含：

- 邀请码批量发放后台；
- 邀请码作废/回收流程；
- 邀请码转赠；
- 复杂批次运营报表；
- 公共领取接口的活动 token、按时间窗口限流、验证码和攻击防护；
- 对 bot 的邀请码绑定。

如果后续需要这些能力，可以在本模型上继续扩展。
