# BCS 作为公司级受治理 A2A 注册中心：登记以 BCS 为准，对外发布代理 Card，调用默认经 BCS

状态：proposed（2026-11-08，待团队评审）。负责人：待定。

调研依据：[BCS AgentCard 填写说明、字段映射与注册中心改造评估](../research/2026-11-08-bcs-agentcard-field-mapping.zh-CN.md)。

## 背景

BCS 已能作为 A2A Client 接入外部 Agent：Provider 提交 A2A 1.0 AgentCard，BCS 校验后把完整原始
Card 保存在 `bcs_bots.agent_card`，用 `supportedInterfaces` 选择下行接口，并基于 Card 做发现检索。
现状有以下限制：

- 每个 Bot 只有一份当前 Card，可以就地覆盖；`version` 只校验非空。
- BCS 不是 A2A Server。`GET /bots/{id}/agent-card` 返回原始 Card（含远端真实地址），需要 Bot 查看权限。
- WebSocket/OpenClaw 等旧 Bot 没有 Card。
- 部分待接入的 Agent 不使用标准 A2A 协议，需要 BCS 提供适配层。BCS 已有自定义绑定扩展点
  `plugin-api/bcs-a2a-binding-api`：部署时安装的 `Binding` 用非标准 `protocolBinding` 名称参与接口选择，
  并通过 `Client` 把远端协议归一为 A2A 的 SendMessage、流式、GetTask、CancelTask、SubscribeToTask。
  目前只有测试实现，生产启动流程没有安装入口（`bootstrap/bcs` 仅在 `test-utils` 下依赖它）。

现在要评估 BCS 能否作为公司级 A2A 注册中心。A2A 1.0.1 把 curated registry 列为发现方式之一，
但没有规定注册中心 API。业界参照 Nacos 3.2.1+ 的 Agent Registry：它只做发现，不在调用链路上；
支持多版本，同一版本号对应不可变的 Card，有 latest 指针；3.3.0 起强制 `MAJOR.MINOR.PATCH`
版本格式；SERVICE 类型在查询时用服务注册表里的实例地址改写 Card 的接口字段。

BCS 相对 Nacos 的不可替代之处是调用治理：可见性、好友关系和 Owner 决定的发现与调用权限，
会话与 Task 关联，审计，工具观察，exec 审批，以及多 Agent 协作。这些能力只有在调用经过 BCS 时才成立。

## 决策

**定位。** BCS 作为公司级"受治理的 A2A 接入中心"：注册与治理以 BCS 为准，对外发布 BCS 生成的
代理 Card，调用默认经过 BCS。BCS 不自建实例级服务发现。

**登记与治理以 BCS 为准。** Agent 的 Provider、Owner、可见性、版本与生命周期以 BCS 记录为准。
Card 自述的 `provider`、身份或权限信息不产生归属与授权。Provider 提交的原始 Card 只作为 BCS
内部的下行配置保存，不对外暴露真实接口地址。

**版本由 BCS 维护，接入方的 `version` 只作标签。** 参照
[ADR 0005](0005-separate-internal-version-ordinal-from-external-version-key.md)，内部版本身份与外部版本字符串分离：

- 每次 Card 内容变化（注册、PUT、URL 刷新）时，BCS 生成一条不可变的内部版本记录，带同一 Agent 内
  单调递增的序号。内容不变的写入或刷新不生成新版本。latest 指针指向当前版本。
- 接入方填写的 `AgentCard.version` 原样保存、展示，不作为版本身份，不要求唯一，不要求格式，
  也不要求每次修改都升号。这一点对接入方不增加新要求，与 v0.1 合同兼容。
- 已接受的 Task 锁定创建时的内部版本与接口。
- 平台基于内部版本提供变更历史、审计与回滚（把 latest 指回某个历史版本）。

**对外 Card 的版本与缓存。** 代理 Card 是 BCS 生成并签名的 Card，其 `version` 填 BCS 维护的版本号；
接入方原来的 version 放在 BCS 扩展字段或目录的外层注册条目中，供展示。版本字符串格式在 spec 中定义，
若要同步到 Nacos 3.3，需满足其 `MAJOR.MINOR.PATCH` 要求。Card 端点的 `ETag` 按最终生成的代理 Card
内容计算哈希，因为 BCS 侧的变化（鉴权方式、对外能力、签名密钥）也会改变代理 Card，而接入方版本不变。

**按版本获取：默认只查看，锁定调用为可选的严格模式。**

- **默认**：客户端默认获取 latest，也可以按版本获取任意历史版本的 Card，用于查看、对比与审计。
  代理 Card 的入口地址不区分版本，调用一律转发到当前版本的远端接口。
- **严格模式**：由 Agent 主动开启。开启后 `AgentCard.version` 成为版本键，要求
  `MAJOR.MINOR.PATCH[-prerelease]`，同一版本号内容不可变，内容变化必须升号；URL 刷新发现内容变化而
  版本号未变时拒绝写入并告警，不静默覆盖。历史版本的代理 Card 入口地址带版本，BCS 转发到该版本登记的
  远端接口。接入方须保证已发布版本的服务持续可用，不可用的版本由 BCS 标记为不可调用。

**对外只发布代理 Card。** 对外 Card 由原始 Card 和 BCS 记录派生，不原地修改原始 Card：

- `supportedInterfaces` 指向 BCS 的 A2A 入口；
- `provider` 由 BCS 填写；
- 安全声明描述 BCS 自己的鉴权方式；
- 输入输出模式与扩展只声明 BCS 能端到端支持的部分；
- Card 由 BCS 签名，原签名不再沿用。

按调用方身份选择性披露：公开发现只返回可见的 Agent，protected 的 Agent 通过认证后的
extended Card 或认证检索返回，private 不发布。旧 Bot 由其登记的能力合成 Card 纳入目录。

**调用默认经过 BCS。** BCS 对外提供 A2A 1.0 Server，下行复用现有的接口选择、断流恢复、
扩展协商与出站策略。直连只作为经过评审的例外，目录中明确标记，且不享有 BCS 治理能力。

**非标准协议在 BCS 内适配，对外一律呈现为标准 A2A。** 非标准 Agent 通过协议适配器接入：

- BCS 内部只有一套 A2A 1.0 任务模型。适配器实现 `bcs-a2a-binding-api` 的 `Binding` 与 `Client`，
  只做协议映射，把远端协议归一到这套模型，不承载业务逻辑。
- 非标准 Agent 的登记 Card 在 `supportedInterfaces` 中使用适配器的绑定名称。没有原生 Card 的，
  由接入方按 BCS 模板提供，或由适配器生成。登记 Card 同样走版本与校验规则。
- 对外代理 Card 只暴露 BCS 的标准接口，适配器的绑定名称与路由键不对外出现。
- 适配器声明的能力（流式、取消、恢复、扩展）不得超出远端真实能力。不支持的操作返回标准 A2A 错误，
  不伪造成功，也不在提交后切换协议或重放有副作用的请求。
- 适配器位于 `plugins/*`，在启动流程按配置安装。按架构规则提供 Noop/Mock 实现与 `tests/contracts/`
  下的一致性测试。适配器版本或路由配置变化时，`fingerprint` 必须随之变化。
- 适配器的接入与发布需要评审，按适配器建立归属、版本与下线流程。

旧的 WebSocket 插件 Bot 与 Provider Gateway webhook 也是非标准接入。它们是否收敛到同一适配机制，
另行决策；在此之前，对外仍由合成 Card 与 BCS 标准接口统一呈现。

**服务发现不自建。** 远端 Agent 的实例、负载均衡与健康检查，由其自身网关、mesh 或现有服务发现
（如 Nacos）负责，BCS 只保存稳定的接入地址。若公司同时使用 Nacos，BCS 可以把代理 Card 登记到
Nacos 作为全局目录镜像，两者不在服务发现层重叠。

**Agent 研发阶段不在 BCS 中建模。** 接入方平台的草稿、预发、发布等阶段属于 Agent 自身的研发流程，
BCS 不建模阶段，也不提供阶段指针：

- 生产 BCS 只登记正式版本，Card 的接口指向正式部署。
- 联调与预发使用按 `env` 隔离的预发 BCS 部署。BCS 的 `env` 按部署进程确定，存储、Provider、名称与
  来源 agentId 的唯一性都按 `env` 隔离，因此预发与生产可以使用相同的名称与 agentId，会话、关系与统计互不影响。
- 草稿由接入方平台自行调试，不接入 BCS。
- 接入方的发布动作负责更新生产 BCS 中的 Card；URL 来源必须稳定返回已发布的 Card。灰度由接入方在稳定的
  正式入口之后自行实现。BCS 的内部版本与回滚作为发布出错时的兜底。

重新评估条件：出现以下任一情况时，再考虑在生产中增加受限调试能力（优先考虑"仅 Owner 可见可调、
不进入发现"的调试可见性，其次才是阶段指针）：

1. 需要在生产的真实协作关系（真实 Bot、真实群）中验证新版本后再放开；
2. 预发 BCS 中维护有代表性的 Bot 与数据的成本不可接受；
3. 多个接入方提出平台内调试无法替代的需求。

**标准化。** Card 严格采用 A2A 1.0。目录入口采用 `.well-known` 与业界正在形成的目录文档约定，
不自造私有格式。A2A 0.3 Card 只在接入时一次性转换为 1.0，内部不长期维护两套模型。

**暴露顺序。** 对外发现入口与代理调用能力同时上线。在此之前，原始 Card 只供内部、需鉴权的调用方读取，
不先以目录模式对外暴露真实地址再改回代理。

## 前提

以下前提需要业务方确认。任一不成立时，本决策需要重新评估：

1. 公司需要统一的 Agent 调用治理（权限、审计、合规），而不只是可发现性。
2. 团队能承担 BCS 进入核心调用链路的容量、可用性与运维成本。

如果第 1 条不成立，应改用 Nacos 作为注册中心，BCS 只承担协作层。如果第 2 条短期不成立，
先只建设登记与治理的控制面，暂不开放对外发现。

## 后果

- BCS 需要新增 A2A Server，并成为 Agent 调用的关键依赖，需要按核心链路做容量规划与故障预案。
  目录读路径读多写少，需要与协作、会话核心隔离，独立扩容并加缓存。
- 存储需要新增只追加的内部版本表与 latest 指针，迁移须新增编号，不修改已有迁移。现有
  `agent_card_revision` 可以演进为内部版本序号。默认模式对接入方无新要求；严格模式的接入方需要自行管理
  版本号并保留旧版本服务。
- Provider 内名称唯一约束属于正确性问题，须先清理存量重名再新增约束。版本、来源 agentId、skill、tag 的
  结构化索引属于性能优化，在新增精确查询接口或测出瓶颈时再加，不预先建设。
- 需要在 spec 中定义：代理 Card 的版本字符串格式、接入方原 version 的存放位置、跨版本改名规则，以及
  严格模式的开启、版本下线与不可调用标记流程。
- 注册入口统一采用 v0.1 管理校验；旧 ID 入口与刷新路径的校验差异需要收敛，存量不合规 Card 不对外发布。
- 对外 Card 与原始 Card 分离，需要 BCS 的签名密钥与轮换机制。外部看到的接口地址稳定，远端变更不影响调用方。
- 直连例外会绕开治理，需要评审流程与目录标记。非标准 Agent 不能直连：标准 A2A 调用方无法使用其协议，
  它们只能通过代理对外提供。这也是采用代理模式的理由之一。
- `bcs-a2a-binding-api` 需要补生产安装路径（配置驱动，启动时一次性安装）与适配器的一致性测试套件。
  每接入一种非标准协议就新增一个适配器插件，其维护成本随协议数量增长，需要按协议评估是推动对方改为
  标准 A2A，还是由 BCS 长期维护适配。
- 0.3 存量 Agent 可以接入，但需要一次性转换；转换无法表达的声明须拒绝，不静默丢弃。

## 备选方案

- **目录模式：直接对外发布原始 Card，调用方直连。** 否决：实现最轻，但 BCS 的访问控制、审计、
  会话与扩展治理全部失效。真实地址一旦流出，调用方很难再迁回 BCS。
- **直接采用 Nacos 作为注册中心，BCS 只做协作。** 不作为默认方案：Nacos 的发现、多版本与高可用更成熟，
  但不提供调用治理。若前提 1 不成立，这就是首选方案。
- **混合模式，默认直连，按需代理。** 否决：默认路径决定治理覆盖面。默认直连会让大多数调用处于治理之外，
  两套路径的长期维护成本也更高。
- **在 BCS 中按阶段建模（每个 Agent 有 draft、staging、prod 等阶段指针）。** 暂不采用：各平台的阶段定义
  不统一，BCS 若建模只能取最小公约数或演变为通用发布系统，偏离治理与调用的定位；现有 `env` 隔离已覆盖
  名称、来源 agentId、数据、会话与关系的隔离。满足重新评估条件时再考虑。
- **每个阶段在同一 env 中注册为独立 Bot。** 否决：与 Provider 内名称唯一、来源 agentId 唯一冲突；
  非正式阶段会进入发现，且无法与生产的数据与关系隔离。
- **以接入方的 `version` 作为默认版本键（Nacos 模式）。** 不作为默认：要求所有接入方内容一变就升号、
  使用 SemVer、保留旧部署，自动生成 Card 的接入方难以满足；URL 刷新时内容变而版本未变的情况只能拒绝或
  静默忽略。保留为可选的严格模式。
- **代理 Card 的 `version` 沿用接入方的值。** 否决：A2A 规范把 version 用作 ETag 来源与扩展 Card
  缓存失效的信号，接入方未升号或 BCS 侧变化时，客户端缓存不会更新。
- **要求所有 Agent 自行改造为标准 A2A 后再接入。** 不作为唯一路径：长期目标仍是推动标准化，
  但存量非标准 Agent 改造周期不可控。适配层让它们先接入并纳入治理，同时不把非标准协议暴露给调用方。
- **适配器在 core 中按协议分支实现。** 否决：违反"配置驱动装配、不散落条件分支"的架构规则，
  core 会被每种协议的细节污染。
- **在 BCS 内自建实例注册与健康检查。** 否决：与现有服务发现基础设施重复，扩大 BCS 的职责与故障面。
