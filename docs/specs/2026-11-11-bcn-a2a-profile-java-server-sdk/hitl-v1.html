hitl/v1：A2A 人机交互扩展

让 A2A Agent 在执行过程中请求人来审批、回答问题或确认切换模式，并在 BCS 工作台中用现有的交互卡片完成处理。本文是 hitl/v1 扩展的独立设计稿，供单独评审。

状态 设计稿 v0.1，待评审日期 2026-11-17上位文档 《BCN A2A Profile 与 Java Server SDK 详细设计》v0.29替代 structured-input-exec/v1（兼容期内并存）

本文新增的条款编号为 H-xx，对引擎的要求为 HR-xx，待决问题为 HQ-xx。引用的 P-xx、Dx、Rx 来自上位设计稿。扩展 URI 尚未确定，文中用 <hitl/v1 URI> 占位。

1背景

1.1BCS 现有的人机交互

BCS 内部已经有一套人机交互（HITL）机制，Provider 通过交互事件发起，BCS 负责路由、展示卡片、校验回复、暂停运行预算，再把结果交回 Provider。交互事件有两个阶段：requested（发起）和 resolved（结束）。共有三种类型：

类型请求内容回复BCS 的校验
exec要执行的操作（命令或工具）和若干选项 {decision, label}一个 decision选项非空、decision 不重复；回复必须是提供过的选项之一
ask_user1–4 个问题，每题可以有 1–4 个选项，支持多选和“其他”submit 加全部答案，或 cancelsubmit 必须每题回答一次；单选最多一个值；不允许自定义值时只能选提供的选项；不支持密码类问题
mode_switch当前模式、目标模式和若干选项，选项可以带目标模式和推荐标记一个 decision与 exec 相同

1.2A2A 侧的现状

A2A Agent 目前只能发起 exec 审批，走 structured-input-exec/v1：Task 进入 INPUT_REQUIRED，状态消息里放一个用 JSON Schema 表达的审批请求（基于上游实验性的 Structured Input 草案，固定在某个提交），业务语义放在 x-bcs-exec 注解里。BCS 的处理方式是：

  • 把一个审批批次拆成每个工具一张审批卡，每张卡独立回答；
  • 每回答一张卡，就发一次带 taskId 的 SendMessage（returnImmediately=true），再从 Task.metadata 中的回执确认 Agent 已经接受；
  • 等待期间暂停运行预算，整批回答完后恢复预算，继续订阅 Task 的后续输出。

1.3问题

  • 只覆盖 exec。ask_user 和 mode_switch 在 A2A 里没有对应，A2A Agent 无法向人提问或请求切换模式。
  • 表达方式过重。审批用 JSON Schema 表达，BCS 只接受其中一个很窄的子集（超出就报错），等于又定义了一套规则。业务方需要同时理解 JSON Schema 和注解。
  • 依赖外部草案。上游草案仍在变化，我们只能固定在某个提交上。
  • 选项含义无法识别。决策值是字符串，现有实现里同时存在 allow_once 和 allow-once 两种写法。调用方无法从协议上知道哪个选项是“允许”、哪个是“拒绝”。

2目标与非目标

目标说明
G1 一个扩展覆盖三种交互exec、ask_user、mode_switch，数据结构与 BCS 交互模型一一对应，BCS 只需要搬运字段，不需要转换
G2 只用 A2A 标准机制INPUT_REQUIRED 加带 taskId 的续交消息。不新增方法，不新增状态值（A2A 扩展规则不允许新增枚举值）
G3 多实例和重启下正确回复可以落到任何实例；接受前先持久化；回复的响应丢失时可以用 GetTask 核对
G4 能扩展新的交互类型新增类型不需要升级扩展版本，不影响不认识它的调用方
G5 平滑迁移与 structured-input-exec/v1 并存，已接入的 Agent 不需要立即修改
非目标归属
群里由谁来审批、谁可以回答BCS 的策略，不进协议
“本会话内一直允许”这类授权范围的含义和持久化Agent 自己负责（HQ-2）
密码等敏感输入不支持。凭据不应该经过对话传递
文件上传、任意结构的表单不在 v1 范围
非流式 Agent（L1）发起交互不在 v1 范围（HQ-7）
推送通知下的交互随推送一起设计；INPUT_REQUIRED 本来就是推送的触发点（P-152）
托管模式不支持（D9）：等待期间的状态必须能跨实例、跨重启恢复

3术语

术语含义
交互（interaction）Agent 请人做的一次决定或回答。有 Task 内唯一的 id。一个工具调用的审批是一个交互
交互批次（batch）Task 一次进入 INPUT_REQUIRED 时同时待处理的一组交互，有 Task 内唯一的 batchId
类型（kind）交互的业务类型：exec、ask_user、mode_switch 或扩展类型。决定展示方式和附加字段
形态（shape）决策型（options，回复一个 decision）或问答型（questions，回复答案）。决定回复格式和校验规则
续交调用方带 taskId 和 contextId 发送的消息，用于提交回复（A2A 标准做法）
接受Agent 校验回复并把结果持久化
回执写在 Task.metadata 中的已结束交互记录，是“回复是否已被接受”的唯一依据
结束原因（outcome）answered（已回答）、expired（过期）、canceled（Task 被取消）、superseded（批次被替换）

4关键决策

编号决策理由
HD1载体完全使用 A2A 标准：INPUT_REQUIRED 的状态消息发起，带 taskId 的续交消息回复A2A 规范的输入请求就是这样定义的；属于 A2A 所说的 Profile 类扩展，只约束标准结构，不新增方法和状态
HD2不用 JSON Schema，用强类型字段卡片和表单需要稳定的结构才能渲染；BCS 已有一套在线上运行的强类型模型，直接复用可以省掉转换层；业务方理解成本低
HD3一次 INPUT_REQUIRED 是一个批次，批次内的交互逐个回答；exec 一个工具调用一个交互与 BCS 现状一致：现在的 A2A 路径已经是每个工具一张卡、逐张续交
HD4两种形态（决策型、问答型）决定回复格式；类型只决定展示和附加字段新增类型时，回复和校验规则不变；调用方遇到新类型也能按形态处理
HD5选项带 effect（allow 或 deny），调用方不解释 decision 字符串决策值由 Agent 自己定义；需要语义的地方（审计、群里谁能批准）读 effect
HD6回执写在 Task.metadata，是是否已接受的唯一依据续交的响应可能丢失；调用方用 GetTask 读回执即可确认，不依赖响应
HD7过期时间由 Agent 决定，过期后由 Agent 兜底；exec 的兜底必须等同拒绝只有 Agent 知道等待多久是安全的；审批类操作必须在失败时保持关闭
HD8只在引擎模式下支持，要求 Agent 支持 Task、流式、GetTask、SubscribeToTask 和 CancelTask等待可能跨实例、跨重启（D3、D4）；调用方需要查询和订阅才能完成续交流程

5总体流程

  1. BCS向声明了 hitl/v1 的 Agent 发送消息时，在 A2A-Extensions 中请求 hitl/v1；Agent 在响应中确认激活。
  2. Agent需要人参与时，先把批次写入引擎的运行记录，再发出 INPUT_REQUIRED 的状态更新，状态消息中放交互批次。按 A2A 规定，Task 进入中断态后这条流结束。
  3. BCS解析批次，为每个交互创建一张卡片（复用现有交互服务），暂停运行预算。
  4. 人在工作台回答其中一张卡。
  5. BCS发送续交消息，回复这一个交互。
  6. Agent任何实例收到后：校验、条件写入回执、返回 Task 快照。批次中还有未回答的交互时，Task 仍是 INPUT_REQUIRED。
  7. BCS从快照的回执中确认已被接受，关闭对应卡片。响应丢失时用 GetTask 核对。
  8. Agent批次中的交互全部结束后恢复执行，状态回到 WORKING；BCS 恢复预算，订阅 Task 接收后续输出。

6声明与协商

6.1Card 声明

{
  "capabilities": {
    "streaming": true,
    "extensions": [
      {
        "uri": "<hitl/v1 URI>",
        "required": false,
        "params": {"kinds": ["exec", "ask_user", "mode_switch"]}
      }
    ]
  }
}
条款内容
H-01声明 hitl/v1 的 Agent 必须同时声明 capabilities.streaming: true，并实现 GetTask、SubscribeToTask、CancelTask（HD8）。
H-02params.kinds 列出 Agent 可能发起的交互类型，只用于展示和注册时的自洽校验，不参与协商。
H-03required 应为 false，Agent 在未激活时按 6.3 兜底。只有没有人参与就无法安全提供服务的 Agent 才设为 true，此时未激活的请求返回 ExtensionSupportRequiredError。

6.2调用方的承诺和类型声明

条款内容
H-04调用方激活 hitl/v1，即承诺能处理三种基础类型（exec、ask_user、mode_switch）的全部字段和两种回复形态。
H-05调用方可以在请求 metadata 的 bcn.hitl.kinds 中列出额外支持的类型。没有这个字段时只支持三种基础类型。Agent 不得发起调用方没有声明的类型。
H-06续交消息也必须激活 hitl/v1，否则 Agent 拒绝（第 10 节）。
// SendMessageRequest.metadata（仅在需要额外类型时出现）
{
  "bcn.hitl": {"kinds": ["exec", "ask_user", "mode_switch", "order.refund_confirm"]}
}

新增标准类型或业务自定义类型时，扩展版本不变：只有声明支持的调用方才会收到新类型，旧调用方不受影响。

6.3未激活时的兜底

条款内容
H-07本次调用没有激活 hitl/v1 时，Agent 不得进入 INPUT_REQUIRED（替代上位稿 P-62），只能按下表处理。
需要的交互Agent 的处理
exec按 Agent 自己的安全策略处理：不执行该操作（等同拒绝），或以 REJECTED / FAILED 结束 Task。需要人工批准的操作不得因为未激活而放行
ask_user不提问。用默认值继续，或以 FAILED 结束，并在状态消息中说明缺少的信息
mode_switch保持当前模式继续

7数据格式

遵循 payload 设计的通用规则：扩展数据放在 DataPart.data；message.extensions 只标记这条消息使用了 hitl/v1；来源等附加信息放在 Part.metadata.biz。示例使用 ProtoJSON 表示，线上为 protobuf。

7.1载体位置

数据位置要求
交互批次Task 进入 INPUT_REQUIRED 时的 status.messagerole 为 Agent；extensions 包含 hitl URI；恰好一个承载批次的 DataPart，可以再有一个 TextPart 摘要
回复续交消息role 为 User；带 taskId 和 contextId；extensions 包含 hitl URI；恰好一个承载回复的 DataPart
回执Task.metadata["bcn.hitl"]已结束交互的结果，GetTask 和每个 Task 快照中都可以读到
额外类型声明SendMessageRequest.metadata["bcn.hitl"]可选（H-05）

bcn.hitl 这个键的位置随 payload 设计定稿；如果最终采用 bcn.extensions 容器，则改为 bcn.extensions.hitl（HQ-5）。

批次字段必填说明

7.3交互的公共字段

字段必填说明
id是Task 内唯一的不透明字符串，跨批次也不重复
kind是交互类型（第 8 节）
title否一行标题，纯文本
description否说明文字，纯文本
options二选一有这个字段即为决策型（7.4）
questions二选一有这个字段即为问答型（7.5）
类型字段对象视类型键为类型名的驼峰形式，例如 exec、modeSwitch。只增加展示信息，不改变回复规则
条款内容
H-08每个交互必须恰好有 options 或 questions 之一。
H-09消费方必须忽略不认识的字段。同一版本内只能增加可选字段。

7.4决策型

选项字段必填说明
decision是决策值，不透明字符串，交互内唯一，由 Agent 定义
label是按钮文字
description否选项说明
effect视类型allow 或 deny。exec 必填；其他类型可选
recommended否布尔值，每个交互最多一个选项为 true
条款内容
H-10决策型交互有 1–8 个选项。
H-11调用方不得根据 decision 字符串推断含义；需要语义时（审计、群里谁能批准）读 effect。

7.5问答型

问题字段必填说明
questionId是交互内唯一
question是问题文字
header否简短标签
options否1–4 个 {value, label, description?}；没有时为自由回答题
multiSelect否默认 false
allowOther否是否允许填写选项以外的值，只在有 options 时有意义；默认 true（与 BCS 现状一致）
条款内容
H-12问答型交互有 1–4 个问题。不支持密码类问题，不得出现 secret 之类的字段。

7.6回复

{
  "message": {
    "messageId": "msg-reply-001",
    "role": "ROLE_USER",
    "taskId": "task-001",
    "contextId": "ctx-001",
    "extensions": ["<hitl/v1 URI>"],
    "parts": [
      {"data": {
        "batchId": "batch-001",
        "replies": [
          {"id": "itx-001", "decision": "allow_once"}
        ]
      }}
    ]
  },
  "configuration": {"returnImmediately": true}
}
形态回复格式规则
决策型{"id", "decision"}decision 必须是该交互提供过的选项之一
问答型{"id", "action": "submit", "answers": {questionId: {"values": [...]}}}每个问题恰好回答一次；values 是非空字符串数组，空数组表示跳过该题；单选和自由回答题最多一个值；不允许自定义值时只能选提供的选项
问答型{"id", "action": "cancel"}用户拒绝回答
条款内容
H-13一条续交消息可以回复同一批次中的 1 到全部交互，replies 中同一 id 只能出现一次。
H-14普通文本 Part 不是回复。Agent 不得从文本、工具事件或摘要中推断回复。

7.7回执

// Task.metadata
{
  "bcn.hitl": {
    "batches": {
      "batch-001": {
        "itx-001": {"outcome": "answered", "reply": {"decision": "allow_once"}},
        "itx-002": {"outcome": "expired"}
      }
    }
  }
}
条款内容
H-15交互结束时，Agent 必须先写入回执，再发出后续事件或恢复执行。回执只有结束的交互，待处理的交互不出现。
H-16回执写入后不可修改。批次结束后回执继续保留，Task 进入终态后也保留。
H-17每个 Task 最多 64 个批次，回执编码后总大小不超过 240,000 字节（沿用 v1）。超出时在恢复执行前以 FAILED 结束 Task。

8交互类型

8.1exec：操作审批

决策型。一个交互对应一个工具调用；同时需要审批的多个工具调用放在同一个批次中。

exec 字段必填说明
toolCallId是工具调用 ID，与工具观察（tools/v2）记录中的 toolCallId 相同，界面可以据此把工具卡片标为“待审批”
name是工具名
args是参数快照（对象）。长整数和金额用字符串
argsSha256是参数快照的摘要：键排序后的 UTF-8 JSON 的 SHA-256。调用方当作不透明的绑定值，不自己重新计算
command否命令类工具的命令文本，便于展示
条款内容
H-18exec 的选项中至少有一个 effect: allow、至少一个 effect: deny，保证人始终可以拒绝。
H-19Agent 只能按被批准的参数快照执行。参数发生变化时必须发起新的交互，不能沿用旧的批准。
H-20过期的 exec 一律按拒绝处理。
H-21工具记录和审批互不推断：工具开始记录不表示已批准（同 P-185），审批通过也不表示工具执行成功。
H-22“本会话内一直允许”这类选项可以作为 Agent 自定义的选项（effect: allow）出现，授权范围的含义和持久化由 Agent 负责（HQ-2）。

问答型，没有类型字段对象。

H-24答案中选项以外的值由 Agent 自己区分（不在 options 中的就是自定义值）。BCS 内部为展示拆出的 customValues 不出现在线上。

8.3mode_switch：确认切换模式

决策型。用于 Agent 从一种工作模式进入另一种之前请人确认，例如从只读的规划模式进入会产生副作用的执行模式。

{
  "id": "itx-020",
  "kind": "mode_switch",
  "title": "进入执行模式",
  "options": [
    {"decision": "proceed", "label": "开始执行", "effect": "allow",
     "targetMode": "execute", "recommended": true},
    {"decision": "stay", "label": "继续规划", "effect": "deny"}
  ],
  "modeSwitch": {
    "fromMode": "plan",
    "targetMode": "execute",
    "plan": "1. 查询库存 2. 生成订单 3. 通知仓库"
  }
}
字段必填说明
modeSwitch.fromMode否当前模式，Agent 自定义的不透明字符串
modeSwitch.targetMode是目标模式
modeSwitch.plan否切换理由或计划文本，纯文本
选项上的 targetMode否不同选项进入不同模式时使用
条款内容
H-25过期的 mode_switch 按保持当前模式处理。

BCS 现有的 Claude Code 桥接把退出规划模式表示成一个 exec 审批；按 hitl/v1，这种场景应使用 mode_switch。

8.4新增类型

条款内容
H-26不带点的类型名保留给本规范。新增标准类型通过修订本规范完成，不改变扩展 URI。
H-27业务自定义类型使用带命名空间的名字，例如 order.refund_confirm。

9处理规则

9.1发起

条款内容
H-29同一个 Task 同时最多一个待处理批次。批次发出后内容不可修改，只能整体替换（9.4）。
H-30Agent 必须先把批次写入引擎的运行记录，再发出 INPUT_REQUIRED。
H-31expiresAtMs 必须晚于发出时间。
H-32摘要 TextPart 是纯文本，不含凭据，写清楚需要人做什么。调用方处理交互时忽略它；不认识本扩展的调用方至少能把它展示给人。

9.2续交的校验顺序

  1. 续交请求是否激活了 hitl/v1（H-06）。
  2. Task 是否存在；contextId 是否与 Task 一致（A2A 规范要求拒绝不一致的消息）；协商了调用上下文时，用户是否与创建 Task 时一致（P-103）。
  3. 消息中是否恰好有一个回复 DataPart。
  4. 幂等重放：如果每条回复都与回执中已接受的结果完全相同，直接返回当前 Task 快照，不做任何修改。不论 Task 处于什么状态，包括终态。
  5. Task 是否处于 INPUT_REQUIRED，batchId 是否为当前批次。
  6. 每条回复：id 是否属于当前批次；已结束的交互，回复相同则跳过，不同则冲突。
  7. 按形态校验每条回复的内容（7.6）。
  8. 全部通过后，条件写入回执（HR-2）。任何一条不通过则整条消息都不生效。
  9. 批次中的交互全部结束时，恢复执行，且只恢复一次（HR-3）。
  10. 返回：returnImmediately=true 时写入后立即返回 Task 快照；否则按 A2A 的阻塞语义等到下一个终态或中断态；流式续交时首帧为 Task 快照。
条款内容
H-33一条续交消息中的回复全部有效才生效，不得只应用其中一部分。
H-34相同的回复重复提交视为成功（第 4 步和第 6 步）。调用方在响应丢失、超时后可以安全地重发同一条回复。

9.3交互的结束

结束原因触发Agent 的处理
answered收到有效回复写入回执，记录回复内容
expired到达 expiresAtMs按类型兜底（H-20、H-23、H-25），写入回执
canceledCancelTask所有待处理交互写入 canceled，Task 进入 CANCELED
supersededAgent 需要替换当前批次（例如情况变化，原来的审批已没有意义）未回答的交互写入 superseded，已回答的保持不变；再发出新的 INPUT_REQUIRED，使用新的 batchId 和新的交互 ID
条款内容
H-35过期与回复同时到达时，只有先完成条件写入的一方生效（HR-4）。
H-36调用方放弃等待时（例如自己的运行预算耗尽）应调用 CancelTask，不要让 Agent 一直等到过期。

9.4Task 状态与流

条款内容
H-37INPUT_REQUIRED 是中断态，按 A2A 规定，发出后当前的流结束。Agent 不得为了等待回复而保持流。
H-38部分回复后 Task 保持 INPUT_REQUIRED。批次全部结束后，Agent 把状态置为 WORKING 再继续执行，也可以直接进入终态（例如因为拒绝而以 REJECTED 结束）。
H-39调用方获取后续输出有两种方式：用 SendStreamingMessage 续交；或用 SendMessage（returnImmediately=true）续交后调用 SubscribeToTask。Agent 两种都必须支持。BCS 目前使用第二种。

11安全

风险措施
从文本或事件中误判为批准只认结构化回复（H-14）；工具记录不表示批准（H-21）
批准后参数被替换回执绑定交互，交互绑定 argsSha256；参数变化必须重新审批（H-19）
等待超时后默认放行exec 过期一律拒绝（H-20）；未激活时不得放行（H-07）
人无法拒绝exec 必须提供拒绝选项（H-18）
别的用户替原用户回答续交时核对调用用户与创建 Task 时一致（P-103）；群里谁能回答由 BCS 决定
回复被并发篡改或重复执行条件写入，只有一方生效；恢复执行只发生一次（HR-2、HR-3）
展示内容注入title、description、label、plan 都是纯文本，调用方不得当作 HTML 或脚本执行
凭据泄露不支持密码类问题（H-12）；参数快照和摘要中不得包含凭据和 userId（P-105）
超大请求批次 1–64 个交互；单个 args 编码后不超过 128 KiB；承载批次的 DataPart 不超过 240,000 字节（沿用 v1）

12多实例与重启（对引擎的要求）

沿用上位稿的结论：Task 状态的唯一来源是引擎的运行记录（D3），停机恢复由引擎保证（D4）。hitl/v1 在此基础上增加以下要求，它们是上位稿 R-01–R-09 的补充。

编号要求
HR-1批次和回执保存在引擎的运行记录中，任何实例都能读出；GetTask 返回的 Task.metadata 包含回执。
HR-2回执按交互条件写入：只有交互仍待处理时才写入成功。两个实例同时接受不同回复时，只有一个成功，另一个按冲突处理。
HR-3恢复执行只发生一次：写入批次最后一个回执的那次条件写入，同时把批次标为已结束并取得恢复权；其他实例不得恢复。
HR-4过期按绝对时间处理，可以由任何实例执行，同样使用条件写入，与回复竞争时只有一方生效。
HR-5重启后待处理批次保持不变，过期时间不因重启而延长。

13Java SDK 支持

hitl/v1 依赖 Task，放在 SDK 支持引擎模式的阶段交付，第一期（消息模式）不包含。托管模式不支持。SDK 提供编解码和校验，状态保存与恢复由引擎负责。

SDK引擎（业务实现）
发起构造批次并校验 H-08–H-12、H-18、H-28–H-32；生成 INPUT_REQUIRED 状态更新和摘要；计算 argsSha256决定何时需要人参与；先持久化批次（H-30）
输出检查没有激活 hitl/v1 时拒绝输出 INPUT_REQUIRED；类型超出调用方声明时拒绝—
续交解析回复，按 9.2 的第 1、3–7 步校验，区分幂等重放和新回复提供当前批次和回执；条件写入（HR-2）；恢复执行（HR-3）
回执编码和解码 Task.metadata["bcn.hitl"]，检查上限（H-17）保存回执
过期提供各类型的兜底结果（H-20、H-23、H-25）按时触发过期并条件写入（HR-4）
错误按第 10 节映射三种绑定的错误—
// 发起：引擎判断需要审批，构造批次（SDK 在 build() 中校验）
HitlBatch batch = HitlBatch.builder("batch-001", expiresAt)
    .add(HitlInteraction.exec("itx-001", toolCall)          // toolCallId、name、args；SDK 计算 argsSha256
        .option("allow_once", "允许本次", Effect.ALLOW)
        .option("deny", "拒绝", Effect.DENY))
    .summary("需要你确认转账 100.00 元")
    .build();
engine.savePending(taskId, batch);                            // 先持久化（H-30）
emitter.emit(Hitl.inputRequired(taskId, contextId, batch));   // INPUT_REQUIRED 状态更新

// 续交：在 sendMessage / sendStreamingMessage 中
Optional<HitlReply> reply = Hitl.reply(call);                 // 带 taskId 且有回复 DataPart 时才有值
if (reply.isPresent()) {
    HitlPending pending = engine.pending(taskId);             // 当前批次和回执
    HitlCheck check = Hitl.check(pending, reply.get());       // 9.2 的第 3–7 步，不合法时抛出对应错误
    if (!check.isReplay()) {
        engine.accept(taskId, check.accepted());              // 条件写入；批次结束时恢复执行（HR-2、HR-3）
    }
    return engine.snapshot(taskId);                           // 快照的 metadata 中带回执
}
