# RFC：谁是卧底的多人操作与换局隔离

状态：待评审。关联 [#2609](https://github.com/inclusionAI/Avernet/issues/2609)。

同一协作群可以连续开局。每次开局锁定当局名单，Human 按座位顺序发言，同时提交投票。玩家换座、换人或切换账号后，服务端仍按认证身份授权，副屏只显示当前局自己的词和操作。

[基线验证](validation.md)在隔离的本地 BCS 上实测了同群两会话、同名词条、A 换座和 B 被 C 替换。会话级 Group Context 通过了 5 次本人读取和 10 次非本人拒绝。当前分支的前端 HumanInput 定义校验拒绝指定处理人和并发等待，同局的另一位在场 Human 可以先提交未绑定的节点。Workbench 副屏使用的 API 前缀也缺少现成的词条读取路由。

## 基线与交付边界

- 文档分支从 `oss-camp2026` 的 `86252c1e98d812f18166f930d9f7c2ceafd06f46` 创建。本地验证使用该版本的 BCS。2026-11-25 复查 `dev` 的 `672804bbcd2ef0865b07d707b0e9d18cb46f3ef1`，前端 HumanInput 的绑定和排序限制仍在。设计依赖 [#2900](https://github.com/inclusionAI/Avernet/pull/2900) 的 Group Context 写入与所有者策略能力，其合入提交 `d163eb905f23de6fd7672162da9d9a5690f74fee` 已是本次活动分支基线的祖先。
- 本 PR 交付 RFC、[威胁模型](threat-model.md)和基线验证记录。评审后，profile 负责名单、发词、计票和编排，游戏副屏负责展示和操作。BCS 的 HumanInput 契约与可能需要的只读路由分别列为待评审项，得到维护者确认后放到独立 BCS PR。
- 多人模式支持 2～4 位 Human、总计 4～8 位玩家、可配置卧底数。主持人另计，开局时校验人数、座位和 actor 唯一性，并检查卧底数符合现有胜负规则。既有单 Human 流程和快照保留。不涵盖观战、断线重连和 8 人以上对局。评审边界以 [维护者回复](https://github.com/inclusionAI/Avernet/issues/2609#issuecomment-6412333662)为准。

## 会话与身份边界

1. 主持人从服务端当前会话成员和本局选定玩家生成不可变的 seat → actor 映射。只把在场且选定的成员列入名单。创建会话时，已有群员可能默认在场，单靠创建新会话不能推导本局名单。按当局规则过滤或校验超员，开局后拒绝换座和补人。
2. 每局绑定一个新会话，并用 BCS 返回的规范 `groupId`、`sessionId` 和各阶段 `runId` 确认归属。保留历史副屏时将它绑定在历史会话。新局使用独立于旧局的状态和词条。主持人提交阶段、录入动作或发布结果前检查其局、轮、阶段和玩家归属。已退场或终局的动作按既有失效规则处理。
3. 副屏从现有认证身份响应或可信宿主取得 actor 和认证会话。公开 roster、节点映射和旧的 `currentViewerActorId` 仅供渲染。词条读取、pending 和 respond 均由 BCS 从服务端认证请求派生 caller，座位号和任何公开参数都不能授权。
4. 模拟回放和缓存可以复用公开信息。明文词和可提交动作存于当前渲染上下文的内存，读取结果至少绑定 `sessionId + actorId`，动作还要绑定 `runId + nodeId + attempt`。身份或会话变化立即清空明文词和动作，丢弃旧请求的迟到响应，旧副屏也不能跟随群内最新运行而切到新局。历史本人读取仍由该局 ACL 决定。

## 私有发词

- 主持人把每位 Human 的词写成独立的 `scope_level=session` 词条。使用无词义、按局生成的词条标识，写入时显式使用单一目标 actor 的 `visible_to`，写权限限定为主持人。读取显式指定当前 `groupId`、`sessionId` 和 `scope_levels=["session"]`。不提供 group 或旧会话的回退。
- 先校验名单并完成全部词条写入，再开放发言。任何词条初始化失败都保持未就绪，不向公共渠道补发，重试须核对同一局的词条标识与 ACL。恢复依赖主持人拥有的当局状态，禁止从旧副屏或任一玩家输入推断名单或词条所有者。
- 公开 panel 参数可以带不含秘密的词条定位符。多人模式只从 Group Context 查询 Human 的词，HumanInput 指令及 `UNDERCOVER_UI_CONTEXT_V1` 只保留动作所需的数据。主持人用现有 worker 私有投递给每个 Bot 送达其词，在查看通用节点详情、instruction、工具事件和广播等路径时，其他参与者仍不能取得词。如果现有 worker 投递不能达到这个边界，必须在实现前明确额外缺口。
- 已验证的 BCS 路径为 `POST /groupcontext/get`，以 Human 认证身份执行 ACL 判断。副屏当前前缀 `/api/v1/collaboration` 下的同名路径在本地 BCS 返回 404。先验证实际 Workbench 网关能否通过同源、携带现有认证的路由访问既有读取操作。若缺少通路，待评审的最小变更是为副屏开放只读调用入口，复用现有请求语义和 ACL。服务端不接收调用者自报身份，副屏不持有主持人凭证。

## 发言与投票

- 按存活座位生成发言依赖，Human 发言节点带 `assignee: {type: runtime_actor, actor: ...}`。上游只传允许公布的发言。离场或已出局玩家不创建待处理动作。
- `vote_start` 后，存活玩家的 `vote_N` 节点并行等待。Human 节点绑定对应的当局 actor，Bot 节点使用既有 Bot 绑定，投票之间没有相互依赖。主持人 `tally` 汇聚当前运行的投票，沿用弃权、超时和 PK 规则。重开的投票运行只接纳本次运行的票。旧轮迟到提交按过期动作处理。
- 若仍有存活玩家 Bot，由现有规则选择一位处理 `vote_start`。若所有玩家 Bot 都已出局且游戏尚未终止，由主持人通过原有 Bot binding 接收独立的 `vote_start` 节点任务，只提交无秘密的固定开投确认。开投命令提交运行后先结束本次激活，收到 `vote_start` 后才确认，避免主持人等待自己。验收须在三个存活 Human、零玩家 Bot 的未终局状态下验证唯一入口、并行等待和计票，并包含 PK 场景。[维护者评审意见](https://github.com/inclusionAI/Avernet/pull/3193#issuecomment-6462132446)
- BCS 最小契约变更是允许无 IM 通知的前端 HumanInput 使用现有 `runtime_actor`，只放行显式绑定不同 Human 的并发等待。重叠窗口中同一 actor 的多个节点、未绑定节点与其他可能并发的人类节点继续受顺序约束。在现有 `pending-human-nodes` 上按认证 caller 过滤已绑定节点。在 `respond` 上核验 caller 是会话中在场的绑定 actor，并沿用待处理状态检查与原子提交。未绑定节点保留既有规则，接口不增加 `human_xxx` 请求字段。
- 参与者视角在当前运行的指定 `tally` 完成且有已发布结果前只显示「已投票」。正常发言继续按原流程展示。PK 或新一轮使用各自运行的计票状态，旧 `tally` 完成事件不能提前解锁新票。保留默认 Full 视角及现有节点详情权限。能调用现有详情接口的参与者可能直接读取未公布票面。完整的后端票面隔离及 `sealed_output` 不在本阶段范围，词条隔离仍按服务端授权验收。

## 兼容与失败处理

- 单 Human 原流程以 `tests/fixtures/flow_baseline.json` 验收。旧 run 和旧面板不迁移到多人流程，既有历史回放仍按原归属读取。
- 多人能力未部署或私有词条读取失败时，拒绝开始多人局或保留当前局的安全错误状态，可以修复后重试同一局。回滚时停用新局入口，由已部署的旧 profile 和副屏承接新开的单 Human 局。
- 对于权威状态写失败、ACL 初始化失败和回复冲突，操作返回错误并保留可诊断的状态。诊断记录仅使用会话、节点及错误类别等非秘密字段，主持人需要回看详细状态时从其受限工作目录读取。
