# Merge user and Bot MCP Headers per key

Status: implemented in Avernet; enterprise integration and deployment pending.

`ac_user_mcp_config` remains the user default and `ac_bot_mcp_config` remains the Bot's explicit configuration. Both the product UI and Manifest write control-plane state. A Manifest Apply replaces the target Bot's complete explicit Header set, not the user's defaults. The effective Header set for a normal MCP Center endpoint is formed by merging user defaults with the Bot's explicit Headers by name, with the Bot value winning on a collision. Thus a Manifest declaration of `{A: 3}` and a user default of `{B: 2}` yield `{A: 3, B: 2}` for that Bot. A later user update of B remains visible without rewriting the Bot row.

This supersedes the explicit-empty-Header inheritance distinction recorded in ADR 0014. It deliberately replaces the previous runtime interpretation in which a Bot `headers` map blocked every user Header, including when the map was empty. Under the new interpretation, `headers: {}` means no explicit Bot Header and therefore inherits user defaults. The existing custom-URL credential isolation remains: user Headers must not be forwarded to an arbitrary Bot URL. Product UI submission is a complete snapshot of its Header groups, split into user defaults and Bot explicit sets in one control-plane transaction; device projection remains best-effort. Before rollout, audit existing Bot rows that may rely on the old blocking interpretation and update the relevant resolver, validation, restart/projection, and compatibility tests.

The first product iteration does not provide a per-Bot exclusion of a user-default Header; an explicit exclusion would require its own later contract. Editable reads return declared user-default and Bot-specific groups, not duplicated effective values. A Bot may hold a connection configuration before installing the MCP. The initial Bot picker is restricted to Bots owned by the configuring user, even if another product surface lists collaborative Bots. Concurrent complete-snapshot saves use last-write-wins without a new aggregate revision token; a successful save is followed by a fresh read.

Both the newer TeamClaw MCP detail page and the older product page need access to the aggregate read/write operation. A product save includes user-level endpoint environment and transport protocol together with user-default and Bot-specific Header groups in the same control-plane transaction. API-key editing remains separate and must not be cleared or echoed by the aggregate Header form.

The older `/api/mcp/user/config` and the existing user-scoped OpenAPI config route retain their current user-only contracts. New aggregate HTTP routes in both namespaces translate to the same control-plane operation; neither existing route is repurposed based on an optional field or the legacy `bot_id=default` query parameter. The aggregate operation is initially scoped to a personal user and Bots owned by that user; project, team, and collaborator-owned Bot scopes are outside this iteration.

The new aggregate write requires the complete `params` list. `params: []` clears only user-default and Bot-explicit Headers; omission is invalid and does not mean no change. The same form requires a user-level `endpoint_env` of `PROD` or `PRE` and accepts a nullable user-level `transport_protocol`; null clears the saved protocol preference so MCP Center's default applies. These snapshot semantics do not change the existing user-only route's null-as-unchanged behavior.

An explicit Bot Header value is retained even when it currently equals the user default, so a later change to the default does not change that Bot's chosen value. An empty string is likewise an explicit Header value, not a deletion marker. Removing a parameter group (or removing a Bot from its scope) is the operation that removes the corresponding explicit rule. Header-name collision and override resolution are case-insensitive, as required by HTTP Header semantics.
