# 谁是卧底：3 个玩家 Bot 与 1～2 个 Human 玩家

状态：Q1～Q4 已确认；按用户限定修改范围修订。双 Human 的输入顺序与信息隔离存在待确认折中，尚未实施。

- 领域语言：[游戏词汇表](../CONTEXT.md)。

## 已确认的需求

1. 主持人另计，玩家 Bot 固定为稳健老陈、逻辑控林工、戏精阿浪。
2. 收到“开始”时，锁定已加入当前会话的 1 或 2 位 Human，与上述 3 个 Bot 组成 4 或 5 人局。
3. 没有已加入的 Human 不开局；超过 2 位 Human 时提示调整后再开；开局后不补人。
4. 单、双 Human 统一在各自面板看词，主持人不在群内念词。原方案要求不能读取对方的词或代交操作；现有接口无法在本次允许范围内保证该服务端边界，不能将下述 UI 折中当作已获确认。
5. 随机座位与身份，默认 1 名卧底，Human 也可能是卧底。仍不向玩家透露其阵营身份。
6. 卧底全部出局则平民胜；剩余人数不超过 2 且卧底仍在，或达到默认 6 轮上限，则卧底胜。
7. 平票规则已由 [平票 PK 方案](tie-break-pk-spec.md) 取代：正票平票先进行一次 PK，再次平票才进入下一轮。

## 流程保持范围

目标仍为“加入会话 → 回复开始 → 发词 → 按座位串行发言 → 主持人汇总 → 投票 → 计票 → 遗言或下一轮 → 终局公布并结束会话”。不增加准备确认或人工推进步骤。双 Human 同时提交投票无法沿用现有 HumanInput 契约，候选方案如下，尚待用户确认。

继续沿用 Bot 出局且游戏未结束时的遗言分支，以及 Human 出局、PK 无人出局或常规零有效票后的下一轮分支。保持发言汇总与开投的分次激活、投票结束后的回灌推进及现有恢复纪律。出局 Human 不再收到发言或投票任务。

4/5 人面板按实际座位展示。访问者身份应来自现有宿主或认证响应；实施前核实游戏组件可取得该信息。公共参数中的玩家 ID 仅表达动作归属，不能作为已认证访问者的证据。若既有接口不能提供当前访问者身份，应明确报告，不增加选座冒充身份的流程。

## 已核实的实现缺口

- `undercover.py` 的会话名单验证拒绝多个 Human，状态、查词和面板投影使用单 Human 模型。
- BCS `definition.rs` 禁止 frontend HumanInput 指定 assignee，并要求所有 HumanInput 存在先后依赖，因此双 Human 并行投票不能直接使用当前契约。
- `runtime.rs` 对未指定 assignee 的待处理 HumanInput 允许所有已获授权 Human 查看；仅在面板隐藏内容不能实现私有发词。
- 游戏面板采用六座布局与单一当前 Human 动作，需要适配实际玩家数和访问者。

## 范围内的候选方案

### 人数与规则

调整 profile 的 `bots.json`、主持人指令与 `undercover.py`，固定三个玩家 Bot，保存逐席 Human 身份，开局校验 1～2 位已加入 Human。更新游戏内示例、提示和测试。保留原有随机分配、胜负及遗言规则。

### 投票：Bot 并行，Human 顺序收集（待确认）

同一投票运行内，Bot 投票分支保持并行，两位 Human 的节点按座位依赖排列。汇总节点等待 Bot 分支与 Human 链全部完成后计票。Human 顺序提交期间不展示任何已投票的目标，上一位 Human 的票不进入下一位的可见指令或副屏内容。

平台会传递直接上游产物，因此必须验证 Human 链的票面隔离；必要时使用现有主持人 bot_task 节点将上游结果转换成无票面的就绪信号，再激活下一位 Human。这些节点只能使用已有协作能力，不发送新的主持消息，也不触发开票。具体图结构及转交内容需用生成 YAML 和真实运行验证，不能只凭 UI 隐藏声称票面已隔离。

这保持一个投票阶段和收齐后计票，但改变了两位 Human 同时操作的体验，不等同于原先确认的全员并行。

### 看词与操作：副屏分别展示（待确认）

副屏只向当前玩家展示其对应节点的词和动作，其他玩家看到等待状态；主持人不在群里念词。词不进入公共 panel 参数、URL 或浏览器持久化存储。现有 pending/node 等接口仍可能被其他已授权会话参与者直接读取，respond 接口也不强制区分本局两位 Human。

因此该方案仅适用于参与者遵守不查看他人节点、不绕过副屏代交操作的游戏约定，不能提供服务端防窥或防代交保证。不以混淆字段或前端自报身份来宣称解决隔离。

### 兼容性

不修改现有 BCS 契约，不借用 IM 通知模式绑定前端玩家。旧运行状态的读取兼容方案尚未验证，不宣称可将正在进行的六人局原地转换。

保留工作区已有的身份认证、名单校验和启动脚本未提交修改，在其基础上形成可审阅的增量。

## 验收要求

- 3 Bot + 1 Human、3 Bot + 2 Human 各完整跑通，覆盖 Human/Bot 抽到卧底。
- 0/3 位 Human、缺少所需 Bot、开局后新增 Human 均不产生错误参赛名单。
- 若接受顺序收集：两位 Human 按序提交，Bot 分支仍并行；未收齐有效票不提前计票，第二位正常操作时看不到第一位的票。
- 若接受 UI 展示边界：正常副屏操作只展示自己的词与动作，群聊和公共参数不泄词；直接调用服务端接口的隔离限制明确记录，不将它计作通过。
- 覆盖平票、Bot 遗言、Human 出局、两个 Human 均出局后继续运行、双方胜利和轮数上限。
- 发言串行、自动推进以及终局行为保持；4/5 座面板与动作归属正确。
- 运行游戏事实层测试、游戏副屏测试与面板现有验证，再做两个真实 Human 身份的端到端验收。不计划修改或测试新的 BCS 契约。

## 待确认

用户是否接受双 Human 在同一投票阶段按序提交，以及只在正常副屏中分别展示词语和动作的隔离强度。若仍要求全员并行及服务端私有隔离，则现有接口与当前修改范围不兼容，不能将本方案标为可完整满足需求。
