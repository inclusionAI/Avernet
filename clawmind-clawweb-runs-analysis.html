v1 修正说明

v1 文档错误地将 TCP 上涨归因于"自动分析 dispatchEvolveCommand() → execFileSync("git", ...) 阻塞事件循环"。经代码核实：

  • dispatchEvolveCommand() 是 async fetch() 到 BaaS API，不阻塞事件循环
  • execFileSync("git", ...) 只在 auto-heal-save-service.ts 和 auto-heal-deploy-service.ts 中，仅由 Web UI 手动触发
  • 自动分析（workflow-automation）不会触发 execFileSync
  • 自动治愈（auto-heal）没有定时任务

本版本基于代码 diff 和新增的 associateRun() 发现，重新分析性能退化的真正根因。

2.1 两条独立的功能线

功能线触发方式是否调 execFileSync？是否阻塞事件循环？

四、性能退化根因：insert() 事务化 + associateRun()

新发现：提交 1f2014f6c 引入了性能退化

提交 1f2014f6c（feat(workflow): scope evolution to immutable run snapshots (#2882)，作者 wienyang，2026-10-19）修改了 FlowRunRepository.insert()，从简单 INSERT 改为事务 + 额外查询。

4.1 修改前（回退版）— 简单 INSERT

// flow-run-repository.ts — 回退版
async insert(run: FlowRunInsert): Promise<boolean> {
  const now = this.db.dialect.now();
  await this.db.exec(
    `INSERT INTO flow_runs (...) VALUES (?, ?, ...)`,
    [run.flowId, run.workflowId, ...]
  );
  return true;
}
// 总计：1 次 DB 操作，快速释放连接

4.2 修改后（新版）— 事务 + associateRun()

// flow-run-repository.ts — 新版（1f2014f6c）
async insert(run: FlowRunInsert): Promise<boolean> {
  // 包在事务里 → 持有 DB 连接更长时间
  return await this.db.transaction(async tx => {
    const now = tx.dialect.now();
    // ① INSERT
    await tx.exec(`INSERT INTO flow_runs (...) VALUES (?, ?, ...)`, [...]);
    // ② associateRun() — 新增！
    await new WorkflowSnapshotRepository(tx).associateRun(run.flowId);
    return true;
  });
}
// 总计：3-5 次 DB 操作，在事务中持有连接更长时间

4.3 associateRun() 的实际查询

// workflow-snapshot.ts:61-79
async associateRun(flowId: string): Promise<void> {
  // ③ 检查列是否存在（每次都查！）
  if (!await this.hasAssociationColumn()) return;
  // → SELECT workflow_snapshot_json FROM flow_runs WHERE 1 = 0

  // ④ 读取刚插入的 run（SELECT *，包含大 TEXT 列！）
  const binding = await this.forRun(flowId);
  // → SELECT * FROM flow_runs WHERE flow_id = ?
  //   （包含 params_json, input_json, result_json, state_json, credentials_json 等大字段）

  // ⑤ 如果是部署版本，还要查部署历史
  // → SELECT * FROM workflow_deploy_history WHERE workflow_id = ? AND deploy_number = ?

  // ⑥ 写回快照绑定
  await this.db.exec(
    'UPDATE flow_runs SET workflow_snapshot_json = ? WHERE flow_id = ?',
    [JSON.stringify(binding), flowId]
  );
}

4.5 连接池耗尽 → 所有请求变慢

核心机制：连接池耗尽导致 GET /runs 也变慢

MySQL 连接池配置：connectionLimit: 10（默认，db/config.ts:357），waitForConnections: true。

新版 insert() 在事务中持有连接 10-50ms（回退版 ~1ms）。当多个 ClawMind 实例同时创建 run 时：

  1. 多个 POST /runs 同时到达 → 每个占用 1 个连接、持有 10-50ms
  2. 10 个连接被占满 → 第 11 个请求（可能是 GET /runs）进入 waitForConnections 队列
  3. 队列中的请求等待前面的事务提交 → 响应时间 = 等待时间 + SQL 执行时间
  4. 如果等了 2100ms，GET /runs 的 P50 就是 ~2117ms（等待 2100ms + SQL 8ms + 开销）
  5. 如果等了 5s → 超时

这解释了为什么 GET /runs 的 SQL 查询本身没变（仍然有索引、8ms），但 P50 从 8ms 涨到 2117ms——因为请求在连接池队列中等待。

4.6 为什么 resolved 接口也变慢（但退化幅度较小）

resolved 接口 P50 从 6ms 涨到 627ms（104 倍），比 runs（264 倍）退化幅度小。这是因为 resolved 的查询模式不同（可能不经过同一个连接池路径，或查询本身更轻量），但同样受到连接池压力影响。

五、放大因素：appendFileSync 同步日志

新发现：internal-logger.ts 使用 appendFileSync

internal-logger.ts 中的 apiLog() 函数在每个内部 API 请求上都调用 appendFileSync()——这是同步文件 I/O，会短暂阻塞事件循环。

// internal-logger.ts:29-53
export function apiLog(method, path, details): void {
  // ① console.log — 快
  console.log(`[internal-api] ${method} ${path} ${details.status ?? "pending"}`);

  // ② appendFileSync — 同步阻塞！
  try {
    ensureLogDir();
    appendFileSync(LOG_FILE, line + "\n", "utf-8");
    // ↑ 每次调用都打开文件 → 写入 → 关闭
    //   在高并发下，文件锁竞争 + 磁盘 I/O 延迟
  } catch (error) { ... }
}

每个 /api/internal/runs 请求至少调用 2 次 apiLog()（pending + 完成）。~24,000 次/天 = ~48,000 次 appendFileSync。在连接池已经紧张的情况下，同步文件 I/O 的短暂阻塞会进一步延迟其他请求的处理。

6.2 为什么回退版正常

回退版的 insert() 是简单 INSERT（1 次 DB 操作，~1ms 持有连接），连接池不会被打满，GET /runs 立即获得连接，8ms 完成。

6.3 为什么预发不涨

预发的 executionEnvironment 过滤（'prod' ≠ 'pre'）使 tick() 不处理工作流 → onRunTerminal 被 authority() 拒绝 → 额外 DB 查询少 → 连接池压力小。但 insert() 的事务化在预发也存在，只是并发量低（工作流少）所以不明显。

七、已排除的假设

假设1：自动分析 dispatchEvolveCommand() → execFileSync("git", ...) 阻塞事件循环

已排除。 dispatchEvolveCommand() 是 async fetch() 到 BaaS API，不阻塞事件循环。execFileSync("git", ...) 在 auto-heal-save-service.ts 和 auto-heal-deploy-service.ts 中，仅由 Web UI 手动触发（POST /api/auto-heal/save 和 POST /api/auto-heal/deploy），没有定时任务，不被自动分析调用。

假设2：scheduleTerminalObserver 触发 execFileSync 阻塞

已排除。 scheduleTerminalObserver（runs.ts:14-26）通过 setImmediate 异步调度 onRunTerminal 回调。回调链是 onRunTerminal → runAnalysis() → dispatchEvolveCommand() → fetch(BaaS API)，全程 async，不调用 execFileSync。

假设3：auto-heal 有定时任务触发 Git 操作

已排除。 搜索 auto-heal.*setInterval、setInterval.*auto-heal、auto-heal.*cron 均返回 0 条结果。auto-heal 没有独立定时器。monitor.reconcile() 每 15s 调和 pending 部署记录，但不直接调 auto-heal save/deploy。

假设4：BaaS fetch 60s 超时导致 TCP 堆积

部分排除。 fetch() 是 async 的，不阻塞事件循环。但如果 BaaS 响应慢（BOT 重启期间），每个 fetch 持有 TCP 连接 60s 确实会堆积 TCP。这是次要因素，不是主因——因为 A/B 测试的 runs 接口不调 BaaS，它是纯 DB 查询，退化 264 倍说明 DB 连接池才是瓶颈。

8.4 关键代码修改：associateRun 移出事务

// flow-run-repository.ts — 修改后
async insert(run: FlowRunInsert): Promise<boolean> {
  try {
    // 1. 先做简单 INSERT（不在事务中，快速释放连接）
    const now = this.db.dialect.now();
    await this.db.exec(
      `INSERT INTO flow_runs (...) VALUES (?, ?, ...)`,
      [run.flowId, run.workflowId, ...]
    );

    // 2. 异步做快照关联（不阻塞 INSERT 返回，不持有事务连接）
    //    如果关联失败，run 仍然存在，只是没有快照绑定
    setImmediate(async () => {
      try {
        await new WorkflowSnapshotRepository(this.db).associateRun(run.flowId);
      } catch (error) {
        console.warn(`[db] associateRun failed for ${run.flowId}: ${error}`);
      }
    });

    return true;
  } catch (error) {
    console.warn(`[db] FlowRunRepository.insert failed: ${error}`);
    return false;
  }
}

9.4 Parent 结果处理

businessOutcomeParent 行为
all_success汇总全部实验结果，统一通知。
partial_failure同时展示成功项和失败项，统一通知一次。
all_failed生成失败汇总，不把 fanout 节点成功误判为实验全部成功。
incomplete标记待人工处理，第一版不做自动 reconciliation。

9.5 第一版明确不做

  • 不新增 workflow_fanout_groups 表。
  • 不新增 child association 表和专用 lookup API。
  • 不改造 flow_runs 的通用 parent/child 字段。
  • 不做父进程崩溃后的自动恢复。
  • 不做启动响应丢失后的自动对账。
  • 不做多 collector CAS 和 item-level retry。
  • 第一版假设同一 parent flow 同一时刻只有一个 collector。
上线限制

如果 parent 在 child 已创建但 childFlowId 尚未写入 parent state_json 的窗口内崩溃，第一版可能遗留孤儿 child，需要人工处理。该限制是为了保持最小实现，不应被误认为已经具备完整生产级故障恢复能力。
