# 两个临时自定义协作的形状

YAML 由 `open-round` / `open-vote`（内部是 `render-speak-run` / `render-vote-run`）生成，**不要手写**。这份文档解释它们为什么长这样，方便出问题时判断是不是渲染出了偏差。

## 一条贯穿两个运行的原则：流程推进只由我做

玩家 Bot 不当任何一个运行的门房。两个运行的零入度入口节点都是我的 `bot_task`，产物就是那一轮的开场稿。这带来两个好处，也带来一个必须一直盯着的代价——都写在下面。

## 发言：我开场，然后传递闭包

存活玩家按座位顺序 `s1..sk`：

```text
speak_open（我，回合开场）
    ├→ s1 ─┬──────────────────────────┐
    ├→ s2 ─┼─ ...                     │
    ├→ ... │                          │
    └→ sk  │                          │
           （s_i 的 targets = 它后面所有发言节点 + collect）
                                      ↓
                                  collect（我，final_output）
```

- `speak_open` 扇出到**每一个**发言节点，不只是第一位：节点提示里只包含**直接父节点**的产物，扇到全部人，开场稿才会出现在每个人的 `[Upstream Outputs]` 里。它不连 collect，collect 的上游保持"只有发言"。
- 第 i 个发言节点的 targets = **它后面所有发言节点 + collect**。为什么不是简单的链：`s1→s2→s3` 会让 s3 看不到 s1 说了什么。把前面所有人都连成父节点，后手才能拿到本轮完整发言，collect 才能一次拿到全部 k 份。
- 人类玩家的位置是一个 `human_input` 节点，没有 assignee、没有 binding，超时给足 15 分钟。人类出局之后这一轮就没有 `human_input` 节点了，入口仍然是 `speak_open`。
- **人类节点的 `display_name` 里写死了"人类玩家"**（`👤 你的发言（2号 · 人类玩家）`）。副屏里
  所有节点长得一样，只写"2号发言"的话他找不到哪个该他点。
- **人类节点的 instruction 是短句版**：他是几号、他的词、一句话多长、别说出那个词、说钝一点，
  五行结束。Bot 那套（枚举二字组合、钝度自检问句、类目白名单）是写给模型看的硬约束，人类
  读到一半就跳过了——实测他两轮都直接给了定义句。字面泄词有 `check_text` 兜底，不必在他
  眼前枚举一遍。
- 每个 **Bot** 发言节点的 instruction 里都带一段**本轮钝度**（`bluntness_block`）。`forbid_line` 管的是字面泄词，钝度管的是语义泄词——第一轮就把词描述到只对应一件东西，卧底当场暴露，整局一轮就结束。钝度按轮次收敛（4 → 3 → 2），信息也就按轮次释放。第一位发言者没有参照，它的指令里会额外说明本轮的钝度由它定。
- **第一轮的起点是 4，不是 5，而且允许带一个属性。** 5 配上"只许说感受、不许说属性"的类目
  白名单，实测第一轮六句全是纯感受，票型完全是噪声：白烧一轮，还冤杀了一个平民。现在第一
  轮可以挑一个角度、带一个具体属性，只是不许把用途和对象塞进同一句（那等于下定义）。
- `speak_open` 的 instruction 里**不带钝度段**，它不是发言节点。

## 投票：我开投，扇出再汇合

```text
vote_open（我，开投）─┬→ vote_s1 ─┐
                      ├→ vote_s2 ─┤
                      ├→ vote_h  ─┤   ← 人类的票也在这一层，和 Bot 同时进行
                      └→ vote_sk ─┘
                                   ↓
                                tally（我，final_output）
```

- 所有投票节点并行，彼此看不到对方的票。每个人的词写在自己节点的 instruction 里，公开的发言史走 `--input`。
- **投票节点只要票号，不要理由。** 一条理由就是"拿我的词比对他的话"的结果，被我在开票时念出来，等于把那个玩家的词属性广播给全场——第一轮结束信息就透明了。所以玩家的唯一判断依据是 `--input` 里所有人全部历史轮次的发言。指令是软的，`votes-set` 还会把票面规范化成票号，就算有人多写了半句也到不了主持稿里。
- **`vote_open` 的稿子是全场内容边界最紧的一段。** 它的产物会流给每一个正在投票的人，投票又是全场信息最敏感的一刻——所以指令里写死了只许说哪四件事，不许提任何玩家、不许复述任何发言、不许流露任何倾向。多说一个字都可能左右选票。
- `tally` 是汇合点，BCS 会等齐全部上游才派给我。全场只有我能同时看到所有票。

## 入口节点归我：好处、代价、和三道保险

**好处有两个。** 一是流程推进全在我手里，人类看到的每一句开场都来自主持人，不会突然冒出一句玩家说的"开始"。二是开场稿从"我这次激活的尾巴"挪成了"入口节点的产物"——提交完运行我不用再说话，人类在提交那一刻就看到"第 N 轮开始"，而不是等我把活干完才看到。

**代价是一个踩过的坑，现在被主动请了回来。** 我是在自己的一次激活里同步提交运行的，运行一启动就把入口节点派回我的会话通道，而那条通道正被提交它的那次激活占着。节点排在我自己后面等我让路。2026-08-28 那次投票卡死就是这么来的：通道在激活结束后泄漏了 6 分钟，节点一直排在队里，BCS 先判了超时——而运行失败**不会**唤醒我，游戏无声地停住。

**三道保险，缺一不可：**

1. **入口节点的 `node_timeout_ms` 是 900000（15 分钟）。** 实测正常交接 3–5 秒；最坏那次泄漏 6 分钟。15 分钟把两种都盖住。
2. **提交必须是本次激活的最后一个工具调用。** `open-round` / `open-vote` 把查槽位、渲染、提交合成一条命令，就是为了让"提交"和"激活结束"之间不再插进任何来回。提交之后我每多花一个 LLM 来回（实测最慢的一个来回 55 秒），入口节点就多等这么久。**"最后一个"是字面意思，`bcs_assign_task` 也算**——见下一节。
3. **末节点里不做下一步。** `collect` 只念转述稿、`tally` 只念开票稿；开投和派唤醒源都等回灌那一拍。这两个节点是各自运行的出口，运行要等这次激活结束才算完成——在里面提交下一个运行就是等自己让路，锁死之后连超时判死都要等满 10 分钟，而运行失败还不唤醒我。2026-08-30 第 2 轮就是在 `collect` 里跑了 `open-vote`：`RUN_SLOT_BUSY` → 重试 → `sleep 10` → 轮询 → `sleep 20`，一路到节点超时。脚本这边现在会把这种自锁单独报成 `IN_COLLECT_NODE` / `IN_TALLY_NODE`，和「上一个运行刚收尾」的普通竞态（`RUN_SLOT_BUSY`，可以再等）区分开。

**曾经有第四道，是投票期间的「看门狗」——已经拆掉了，因为它是净负的。** 那是派给一个已出局
Bot 的任务，让它三分钟后回一句把我叫醒、去查投票运行还活着没有。问题出在它只能在 `open-vote`
提交**之后**才知道派给谁，而那一刻 `vote_open` 入口节点正排在我后面：`bcs_assign_task` 的派单
和回执都会往我自己的会话里回灌一条 `[任务状态]`，而回灌会打断当时正在跑的激活。"等三分钟"
是模型做不到的事——2026-08-31 第 3 轮实测 5 秒就回了，正好打在 `vote_open` 产出的中间，节点
失败、运行失败、整局停在开投前。**它保护的是"运行失败"这个小概率事件，而它自己就是运行失败
的主因。** 投票运行失败的兜底现在统一是人类：开场白里的"超过 5 分钟没动静回我一句『卡住了』"
对每一轮都算数，走 SX 用 `--retry` 重开。

## 派任务会打断我自己

`bcs_assign_task` 不是免费的工具调用。我是这个主从群的 driver，**每派出一条任务，BCS 会立刻
往我自己的会话里回灌一条 `[任务状态]`**，那条回灌会打断我当时正在跑的激活；任务的**回执**到达
时还会再回灌一条。2026-08-31 那一局里 5 次激活被打断，其中 4 次是我自己派单打断了自己（两次
遗言、两次看门狗），第 5 次是看门狗回执打断了 `vote_open`。协作节点的派发不会回灌，只有
`bcs_assign_task` 会。

由此两条硬纪律：

1. **`bcs_assign_task` 必须是本次激活的最后一个工具调用。**
2. **派任务的那一刻，身后不能有任何节点在排队等我让路。** 提交过运行的那次激活里一律不派任务。

现在整个流程里只剩一处 `bcs_assign_task`：S4b 派遗言/预备任务。它满足第 2 条——那时下一轮的
运行还没提交（S5 才提交），我身后是空的。**再往别处加派任务之前，先用这两条量一遍。**

## 两个运行为什么不合并

合并成一个运行会让"发言转述"变成中间节点的产物——而中间节点的产物只进副屏，不进群聊。人类就看不到发言转述了，整局在聊天里只剩一条最终结果。

分成两个运行，发言转述才能作为第一个运行的 `final_output` 自动发成群消息。

这中间那一拍**不再需要人类说话**：转述稿发出去之后会回灌成一条群消息，把裁判自己叫醒一次
（实测比转述稿晚三五秒），那次激活直接开投。以前这一拍要等人类打一句"开始投票"，实测第
二轮就等掉了一分四十秒——而他要读转述、要想，本来就可以边看边等票箱弹出来。

唯一的代价是开投那一刻发言运行可能刚收尾、协作槽位还没释放，所以 `open-vote` 内部会退避
重试三次。

**这一拍必须落在回灌那次激活里，不能提前到汇总节点里。** 汇总节点是发言运行的 `final_output`，
运行要等那次激活结束才算完成、槽位才释放；在里面开投就成了「我等槽位、槽位等我」。退避三次
扛的只是回灌那次激活里的几秒竞态，扛不住这种自锁——所以 `open-vote` 在 phase 仍是
`AWAIT_VOTE_START` 时把它单独报成 `IN_COLLECT_NODE`，并明说不要重试。

## 硬约束（服务端会拒绝的写法）

- 顶层只允许 `name`、`metadata`、`participants`、`runtime`；不能有 `api_version` / `id` / `version`。
- `runtime.kind: state_machine`、`state_machine.version: 1`、`graph_mode: acyclic`。
- 只能用 `bot_task` 和 `human_input`；不能用 `initial_node`、`variables`、`events`、`guard`、`action`、`output_contract`、`input_schema`。
- 唯一零入度入口、唯一 `final_output` 出口，所有节点从入口可达且能到达出口。
- `human_input` 不设 `assignee` / `max_attempts` / `final_output`，但**必须**显式给 `node_timeout_ms`。
- 一个运行里只能有一个 `human_input` 节点。
- 提交时人类必须处于 Present。
- 真实 Bot UUID 只出现在 `--binding`，不写进 YAML。

## 超时与重试为什么是这三个数

Bot 的会话通道是串行的：同一时刻只跑一个激活，其余排队。通道偶尔会在一次激活结束
后没及时释放，节点任务就一直排在队里不动，要等 Bot 侧的自愈把通道抢回来——那个
窗口是**分钟级**的。所以：

- `node_timeout_ms` 默认 **420000**（7 分钟），必须明显大于那个自愈窗口。短于它的话
  BCS 先判死、自愈后到，节点产物变成没人认领的孤儿，还会迟到几十秒后突然冒到群里。
- 派给我的汇合节点（`collect` / `tally`）用 **600000**。我的通道最挤：人类的自由聊天、
  节点任务、以及我自己 `final_output` 的回灌都走这一条。
- **入口节点（`speak_open` / `vote_open`）用 900000。** 它和别的节点不一样：它是在我
  还占着通道的时候被派出来的，等的就是我自己。上一节的第 1 道保险。
- `max_attempts` 固定 **1**。重试对「通道堵住」这类故障毫无作用，只会让同一个节点排
  两份，排空时还可能逆序执行，在群里留下重复播报和一条空回复。真正的瞬时失败由
  Bot 侧自己重试。

这几个数由 `undercover.py` 顶部的常量统一给出，不要在 YAML 里手动调小。
