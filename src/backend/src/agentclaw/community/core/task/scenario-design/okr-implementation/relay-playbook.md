## 0、接力协议(V2 背景式运行简报)

### 0.1 单块透传,框架不做摘要/合成

框架在每个节点的输入里只透传上游的**完整产出正文**(yaml 的 `handoff: $.result`),
**不再为各节点做摘要、不重写目标、不做 fan-in 全料拼装**。"接自谁/群组成"由框架拓扑身份注入(phase2),
内容(背景、目标、产出、给下家的问题)全部由各 bot 自身 rule 产出。真实上报不可靠时,下游靠上游正文读懂。

### 0.2 每个 bot 产出正文须含的 4 块(强制,在 bot rule 里)

```
### 背景、目标与我的分析
- 我接到的需求 / 上家给的背景
- 我做了什么分析
- 本跳目标 / 结论

### 我的产出摘要
<本节点交付物的要点版,完整内容见下方正文>

### 处理不了的问题(每条带背景 + 给下家的目标)
- 问题A:<...> 我闭环不了 —— 给<下家职能词,如"营销策略专家/圈人/选品/风控/无人承接">
  给下家的目标:<...>

### 本跳产出正文(完整)
<完整交付内容>
```

### 0.3 写产出正文的硬约束(去"漏下家")

- **不写框架拓扑具名**:`③风险评审群/④BBS广场/automatic-research bot` 这类点号/集团 id 不写进产出正文,
  只用自然职能词(`找风控评估`、`无人承接`、`需安全架构师能力补`)。固定顺序拓扑里下家由框架按 depends_on 直接起,
  bot 不必指名。
- **不引入下家专属 deliverable 术语**:本家产出里写自己专业领域的产出名词即可,不替下家预写
  deliverable 名(`分层包/主推池/风险清单/舆情 MVP` 等)。下家专家拿到的问题只描述上家发现与方向,
  具体 deliverable 由下家自己 rule 写。
- **入口 OKR 实现 bot(8azkbtgs)**:OKR 入参里也别塞策略词。8azkbtgs 的 rule 含映射:
  "大促 OKR(GMV 增长目标 + 大促营销场景)→ 关键抓手营销策略补齐 → 我做不了 → 找营销策略专家";
  OKR 里只要含 GMV 增长目标与一句大促/营销背景即可,专家与否由 bot 推断,不由 OKR 显式写。
- **④ 安全架构师**:`unhandled_tasks` 的 JSON 结构化字段是框架路由 BBS 的硬字段,保留;
  叙述正文仍按职能词("舆情监测缺口无人承接"),不写"转 BBS 自我承接"。
  另:④ 必须在自己产出正文里** Carry-forward 全料**(①策略正文 + ②圈人选品细节 + ③完整风险清单),
  供⑤审核;否则⑤只读④ handoff 一定审不齐。这是 ④ rule 的责任,框架不做 fan-in 兜底。

### 0.4 输入结构(目标态,phase2 框架注入后)

```
# 接自 <上家角色名>(<上家 bot/群 id>)

- 角色/bot1 = driver / 总结者
- 角色/bot2
- 角色/bot3
## 上游产出正文
<上游完整产出正文块,框架逐字透传>
## 本角色任务(中性,只含上家已知信息)
<...
```

phase2 前框架尚未注入"接自/群组成/上游产出正文"标题。当前(本轮)实际下放是
`instruction` + `\n输入: {resolved}`,其中 resolved 含 `handoff: <上游完整产出正文>`。
bot 暂靠 instruction + 输入 dict 自取上游正文。phase2 后升级为标题化展示,bot 行为不变。
