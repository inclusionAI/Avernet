# 工作流版本快照、问题聚合与进化范围

日期：2026-10-19。状态：核心能力已实现；历史版本展示与读取修复已补充本地验证，线上效果待部署验证；扩展指标后做。

实施计划：[核心计划](../plans/2026-10-19-workflow-versioned-evolution.md)、[扩展指标计划](../plans/2026-10-19-workflow-versioned-evolution-metrics.md)。

## 1. 已确认的需求与边界

| 编号 | 必须实现的行为 |
| --- | --- |
| R1 | 每次运行关联其实际使用的 workflow 版本快照。 |
| R2 | 每次问题分析及其建议关联同一份版本快照；分析输入不得读取后来保存的配置。 |
| R3 | “问题与优化”首先按问题聚合；默认展示当前生效版本的问题和建议，并整合重复、互补建议。 |
| R4 | 新版本生效后，之前版本进入 archive 折叠；可展开查看、勾选建议。 |
| R5 | 手动勾选历史建议可以生成针对当前生效版本的进化草稿，保留原始版本、要求和证据。 |
| R6 | 每日进化任务默认只选择当前生效版本的问题和建议；不自动纳入历史或测试版本。 |
| R7 | 扩展按问题、版本统计复现、分析覆盖、修复观察及建议整合情况。 |

“最新版本”在本功能中统一指 `workflow_deploy_history.is_active=1` 的工作流版本，不是最大 save 版本、最大运行版本或最后完成分析的版本。回滚后同样以实际生效记录为准。

使用场景：线上运行 A，同时用 `run --remote` 测试保存快照 B，两者的分析各读自己的配置，默认页面和每日进化仍只选 A。B 部署生效后，页面立即切到 B，A 折叠为历史；用户仍可展开 A、勾选旧建议，连同 B 的建议一起生成针对 B 的草稿。新版本没有问题或建议时就显示为空，不拿旧版本填充。

不增加自动发布、自动回滚、每条历史建议单独重新分析、通用版本管理服务或第二套进化任务系统。不改变 Bot 单 case 分析、ClawWeb 跨运行聚合的职责。版本归档不得被用来掩盖聚合 worker 故障。

本期不得修改已有 retry 的命令参数、接口或执行行为，不要求生产用户改变重试方式。低频特殊续跑不增加专用协议、任务或验收门槛；来源无法确认时沿用“需核对、不自动选取”的通用规则。

生产兼容与投入边界：快照关联采用增量字段和兼容读取，先部署可兼容旧客户端的服务端，再逐步上报新关联；不得要求生产插件同步升级才能继续运行。关联缺失只影响本功能的可信归属和自动选取，不新增阻断既有运行/重试的条件。关联写入失败仍必须明确报错，不能伪报注册成功或重跑业务。每项改动须直接服务 R1–R6；不因低频例外改造运行引擎、重试系统或部署流程。

本规格取代本次讨论中“历史建议不能选”“所有运行仅凭正整数版本取快照”“不同来源运行版本绝不能合并”的临时结论。既有权限、不可变候选、Git 完整性、幂等、大小限制继续有效。

## 2. 术语与版本身份

产品用语使用“工作流运行版本”“当前版本”“历史版本”，不把内部的 baseline/digest 当作用户需要理解的新概念。

- `workflow_version`：工作流运行版本。
- `workflow_deploy_number`：部署编号。版本 39、部署编号 34 是合法的两项身份，不能解释为“save 39、部署版本 34”。
- 部署快照：已有部署历史中的固定 `spec_json`，及其 tag/Git 身份。
- 保存快照：`run --remote` 实际解析到的固定 Git 提交；当前源码的运行版本可能是 `-1`、部署编号为 NULL，不能用 `-1` 区分不同保存快照。
- 分析来源快照：被分析运行实际使用的配置；本规格要求建议也关联该快照。
- 任务目标快照：本次生成修改所针对的当前生效版本。历史建议的来源快照不能被改写成任务目标快照。

问题身份复用现有稳定 signature（含节点/问题模式等既有规则），版本作为问题下的作用域。相似标题不是相同问题或相同根因的证明。展开 loop 节点沿用已有规范化规则，不能为本功能临时删除节点身份。

## 4. 快照关联契约（R1、R2）

### 4.1 复用现有快照，只补关联

不新建完整配置内容仓库。部署配置复用部署历史，保存配置复用已有 Git 保存快照；已有运行状态中的实际配置可用于可靠回填。新写入的关联不能依赖可变的 `saved/<workflowId>` 指针或未来的 `workflow_specs` 内容。

新增共享小型引用契约，建议名称 `WorkflowSnapshotRef`：

```ts
type WorkflowSnapshotRef =
  | { kind: 'deployment'; workflowId: string; workflowVersion: number;
      deployNumber: number; configDigest: string }
  | { kind: 'saved'; workflowId: string; repoId: string; commit: string;
      packDigest: string; specPath: string; configDigest: string };

type WorkflowSnapshotBinding =
  | { status: 'resolved'; snapshot: WorkflowSnapshotRef }
  | { status: 'unresolved'; reason: 'LEGACY_MISSING' | 'SNAPSHOT_MISSING' | 'IDENTITY_MISMATCH' };
```

- 部署引用必须能定位该 workflow 的唯一历史记录，并核对版本和部署编号。
- 保存引用复用 Host 已有仓库身份 `repoId`，必须能定位实际 commit/tree/配置文件；启动时固定一次。后续 save 或仓库绑定变化不改写它；沿用已有 Git 留存机制保证被引用对象可读取。保存 key 为 workflowId/repoId/commit/specPath，不能靠当前可变仓库绑定反查旧 commit。
- `configDigest` 使用已有 canonical JSON 契约，对实际提供给分析的配置计算，并与该分析的 `workflowSpecDigest` 对齐；不能拿 Git commit、raw YAML 摘要或 `remote-snapshot:` 字符串直接比较。建议的 `baseSpecDigest` 保留补丁基线含义，不作为运行版本归属的读取门槛；文字建议同样可由原运行关联版本。目标 Git/部署序列化差异复用既有 `proposalSpecDigest` 校验，不再发明一种摘要。
- 复用既有规范化/序列化规则，不任意删业务字段让摘要相等。原文件字节、commit/tree 完整性与配置身份仍分别保留。

### 4.2 最小持久化

在 `flow_runs` 与 `workflow_evolution_analysis_runs` 各增加 nullable TEXT 字段 `workflow_snapshot_json`，保存上述小型 binding，不复制完整 Pack/日志。普通部署运行优先由服务端用已有workflowId、workflow_version、workflow_deploy_number关联部署历史，不要求ClawMind重复上报相同身份；新分析必须固定这次解析结果。旧行可在分析前只读解析，不要求先完成全库回填才启用功能。

- 已能确定的运行binding与`/runs`注册原子写入；历史记录暂缺或身份不符时记录unresolved并明确原因，不能因此拒绝原本合法的运行注册。数据库写入失败仍报错，不得伪报注册成功。
- remote复用已有workflowPin/workflowSnapshot的固定身份；只有实际发现该信息未到达服务端，才补最小注册转发字段，API/本地适配一致，不另改Git保存、加载或运行控制流程，也不只依赖后续best-effort state镜像。
- 沿用启动时已有的快照捕获与业务运行策略，不增加执行前联网确认。远端注册失败沿用同flowId幂等补报，不重跑业务；来源尚无法确定时只限制依赖该关联的新分析/自动选取。
- 沿用现有签名运行注册/权限校验；核对 workflowId 和实际运行解析结果。不得让未认证来源任意声明可信版本。
- 创建分析时一次性绑定该运行的 binding；分析输入及重试重复读取同一引用，加载后验证摘要。分析不得再解析当前 active 或最新 save 作为替代。
- 分析复用既有 evidence manifest 的capturedAt/maxId固定证据范围；已完成分析不得因后续运行或配置变化被改写到新版本。
- 分析 API 保留既有 `workflowSpec/workflowSpecDigest` 字段，内容改为来源快照；增加 `workflowSnapshot` 元数据。建议从分析结果投影继承该引用，不要求模型生成可信版本身份。
- 配置快照/身份缺失时返回明确 `WORKFLOW_SNAPSHOT_UNAVAILABLE`，保留该运行诊断可见性，不向模型伪装成最新配置；多运行分析混入不同快照则拆为单 case/同快照范围，不混给模型一个 spec。
- 快照引用写入失败必须报错；不得吞掉后继续成功创建依赖该引用的分析。

request:// 候选沿用其已注册固定身份校验；无法可靠关联的候选同样不得冒充部署/普通 remote 快照。

### 4.3 旧数据兼容与可选回填

部署记录可由 workflowId、实际部署编号/版本核验后回填。保存运行可从已有 pin、快照及可核对的 Git 对象回填。旧建议的 `baseSpecDigest` 不得覆写；来源版本由冻结分析引用或原运行的唯一部署/保存快照确定，文字建议无需携带补丁摘要。版本归属不代表旧补丁适用于当前配置，自动生成仍须通过既有补丁基线校验；已经明确的身份不符不因 flowId 可解析而被“补正”。

无法证明的记录显示“运行版本未确认/分析配置需核对”，原文和证据保留；不自动参与每日任务或伪称当前版本建议。可证明旧记录在读取/创建分析时即可解析关联；批量回填是可选维护，不是上线前置。如确需执行，先只读盘点数量及原因，再按幂等小批事务写入；本规格文档交付不授权执行线上回填。

## 5. 问题优先、版本分层和聚合（R3、R4）

### 5.1 页面

保留现有问题分页和排序。默认查询当前生效版本，在每个问题下展示该版本的影响、原因和整合方案；提供“历史版本”折叠区域，按原部署版本、保存快照和版本未确认分组，再列出问题/建议/证据。只有展开的历史问题加载其建议，查询携带该来源的 snapshotKey。筛选、列表和分页属于同一个列表容器。只有历史记录的问题可通过现有历史开关查看，不占默认当前问题页。

版本与时间窗口独立：页面明确显示沿用的时间范围；展开archive须开启既有includeHistorical的全历史读取，覆盖保留数据，不能因默认30天窗口隐藏旧版本。已选ID的完整读取/提交复核不受默认列表窗口截断；时间筛选不授予跨版本引用权限。

保存测试在“其他运行版本”中显示实际保存快照身份，不把所有 `-1` 合成一个版本；不把测试样本充入正式运行统计。配置完全相同也要保留各运行的版本来源，不能覆盖原来源。

历史建议允许勾选，跨页选择保留。底部明确本次修改目标为当前版本，并显示历史来源数量。归档前已选的建议不自动丢失/增选；active 变更时显示版本变化并重新核对，不在用户不知情时换任务目标。

没有 active 记录时显示“尚无当前部署版本”，仍可查看历史/其他运行版本，不默认改选最大版本或 save；针对当前版本的生成和每日任务明确不可用。多个 active 记录属于身份异常，不能任取一个。版本过滤先于计数、排序和分页，查询缓存/分页令牌包含版本范围与 snapshotKey，部署切换后重新读取。

### 5.2 聚合范围

- 聚合工作单元必须携带稳定 `snapshotKey`，部署按 workflowId/version/deployNumber，保存按 §4 的 Git 身份；不同来源版本不自动组成同一可执行原始方案。
- 同一问题、同一来源快照内：完全重复去重、互补目标归并、真正矛盾保留取舍、不确定保持独立。允许已有服务保留跨问题共同目标及多对多来源关系，但页面仍先按问题组织。
- 新建议/聚合身份必须包含版本作用域，防止“相同配置/相同补丁”的新版本继承旧版本 verified/processing 生命周期。已有 itemId 和冻结任务不批量重算；单一来源可证明的旧条目附加关联并兼容读取，既有任务仍按原冻结输入恢复。旧条目若混入多个来源版本，不任取一个贴标签，保留原任务/证据并标需核对；未经可靠拆分不用于新任务，不建设通用 ID 映射服务。
- 历史整合结果的 fingerprint 只随该来源快照、原始成员内容/证据版本和分类协议变化；不得仅因另一个版本变为 active 就反复作废历史整合结果。active 只影响默认展示和本次任务目标。
- 保留完整 originals、独立来源及证据；列表继续使用 bounded summary、完整分页和按需原文读取。摘要里的 operations 省略不能被渲染成“没有结构化修改”。
- 后台首先整合当前版本的新建议；历史展示复用已有结果与原始建议，按需分页读取。归档、展开历史或版本切换不触发全历史模型重算；用户勾选历史建议后，在本次草稿生成中整合其目标，不另建历史重新分析队列。

### 5.3 归档与后台独立

archive 是按当前 active 动态产生的视图，不删除数据、不改写原建议、不把 pending 自动变 closed/verified。部署生效后切换默认范围，旧版本迟到分析仍落回旧版本。回滚以实际active记录为准：重新激活旧记录则恢复其原范围；若既有发布路径产生新部署记录则使用新key，不能仅凭配置相同合并身份。历史证据不丢失。

聚合只需已存配置引用和身份，不得为了列表/分桶强制读取整个 Git Pack；生成/发布保留其 Git 完整性校验。worker 的 queued、organizing、retryable、blocked/失败原因、完成时间必须与“版本不匹配”分别展示。没有任务记录不能显示已真实入队。

沿用持久队列、lease、预算、429 退避与重试；输入过大/验证失败必须有可定位状态。禁止在 GET 中调用模型、假装排队或用精确 fallback 宣称语义整合完成。

## 6. 手动选择历史建议（R5）

一次任务始终只有一个目标：用户核对并在创建时固定的当前生效版本。勾选历史建议代表“以原目标和证据作为参考，在当前版本重新生成”，不是原补丁的跨版本应用授权。

### 6.1 请求与冻结

- `RepairSelectionRequest` 增加 `targetSnapshotKey` 和 `historicalItemIds?: string[]`。目标 key 来自本次用户核对的服务端响应；历史集合必须等于所选 itemIds 中经服务端核验为非目标版本的集合，不只验证“是子集”。客户端不能自行声明建议版本。
- 用户勾选后由客户端自动携带这些字段，底部展示本次目标和历史来源数量；点击现有生成按钮即可，不增加逐条确认或额外审批。
- 未声明却含不同来源版本，返回 `HISTORICAL_REFERENCE_CONFIRMATION_REQUIRED` 并指出 itemIds；不清空其他有效选择。
- 创建前比对请求目标 key 与实际 active；不相等返回 `TARGET_VERSION_CHANGED`。内容版本、目标 key、历史集合都进入请求幂等摘要；历史选择缺目标 key 不允许降级。旧客户端仅当前项的请求沿用既有严格相容校验，不得因此获得跨版本引用能力。
- 当前版本建议继续执行既有配置相容及生命周期校验。历史参考保留权限、内容版本、来源/快照完整性、大小、目标文件/节点范围校验；生命周期按 §6.3 的“只读来源”规则处理。
- 冻结任务在现有 input 的 item.context 中保存 `sourceSnapshot`、`targetSnapshot`、`referenceOnly`；原 `proposal/baseSpecDigest/operations` 原样保留，不把旧摘要改成当前摘要，不把历史 operations 当自动 apply 列表。冻结目标还保留现有完整 RepairBaseline。
- 复用 `workflow-proposal-plan/v1` 的 baselineSpecDigest、plans、originalItemIds 和 goals，不新增 action 或结果协议。所有来源原始成员仍须各覆盖一次；引用角色由服务端冻结、Host 校验，不能从模型结果反推授权。

### 6.2 消费、校验和结果

历史选择经现有草稿生成完成目标整合，不新增逐条模型重新分析队列。生成器读取当前目标完整内容，同时获得原始目标和历史证据。逐原始成员沿用 `changed/not_needed/unresolved`：已满足或已失去适用对象由 not_needed 的具体原因区分；不能确认适用性则 unresolved，不能伪称已解决。保留既有逐操作/目标覆盖检查；明确冲突不得被悄悄选边。

当前版本与历史参考在相同字段上重叠，不仅凭路径重叠阻止；已知不兼容取值仍需取舍。旧节点已删除或输出契约改变时不得凭名称相似扩大范围。生成新候选后检查真实 diff、字段/文件范围、Pack 语义和逐项覆盖；不确定目标不得写入补丁。

冻结生成计划前，对所有选中目标共同检查：有写入范围重叠的目标放在同一整合单元（连通范围取并集），互不重叠的目标才可分开生成；不能把历史与当前按版本分成两个依次覆盖同一 Prompt 的计划。分组必须可追溯，已知真冲突先交用户取舍，不以标题相似证明兼容。

Host 继续使用 `integrate_candidate_v1`，不得降级为逐项 `generate_candidate`。启用历史生成前必须用实际 producer/parser/writer/checker 做配对 fixture，核对已安装制品；不支持时在派发前返回 `HISTORICAL_REFERENCE_UNSUPPORTED`，不创建“处理中”假任务。核心验收要求历史生成实际可用，不能以“不支持”作为完成 R5 的证据；只有配对测试证明确有契约缺口才另行调整协议。

这只允许生成消费者的必要契约适配，不扩大 TaskGuard 单 case 分析、工具或自动发布职责。已有 AIS 配置/消费者制品的线上变更仍需单独授权，本次文档不执行它们。

### 6.3 历史来源的状态与结果

历史建议是只读来源。pending、processing、verified、ineffective 或 no_action 不因原状态自动禁选；用户显式选为参考也不重开原建议。原任务是否在处理不单独阻止读取/引用，仍须核对来源内容版本；真正针对本次目标的生成/发布互斥沿用现有规则，不以原历史item的activeTaskId替代目标任务检查。

新任务的引用、逐项结果、部署及效果关联保存在已有冻结输入和任务/发布/验证记录，绑定新目标；不得把旧 item 改为 processing、抢占其 activeTaskId，或用本次结果改写旧 item 的 verified/no_action 等状态。当前项沿用既有占用规则。发布确认、changedChainItems、结果回写、失败/取消释放和自动验证都须识别引用角色：校验引用和当前候选范围，但不向原历史项传播生命周期。来源仍保留原版本处理记录，新目标的处理结果可从本次任务追溯，不新建第二套建议生命周期。

只读引用不等于取消防重：复用现有任务记录按workflow/目标key/所选来源内容核对相同在途任务，同requestId重试返回原任务；不能通过修改原历史项状态实现防重。

### 6.4 版本变化

选择时、提交时、生成准备完成后核对同一目标；变化返回 `TARGET_VERSION_CHANGED`，保留原选择并显示旧/新目标，用户重新核对后才能创建新请求。已提交任务按冻结目标核对结果，不重写输入或重复派发；发布仍拒绝不相容的 active 变化。反馈继续该任务固定目标及 parent candidate，不读取后来 save 替换它；自动任务后续批次另受 §7 的 active 复验约束。

## 7. 每日进化任务（R6）

复用现有开关、时区 Asia/Shanghai、每日时间、持久周期和幂等机制，不新增 cron 服务。

- 每轮固定 active snapshot 和 evidence cutoff。问题排序、来源运行、建议、模型方案成员均限制为该 active 版本；`historicalItemIds` 必须为空。
- 请求携带同一 `targetSnapshotKey`，inputDigest/selection fingerprint 只包含该版本及选取所需证据、策略；历史条目状态变化不能无故使当前选择失效。
- 延续既有影响程度、自然日窗口、单批大小、冲突与完整方案选择规则。当前版本没有样本/可用建议时不从历史凑数、不创建空任务，展示对应原因。
- 分析可继续处理历史运行，输入必须为其实际快照；“每日生成只选当前版本”不意味着把所有分析都改成当前版本。
- 选取后到派发前 active 变化，使旧范围失效并按新版本重新选取；已派发请求保留原幂等身份，不自动重复执行。
- 每个后续批次、重试生成和恢复派发都复验目标；新部署后不再向旧目标追加自动批次，已有候选留待查看。结果未知先查询原 requestId，不因换版重建一个可能重复的请求；旧请求查清后才能另建新版本范围。
- 旧版本任务的 review/blocked 状态不能被 workflow 级 activeDraft 当成永久阻挡新版本的理由；自动去重按目标版本。真实生成/发布仍在途、结果未知或既有跨任务互斥存在时，明确延期并显示占用任务与原因，不自动取消旧任务或绕过互斥。无 active/来源未确认分别记原因，不从历史补足。
- 新版本不能因旧版本同名问题已生成/已验证而被永久跳过；同一新版本、同一未变化输入仍去重。

## 8. 配套指标（R7，扩展交付）

复用现有问题 signature、运行/分析/任务/发布/验证记录，数据库查询与投影优先，不增加独立统计事件系统。正式部署运行与保存测试分别统计，未知来源单列。

| 指标 | 明确口径 |
| --- | --- |
| 当前版本问题与影响 | 指定版本/时间窗内去重 flowId；一次运行多条同类诊断只记一次。展示首次/最近发生时间。 |
| 分析覆盖率 | 完成分析的去重运行数 / 范围内符合分析条件的运行数；证据完整运行数另列，不以 completed 冒充完整证据。 |
| 同类问题命中率 | 分母为已有可用分析且实际执行相关节点的运行数，分子只取该集合内命中的运行；全部已证实影响另列，不能混用不同样本集合。分析不全时不能称全量发生率。 |
| 跨版本复现 | 同一稳定问题标识按版本列出受影响运行、样本分母、首次/最近出现和时间窗；同类症状不自动等于同一根因。 |
| 新版本变化 | 有新版本证据才标“首次发现/再次复现”；没有命中但有观察样本标“暂未复现”；无样本、证据不全或相关节点未运行标“观察不足”。 |
| 修复后观察 | 精确关联成功发布的任务/建议/新部署，显示有效样本、复现数量和既有验证结果；归档、生成或部署完成不代表已解决。 |
| 聚合情况 | 指定版本原始建议成员数、展示方案数、保留来源数、worker 状态/原因/更新时间；不以压缩比例单独评价语义质量。 |
| 处理周期 | 首次发现→首次可用方案→生成→实际部署→得到有效观察；未完成阶段分别显示，不拼成已修复耗时。 |

后续优先项：连续复现版本数、达到验证条件后再次复现、无效修复次数、前后版本命中率/耗时/token 比较。必须同屏呈现样本量和覆盖差异；只提供观察比较，不把版本前后差值当成修复因果证明。不新增任意“3次就已修复”业务阈值；已有验证规则的阈值沿用并明确展示，无规则只呈现事实。

同一 flow 多次分析按该快照、统计截止点内最后一次成功完成的兼容分析取一份，排序以 completedAtMs、analysisId 稳定决胜；固定运行窗口和analysisCutoff，截止点推进后才纳入迟到分析。部分证据状态单列，不与旧完整结果静默拼接；该问题/节点不可判定的样本不进命中率分母。旧运行迟到分析更新其原版本统计，不迁移到新版本。

## 9. 模块边界与交付顺序

1. ClawMind：复用已有运行身份；只有remote固定身份缺少转发时补最小上报，不把插件升级作为普通部署运行关联的前提，不调整运行/重试/保存语义。
2. Avernet shared：小型快照契约、两个字段迁移和持久化；不得引入内部公司服务依赖。
3. Clawevolve：单 case 分析关联/输入；版本解析通过公开接口注入，不能反向依赖 Workflow 业务实现。
4. Workflow：问题版本范围、聚合、手选历史、每日范围、指标与 UI。
5. OCB Host：已有 Git/部署身份适配及生成消费者选择；内部启动和凭据继续由 Host 所有。
6. 生成消费者：验证已有 v1 整合与逐项结果，只有确定缺口才做最小适配，不预设新增协议或编排系统。

依次交付快照关联→版本视图与后台聚合→历史参考生成→每日范围与端到端验收。指标有独立扩展计划，不能阻塞前三项正确性，也不能在版本关联未正确时先给出错误统计。
