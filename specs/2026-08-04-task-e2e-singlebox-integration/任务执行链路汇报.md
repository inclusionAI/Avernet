# 任务执行链路设计汇报

> 主题:目标驱动任务的端到端执行链路(以"存储行业尽调"为实例)。
> 日期:2026-08-04。面向:架构/方案汇报。
> 内容:整体设计思路 → 领域模型 → API 设计 → 端到端执行链路(流程图 + 逐步执行)。

---

## 一、整体设计思路

### 1.1 要解决什么

一个由用户交付的"目标型任务"(如"做一份存储行业尽调报告"),系统要能**自动**把它拆成若干子任务、搜推合适的执行 bot/协作群来执行、验收产出、对缺项补做,直到全验收标准达成 —— 全程真实 bot 经消息网异步执行,而非测试桩。

### 1.2 核心模型:图节点 = 实体,动作 = 执行器内部阶段

- **图节点 = 实体**(子任务 / 少量阶段节点),不是动作。搜推 / 执行 / 验收 / 拆解 / 上升 都是子任务执行器**内部的 phase**,不再为每个动作单独建节点 —— 避免图爆炸。
- **NodeType 只有 4 种**:`RECOGNITION`(识别)、`CLARIFY`(澄清)、`DECOMPOSE`(拆解规划)、`SUBTASK`(所有拆出来的子任务,含汇总与终验)。
- **两维度状态**(by `node_id` 同进同退):`Node`(拓扑维度:status)+ `NodeState`(实体维度:status / phase / 产出数据)。
- **终验不特殊**:终验就是一个普通 `SUBTASK`(拆解 skill 决定要不要,通常最后一个),由"终验 bot"自调 goal-verify 验任务级全 AC。执行层不做特殊处理。

### 1.3 驱动架构:reactor 泵 + Scheduler↔Executor 路由 + 异步边界回投续驱

- **唯一驱动 = `on_event` 泵**:reactive(不 poll、不阻塞等待)。每来一个回投事件推进一步(fold 状态 → 按 NodeType 路由 → phase 转移 → 可能再派发/传播)。
- **Scheduler 薄,只认 NodeType**:`on_event` / `drive` 按 node 的 NodeType 查 `ExecutorRegistry` 路由到执行器;phase 逻辑封装在执行器内。
- **执行器认 `(event.kind, phase)`**:`SubtaskExecutor`(SUBTASK)/`DecomposeExecutor`(DECOMPOSE)内部按事件类型 × 当前 phase 细路由到 phase handler。
- **两个异步边界(唯一进出 bot 通道)**:
  - **出去(dispatch,fire-and-forget)**:执行器 → BCN `chat.send` → bot 进程;泵不阻塞等。
  - **回来(回投)**:bot 的 skill 干完(含自调 goal-verify)→ skill 内 HTTP client → `POST /api/tasks/{id}/events` → 重新进 `on_event` 推进下一步。
  - **bot 不"触发"继续,而是回投事件**;bot 是异步喂数据进泵的 worker,驱动权永远在泵。
- **`tick` 降为 watchdog**,只对长期 RUNNING 节点超时探活,不正向推进。

### 1.4 子任务执行回路(统一一套状态机)

```
SUBTASK: pending → searching(搜推)
  → 命中 → executing(派发给执行实体)→ 产出 state.updated(流式)+ 自调 goal-verify 验收
       → node.accepted(PASS,两维度 DONE)/ node.rejected(FAIL,reroute)
  → miss + 深度<MAX → decomposing(派发拆解)→ plan.reported → spawning 子任务(深度+1,递归)
       → 子任务全 DONE → aggregating → done;有子 HUNG → 本节点 HUNG(向上传播)
  → miss + 深度≥MAX → HUNG(不拆不立刻 BBS)
  → (HUNG 后)任务级用户确认升 BBS → escalating(广场悬赏)→ BBS bot 认领 → executing → 自验 → done
```
- **执行 + 验收 = 同一执行实体的两步**(不拆给不同 bot):命中单 bot→该 bot;命中协作群→群 master;动态拉群→拉群 bot;升 BBS→认领的 BBS bot。验收都由该执行实体自调 goal-verify。
- **BBS 是任务级、用户确认才升**:HUNG 挂起等,DAG 其它可执行子任务继续跑;全可执行 DONE 仍有 HUNG → 图 `HUMAN_REQUIRED` → 用户确认 → 整体任务升 BBS → HUNG 叶子广场悬赏 → BBS bot 认领执行+自验 → 解除 HUNG。

### 1.5 数据依赖与上下文流转

- **三套数据语义**:`depend_on`(plan 声明的兄弟依赖,既作执行门控又作数据血缘)、`spawn`(递归拆解的父→子,由 spawning phase 计数门控 + 聚合时 fold 子产出)、**任务级读**(终验读全 `TaskState.subtasks`,非血缘)。
- **上游上下文 fold**:`retrieve_state(node, with_upstream)` = 任务公共上下文 + 自身状态 + 上游依赖产出 fold;投影成 dispatch prompt 发给执行实体。**SSOT = `TaskState.subtasks`**(每节点分区),dispatch prompt 是其瞬时投影。

### 1.6 结果落 State(两维度 fold 契约)

| 回投 | 类型 | 落点 | 状态 | 触发 |
|---|---|---|---|---|
| `state.updated` | 执行结果(流式,多次) | `NodeState` 数据字段(MERGE/APPEND) | **不变**(仍 executing) | **不 drive**(只累积) |
| `node.accepted` | 验收 PASS(终态 1 次) | 验收快照入数据面 | 两维度 → **DONE** | **依赖传播 drive 下游** |
| `node.rejected` | 验收 FAIL(终态 1 次) | `gap_records` APPEND | 两维度 → **FAILED** | **reroute 补缺口** |

> 收口契约:`accepted`/`rejected` 是**唯一**状态终态翻转点 + 唯一下游触发点;`state.updated` 只 fold 数据不翻态、不触发。

## 二、执行层设计:TaskScheduler 与 TaskExecutionGraph

> 执行层两个核心组件:**TaskScheduler**(驱动服务,泵)+ **TaskExecutionGraph**(运行图,SSOT)。Scheduler 不持有业务状态,所有图状态读写经 Graph;二者通过「load → mutate → save + 事件溯源」协作。

### 2.1 TaskExecutionGraph — 运行图(任务运行态唯一权威)

任务运行态的唯一权威载体,随 Task 聚合根持久化:

```python
TaskExecutionGraph:
  status: GraphStatus      # 任务运行态唯一权威:RUNNING/HUMAN_REQUIRED/BBS_ACTIVE/DONE/FAILED/...
  loop_round: int           # reroute 轮次
  nodes: list[Node]         # 拓扑维度(by node_id):node_type/status/run_mode/assignee/node_spec
  edges: list[Edge]         # 依赖:DEPENDENCY(兄弟执行+数据) / CONDITIONAL(reroute) / ...
  state: TaskState          # 状态 SSOT:public(任务级公共上下文) + subtasks{node_id: NodeState}
```

- **两维度 by `node_id`**:`Node`(拓扑维度,status/node_spec/assignee)+ `NodeState`(实体维度,在 `state.subtasks[node_id]`,status/phase/产出)。Scheduler/Executor 的 fold 两维度同进同退。
- **结构 append-only**:`nodes`/`edges` 只经 `add_node`/`add_edge` 增,不改(`Node.node_spec` 一次性写定;reroute 追加新 Node,不改旧 node_spec)。运行态变的是 `NodeState`(phase 前进、产出累积)与 `Node.status`(flip)。
- **图状态机**:`DRAFTING→DEFINED`→`RUNNING`→(全子任务 accepted)`DONE` / (有 HUNG 且全可执行 DONE)`HUMAN_REQUIRED`→(用户确认)`BBS_ACTIVE`→`DONE`/`FAILED`;任一非终态→`CANCELLED`。
- **读写经 `GraphStateOps` 写口**:`add_node`/`add_edge`/`update_state`(fold MERGE/APPEND)/`retrieve_state`(读 + 上游 fold)/`snapshot`;所有变更 fold→save,事件 append 由 `on_event` 统一收口(事件溯源,`GraphCheckpoint.replay` 可还原)。

### 2.2 TaskScheduler — 驱动服务(唯一正向驱动 = `on_event` 泵)

执行层服务,唯一职责 = 驱动 `TaskExecutionGraph` 前进;reactive(不 poll、不阻塞):

```python
TaskScheduler:                         # 唯一正向驱动 = on_event 泵;薄路由 + 依赖传播;无业务状态
  on_event(event):                                                       # 编排半(POST /events 先经 TaskService.on_event fold,再调此)
    task = task_repo.load(event.task_id)                                 # load aggregate(定义层 + execution_graph)
    node = locate(event.node_id or event.parent_node, task)
    if event.kind == STATE_UPDATED: fold_state(task, event); save; return   # 只 fold 数据,不路由不 drive
    ExecutorRegistry[node.node_type].handle(event, node, task)            # 按 NodeType 薄路由;phase 状态机封在 Executor 内
    if node.status in (DONE, FAILED, HUNG):                              # ★仅终态翻转后传播(对齐 Yuque:ACCEPTED→DONE / REJECTED→FAILED / MISS→HUNG)
      propagate(task, node)                                              # 续驱:依赖传播 + 任务级收口
    save(task)                                                           # 落盘 + 事件日志 append(事件溯源)

  drive(task, node_id):                                                  # 节点就绪(plan 报出 / deps met / 重开)→ 入口 phase
    node = task.execution_graph.nodes[node_id]
    ExecutorRegistry[node.node_type].enter(node, task)                   # enter 内部按当前 phase 决定进哪一阶 + 发 dispatch★OUT

  propagate(task, node):                                                 # ★对齐 Yuque propagate;在其基础上补 reopen/递归父聚合/HUNG 上传
    if node.status == DONE:                                              # DONE → 驱 depend_on 下游 + 递归父聚合
      for Y in dependents(node, task):
        if Y.status == FAILED: reopen(Y, PENDING)                       # reroute:重开原失败节点(handle_reject 已加补做新依赖)
        if deps_met(Y, task) and Y.status != DONE: drive(task, Y.node_id)
      parent = spawning_parent(node, task)                               # 递归父(spawn 关系,非 depend_on)
      if parent and parent.phase == "spawning" and all_children_done(parent, task):
        drive(task, parent.node_id)                                      # 父 enter:spawning→aggregating → dispatch 聚合★OUT
    elif node.status == HUNG:                                            # HUNG(MISS+depth≥MAX)→ 向上传播到 spawning 父链
      propagate_hung_up(task, node)                                      # 子 HUNG → 父无法聚合 → 父 HUNG,递归向上
    # 任务级判定(任一终态后都查)
    if all_done(task) and not has_hung(task):         task.status = DONE              # 全子任务 accepted → 图 DONE
    elif has_hung(task) and all_executable_done(task): task.status = HUMAN_REQUIRED  # HUNG 残留 → 等人确认升 BBS

  deps_met(node, task):                                                  # 两套语义:depend_on 全 DONE + (spawning? children 全 DONE : true)
    all(task.execution_graph.state[d].status == DONE for d in node.node_spec.depend_on)

  propagate_hung_up(task, hung_node):                                    # HUNG 沿 spawning 父链上传
    p = spawning_parent(hung_node, task)
    while p and p.status not in (HUNG, FAILED, DONE):
      p.status = HUNG; p = spawning_parent(p, task)

  tick():  # watchdog only —— 超时探活 long-running RUNNING 节点(PROBE/REDRIVE/ESCALATE),非正向驱动
```

- **双 `on_event` 分工**:`POST /events` → ① `TaskService.on_event`(写权威:落态 fold 到 `execution_graph` + 事件日志 append)→ ② `TaskScheduler.on_event`(编排权威:`ExecutorRegistry[NodeType].handle` → 终态后 `propagate` 续驱 + 收口)。两者都无业务状态,每次 `load→mutate→save`。
- **`propagate` 续驱收口(对齐 Yuque,补全三处扩展)**:对齐 Yuque `propagate`(驱 `depend_on` 下游 + 任务级收口 `all_done→DONE` / `has_hung+all_executable_done→HUMAN_REQUIRED`),并补三处 Yuque 未展开的扩展:① `DONE` 时对 `FAILED` 下游 `reopen(FAILED→PENDING)` 再 `drive`(reroute 重开);② `DONE` 时驱 `spawning` 递归父聚合(spawn 关系,非 depend_on);③ `HUNG` 时 `propagate_hung_up` 沿父链上传。门控 = "node 翻终态(DONE/FAILED/HUNG)后",覆盖 Yuque 的 `NODE_ACCEPTED` + `NODE_REJECTED`(reroute)+ `MISS→HUNG`。`STATE_UPDATED` 不翻态、不进 `propagate`;`plan.reported`/`discover.reported` 的新节点由 Executor 在 `handle` 内直接 `drive`,不经 `propagate`。
- **reroute 重开链**:`node.rejected`→`handle_reject` 加补做新依赖 + `propagate` 驱下游时对 `FAILED` 下游 `reopen(FAILED→PENDING)` 再 `drive`;重开节点 `enter` 复用原 assignee 跳过搜推直进 `executing` 重跑 + 重自验(产出新 verdict)。见 §六 Phase F。
- **薄路由**:Scheduler 只认 `NodeType` 查 `ExecutorRegistry` 路由 + `propagate`;phase 状态机封装在 Executor 内,Scheduler 不感知 phase。
- **无业务状态**:每次 `on_event` 从 `TaskRepo` load Graph → mutate → save;Scheduler 自身不缓存图。
- **续驱闭环**:`handle` 翻 phase / flip status / 发 async dispatch(出 BCN ★)→ bot 异步执行 → 回投 `POST /events` → 再进 `on_event` → `handle` 进下一阶;`propagate` 跨节点续驱 + 收口。
- **终态翻转收口**:`node.accepted`/`node.rejected` 是唯一 `status` 终态翻转点(Executor 的 `handle_accept`/`handle_reject`),两维度同进同退;`state.updated` 只 fold 数据不翻态、不 drive。
- **`tick` 降 watchdog**:仅超时探活,不代替 `on_event` 正向推进(对上 §一 1.3)。

#### 2.2.1 ExecutorRegistry + 四执行器(节点内 phase 状态机)

Scheduler 只认 `NodeType` 查表;**节点内 phase 推进 + dispatch 什么请求全在对应 Executor 里**。每个 Executor 只改节点态(翻 phase/flip status/fold 数据)+ 发 `dispatch★OUT`;`save`/事件日志由泵收口;`drive`/`dispatch`/`add_node`/`add_edge`/`retrieve_state`/`reroute`/`deps_met` 是 Scheduler/-domain 提供的上下文 helper;`drive` 幂等(只对 `PENDING` 节点生效)。

```python
class TaskNodeExecutor(Protocol):
    def enter(self, node, task) -> None: ...        # drive 入口:就绪 → 入口 phase + 首个 dispatch★OUT
    def handle(self, event, node, task) -> None: ...  # 回投驱动:(event.kind, phase) → 翻 phase + 下一 dispatch★OUT
    def watchdog(self, node, task, action) -> None: ...  # tick 超时探活

class ExecutorRegistry:
    _registry = {NodeType.RECOGNITION: RecognitionExecutor(),
                 NodeType.CLARIFY:     ClarifyExecutor(),
                 NodeType.DECOMPOSE:   DecomposeExecutor(),
                 NodeType.SUBTASK:     SubtaskExecutor()}
    @classmethod
    def get(cls, nt): return cls._registry[nt]

class RecognitionExecutor:    # create_task 落图即 DONE,无异步
    def enter(self, node, task): node.status, node.phase = DONE, "done"
    def handle(self, event, node, task): pass
    def watchdog(self, node, task, action): pass

class ClarifyExecutor:        # clarify(confirmed) 落图即 DONE,无异步
    def enter(self, node, task): node.status, node.phase = DONE, "done"
    def handle(self, event, node, task): pass
    def watchdog(self, node, task, action): pass

class DecomposeExecutor:      # n_root / reroute_dec:pending→decomposing→(PLAN_REPORTED)→子物化+DONE
    def enter(self, node, task):
        node.phase = "decomposing"; dispatch(DECOMPOSE, BotTarget(owner), {spec, state})   # ★OUT
    def handle(self, event, node, task):
        if event.kind != PLAN_REPORTED: return
        children = event.subtasks
        if not children:                                    # ★空分解护栏:不翻 DONE,FAIL/reroute
            node.status, node.phase = FAILED, "failed"; reroute(task, node, "空分解"); return
        for c in children:
            child = add_node(task, NodeSpec(c.metadata.id, c), SUBTASK); add_edge(task, node.node_id, child.node_id, DEPENDENCY)
        node.status, node.phase = DONE, "decomposed"        # 脚手架 DONE(子已原子入图)
        for c in children:
            if deps_met(child_of(c), task): drive(task, c.metadata.id)
    def watchdog(self, node, task, action):
        if action == REDRIVE: dispatch(DECOMPOSE, BotTarget(owner), {spec})  # ★OUT 重派

class SubtaskExecutor:        # 所有拆出子任务(含汇总/终验/递归 children)
    def enter(self, node, task):
        if node.phase == "pending":                         # 就绪 → 搜推(或重开复用 assignee 直派执行)
            if node.assignee:                               # reroute 重开:跳过搜推直派
                node.phase = "executing"; dispatch(EXECUTE, node.assignee, {state, upstream})   # ★OUT
            else:
                node.phase = "searching"; dispatch(SEARCH, BotTarget(owner), {spec, state})     # ★OUT
        elif node.phase == "spawning":                      # 子全 DONE 后被 propagate 重驱 → 聚合
            node.phase = "aggregating"; dispatch(AGGREGATE, agg_bot, {state, children_fold})    # ★OUT
    def handle(self, event, node, task):
        match (event.kind, node.phase):
          (DISCOVER_REPORTED, "searching"):
            rec = event.recommendation
            if rec.outcome == HIT:
                node.assignee, node.run_mode = resolve_route(rec); node.phase = "executing"
                dispatch(EXECUTE, resolve_target(rec), {state, upstream})        # ★OUT
            elif rec.outcome == MISS and node.state.depth < MAX:
                node.phase = "decomposing"; dispatch(DECOMPOSE, BotTarget(owner), {spec})  # ★OUT 递归拆
            else: node.status, node.phase = HUNG, "hung"    # MISS+depth≥MAX,不发 dispatch,等人工
          (PLAN_REPORTED, "decomposing"):                   # 递归拆解回投
            children = event.subtasks
            if not children: node.status, node.phase = FAILED, "failed"; reroute(task, node, "空分解"); return
            for c in children:
                child = add_node(task, NodeSpec(c.metadata.id, c), SUBTASK, depth=node.state.depth+1)
                add_edge(task, node.node_id, child.node_id, DEPENDENCY)
            node.phase = "spawning"                         # 递归父保持 RUNNING,等子全 DONE(propagate 检测)
            for c in children:
                if deps_met(child_of(c), task): drive(task, c.metadata.id)
          (STATE_UPDATED, "executing"|"aggregating"):       # 中间结果流式 → 只 fold
            merge(node.state.execution_result, event.patch) # MERGE;phase 不变,不发 dispatch
          (NODE_ACCEPTED, "executing"|"aggregating"|"escalating"):   # 自验 PASS → 终态
            node.status, node.phase = DONE, "done"; node.state.acceptance_result = event.acceptance_result
          (NODE_REJECTED, "executing"|"aggregating"|"escalating"):   # 自验 FAIL
            node.status, node.phase = FAILED, "failed"; node.state.gap_records.append(event.gaps)
            reroute(task, node, gaps=event.gaps)            # add reroute_dec + dispatch 补拆 ★OUT
          (BBS_CLAIMED, "hung"):                            # transition{confirm_bbs} 后 BBS bot 认领
            node.phase = "escalating"; node.assignee = event.bbs_bot_id
            dispatch(EXECUTE, BotTarget(event.bbs_bot_id), {state, gaps})  # ★OUT BBS 接力
    def watchdog(self, node, task, action):
        match action:
          PROBE:    dispatch(PROBE, node.assignee, {node_id})                       # ★OUT 探活
          REDRIVE:  dispatch(EXECUTE, node.assignee, {state, upstream})            # ★OUT 同执行方重派
          ESCALATE: node.status, node.phase = HUNG, "hung"                         # 超时无响应 → 挂起
```

**Executor 要点**:
- `Recognition`/`Clarify` 退化:落图即 DONE,无异步回投(历史脚手架,不参与 on_event 续驱)。
- `Decompose` vs `Subtask` 的 `(PLAN_REPORTED, decomposing)` 同名收尾不同:DECOMPOSE 翻 `decomposed(DONE)`(脚手架完工,子接力);SUBTASK 翻 `spawning`(递归父保持 RUNNING,等子全 DONE 再 `aggregating→done`,由 `propagate` 重驱)。
- **空分解护栏**:两个 `PLAN_REPORTED` 处都守,0 子任务 → `FAILED`+`reroute`,绝不翻 DONE,堵掉"假 DONE"。
- **BBS 接力**(`BBS_CLAIMED`)与正常执行同口同逻辑:`escalating`+`assignee=bbs_bot` 走 `EXECUTE` dispatch,回投 `accepted/rejected` 走同一终态分支,无 BBS 特殊路径。
- **重开复用 assignee**:`enter` 见已有 `assignee`(reroute 重开)跳过 `searching` 直进 `executing` 重派原执行方——"重新判断状态"= 原执行方再跑一遍 + 重自验出新 verdict。

#### 2.2.2 "还会动态生子节点"被误判完成的护栏

`all_done = nodes 全 DONE` 能正确区分"真完成"与"还在生/未跑完",靠四条不变量:① 动态加进来的子/孙节点全在 `nodes`,被 `all_done` 检查;② 会生子的节点生完前是 `decomposing`/`spawning`(RUNNING,非 DONE)→ `all_done=False`;③ `add_node + flip 父态 DONE` 在同一 `handle` 里原子 `save`,无"DONE 但子未入图"窗口;④ reroute 重开把 DONE/FAILED 翻回 PENDING,`all_done` 立即失效。**空分解是唯一能制造"假 DONE"的口子**,由上面空分解护栏补上。崩溃窗口由事件溯源 `replay` 兜底。

### 2.3 二者交互(load → mutate → save,事件溯源)

```
HTTP POST /api/tasks/{id}/events {kind, payload}
  → TaskService.on_event → TaskScheduler.on_event
     → load TaskExecutionGraph(从 TaskRepo)
     → fold State(写口 update_state)+ 按 NodeType 路由 executor.handle
       → executor:翻 NodeState.phase / flip 两维度 status / dispatch(出 BCN ★async)
     → 若 node 翻终态:propagate(DONE→drive depend_on 下游+reopen FAILED+递归父聚合 / HUNG→propagate_hung_up)+ 任务级收口(all_done→DONE / has_hung→HUMAN_REQUIRED)
     → save Graph(事件 append 进日志,可 replay)
  → 返回 {accepted, seq}
```
> 图变更进事件流,`GraphCheckpoint.replay` 重放事件 = 还原图快照;`GET /tasks/{id}/history` 拿到权威 seq 轨迹(集成用例断言依据)。生命周期/迁移写口(`run_task`/`create`/`clarify`/`transition`)在 service 层 in-process 构造对应事件(`task.created`/`task.clarified`/`task.started`/`bbs.confirmed`/`task.cancelled`)经同一个 `on_event` fold,不经 bot 回投。

## 三、领域模型

> 两视图聚合根:`Task.spec`(需求/验收面)+ `Task.execution_graph`(运行图面)。运行图三要素:Node(拓扑)+ Edge(依赖)+ TaskState(状态 SSOT)。

### 2.1 聚合根 + 两面

```python
Task:                       # 聚合根
  id, user_id
  spec: TaskSpec            # 需求/验收面(intake)
  execution_graph: TaskExecutionGraph   # 运行图面(runtime)
  owner_bot_id              # 任务绑定 owner-bot
  execution{run_mode?, owner_bot?}      # 可选预执行 hint,调度可覆盖(子任务 run_mode 运行期搜推定);clarify patch 可改
  @status                   # @property → execution_graph.status(任务运行态唯一权威在图)

TaskSpec:                   # intake face(渐进,仅 metadata 必填于 DRAFTING);根 Task.spec + 子任务 Node.node_spec 同型(SubTaskSpec 已合并于此)
  metadata{id, title}                  # 子任务 metadata.id = node_id
  context{background, constraints[]}
  goal{objective, acceptances[AcceptanceCriteria]}
  depend_on: list[str] = []            # root=[];subtask=兄弟依赖(plan 期声明;edges 为 SSOT,此为便捷镜像)
```

### 2.2 节点拓扑 + 计划面内嵌

```python
Node:                       # 拓扑维度(by node_id)
  node_id
  node_spec: TaskSpec        # ★计划面内嵌(子任务);阶段节点(RECOGNITION/CLARIFY/DECOMPOSE)为空
  status: NodeStatus         # pending/running/done/failed/hung
  node_type: NodeType        # 4 种之一,执行器 discriminator
  run_mode?, assignee?       # 搜推命中后填:single_bot/coop_group/bbs + bot_id/group_id
  properties{retry_count, max_attempts, loop_round, reroute?}

NodeType(4):
  RECOGNITION  # create 时落,owner recognition-skill
  CLARIFY      # clarify(confirmed) 时落,owner clarify-skill
  DECOMPOSE    # 规划节点(根 n_root / reroute_dec),owner plan-skill
  SUBTASK      # 所有拆出子任务(含汇总 3_1、终验 3_2、递归 children)→ 搜推→执行实体执行+自验

# SubTaskSpec 已合并进 TaskSpec:need/goal/acceptances/depend_on 都在 TaskSpec;depth 留 NodeState;dispatch 文本从 goal.objective 派生(不存字段)
```

### 2.3 运行态(状态 SSOT)

```python
NodeState:                  # 实体维度,在 TaskState.subtasks[node_id](对齐 Yuque)
  status: NodeStatus
  phase: str                 # ★searching/executing/verifying/decomposing/spawning/aggregating/escalating/done/hung
  depth: int                 # 递归深度(根=0,children=父+1);判 miss+depth≥MAX→HUNG
  execution_result: dict             # MERGE(流式执行结果 + 产出 fold;state.updated 增量合并于此)
  acceptance_result: Optional[AcceptanceResult]   # 终态验收结论(PASS/FAIL + gaps)
  gap_records: list[GapRecord]       # APPEND(验收 gap 历史;reroute 补拆依据)

TaskState:                  # 图级 SSOT(一等要素)
  public: dict                                # 任务级公共上下文(MERGE):spec 摘要/全局约束/递归上限
  subtasks: dict[node_id, NodeState]          # per-subtask 实体分区

TaskExecutionGraph:
  status: GraphStatus, loop_round, nodes[], edges[], state: TaskState
```

### 2.4 图运行态状态机(GraphStatus)

```
DRAFTING → DEFINED(clarify confirmed)→ RUNNING(start)
RUNNING  → HUMAN_REQUIRED(有 HUNG 且全可执行 DONE)→ BBS_ACTIVE(用户确认升 BBS)→ DONE/FAILED
RUNNING  → DONE(全子任务 accepted)/ FAILED
任一非终态 → CANCELLED
```

### 2.5 依赖与枚举

- **Edge**:`from_node → to_node`,`kind = DEPENDENCY`(兄弟执行/数据依赖)/ `CONDITIONAL`(reroute)/ `FALLBACK`...
- **RunMode**:`SINGLE_BOT` / `COOP_GROUP` / `BBS`。`RouteRecommendation.run_mode` 只产 `SINGLE_BOT`/`COOP_GROUP`(HIT)或 `None`(MISS);`BBS` **非搜推产物**,由 `transition(CONFIRM_BBS)` → `escalating` 期置(节点 `run_mode=BBS`+`assignee=bbs_bot`)。
- **AcceptanceCriteria**:`kind`(output / threshold / invariant / behavior / custom)+ `properties`(多态,无子类爆炸)

### 2.6 搜推结果与执行目标 DTO

```python
class SearchOutcome(StrEnum):
    HIT = "hit"       # 命中 → 落 assignee/run_mode,phase: searching→executing
    MISS = "miss"     # 未命中 → Scheduler 按 depth:<MAX→decomposing / ≥MAX→HUNG

@dataclass
class BotCandidate:
    bot_id: str
    fit_score: float = 0.0
    reason: str = ""

@dataclass
class KnownGroupRef:               # 搜推匹配到已知协作群:引用现有 group,直发不建群
    group_id: str
    members: list[str] = []

@dataclass
class DynamicGroupSpec:            # 无现成群:BCS POST /groups 动态建
    driver: str
    members: list[str]
    collab_mode: CollabMode

@dataclass
class RouteRecommendation:         # apply_search_result 的 recommendation 入参
    outcome: SearchOutcome
    run_mode: Optional[RunMode]                                    # SINGLE_BOT / COOP_GROUP;MISS=None
    candidates: list[BotCandidate]                                # SINGLE_BOT 填;余空
    group_ref: Optional[KnownGroupRef | DynamicGroupSpec]         # COOP_GROUP 必填其一;余 None
    confidence: float = 0.0
    rationale: str = ""

@dataclass
class BotTarget:     bot_id: str
@dataclass
class GroupTarget:   group_id: Optional[str]; spec: Optional[DynamicGroupSpec]   # 已知群 group_id / 动态建群 spec
@dataclass
class OwnerTarget:   bot_id: str                                                 # reroute 拆解
DispatchTarget = BotTarget | GroupTarget | OwnerTarget

@dataclass
class NodeView:                    # 节点视图(平铺);detail 字段仅 scoped 查询时填,全图查询 None(对齐 Yuque)
    node_id: str
    node_type: NodeType
    node_spec: Optional[TaskSpec]    # SUBTASK 有;阶段节点(RECOGNITION/CLARIFY/DECOMPOSE)None
    status: NodeStatus
    phase: str
    run_mode: Optional[RunMode]
    assignee: Optional[str]          # bot_id 或 group_id
    depth: int
    execution_result: Optional[dict] = None            # detail:流式产出 fold
    acceptance_result: Optional[AcceptanceResult] = None  # detail:终态验收结论
    upstream: Optional[dict[str, dict]] = None         # detail:{upstream_node_id: execution_result} 上游 fold

@dataclass
class NodeOpResult:                 # 节点级写口(add_subtasks / apply_search_result / update_subtask)出参(对齐 Yuque)
    seq: int
    nodes: list[NodeView]              # search/update=[该节点];add=新增 children
    dispatch: Optional[DispatchTarget] = None   # apply_search_result 触发 dispatch 时;HUNG 时 None
```

## 四、API 设计

> bot 不直连写任务状态;bot 产出经 skill 内 HTTP client 调 task API 回投,由 `on_event` 泵翻态。`POST /events` 是执行链路的主入口。

### 3.1 HTTP 端点

| 方法(typed) | 路径 | 发起方 | body / 关键入参 | 响应 | 作用 |
|---|---|---|---|---|---|
| `run_task` | **POST** **`/api/tasks/run`** | **测试 / 调用方** | `RunTaskRequest{spec: TaskSpec, meta: ExecutionMeta}` | `TaskOpResult{task_id, status, seq, spec}` | **★统一执行入口**:`create_task+clarify_task(confirmed)+execute_task` 编排;`meta.execution_mode` 决定图怎么长(`AUTO_PLAN` 默认=现有 / `MANUAL_PLAN` 预拆 / `DIRECT` 直派) |
| `create_task` | POST `/api/tasks` | owner recognition-skill | `CreateTaskRequest`(TaskSpec:metadata/context/goal/acceptances) | `TaskOpResult{task_id, status:"drafting", seq, spec}` | 建任务 + 落 n_recognition DONE(skill 驱动链路用;`run_task` 内部亦调) |
| `clarify_task` | POST `/api/tasks/{id}/clarify` | owner clarify-skill | `{patch:TaskSpecPatch, confirmed:bool}` | `TaskOpResult{status, seq, spec}` | 补/锁 spec;`confirmed:true` → DEFINED + n_clarify DONE(`run_task` 内部亦调) |
| `execute_task` | POST `/api/tasks/{id}/transition`(action=start) | owner task-execute skill | `{action:"start"}` | `TaskOpResult{status:"running", seq}` | Step 3 确认执行:DEFINED→RUNNING + seed `n_root`(DECOMPOSE)+ dispatch 拆解★(≡ `transition(START)`;`run_task` 内部亦调) |
| **POST** | **`/api/tasks/{id}/events`** | **任意 bot skill** | `EventReportRequest{kind, payload}` | `{accepted, seq, note}` | **★on_event 泵入口**(bot 回投;执行链路主驱动) |
| `transition` | POST `/api/tasks/{id}/transition` | 用户·测试(confirm_bbs,cancel) | `{action: confirm_bbs\|cancel}` | `TaskOpResult{status, seq}` | 任务级状态迁移用例:guard + 副作用 + event(per action,见下表) |
| `query_task` | GET `/api/tasks/{id}` | owner / 测试 / BBS relay | `?node_id=&filter=`(可选 scope) | `TaskView{task_id, status, loop_round, owner_bot_id?, spec, public_context, nodes, edges}` | 读权威状态(投影 DTO,隐藏图细节;lean 全图 / rich scoped;断言用) |
| `get_history` | GET `/api/tasks/{id}/history?after_seq=N` | 测试 | — | `events[]`(seq 单调) | 权威执行轨迹(断言依据) |
| (watchdog) | POST `/api/tasks/{id}/tick` | 系统 watchdog | (无) | `{action:"ticked", progressed}` | 超时探活(非主驱动,可选) |

`transition` 的 action 明细(每个 = guard + 副作用 + event,非裸 status 翻转):

| action | guard | 副作用 | event |
|---|---|---|---|
| `start` | `DEFINED` | →`RUNNING` + `add_node(n_root, DECOMPOSE)` + dispatch 拆解★ | `task.started` |
| `confirm_bbs` | `HUMAN_REQUIRED` | →`BBS_ACTIVE` + 对每个 HUNG 叶子 `escalate_to_bbs`(悬赏 BBS 广场★)+ `phase→escalating` | `bbs.confirmed` |
| `cancel` | 任一非终态 | →`CANCELLED` + 中止在途 dispatch | `task.cancelled` |

> `start` 即 `execute_task`(Yuque Step 3),typed 方法名 `execute_task`、wire 层 `transition(START)` 同物异名。`clarify_task` 不并入 transition(带 spec patch 数据,非纯迁移);`create_task` / `events` / `tick` / 读口各保持独立。`transition`(任务级状态迁移)与 `update_subtask`(节点级 Node+State)分工:任务级走 `transition`,节点级走 `update_subtask`。

**`run_task` 入参 `ExecutionMeta` 与内部编排**(两层对齐:`spec` 是定义层输入,`meta` 是执行层 steering):

```python
@dataclass
class ExecutionMeta:
    execution_mode:      ExecutionMode = ExecutionMode.AUTO_PLAN   # 默认 = 现有模式
    user_id:             str = ""                                   # 发起人(事件 actor)
    owner_bot_id:        Optional[str] = None                       # owner-bot(缺省系统指派)
    sub_dag:             Optional[TaskDagDef] = None                # MANUAL_PLAN 必填:预拆子 DAG
    routing_hints:       Optional[RoutingHints] = None              # 搜推提示(偏好单 bot / 禁协作群 / 指定引擎)
    retry_policy:        Optional[RetryPolicy] = None               # 重试/探活策略覆盖
    max_recursion_depth: Optional[int] = None                       # 递归分解深度上限覆盖
    timeout:             Optional[timedelta] = None                 # 任务级超时

class ExecutionMode(StrEnum):
    AUTO_PLAN    = "auto_plan"      # 默认=现有:scheduler 自驱 DECOMPOSE→搜推→执行
    MANUAL_PLAN  = "manual_plan"    # 指定 sub_dag:跳过 decompose,直接物化预拆子任务
    DIRECT       = "direct"         # 不拆:整 spec 当单个 SUBTASK 直接派单
```

| 模式 | `meta.sub_dag` | `run_task` 内部串接 | 起跑后图状态 |
|---|---|---|---|
| `AUTO_PLAN`(默认) | `None`(忽略) | `create_task(spec)` → `clarify_task(confirmed=True)` → `execute_task`(=Scheduler.start:DEFINED→RUNNING + seed `n_root`(DECOMPOSE) + dispatch 拆解★) | `n_recognition DONE / n_clarify DONE / n_root:decomposing` |
| `MANUAL_PLAN` | 必填(`TaskDagDef`) | `create_task` → `clarify_task(confirmed)` → `add_subtasks(parent=n_root, sub_dag=meta.sub_dag)`(bypass decompose)→ propagate 驱就绪子节点搜推★ | `n_root DONE / <预拆子任务:searching>` |
| `DIRECT` | `None`(忽略) | `create_task` → `clarify_task(confirmed)` → seed 单个 `SUBTASK` 节点(spec,depth=0)直接进 `searching` | `<单 SUBTASK:searching>` |

> `ExecutionMeta` 落库为任务级执行配置(planner / 搜推 / reroute / watchdog 随时读),不只起跑用一次。`AUTO_PLAN` = 现有模式;`MANUAL_PLAN`/`DIRECT` 入口已预留,流程先用 `AUTO_PLAN` 拉通。

### 3.2 事件协议与三层 API

**三层 API(typed skill 方法 / wire 传输 / 内部泵——别混在一层看):**

```
① skill 调 typed 方法(skill-facing)        ← §3.1 端点表 + §3.5 apply_search_result 这类
     apply_search_result / add_subtasks / update_subtask / transition …
              │  (SDK 内序列化)
              ▼
② wire 传输(HTTP,单一口)                   ← POST /api/tasks/{id}/events {kind, payload}
              │  (router 收)
              ▼
③ 内部泵(backend in-process,非 skill-facing)← TaskService.on_event(fold+事件日志)→ TaskScheduler.on_event(handle+终态后 propagate)
```

`on_event` 和 `POST /events` 不在 skill typed API 表里:二者是 ②③ 层。skill 只触 ①;① 经 ② 触发 ③。typed 方法 ↔ event kind ↔ on_event 内部动作 一一映射(下表)。`POST /events` 作为 wire 口保留(测试/低级回投可用),typed 方法为正式 skill API。

**事件目录(EventKind):**

| ① skill typed 方法 | ② kind | 谁投/触发 | payload 关键 | ③ 泵处理(on_event → handle/propagate) |
|---|---|---|---|---|
| `run_task`(execute 步) | `task.started` | run_task 内部 | `{}`(task_id 在 path) | graph→RUNNING;seed `n_root`(DECOMPOSE);`drive(n_root)`→dispatch 拆解★ |
| `run_task`(create 步) | `task.created` | run_task 内部 | `{title, user_id}` | graph=DRAFTING;seed `n_recognition(DONE)` |
| `run_task`(clarify 步) | `task.clarified` | run_task 内部 | `{patch, confirmed:true}` | apply patch 到 `Task.spec`;graph→DEFINED;seed `n_clarify(DONE)` |
| `add_subtasks` | `plan.reported` | owner plan-skill | `{parent_node, subtasks:list[TaskSpec]}`(TaskSpec 含 metadata{id=node_id}/goal/depend_on) | `DecomposeExecutor`(parent=DECOMPOSE)或 `SubtaskExecutor`(parent=SUBTASK,decomposing)→ handle:物化子+边+flip DONE/spawning+drive 就绪子 |
| `apply_search_result` | `discover.reported` | owner discover-skill | `{node_id, recommendation:RouteRecommendation}` | `SubtaskExecutor.handle(searching)`:**HIT**→executing+dispatch 执行★ / **MISS+d<MAX**→decomposing+dispatch 拆解★ / **MISS+d≥MAX**→HUNG |
| `update_subtask`(中间结果) | `state.updated` | 执行实体 | `{node_id, semantics:merge\|append, patch:dict}` | fold `execution_result`(MERGE/APPEND);**不翻态、不 drive** |
| `update_subtask`(自验 PASS) | `node.accepted` | 执行实体 | `{node_id, verifier, acceptances_met:list[str]}` | flip DONE + 落 `acceptance_result`;`propagate`:drive depend_on 下游 + 递归父聚合 + 任务级收口 |
| `update_subtask`(自验 FAIL) | `node.rejected` | 执行实体 | `{node_id, verifier, gaps:list[GapRecord]}`(`GapRecord{unmet_criteria,reason?}`) | flip FAILED + `gap_records` APPEND;`propagate`:reroute(add reroute_dec + dispatch 补拆★)+ reopen FAILED 下游 |
| `transition(CONFIRM_BBS)` | `bbs.confirmed` | 用户·测试 | `{by:actor}` | graph `HUMAN_REQUIRED→BBS_ACTIVE`;对每个 HUNG 叶子 dispatch escalate★(BBS 广场) |
| (BBS bot 认领) | `bbs.claimed` | BBS bot | `{node_id, bbs_bot_id}` | `SubtaskExecutor.handle(hung)`:phase=escalating + assignee=bbs_bot + dispatch EXECUTE★ |
| `transition(CANCEL)` | `task.cancelled` | 用户·测试 | `{by, reason}` | graph→CANCELLED;中止在途 dispatch |

> 生命周期三事件(`task.created/clarified/started`)是 `run_task` 内部 in-process 构造、同步 fold(非 bot 回投);节点级事件(`plan/discover/state/accepted/rejected/bbs.claimed`)由 bot 异步 `POST /events` 回投;`bbs.confirmed`/`task.cancelled` 由 `transition` 端点构造。所有事件统一落 `TaskEvent{task_id,seq,kind,payload,actor}` 进事件日志(事件溯源)。

### 3.3 统一派发(dispatch,系统出 bot 边界)

```
dispatch(route, target, prompt, *, group=None)   # 三分支靠 route 区分
  single_bot  → target=bot_id,            prompt="执行/搜推"  → BCN chat.send
  group       → target=已有 group_id 或 None+GroupSpec(动态建群) → BCS POST /groups + 群 chat.send
  unmatched   → target=owner_bot_id,      prompt="拆解/补拆"  → BCN chat.send
```
- 出经 `ExecutionPort` → BCN `chat.send`,**fire-and-forget**(泵不阻塞);消息含 `{task_id, parent_node, prompt}`,parent_node = 目标节点 node_id(全程不变,执行实体回投时原样回带)。

### 3.4 bot / skill 装机

- **owner-bot**:`task-recognition` / `task-clarify` / `task-plan`(3 个规划 skill)+ 搜推能力(内置 discover);内建 HTTP client 调 task API。
- **执行实体**(各执行 bot / 协作群 master / 汇总 bot / 终验 bot / BBS bot):`task-exec-skill` + `goal-verify`;执行产出后自验,回投 `state.updated` + `node.accepted`/`node.rejected`。

### 3.5 `apply_search_result` — 搜推结果写口(discover-skill 回投)

```python
def apply_search_result(
    task_id, node_id, recommendation: RouteRecommendation
) -> NodeOpResult                # {seq, nodes:[NodeView], dispatch?};类型定义见 §三 2.6
```

bot 经 `POST /events {kind:discover.reported, payload:{node_id, recommendation}}` 回投,泵内部调 `apply_search_result`(BBS 接力 / 测试亦可直调;调用方身份由 auth 写进 event `actor`,不传 `source`)。handler 按 recommendation 落点:

| recommendation 况 | 落 Node+State | dispatch(出参) |
|---|---|---|
| HIT / SINGLE_BOT | assignee=candidates[0].bot_id, run_mode, phase→executing | `BotTarget` |
| HIT / COOP_GROUP / `KnownGroupRef` | assignee=group_id, run_mode, phase→executing | `GroupTarget(group_id)` 直发 |
| HIT / COOP_GROUP / `DynamicGroupSpec` | run_mode, phase→executing(assignee 待建群回填) | `GroupTarget(spec)` → BCS 建群 |
| MISS / depth<MAX | phase→decomposing | `OwnerTarget` reroute 拆解 |
| MISS / depth≥MAX | status=HUNG, phase→hung;HUNG 上传 → 可触发任务级 HUMAN_REQUIRED | None |

> 已知群 vs 动态建群由 `group_ref` 区分(`KnownGroupRef{group_id}` 复用 / `DynamicGroupSpec` 新建),均经 `GroupTarget`;SINGLE_BOT 走 `BotTarget`;MISS 走 `OwnerTarget` 或挂起。

## 附:一句话总结

**泵 `on_event` 是唯一驱动;`run_task`(内部的 `execute_task` = Scheduler.start)是唯一起跑触发,之后每个 bot skill 干完用 `POST /api/tasks/{id}/events` 把结果投回来,这个 POST 重新进 `on_event` → `Executor.handle` 翻 phase + 发下一个 dispatch★OUT + `propagate` 跨节点续驱/收口;如此 `dispatch →[async bot]→ POST events → on_event → handle/propagate → dispatch →…` 一路反应,直到终验 `node.accepted` 触发 `all_done` 全图 DONE。中间没有阻塞等待,只有"等下一个 `POST /events`";HUNG 走人工门控 `transition`,reroute 靠 `reopen+propagate` 重开链闭合。**
