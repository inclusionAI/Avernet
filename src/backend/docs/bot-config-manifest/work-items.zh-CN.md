## 2. 已定决策

以下都是 #1031 合入之后拍板的，不再开放讨论。记在这里是因为设计文档早于它们。

### 2.1 manifest 是上层

配置清单文档位于既有的分类 API、服务和表**之上**。apply 是**向下**物化：通过
TC Open API 已经在用的那些 core service，写出真实的平台实体。这就是设计 §2.3
的「路线 B」，只是把它表述成一条归属规则而不是实现备注。

```text
         config-manifest 文档               ← 用户书写的事实来源
                    │
                    │  apply（向下物化）
                    ▼
   skills · identity · resources · mcp · engine_config · script
                    │                        ← 既有实体，既有服务
                    │  下发
                    ▼
        BotConfigArtifact (teclaw)  ·  push / NAS (ARCA 系)
```

这条规则唯一没法照字面执行的地方是**容器还不存在时的下发**，因为既有服务要求
一个活着的 device。这就是 **D4**。

### 2.2 `script` 不是特例

启动脚本像其他类目一样住在配置清单文档里，apply 通过
`BotStartupScriptService` 把它物化进既有的 `ac_bot_startup_script`。带来的后果
都是有意为之：

- `BaasService._get_start_cmd` 永远不知道 manifest 的存在，所以 #935「无脚本时
  启动命令逐字节不变」这个不变量是**由构造保证**的，而不是靠测试守着（设计
  §10.4 的测试照样要写）。
- 既有的 `GET/PUT/DELETE /openapi/v1/bots/{bot_id}/startup-script` 端点继续工作、
  原样不变，因为它们的表仍然是物化目标——**而且它们不感知 manifest 的存在。**
  这份计划的早期版本曾把老端点做成 manifest `script` 的别名视图（write-through）；
  W8 评审（inclusionAI/Avernet#1836）撤回了它：manifest 是上层，启动脚本是它物化
  进去的实体之一，不是它的视图。后果说清楚，免得被当成 bug：在 manifest 声明了
  `script` 的 bot 上，走老端点 `PUT` 写的是那一行，下一次 apply 会把声明的正文写
  回去——manifest 是它所声明内容的真相源，要改就改 manifest。
- 以后要不要把 `ac_bot_startup_script` 并进 manifest 模块，是个可逆决策，推迟。
  这解掉了设计 §8 的开放选项。
- apply 对这个类目**唯一**做的事就是那一次 DB 写入；平台自己会把脚本拼进启动
  命令。这个机制确认了什么、又给第一期强加了什么顺序限制，见 §2.12。

### 2.3 manifest 物化出来的实体与手工创建的无法区分

因为 manifest 在既有服务之上一层，它创建的实体与手工创建的**完全一样**存储：
同一个服务、同一张表、同一个形状。下游没有任何组件——reconcile、compose、界面、
引擎——能把它们区分开，而且下游也不需要区分。

因此 manifest **不**在实体上盖标记。它保留自己的一份「上次 apply 物化了什么」
的记录，现在只服务**一个**用途：**`keep_last` 与审计**（§2.8）——它们本来就
需要上次成功物化的内容。

这条记录原本还有第二个用途——「摘标记」，即某个类目清空时得知道该停止管理什么。
§3.2 改成类目覆盖之后这个用途消失了：`skills: []` 本身就是「集合为空」的声明，
清空该区域不需要知道之前声明过什么。

这比设计 §3.2 说的「界面/API 上可见的 `managed by manifest` 标记」刻意小得多。
那个标记是 **v2 的产品锦上添花**，不是机制：v1 里没有任何组件需要问「这个实体
是不是 manifest 管的」。用户真正关心的问题——*我当前的配置是什么、上次 apply
做了什么*——由 `GET .../config-manifest` 和 `GET .../last-apply` 回答，不需要
逐实体标志位。

### 2.4 `skills` 与 `identity` 领跑取源类目

它们是驱动业务的场景（「拉取内容 → 装上去」）。`resources` 跟着 W6 与目录相关
的工作一起做，不搭 W5 的便车。

### 2.5 能力是个二值问题——范围只覆盖新 bot

**这个特性面向新 bot。**生产环境里，新建 bot 只会解析到两个 device provider：
`baas` 和 `teclaw`。`arca`、`daas`、`local` 对本特性上线后创建的 bot 不可达。

这把能力模型压缩成 bot 记录自己就能回答的问题，不需要实时查询，也不需要第三种
「查不到」状态：

- `is_teclaw(active_engine)`——引擎判定的权威入口，也正是
  `provider_resolver.resolve_device_provider` 自己所依据的（`teclaw`，否则落 `baas` 默认）；
- `bot_type == "desktop"`——另一个维度，且是 bot 记录上的字段。**desktop 不在本
  特性范围内**，所以这个判断只用来拒绝它。

**与 `engine-requirements.zh-CN.md` §2 的分歧：**那份矩阵说 ARCA-direct 和
LOCAL/singlebox 在写入时拒绝。在「只覆盖新 bot」的范围下，压根不存在这类 bot
需要拒绝，所以 v1 保留 #935 的判定面（`script` 拒绝 teclaw 与 desktop），矩阵里
那两行属于范围之外而不是新增强制。singlebox 仍然只是研发/测试关注点：`script`
在那里报告 supported 但不会被派发——这是 #935 的既有行为，不是本特性引入的。

### 2.6 manifest `PUT` 立即生效，且不需要重启

**与设计 §3.1 的分歧**——设计里 `PUT` 是惰性的（不 apply，等下次因为别的原因
重启时才生效）。改成：给**已存在**的 bot 写入新版本 manifest，当场生效，于是
运行中的 bot 永远反映最后被接受的那份 manifest。

**动作就是 §3.2 的覆盖，两个引擎系都不需要重启。**本节早先的版本规定了按引擎
系分别「重启」，那个说法已撤销——重启从来就不是让配置生效的东西，它只是 payload
被重建的方式。

| | 声明类目怎么被覆盖 | 需要重启？ |
| --- | --- | --- |
| **BaaS / ARCA** | `identity` 和 `resources` 是经 `DeviceFileSystem` 的文件写；`skills` 写进 active skill set，由既有的全量 symlink 对齐负责收敛，运行中的 bot 上通过 `DeviceSyncDispatcher` / `sync_symlinks` 即可触发 | **否** |
| **teclaw** | 经 `TeclawDeviceFileSystem` 的逐文件写——它*「把每一次读写逐文件转发给引擎，因此既不需要 OSS 也不需要整包 device-sync 重投」*；整包重投（`TeclawDeviceSyncPlugin.sync_symlinks([])`，`ChannelService` 已经在这么用）在确实需要的类目上仍然可用 | **否** |

**`script` 是唯一的例外，而且与其说是「需要重启」不如说是「延后生效」。**它通过
写 `ac_bot_startup_script` 物化（§2.12），而 `_build_create_bot_payload` 在拼装
启动命令时读这张表——所以改动后的脚本是**立即下发**、**下次启动时生效**。这是
一致而非特殊：apply 记录的是下发，不是执行（§2.7）。

**永远不要让 teclaw 的 manifest 变更走 `BotService.restart_bot`。**它会抛
`BotOperationNotAllowedError("teclaw 类型的 Bot 不支持重启")`，
`bot_publish_service.py` 记录了原因：teclaw 重启会销毁容器、重新分配失败，把
bot 打成无 binding 的坏状态并丢失容器内文件。按本节的方案本来就不需要重启，
所以这条规则很容易守住——写在这里，是因为实现者去找一个「让它生效」的动词时，
可能会顺手抓到那一个。

**去掉重启还顺带消掉一个生命周期状态问题。**`BotService.restart_bot` 只接受
`ACTIVE`、`FAILED`、`PENDING`；`REACTIVATING` 是空操作，其余状态一律抛
`BotInvalidLifecycleStateError`。要是 `PUT` 被定义成「总是重启」，调用方会因为
bot 恰好处在某个生命周期位置，而对一份完全合法的 manifest 收到 4xx。写文件加
对齐 skills 没有这道门。

规则：

1. **永远先落库并校验。**接受这份文档从不依赖 bot 的运行时状态。
2. **覆盖声明的类目**（§3.2）。不重启。
3. **`script` 若有声明，现在写入、下次启动时执行**——而且响应里说清楚，调用方
   永远不用猜。

通过**创建** API 提交的 manifest（§2.11、W13）是同一个操作在创建流程里跑一遍，
所以 bot 的第一个容器就带着它。

有一个残留情形属于 **D2**：源是**移动引用**（分支而非 tag 或 SHA）的 manifest，
可能在一次没人把它跟配置变更联系起来的重启里解析出不同内容。

### 2.7 apply 逐条记录「配置有没有下发成功」

**apply 没有「首启」这个概念。**不管 bot 是第一次起还是已经跑了一个月，apply
做的事完全一样，里面不存在按这个分支的逻辑。本节早先的版本在这个区分上建了一套
策略，已撤销。

**它的全部职责：manifest 里每一条，那一条的配置有没有被下发？逐条单独记录。**
这些逐条记录**就是**报告，也是 apply 唯一的产出。

本节过去说过的一切都是这条的推论，不需要单独作为策略陈述：

- **没有 bot 级的失败策略，因为根本没有 bot 级的决策。**「运行中的 bot 拉取失败
  时不要动它」不是一条规则——失败的条目就是没下发的条目，而没下发本身就是没动
  它。bot 继续用着原有的东西，是因为没有东西覆盖过去。
- **永远不往 bot 记录里写任何东西。**不改状态、不去激活、没有 readiness gate。
  这同时消除了对一个生命周期里不存在的状态的需求——没有 `INACTIVE`，所以那道门
  只能落在 `FAILED`，从而让「容器压根没起来」和「容器好好的、只是 manifest 没
  生效」变得无法区分。**这反而回到了设计 §4.3**，它本来就把 apply 失败放在
  readiness gate 之外。
- **记录是逐条的；写入决策是逐类目的。**这是两个层级，把它们混为一谈正是本条
  上一版出错的原因。每一条的结果永远单独记录。从这些结果里被**决策**的只有一件
  事：这一条所属的**类目**要不要写（all-or-nothing，见下）。
- **apply 全局的汇总值不决策任何事。**`SUCCEEDED` / `PARTIAL` / `FAILED` 是从
  逐条结果推导出来、给调用方看的摘要。没有东西读它然后据此行动——更不会作用在
  bot 记录上。
- **`on_fetch_failure` 是逐条的**（`keep_last` / `fail`），「**这一条**失败了
  怎么办」本来就该在条目上。`keep_last` 意为「复用上次为这一条物化的内容」，
  它的存储就是 §2.8 要求的那个。**`skip` 已在 §3.2 改为覆盖时删除**——见下。
- **类目是 all-or-nothing 覆盖的。**声明类目里只要有任何一条无法物化，该类目
  **完全不覆盖**；关于它的一切都不变，而每一条的结果照样记录。在覆盖语义下，
  一个不完整的集合是**破坏性**的集合：声明是 `{A, B}` 却写入 `{A}`，就等于删掉
  了 B。所以类目只会从完整的目标状态被写入。

  这是**唯一**驱动决策的汇总，而且它的作用域刻意是类目：一个类目的失败绝不牵连
  另一个。它同时由构造解决了 `keep_last` 的边界情况——某条的源在**首次** apply
  就失败时，没有此前物化的副本可以回退，集合补不全，于是该类目不写。所以首启
  遇到不稳定的源，那个类目交付的是「什么都没有」而不是「一部分」，这是这笔交易
  安全的那一端。
- **第一期只记录，不推送。**逐条记录就是交付物，用户想知道的时候自己来拉。没有
  通知、没有告警、没有主动消息。

**apply 记录的是下发，不是执行。**这条边界让职责保持在上面说的那么窄，同时它
消解了本节上一版错误地当成「例外」的两个情形：

| | apply 的记录到此为止 | 之后发生的事属于另一层 |
| --- | --- | --- |
| `script` | `ac_bot_startup_script` 那一行写入完成 | 脚本在容器启动时运行，共用启动命令那一个退出码（#935）。apply 既看不到也不记录 |
| **teclaw** | artifact 递交完成，或逐文件写落地 | 引擎去 apply——而且是全部完成才报 ready（X2/T1）。那是引擎的契约（W12），不是 apply 的记录 |

所以它们从来就不是「关于 bot 状态的规则」的例外，而只是在 apply 的职责范围之外：
apply 回答「我们有没有下发」，容器和引擎回答「有没有生效」。

**由什么承载这个信号**（既然 bot 记录不承载）：

- `GET .../config-manifest/last-apply` 是「这个 bot 的 manifest 生效了吗」的
  权威答案；W13 的轮询以终态形式返回同样的逐条明细，同样不碰 bot。
- **任何把 bot 显示为健康的界面，都必须能显示出它 manifest 的某一条并不健康。**
  这是 UI/API 的要求而不是状态列的要求，由 W8 负责让这个信号真的可达——信号被
  记录在没人看的地方，正是这笔交易换来的失败模式。

**关于通知，特此记录。**本节早先的版本要求「一条被呈现的通知」。那**不是**已合入
设计的要求——五份设计文档里没有任何一处提到通知——所以它被撤销，而不是作为一个
无法兑现的承诺留着。平台该不该主动把配置失败推给 owner，是一个没人提出过需求的
产品决策。

万一以后要做，复用点写在这里以免重新调研：`core/work_orders` 已经建模了纯通知
（`WorkOrderNotificationService`，`NotificationCategory.NOTICE` 与 `APPROVAL`
并列），需要新增一个 `WorkOrderBizType` 加一条 event→message 映射。`core/notify`
**不是**它，虽然名字像——那个是列出可被*引擎*轮询通知的 bot，即 bot 往用户推
消息。

### 2.8 平台自己物化并留存 manifest 内容

**硬性要求，来自审计与对账。**内容被拉取时，平台保存自己的一份副本，而不是仅仅
把它透传给下发通道。后续步骤从这份副本读。

除审计之外，还有两条性质让它成为承重的：

- **它把流水线解耦。**fetch 与下发不再是一个操作，于是重试下发不会重新 fetch，
  源侧故障也不会污染一次进行中的下发。
- **`keep_last` 就住在这里**（§2.7），于是两个需求合成一个存储而不是两个。

跟踪项 **W11**。

### 2.9 替换变量命名为 `BOT_*`，不是 `OCB_*`

`design.zh-CN.md` §4 与 `manifest-schema.zh-CN.md` 把替换变量命名为
`OCB_BOT_ID`、`OCB_ENGINE_TYPE`、`OCB_ENV`、`OCB_TENANT`。**`OCB` 是内部代号，
写 manifest 的用户没有任何理由需要知道它。**在代码里它只出现在内部机件上——
`__OCB_RC`（启动命令包装器里的私有 shell 变量）和 `OCB_AGENT_LOG_PRICE_*`
（后端配置）。它从来就不是一个面向用户的命名空间。

改名为 **`BOT_ENGINE_TYPE`、`BOT_ENV`、`BOT_TENANT`、`BOT_ARCH`**：
自解释（用户配置的就是一个 bot）、与容器环境里已有的 `BOT_DATA_DIR` 一致、而且
仍然带前缀——这点重要，因为它们会作为环境变量注入 `script`，不带前缀的
`${ENV}` 会跟脚本作者自己的变量撞车。

`OCB_BOT_ID` 没有对应的 `BOT_ID`，是**去掉**而不是改名（W1 评审结论）。留下的
四个都是**机群**属性，这正是一份文档能被多个 bot 复用的原因；bot 标识不是——
它由 `generate_bot_id()` 在创建时生成（日期 + 8 位随机字符），调用方指定不了，
在 git 仓库里准备内容的作者也无从得知。真按 bot 区分的内容，写在那个 bot 自己
的 manifest 里、直接写字面量。

### 2.10 校验与鉴权迁到一个可复用的缝上

apply 调用服务层，但相当一部分校验与鉴权目前住在 `openapi_v1` 的 router 里——
归属与授权检查、包校验、路径清单校验。apply 必须执行同样的规则，而手工复制一遍
必然漂移。

因此把它们重新表达为一个被声明的依赖/拦截器，router 与 apply 共同消费，沿用
协作者权限已经立下的先例（内部的 `CollaboratorPermissionInterceptor`，以及公开
面上 `specs/2026-08-21-openapi-v1-collaborator-authorization-seam` 的表驱动门）。
重新实现这些检查是可以接受的；**各自独立地实现两遍**不行。

跟踪项 **W10**，排在 W4 之前。

### 2.11 可以**用** manifest 创建 bot

manifest 不只是挂在已有 bot 上的东西。有一个公开 API **用 manifest 创建 bot**，
把 manifest 连同普通创建参数（引擎、名称、描述……）一起收下。它是**异步**的——
创建很慢——并且搭在既有的两段式 Passport 流程上，所以调用方轮询结果。

这补上了设计 §3.1 那句承诺——「bot 收到的第一份配置就已经包含 manifest 的结果」
——否则会留下的一个洞：光靠 `PUT`，对一个真正的新 bot 这个承诺是达不到的，因为
bot 存在之前你没法往 `/bots/{bot_id}/config-manifest` 写 manifest，于是它的首启
永远是空的。用 manifest 创建把这个洞补上——manifest 在 bot 记录写入之前就已在手，
所以 apply 在创建过程内部执行。

**它如何落在既有流程上**（`core/bot_management/create_flow.py`）：

| | 发生了什么 | bot 记录 |
| --- | --- | --- |
| 第一段 `create_bot_with_authorization` | 平台侧分配 `bot_id`（`generate_bot_id`，在 router 里调用）；preflight；申请 Passport；返回 `iframe_url` | **不存在**——代码自己的注释：*"No token yet → authorization pending; nothing is created."* |
| 用户点击授权链接 | | |
| 第二段 `complete_bot_authorization`（被轮询） | 查询 Passport 状态；`ISSUED` 时执行 `bot_service.create_bot(...)` | **在这里写入** |

**manifest 在第一段就落库**，以已分配的 `bot_id` 为键。这**不需要改表结构**：
manifest 表的键是 `(avernet_tenant, sha256(env, entity_id, bot_id))`，三个部分
在第一段全部已知。

另一个方案——让调用方在每次轮询时重新提交 manifest，也就是现有流程对 `spec` 的
做法——被否掉了：那意味着**被校验的 manifest 未必是被应用的 manifest**，因为
调用方可以在轮询时送一份不同的。这对 `spec` 是个潜在问题；对一份会安装 skills、
identity 文件、MCP 配置和 shell 脚本的 manifest，不可接受。

代价是用户始终没点链接、或 Passport 拒绝时留下的孤儿行。v1 仍然接受，清理推迟到
#1698——但理由必须说老实话，因为「一条孤儿 manifest 不占用任何运行时资源」这句
话是对的，却回答的是另一个问题。**没有任何东西能给这些行封顶。**bot 记录从未
写下，所以常规的删除 bot 走不到它们；而第一段分配 `bot_id` 时**不消耗 bot 配额**，
所以约束着其他所有创建路径的租户上限，在这里同样不起作用。哪怕是无辜的重试——
用户点了三次创建、一次都没走完——也会让这张表无上限地长，而且没有回收路径。

**已被 PR #1791 取代：没有特性开关，#1698 也不再卡这个端点。**上面对隐患的判断
是对的，对「唯一可行解」的判断是错的。创建 job 自带一个可配置的 wall-clock
deadline（默认 10 分钟），于是每一次创建都有一个终态时刻；创建以「没有 bot」告终
时——拒绝和过期都算——job 会把 manifest **以及 A 阶段写下的 startup script 行**
一起删掉。所以这个端点写下的行由它自己的 job 封顶，而这正是那个开关原本要顶替的
事情。#1698 的通用清理对那些没有 job 能认领的行仍然值得做，但它不再是本项上线的
前置条件。

**一条固定约束，不是设计选择：创建永远需要人。**Passport 授权链接是 AgentPass
的限制，不在我们控制范围内。所以「创建一个 bot」本质上是一次一个、人在环里的
操作，任何特性都不得建立在相反的假设上。

它的影响面比乍看要窄，而这个区分很重要：

| | 需要点授权？ |
| --- | --- |
| 用 manifest **创建** bot（W13） | **需要，每个 bot 一次。**固有 |
| 给**已有** bot `PUT` manifest（§2.6） | 不需要 |
| 在重新发布 / 重启时 apply（W8） | 不需要 |
| 已有 bot 的扩容 | 不需要——实例共享同一份平台状态（#926） |

所以设计 §9 的 **O6（模板级 manifest，一份声明服务多个 bot）**在它真正被写下来
的那个场景上是成立的——把一份声明*应用*到多个**已有** bot 上，完全不涉及授权。
不成立的是「用一份 manifest 批量创建 N 个 bot」：那是 N 次授权点击，再多平台
工作也消不掉。v1 没有任何东西依赖它；写在这里是为了以后不会有人再提。

跟踪项 **W13**。

### 2.12 第一期 `script` 不得依赖 manifest 声明的任何内容

**机制，已对照代码核实。**apply 物化 `script` 的方式是往
`ac_bot_startup_script` 写一行，别的什么都不做。那张表**就是**脚本的元配置，
与 `mcp` 是注册表引用同理：一次普通的、租户作用域的 DB 写入，不需要 device
绑定。这正是 `script` 成为唯一能在容器存在之前就物化的类目的原因。平台自己会把
它拼进启动命令：

- `BaasService._build_create_bot_payload` 在构造 payload 时解析存量脚本
  （`_resolve_startup_script`），`_get_start_cmd` 把它烤进 `after_create_cmd_hook`。
  生产上没有任何调用方传入脚本——集中解析正是让每条路径都能下发它的原因。
- 所以每条重建 payload 的路径都会重读这一行：创建、服务 bot 发布、`upgrade_bot`、
  以及两个 device service。因此改写后的行会被下一次重建 payload 的动作取走，
  不需要额外机件——这也是 §2.6 不为它重启的原因：`script` 是**立即下发**、
  **下次启动生效**。

**后果。**因为脚本是在构造 payload 时被烤进启动命令的，它在容器启动时执行——而
`identity`、`skills`、`resources` 和 `engine_config` 只能在容器起来**之后**下发
（§3.4）。所以在**首启**时，脚本先于它们中的任何一个存在而运行。

**第一期把这一点定成规则，而不是绕开它：manifest 的 `script` 不得依赖该 manifest
声明的任何其他内容。**这要写进 API 文档、manifest 参考，以及 W8 的一个测试。不
插入额外的重启来关掉这个窗口：首启压住脚本再重启，等于给每次创建加一整轮启动；
不压住则脚本跑两遍——而那正是设计 §2.4 否掉它第二个备选方案的理由。

**第二期解除它。**一旦所有类目都能在启动**之前**下发进容器（#1508 —— D4 的
方案 (a) 或 (c)），顺序会自然反转：实体先落地，脚本后运行，限制随之删除。它
由构造就是临时的，每一处写到它的地方都必须这么说，以便到时是被删除而不是被
重新辩论。

**这修正了设计 §3.4。**它固定的 apply 顺序（`engine_config → identity →
resources → skills → mcp`，script 最后）以及「script 可以依赖 manifest 声明的
实体已经就位」这句承诺，要等第二期落地才成立。在那之前，BaaS 系的首启上
`script` 实际上是**最先**的。teclaw 双重不受影响：它的 artifact 在启动前就带齐
一切，而且 teclaw 根本不支持 `script`（`bot_startup_script/services/_support.py`）。

## 3. 设计问题

### 3.1 D1 — 能力模型 · #1466 · **已解决**

**原问题：**设计 §5.1 既要求「支持与否」只从 bot 记录回答，又要求拒绝
ARCA-direct 与 LOCAL/singlebox——但这两个判别依据都不在 bot 记录上
（`device_provider` 在 `EntityDeviceBinding` 上；LOCAL 的判别来自 BaaS 模板）。

**由范围解决。**生产上新建 bot 只会到 `baas` 和 `teclaw`，所以不存在第三种情形
需要检测，也不存在含糊状态需要表达。见 §2.5。`engine-requirements.zh-CN.md` §2
矩阵里 ARCA-direct 与 LOCAL/singlebox 那两行属于范围之外而非被强制执行；修订那份
矩阵是另一个文档变更。

### 3.2 D2 — manifest 升级策略 · #1467 · **已解决（修订为：覆盖）**

失败那一半此前已定（§2.7）。收敛这一半定为**类目级覆盖**，与 teclaw 接收 artifact
的既有方式对齐。

**这修订了 D2 早先的结论**——实体级三方 diff（N、N+1、磁盘）加逐条 `on_conflict`
策略。那套被撤销，换成下面这条更简单的规则。早先版本想保护的东西，现在由一份
具名的保留清单来保护，而不是由 diff。

#### 规则

**让 manifest 生效 = 把每个被声明的类目覆盖到等于声明。**manifest 没有声明的
类目完全不碰。

| | 行为 |
| --- | --- |
| 声明了的类目 | 它的区域变成**恰好**是 manifest 说的样子。该区域内其余的一切被移除 |
| 没声明的类目 | **不碰。**manifest 没有表态，所以什么都不发生 |
| `skills: []` | 空集合本身**就是**一种声明：**所有 skill 被移除。**这与早先把 `[]` 读作「停止管理但不删除」相反 |
| 保留名单（见下） | 永不写、永不删——在所有覆盖之外 |

#### 「区域」逐类目定义，不是全局的

覆盖需要一个作用域，而这个作用域对每个类目并不是同一个形状。搞错这一点，一条
本意是收敛 skill 列表的规则就会删掉 bot 的工作目录：

| 类目 | 被覆盖的区域 |
| --- | --- |
| `skills` | **active skill set**。它等于声明；未列出的 skill 被移除 |
| `identity` | **identity 文件集合**，减去下面的保留名单 |
| `resources` | **仅声明的 `path` 子树。**声明的 `path` 之外一律不碰——workspace 是 bot 的工作区，不是 manifest 的 |
| `mcp` | **已启用的 server 集合** |

`resources` 是绝不能读成「类目区域 = 整个 workspace」的那一个。W6 早就写了更窄的
规则（声明的 `path` 那棵树整体替换，之外不碰）；上面这张表是把那条规则一般化，
不是新规则。

#### 类目是 all-or-nothing 写入的

声明类目里只要有任何一条无法物化，**该类目不被覆盖**——关于它的一切都不变，
逐条失败照常记录（§2.7）。覆盖让不完整的集合变成破坏性的：声明是 `{A, B}` 却
写入 `{A}`，B 就被删了，于是一次瞬时的拉取失败会删掉一个正在工作的实体。类目
只会从完整的目标状态被写入。

**这个保证的作用域是「下发开始之前」，而且这个作用域是有意的。**一个类目里的每一条
都**先全部物化**——拉取、校验、解包、存储（W11）——然后才对该类目发出任何下发写入。
所以 all-or-nothing 的决策是在完整目标状态已经在手时做出的，它消掉的正是那个最常见
的失败：网络拉取失败。

它**不覆盖**的是：一个所有条目都已物化的类目，在下发写入过程中途失败。第三个
identity 文件写失败时，前两个已经写进去了，而且在覆盖语义下某些旧条目可能已被移除。
**v1 不回滚这种情况**——apply 所穿过的那些服务之间没有类目级的暂存或事务，而发明一个
意味着要在 `IdentityService`、`SkillSetService` 和资源服务之间做分布式事务。

写出来而不是藏着，因为这两类失败的概率差别很大：跨互联网从调用方服务器拉取是常态性
会失败的；一个本地服务写入在类目中途失败则不然。残留的这种情况像其他情况一样逐条
记录，apply 报告就是显示某个类目处于混合状态的地方。要正经关掉它，需要一套跨物化器
的「暂存-提交」协议——如果哪天证明确有必要，那值得单独立项，不值得预先构建。

这也是 **`on_fetch_failure` 失去 `skip` 取值**的原因。在被撤销的逐条 diff 下，
`skip` 意为「跳过这一条继续」，已有实体不受影响。在覆盖下它会意味着「删掉这一条」
——与字面意思相反。保留 `keep_last`（用存量副本补全集合）与 `fail`（不写该类目），
它们覆盖了原本会去用 `skip` 的场景。

#### 保留名单——唯一的例外，而且它是一份清单，不是一条规则

有两个文件是引擎生成的运行时状态，而它们恰好住在两个引擎系的 identity 区域内
（ARCA：平铺在 workspace；teclaw：在 `/identity` 下）：

```
MEMORY.md
IDENTITY.md
```

它们**永远不被 apply 写入、也永远不被 apply 删除**，无论 manifest 是否声明了它们。
`kernel/bot_config/artifact.py` 已经把这两个（且正好是这两个）点名为引擎生成；
今天没有任何代码强制它，本条让它被强制。

**这是一份有限的、可枚举的清单**，正是这一点让该策略能与另一个引擎团队谈成。
上一版策略要保护的是「保留两个版本都没声明的所有文件」——一个**无界**集合，我们
既无法替 teclaw 计算，也无法要求他们遵守（那是 W12 最难的一条）。两个名字、两边
共用，是一份真能被同意的契约。

#### 刻意接受的代价

- **通过界面安装的 skill 会被移除**，当一份声明了 `skills` 的 manifest 被应用时。
  对一个被声明的类目，manifest 是唯一的所有者——在那个类目上 manifest 与界面
  互斥。已决策接受。
- **被声明类目内、由 bot 创建的文件会被移除**，除非它在保留名单里。这就是放弃
  三方 diff 的代价，也正是保留名单存在的理由。

#### 换来了什么

- **两个引擎系一套语义**，这本来就是重新审视 D2 的理由。teclaw 收下整包 artifact
  并替换；ARCA 现在对被声明的类目做同一件事。
- **收敛不再需要版本 N 的文件清单。**旧策略需要它来区分「声明里删掉了」和「bot
  自己建的」；覆盖不需要这个区分。**W11 不再是 W4 的硬依赖**——它仍然是 §2.8 的
  审计和 `keep_last` 所必需的，但不再卡住 apply 引擎。
- **没有 `on_conflict` 旋钮。**`overwrite` / `preserve` / `fail` 全部消失；类目
  规则加保留名单覆盖了它们原本的用途。
- **W12 从一场谈判缩成一份陈述。**我们不再要求 teclaw 实现一条我们无法验证的
  保留规则。见 W12。

#### 与设计 §3.2 的关系

这**回到了**已合入设计的方向——设计本来就是整体替换被声明的那棵树。本节早先的
修订取代了那条规则；这一次基本恢复了它，保留名单是唯一一处被记录在案的细化。

#### 在 ARCA 上这基本是现成机件

两个发现让 ARCA 这一侧比看起来小：

- **skills 本来就是从 DB 全量对齐的。**`skill_symlink_listener` 执行的是
  *「full skill-symlink sync … refreshed from the DB's current active skill sets」*，
  而同一个对齐在运行中的 bot 上可以通过 `DeviceSyncDispatcher` / `sync_symlinks`
  触发。apply 把声明的集合写进 active skill set 再触发既有对齐即可；删除那一半
  已经实现了。
- **identity 就是普通文件写。**`core/services/identity.py` 里跟重启毫无关系。

#### 移动引用：两种模式

分支引用仍然可能在一次没人把它跟配置变更联系起来的重启里解析出不同内容（§2.6 的
残留情形）。用模式开关而不是一刀切来解决：

- **严格模式**——若解析出的 SHA 与上次 apply 记录的不同，**拒绝这次变更**。bot
  继续跑它现在跑的。
- **非严格模式**——应用新内容并**告警**。

两种模式都要求每次 apply 记录解析出的 SHA，而报告里本来就带着它（设计 §7）。

**模式在哪里设，默认是什么。**上一版把这件事留给 W4 的 spec，这不够：W8 那条
「D2 关于移动 ref 的决定在这里被执行」在选择器还不存在时根本无法实现，而两个
实现者会对同一份文档猜出相反的行为。在这里定掉：

- **字段就叫 `mode`，写在源上，取值 `strict` 与 `non_strict`。**在这里点名，是为了
  让这段散文和实现它的验收标准（W1 的拒绝清单、W7 的 `Done when`）不会各写各的。
- **按源设，写在源声明上**——不是按 bot，也不是按 manifest。要描述的性质是
  「这个 ref 允不允许在我脚下移动」，它属于持有 ref 的那个东西。一份 manifest 里
  同时有一个钉死的外部依赖和一个快速变动的内部仓库是常态，而按 bot 的开关表达
  不了这件事。
- **默认非严格。**写 `ref: main` 而不写 SHA 的人，要的就是会动的行为；把默认设成
  拒绝，等于让常见情形变成意外。严格模式是给「想要钉扎语义但不想手写 SHA」的
  调用方用的。
- **告警出现在 apply 报告里**，挂在条目上，写明前后两个 SHA。第一期按决策是
  pull-only 的（§2.7），所以报告是它唯一能出现的地方——没有推送通道可放，而在这里
  发明一个就会跟那条决策矛盾。
- **SHA 形式的 ref 完全忽略这个模式。**它动不了，开关的两个分支都触发不了；在它上面
  设模式是「接受但无效」，不是报错。

### 3.3 D3 — reconcile 与 manifest 装的 skill · #1468 · **已解决**

**对原始结论的更正。**它把 `skills_pool` 的「quarantine cleanup」读成了一个会
删除无法识别的 skill 的漂移清理器。它不是：quarantine 是一个**迁移**机制——在
pool 切换期间，bot 的旧 skill 目录被改名搁置、保留 7 天后清理。没有任何组件会
因为「不认识」而删除 skill，所以从来就不存在 manifest 装的 skill 被当作漂移清掉
的风险。

**由 §2.3 解决。**manifest 装的 skill 走与手工完全相同的上传与激活路径、存储也
完全相同，所以 `skills_pool` 无法区分它们，也不需要区分。有两个事实值得作为验收
标准带进 W5，而不是作为问题：

- skill 必须被**注册**（走服务调用、有 DB 行）——激活流程会把未注册的文件系统
  内容枚举进 pool 而不创建记录，所以「把文件丢在磁盘上」是要避免的失败模式。
- teclaw 完全不参与 `skills_pool`，所以这只是 BaaS 系的关注点。

### 3.4 D4 — 容器存在之前的下发 · #1508 · **推迟——不再阻塞**

**临时策略：bot 启动之后再下发。**对于任何「下发 API 只在容器起来后才可用」的
类目，apply 在启动**之后**下发而不是之前。启动前下发是一个之后再回答的独立问题，
W5/W6/W8 不等它。

**#1508 是第二期的工作项，而且它带两份 payload。**关掉它不只是把下发时机提前；
它同时是解除 §2.12 那条「manifest 的 `script` 不得依赖 manifest 声明的任何内容」
的东西。接手的人要负责把那条限制从文档、manifest 参考和 W8 的测试里**删掉**，
而不只是改下发。

#### 问题本身，存档

`design.zh-CN.md` §3.1 承诺 bot 收到的第一份配置就已包含 manifest 的结果。但
apply 必须调用的那些服务在容器存在之前跑不了，而且是刻意的：

- `IdentityService._device_write` 通过 device binding 解析 `DeviceFileSystem`，
  **未绑定时抛异常**；
- `EngineConfigService.write_bot_config` 同理，指定 stage 没有活着的东西时抛
  `EngineStageNotLiveError`。

`core/services/identity.py` 写明了意图：*「一个没有可解析 device 上下文的 bot 是
个 bug，应当以 resolver 的错误暴露出来（尽早失败，绝不静默地去碰一个死的本地
路径）」*。

#### teclaw 不受影响

artifact **就是**下发载体，所以物化出来的内容变成 `BotConfigArtifact` 里的
`{store, path}` 引用，第一份 artifact 就带着它们——真正做到了启动之前。有一处
后端改动是必须的，应当被点名而不是被撞见：`ConfigComposerInputCollector.identity_files()`
目前对 teclaw 按设计返回 `[]` ——

```python
if req.engine_type == "teclaw":
    return []   # teclaw owns its identity files in the running container;
                # gathered from the engine at promotion, like resources
```

但 `engine-requirements.zh-CN.md` §1 那句「下发层：零新增」在后端侧不成立了。

#### 临时策略的代价，直说

### X1 — Ant Code 凭证选择

Ant Code 的公开文档解决了其中大部分，并且包含一个推翻设计决策的事实。

**不存在只读的 API 权限。**访问令牌的几种 scope 里：

- `api` —— *「授予对 API 的完整读/写访问权限，包括所有组和仓库」*：对该账号可见
  的每个组和仓库都有完整读**写**；
- `read_repository` —— 只读，但*「使用 Git-over-HTTP（不使用 API）」*：只有 Git
  传输，**没有** API。

只读和 API 访问，二者只能取其一。

| 选项 | 作用域 | 传输 | 结论 |
| --- | --- | --- | --- |
| 访问令牌 + `api` | 用户级，读**写**，所有组和仓库 | API | **不行。**为一件只读的工作换来对一切的写权限 |
| 访问令牌 + `read_repository` | 用户级但**只读** | Git-over-HTTP | **推荐**，搭配机器账号 |
| 私有令牌 | 该人的全部权限，无过期控制 | API + git | **不行。**换个名字的个人访问令牌——schema §2.1 已排除 |
| SSH 公钥 | 该用户的*全部*权限——文档正好警告了这一点 | SSH | **不行** |
| 仓库部署公钥 | **仓库级、只读**——可选项里作用域最好的 | 仅 SSH | 安全性最好，但 v1 的传输方式不对 |

**推荐：专用机器账号 + scope 为 `read_repository` 的访问令牌。**文档给出的用法
形式 `https://git:{token}@code.alipay.com/{group}/{project}.git` 是 HTTP Basic，
所以它以 `Authorization: Basic base64("git:<token>")` 存储、以请求头注入——
**v1 的凭证模型不需要任何改动**。作用域收窄来自该账号的*成员身份*（只加入内容
仓库），而这正是 schema §2.1 为「没有仓库级令牌的宿主」预想的兜底做法。
`allowed_prefixes` 仍然是叠在上面的平台侧检查。

**后果：这推翻了设计 §10.5。**那一节把 git 源编译成一次经宿主 API 的 HTTPS 归档
拉取，明确避免在后端进程里 `git clone`。`read_repository` 够不到 API，所以 W7 改为
做一次**浅层单 ref fetch**。走 API 那条路意味着接受 `api` scope——对一切的读写
权限——那件事放进我们的数据库里，比跑一次 clone 糟糕得多。

**两个后续问题现已回答，X1 关闭。**Ant Code 不提供 Deploy Token，且**令牌过期由
凭证 owner 负责**，不是平台去轮换。

owner 自管过期有一个设计后果，属于 W3 和 W4：除非我们让它可区分，否则一个过期的
令牌与任何其他拉取失败无法区分。按 §2.7，失败的条目就是没下发的条目，运行中的
bot 不受影响——这是对的，但意味着**令牌可以静默过期而不显式坏掉，直到下一次
创建或重启 bot**，那时失败被报告在 manifest 上而不是 bot 上（§2.7）。

所以：认证失败（401/403）必须在 apply 报告里报告为*「凭证 `<name>` 被拒绝」*，
具名且与通用拉取错误区分开，让 owner 知道该去轮换而不是排查网络问题。做起来很
便宜，而且这是让「owner 自管过期」可运维的唯一办法。

Deploy **key** 在纸面上仍是安全性最好的答案——仓库级只读优于用户级只读——但它们
是 SSH：在一个围绕 SSRF 防护、host-key 校验、以及「存请求头而非私钥」的凭证模型
构建的纯 HTTPS fetcher 里引入第二种传输。既然请求头这条路已经定了，v1 不值得。

### X3 — `cli_tools`，已收窄

**PATH 这件事 teclaw 不需要我们做什么。**artifact 就是下发载体，所以我们这一侧
是协议设计：一个 CLI 工具在 `BotConfigArtifact` 里如何表达，好让 teclaw 放置并

**ARCA 是引擎相关的，需要我们出方案**——平台工具目录该落在每个引擎的 agent 进程

怎么调用。

#### 调研：今天已经有什么（动手前被要求先查）

对照代码核实的结论：

- **确实有一套能用的 CLI 模式，但只在 singlebox 里。**`scripts/modules/bots.sh`
  用 `PATH="$bcs_cli_dir:$PATH"` 启动 openclaw 网关（约 954 行），并单独把
  `bcs-coordination` skill 复制进 bot 的 `workspace/skills/`
  （`bots_dynamic_setup_bcs_skill`，约 704 行）。这就是设计引用的「二进制挂 PATH
  + SKILL.md 教用法」双件套。
- **生产上不存在。**生产的启动命令拼装里（`baas_service.py`、`core/devices/`）
  没有任何 PATH 注入。`Dockerfile.ocb` 确实把 `bcs-cli` 烤进 all-in-one 的 OSS
  镜像（`/opt/ocb/src/bcs/target/debug/bcs-cli`），但那是 singlebox 镜像，不是
  ARCA 的 bot 容器。
- **生产上 skill 是通过 skill-center 到达的**，不是文件复制——`bcs-coordination`
  以 `git://default/bcs-coordination` 被引用，经技能集机制安装。`SkillSetService`
  已经有一个按引擎类型区分的**默认技能集**及其选择策略
  （`_default_skill_set_selection`、`DefaultSkillSetSelectionPolicy`），那就是
  「工具用法 skill」的天然归宿。
- **代码库的走向是在远离 CLI。**较新的任务类 skill 明确禁止它——
  `specs/2026-08-09-task-goal-driven-task-runner-bbs/bbs-relay-pickup/SKILL.md`
  规定所有任务 API 都走 `exec` + `curl`/`jq`，并写明
  「**禁止引用 bcs-cli 或任何子命令**」。`bcs-coordination` 自己声明的
  `allowed-tools` 就只有 `[exec]`。

**这里真正悬着的只有 O9**，而且比它那句摘要暗示的要窄。

#### 已回答：`linux/amd64`

ARCA bot 容器内 `uname -m` 返回 **`x86_64`**，所以 v1 每个工具只需一个
`*-linux-amd64` 的 URL，不需要按架构分源。

同一次核查记录下的两点观察：

- 镜像是 **RPM 系**而非 Debian（没有 `dpkg`）。对 `cli_tools` 无影响——它交付的是
  静态二进制和归档——但值得记下，因为 schema §3.7 把 `apt` 举为「属于 script 的
  包管理器安装」的例子，在这个机群上那应该是 `yum`/`dnf`。
- 证据是**一个抽样容器**。这很强，但不构成跨集群跨地域的机群一致性证明。它也不
  需要是：下面的 ELF 校验会把一个错误假设变成 apply 时的大声失败而不是静默失败，
  而 `${BOT_ARCH}` 实现为一个常量，所以将来若机群变成混合的，改的只是那个值从哪
  里来。

#### 为什么这个问题是关于 CPU 架构而不是路径

`cli_tools` 交付的是**编译好的二进制**，而二进制在**两个独立维度**上要与宿主匹配：

| 维度 | 取值 | 状态 |
| --- | --- | --- |
| 操作系统 / libc | linux · darwin · windows | **已答：Linux** |
| CPU 指令集 | `x86_64`/amd64 · `aarch64`/arm64 | **已答：amd64** |

两者都体现在惯用文件名 `mycli-linux-amd64` 里。一台 Linux **arm64** 宿主跑不了
`linux-amd64` 的二进制——它会在容器内、在模型试图使用该工具的那一刻以
`exec format error` 失败。所以知道操作系统是 Linux 只定了一个维度，另一个还留着。
而一条 manifest 条目只写**一个** URL。

这**不是**「工具目录放哪、PATH 够不够得到」的问题。那是我们自己的设计选择，与
引擎无关，已经定了。它也不随引擎变化：它随**容器被调度到的机器**变化，所以是问
ARCA 机群运维方的问题。

**它无法从代码里回答。**后端没有容器架构的概念：镜像按名字钉死
（`arca_image_pin.py`、`sbot_docker_image`），调度是 ARCA 的决定。
`core/service_bot/` 和 `core/devices/` 里任何地方都没有按架构分支。

#### 这个问题不必卡住 W9

两个便宜的选择让这个答案不构成阻塞：

- **现在就实现 `${BOT_ARCH}`，解析为常量 `amd64`。**大约一行。用户可以立刻写
  `mycli-linux-${BOT_ARCH}` 并且它就是对的。如果机群将来不再统一，我们只改*这个
  值从哪里来*——按 bot 查询而不是常量——**不改 schema、不改 manifest、不升版本、
  用户什么都不用重写**。仅仅「保留」这个名字反而会拒绝用了它的人，对谁都没好处；
  白名单是随 `schema_version` 版本化的，所以要点是避免以后修订一份已发布的契约，
  而实现它做到了这一点还不止。
- **在物化时校验二进制架构。**读取拉下来的二进制的 ELF 头，与目标不匹配就拒绝。
  这样不匹配会在 apply 报告里大声失败，而不是变成模型在任务中途撞上、又毫无解释
  的 `exec format error`。

有了答案之后，第一条让将来可能出现的混合机群对**用户不可见**，第二条则不管架构
如何都值得保留：`digest` 回答的是*「这些字节是不是你要的」*，ELF 校验回答的是
*「这台机器能不能跑它们」*，而**错误**二进制的 digest 仍然是一个有效的 digest。
它实际能抓到的失败通常是用户错误——把 darwin 构建发到了那个 URL、amd64 与 arm64
的路径搞反、或者对一个 404 的 HTML 页面算了 digest。这三种都能通过 digest 校验。

**第三个选项，现在不需要但记录在案。**在 D4 的临时策略下（§3.4）下发发生在 bot
启动**之后**，所以物化 `cli_tools` 时容器已经存在。若引擎能报告自己的架构，
`${BOT_ARCH}` 就可以**按 bot 在下发时解析**，由构造回答这个问题。对统一的 amd64
机群没必要；若哪天不再统一，这是自然的答案。

**是不是已经有一套我们会重复造的 CLI 机制？没有——这才是那个要紧的答案。**
仓库里每一处 `bcs-cli` 引用都在 `scripts/modules/*.sh`，即 singlebox 编排。平台
里不存在 CLI 下发机制：生产启动命令拼装里没有 PATH 注入，而且**任何下发路径
（resources、skill-center、artifact）里都没有可执行位处理**。所以 `cli_tools` 是
新机件，不是某个已有东西的第二份实现。

**重复的风险是真实的，但方向相反。**一旦 `cli_tools` 存在，`bcs-cli` 应当成为
**它的第一个消费者**，而不是继续当 singlebox 的特例——否则我们才真的会有两套
机制：一个脚本在本地手工放置它，manifest 路径放置其他一切。把 bcs-cli 收进

#### W13 — 用 manifest 创建 bot · #1696

**Owner.** `totalfrank` · 0.5 天 · 第 3 天 · 设计（§7）

> **设计已在 PR #1791 定稿** —— 见
> `specs/2026-09-01-create-bot-with-manifest/`。下文有四处被它取代，已就地更正：
> 这个端点**只服务 ARCA**（teclaw 的创建归 W8）；创建由**任务队列的一个 job**
> 推进，而不是靠调用方轮询；**apply 本身也变成了任务**，在所有路径上取代 W4 的
> daemon 线程；终态会说明**是哪一件事**失败了。没有特性开关。

**目标。**一个公开的异步 API，用 manifest 加普通创建参数创建 bot，于是 bot 的
**第一个**容器就带着它的配置（§2.11）。

**依赖。**W1（文档存储、schema、能力解析器）和 W4（它调用的 apply 引擎），
**外加这个端点所接受的每一个类目都要有物化器**。光有 W4 只物化 `mcp` 与 `script`，
所以 W5/W6 缺席时，一个声明了 `identity`、`skills` 或 `resources` 的创建请求会通过
预检、把用户带完 Passport 授权、把 bot 开出来，**然后**才 apply 失败——这是最糟糕的
发现时机，因为 bot 已经存在了。要么 W5、W6 也是依赖，要么这个端点接受的词汇被收敛到
已落地的范围（W1 的门禁规则）。绝不能让它接受一个物化器还不在的类目。**已定：门禁
从物化器注册表推导**，所以 W5/W6 落地就自动放宽这个端点，不需要在这里改一行。·
**阻塞于。**—

**引擎范围：只有 ARCA。**本项之所以要分「容器前 / 容器后」两段，是因为
`BaasService._build_create_bot_payload` 在拼装启动命令时会读 startup script 那一行。
teclaw 没有对应物——`TeclawProvisionService` 在开通时组装 config artifact——所以
**teclaw 的创建归 W8**：W8 的范围里本来就写着「在 bot 创建时 apply……teclaw 在第一份
artifact 组装之前」，它的第一条验收标准就是「第一份 artifact 已包含 manifest 的
结果」。本端点拒绝 teclaw 引擎；**解除这条拒绝也归 W8**，与 teclaw 的创建机制一起做。

**为什么它自成一项而不是 W1 的一部分。**W1 被刻意限定为绝不触碰 `create_flow`；
那个耦合正是本计划最想避免的。本项才是那个耦合该在的地方，而且它自身就很有分量：
一个新的公开端点、一个异步状态面、bot 记录存在之前的 manifest 存储、从参数而非
记录做能力校验、以及与两段式 Passport 流程的集成。

**范围内。**创建端点（manifest + 引擎、名称、描述……）；第一段以已分配 `bot_id`
为键的 manifest 落库；轮询/状态端点及其状态；把 apply 作为创建的一部分调用。

**范围外。**#1698 的通用孤儿清理（仍然值得做，但**不再是本端点的前置条件**——创建
job 的 deadline 给它写下的行封了顶，而且创建以「没有 bot」告终时，job 会自己把
manifest 和 phase A 写下的 startup script 行一起删掉）与创建幂等
（#1697 —— 一个既有缺口：`generate_bot_id` 在平台侧铸造 id 且没有幂等键，所以
重试创建会产生第二个 bot，与 manifest 无关）。

**轮询状态。**三个终态，让调用方的循环保持简单：

```text
AWAITING_AUTHORIZATION   等待用户点开 Passport 链接
        │                （响应携带 iframe_url / redirect_url）
        ├──► AUTHORIZATION_REJECTED   终态——用户拒绝
        ├──► AUTHORIZATION_EXPIRED    终态——Passport 过期，或 job 的 deadline
        │                             在无人点击的情况下走完
        ▼
CREATING                 已授权；bot 记录已写入，容器正在开通
        ├──► CREATE_FAILED   终态——没有可用的 bot，与 manifest 无关
        ▼
APPLYING                 容器后那一段 apply 进行中
        ├──► READY         终态——bot 起来了，manifest 也生效了
        └──► APPLY_FAILED  终态——bot 起来了，manifest 有一部分没生效
```

轮询**只按 `bot_id` 寻址**，不收 manifest，也不收创建参数，并且不发起任何外部调用。

- **`PARTIAL` 意味着某个类目没有被覆盖**（§3.2 all-or-nothing），所以它汇报为
  失败而不是 `READY`。早先的修订把 `PARTIAL` 映射到 `READY`，理由是那些跳过是
  作者授权的；那个理由建立在 `on_fetch_failure: skip` 之上，而它已不存在。
- **三种失败，三个不同的回答，不需要读文案就能分辨：**manifest 非法是提交时的
  `422`，既没有 bot 也没有状态；bot 建不出来或压根没起来是 `CREATE_FAILED`；
  bot 在跑但 manifest 没全生效是 `APPLY_FAILED`。用一个 `FAILED` 同时表示后两者，
  才是「我到底有没有拿到 bot」这个歧义的真正来源。
- `APPLY_FAILED` 是一个 **manifest 层**的终态（§2.7）。bot 记录不被触碰，而且
  状态名本身就把这一点说清楚了，不必再靠响应体去辩解。apply 记录自己仍然是
  `PARTIAL`——只有这个轮询的一词总结做了映射，`POST …/config-manifest/apply` 打在
  运行中 bot 上的行为完全不变。
- **`APPLYING` 把 D4 的临时代价变成一个可见状态。**启动后下发（§3.4）留下一个
  bot 已 ACTIVE 但未配置的窗口；等待 `READY` 的调用方永远观察不到它。这个窗口
  不再是一个隐形陷阱。
- **不是本端点创建的 `bot_id` 返回 `404`，而不是某个状态。**用普通方式建出来、
  事后 `PUT` 了一份 manifest 的 bot，既有 bot 记录也有 apply 记录，就是没有创建
  job——而那正好是 `CREATING` 的形状，所以少了 job 这一问，轮询就会汇报一次从未
  发生过的创建。job 用 `(tenant, entity_id, bot_id)` 推导出的幂等键找到，这同时
  也保证一个 owner 拿另一个 owner 的 `bot_id` 去轮询只会一无所获，而不是拿到对方
  待授权的链接。

**部署前提（PR #1791）。**apply——因而「用 manifest 创建 bot」——只在
`task_queue_worker.enabled=true` 且 `ac_task_queue` 已开好的部署里推进。这个开关
在本项之前只是一个优化开关，从本项起它决定功能可不可用，而且失效方式不是「变慢」：
worker 关着时，提交照常返回 `202`，轮询会一直停在 `AWAITING_AUTHORIZATION`，直到
deadline 把它判为 `AUTHORIZATION_EXPIRED`；显式 apply 照常给出 `202`，报告则一直
停在 `RUNNING`，直到 apply 锁的 TTL 到期。两者都永远不会完成。

**验收标准。**

- [ ] manifest 在**申请 Passport 之前**被校验——在 `create_bot_with_authorization`
      的 preflight 阶段，与配额、名称、引擎检查并列。用户绝不该在完成授权之后
      才被告知 manifest 非法；那既浪费他的时间，也白烧一次 Passport 申请。
- [ ] 能力从**请求参数**（引擎、bot 类型）校验，而不是从 bot 记录，因为第一段
      还没有记录。W1 的解析器要长出这个入口。
- [ ] manifest 在第一段落库、第二段读回——**被校验的 manifest 就是被应用的
      manifest**。它绝不由调用方在轮询时重新提交。
- [ ] 存储**不需要改表结构**：既有的
      `(avernet_tenant, sha256(env, entity_id, bot_id))` 键可用，三个部分在第一段
      全部已知。
- [ ] **租户上下文能活着到达 apply 真正运行的地方**，用与它调度方式相匹配的机制
      （见下方备注）。要有测试，不能靠记忆：这里租户错了，会静默替换成错误的
      `${BOT_TENANT}`，**并且在错误的租户下读写 manifest 表**——这是隔离故障，
      不只是正确性故障。
- [ ] 轮询报告上述状态，两个终态都携带 apply 报告。
- [ ] 既有的 `PUT` 路径不变：以任何其他方式创建的 bot 仍然可以事后被赋予一份
      manifest，并且**立即生效、走与其他已有 bot 完全相同的不重启路径**（§2.6）。
      两条路径共存；任何一条都不会让 bot 停在旧配置上直到下一次生命周期事件。
- [ ] **apply 分两阶段调用**（W4），而本项正是编排器需要那个形状的原因：
      **A 阶段**（`script`）在 `_build_create_bot_payload` 拼装启动命令之前运行，
      **B 阶段**（其余一切）在容器起来之后。
- [ ] **已定：A 阶段在 bot 记录被创建之前就跑完**，而不是靠 `create_bot` 里的一个
      钩子。它不需要 bot 记录里的任何东西——startup script 那一行的键是
      `(entity_id, bot_id)`，两半在提交时都已知；占位符白名单也正好只有
      `BOT_ENGINE_TYPE`、`BOT_ENV`、`BOT_TENANT`、`BOT_ARCH`（没有 `BOT_ID`，
      也没有 `BOT_NAME`）。把它排在创建之前，这条保证就是**结构性成立**的，而且
      `bot_service.py` 一行都不用动。
- [ ] **已定：创建由任务队列上的一个持久 job 推进**，不是靠调用方轮询，并带一个
      可配置的 deadline（默认 10 分钟）。job 等授权 → 跑 A 阶段 → 创建 bot →
      等容器 → 启动 B 阶段 → 结束；它**不等 B 阶段跑完**，因为平台侧没有任何东西
      卡在 B 阶段上。调用方中途不轮询了，bot 照样会被配置好；用户始终不授权，也会
      在有界时间内落到一个终态。
- [ ] **`script` 在构造创建 payload 之前写入**，不与 apply 的其余部分同时。它是
      唯一不需要容器的类目（§2.12），而 `_build_create_bot_payload` 在拼装启动
      命令时会读这一行——所以那一行必须在那之前就存在，首启才可能带上脚本。其余
      一切都在启动后下发，这也是第一期禁止脚本依赖它们的原因。

**备注 —— 租户上下文如何到达 apply，取决于 apply 怎么被调度。**有两种机制，行为
不同，只有一种是已经解决了的：

| 机制 | 租户能活下来吗？ |
| --- | --- |
| 请求期间派生的线程 | **能——已经解决。**`threading.Thread(target=bind_current_avernet_tenant(fn), daemon=True)` 是既定模式：`bot_publish_service.py:1267`（`_do_restart`，它自己就是一个 apply 点）、`baas_publish_poller.py:57`（`_poll`，`CREATING → APPLYING` 的天然归宿）、`bot_service.py:1979`。包装器在**绑定**时（即在请求线程内）读取租户，并在新线程内重新建立它。照着模式写就什么都不用做 |
| 任务队列 | **不能，而且这已经是现在的场景。**`core/task_queue` 的模型带 `env`、`app` 和 `idempotency_key`，但没有任何租户形状的东西，整个模块也没有租户处理。任务现在入队、之后由 worker 执行，所以没有请求上下文可捕获，`bind_current_avernet_tenant` 帮不上忙。租户搭在任务 `payload` 里，handler 用 `avernet_tenant_scope(...)` 把整个函数体包住。**这一条要写测试，不能只写注释**，因为它的失败是无声的：`get_current_avernet_tenant()` 是个*全函数*，在请求之外返回**默认租户**而不是抛异常——所以 handler 忘了这件事不会崩，它只是悄悄在错误的租户下读写 manifest 表 |

**已被 PR #1791 取代：现在每一条 apply 路径都走任务队列。**写下这段备注时确实没有
任何 apply 路径用它，也确实告诉过 W13 不必解决租户问题。它必须解决：W13 不但把创建
放到一个 job 上，还把 **apply 的执行本身**从 W4 的 daemon 线程搬到了任务上——三种
情况全部如此：容器前那一段、容器后那一段，以及打在运行中 bot 上的显式 apply。队列
自己的 README 就把 daemon 线程这个模式点名为它要取代的对象（「重启即丢失、跨 pod
重复执行」），而创建**依赖**某次 apply 跑完，所以线程一死，bot 就会带着空的启动
脚本起来。在此之前 `skills_pool` 是唯一的使用者（`skills_pool.reconcile`、
`skills_pool.quarantine.cleanup`）。

有两条后果要一并带走。**worker 从此是关键路径**：apply、以及由它派生的 bot 创建，
只有在 `task_queue_worker.enabled=true` 且 `ac_task_queue` 已开表的部署上才会推进
——worker 关着的时候，创建不是变慢，而是永远完不成。以及**重跑之所以安全是因为
收敛，绝不是因为「关掉了重试」**：at-least-once 是结构性的，worker 崩了以后租约
过期，任务照样会被重新领走，handler 有没有返回过 `Retry` 都一样；安全性来自 apply
对着当前状态重新 plan，加上 apply 锁。

一个值得知道的小坑：`bind_current_avernet_tenant` *看起来*像装饰器（它用了
`functools.wraps`），但它是在包装表达式被求值的那一刻捕获租户的。若真的当
`@decorator` 用在模块级函数上，它会在**导入**时捕获——那时没有请求——从而永久绑定
默认租户。当前所有调用点都是在 `threading.Thread(...)` 构造处内联包装，是正确的。

**规模。**大。

**范围外。**任何 apply。任何拉取。凭证。对既有 `/startup-script` 端点的任何改动。
对 `BaasService` 的任何改动。

**验收标准。**

- [ ] 从未有过 manifest 的 bot 读出来是一份空文档而不是错误——与

- [ ] 校验会拒绝下列情形，且每条错误消息指名违规条目：
  - 一个条目上同时出现两个及以上的 `from` / `source` / `content` / 注册项引用；
  - `from` 指向 `sources` 里没有声明的源；

    所有私有源的秘密都必须走凭证引用（W3），而内联的 token 会被存进文档、被 `GET`
    逐字节读回、还被 W11 作为溯源记录下来 —— 这三处正是那个加密、永不可读回的凭证
    库存在的意义所在；

  - 用了 `from` 的条目上写 `auth`（auth 声明在命名源上），或 `content` 条目上写

    `content` 大小）。
- [ ] `PUT` 是 all-or-nothing：只要有一个不受支持的类目，整份文档被拒绝，附逐条

- [ ] 该函数还必须能**仅凭引擎类型与 bot 类型**回答，不需要 bot 记录——W13 在

#### W2 — 带防护的 fetcher 与归档流水线 · #1470

**目标。**一个安全拉取调用方给定 URL 的组件，和一个安全解包归档的组件。不含任何

- [ ] 逐条目的字节上限在**流式过程中**强制，而不是只看 `Content-Length`。

- [ ] 解包支持 `zip` 与 `tar.gz`，并拒绝：路径穿越、成员绝对路径、逃出根目录的

- [ ] 解包强制成员数上限与解包后总大小上限，于是一个小归档无法无限膨胀。
- [ ] `strip_components` 恰好剥掉声明的那么多层前导路径段，**绝不**自动探测单一
      顶层目录——相同输入必须表现相同，与归档内部形状无关（schema §3.2）。
- [ ] 权限位被抹平：解包出来的任何东西都不可执行。**对所有下发数据的类目来说这是

      必须由取下来的一方设置、而不是一路带过去的原因。`cli_tools` 摊平为一个条目一个
      文件（W9）之后，这个例外很窄，也不需要动本条规则：引擎把下发的那一个文件置为
      可执行即可。**不要在这里放宽抹平。**

先例，值得先读，但它在 engine 仓——后端这一侧是新代码，今天没有任何 SSRF 防护。

#### W3 — 源凭证 · #1471

**Owner.** `lucas-xzp` · 0.75 天 · 第 1–2 天 · 实现（§7）



**目标。**租户可以注册一次命名凭证并在多份 manifest 里引用它，平台可以在拉取时
出示它——而这个秘密永远不能被读回、不被日志记录、不进入容器。

**范围内。**存储、加密、前缀授权模型、API，以及绑定 W2 的注入端口。

**范围外。**`header` 之外的任何凭证类型。apply 对它的任何使用。

**依赖。**— **阻塞于。**—

**验收标准。**

- [ ] 租户级表，键为 `(avernet_tenant, name)`；`name` 是自由标识符，与
      `allowed_prefixes` 里的主机没有派生关系。
- [ ] 秘密通过既有的 `TokenVault` **可逆加密**存储（`enc:v1:` 前缀，经
      `utils/secret_utils.symmetric_encrypt` 的 AES-GCM），主密钥由
      `SecretResolver` 解析。不引入新的密码学。
- [ ] **新增的 fail-closed 守卫：**在生产 profile 下，若主密钥解析不出来，凭证
      写入必须被**拒绝**。`TokenVault` 今天会退化成无前缀明文存储——这对
      singlebox/CI 是对的，对这些秘密不可接受：一次密钥库配置错误就会让所有租户
      的令牌明文躺着。
- [ ] `allowed_prefixes` 必填，至少一项，每项都是绝对的 `https` 前缀。
- [ ] 前缀匹配按**路径段边界**：目标必须等于前缀，或以「前缀 + `/`」开头。
      `…/team/content` 不得授权 `…/team/content-secret`。要覆盖整个 origin，必须
      显式写 `https://host/`。
- [ ] **比较之前两边都要结构化地规范化。**光靠 `startswith` 不够：
      `https://host/team/content/../admin` 作为字符串是以前缀开头的，但它解析之后
      落在前缀之外，而客户端会把带秘密的请求头发到解析后的那个路径上。要解析 URL、
      比较**完整的 origin**——大小写不敏感的 scheme 与 host，**外加生效端口**，并
      把默认端口折进来，使 `https://host` 与 `https://host:443` 是同一个
      origin——再解开百分号编码（含 `%2F`、`%2E` 这类被编码的分隔符）、折叠
      `.`/`..` 段，**然后**才比较路径。初始目标与**每一跳重定向**同等处理，因为
      重定向正是恶意服务器会下手的地方。
- [ ] **端口是 origin 的一部分，不是细节。**`https://host:8443` 与 `https://host`
      是两个不同的服务——而且常常就是同一台机器上的内网服务——所以一个只授权给后者
      的凭证，绝不能被带到前者上去。只比较 scheme 与 host 就会放行它。
- [ ] 目标落在所有前缀之外时，该条目**失败**——绝不是「不带凭证继续」。
- [ ] 离开授权前缀的重定向**失败**；凭证既不跟着跨过去，也不会被剥掉后继续跟随。
- [ ] `GET` 只返回脱敏元数据——`has_secret`、`header_name`、`allowed_prefixes`、
      `updated_at`——任何路径下都不返回值。
- [ ] 保留类型 `oss_aksk` 与 `basic` 在写入时被拒绝，并给出「这是保留类型」的
      消息，让判别字段从第一天起就是真的。
- [ ] 该值不出现在任何日志、任何错误消息、任何 apply 报告里；只有名字会出现。
- [ ] 认证失败（401/403）报告为*「凭证 `<name>` 被拒绝」*——具名，且与通用拉取
      错误区分。过期由 owner 自管（§4, X1），所以一条读起来像网络问题的轮换提醒
      是真实的运维故障。
- [ ] 轮换就是对同一个名字重新 `PUT`，且不触发 apply。

**规模。**中等。

#### W4 — apply 引擎、apply 记录，以及免取源物化器 · #1472

**Owner.** `totalfrank` · 0.75 天 · 第 2 天 · 设计（§7）


**目标。**一份 manifest 可以按需被应用，把 bot 的实体向文档收敛，并给出一份
「发生了什么」的报告——在三个不需要拉取的类目上先跑通。

**范围内。**

- apply 编排器：bot 级串行化、类目顺序、逐条结果分类、`on_fetch_failure` 策略
  处理。
- **apply 记录**——manifest 模块自己关于「上次 apply 物化了什么」的记录（§2.3），

  「摘标记」；§3.2 改为覆盖之后那个用途消失了。）
- apply 报告的存储与 `GET .../config-manifest/last-apply`，形状按设计 §7。

- 第一期两个免取源类目的物化器：`mcp`（注册表引用 → 既有的 per-bot 启用服务
  `DirectActivationService`，收敛「已启用 server 集合」这个 §3.2 定义的区域）与
  `script`（→ `BotStartupScriptService`）。

  `ac_user_mcp_config`（键 `(user_id, server_code)`），写入路径调用
  `sync_mcp_detail_to_all_bots` **扇出到该 owner 的所有 bot**；它装的又正是
  `api_key` / `custom_headers`，design §4.5 明令不得进 manifest。账号级配置继续
  走既有的 `/openapi/v1/bots/mcp/servers/{server_code}/config`。

**范围外。**拉取。生命周期触发（W8）——本项唯一的入口是显式 apply。
**`engine_config` 按 X2/T3 的决定排除在第一期之外**（§4）；它回来时，其物化器是
经 `EngineConfigService.write_bot_config` 的顶层键合并，归属本项。

**依赖。**W1 与 W10（apply 调用穿过的那条缝）。**W11 不再是硬依赖**——被撤销的
三方 diff 需要版本 N 的物化文件清单来区分「声明里删掉了」与「bot 自己建的」；
类目覆盖不需要这个区分。W11 仍然是 §2.8 审计与 `keep_last` 所必需的，但它不卡

**阻塞于。**—。D2 已解决（§3.2），它的规则正是本项要实现的。X2/T3 把
`engine_config` 整个移出第一期，所以它在 teclaw 上的行为不再是本项的问题。

**验收标准。**

- [ ] **收敛性：**对同一份未变的文档再 apply 一次，每一条都报告 `unchanged`，
      且不执行任何写入。
- [ ] 逐条结果分类为 `created` / `updated` / `unchanged` / `skipped` / `failed`，
      apply 结果相应为 `SUCCEEDED` / `PARTIAL` / `FAILED`。`skipped` 现在意为
      「因为所在类目被中止而没写」（§3.2 all-or-nothing）——它不再来自作者要求的
      `on_fetch_failure: skip`，因为那个取值已经没有了。
- [ ] **apply 是两阶段的，不是一趟有序执行。**编排器的形状必须承载这一点，否则
      W13 只能绕开它：
      - **A 阶段 —— 不需要容器。**只有 `script`。它是对
        `ac_bot_startup_script` 的一次普通写入（§2.12），而在创建路径上它必须
        落在 `_build_create_bot_payload` 拼装启动命令**之前**，否则首启根本不带
        脚本。

      在已经运行的 bot 上，两个阶段紧挨着执行，这个切分不可见。在创建路径上，它们

      —— 见 §2.12。
- [ ] 针对同一个 bot 的两次 apply 串行；锁沿用既有的 `BotRestartLockRepository`
      模式，而不是新机制。
- [ ] §2.7 成立：apply 不按「是否首启」分支，逐条单独记录下发结果，且不往 bot
      记录写任何东西。汇总结果由逐条推导得出，绝不作为决策输入。
- [ ] apply 通过调用 W10 的缝执行与公开 API 同样的校验与鉴权——而不是手写第二份
      检查。
- [ ] `engine_ext` 在任何路径上都不可从 manifest 到达。（`engine_config` 类目本身
      不在第一期；它回来时按顶层键合并。）
- [ ] `mcp` 拒绝租户没有权限的 `server_code`，复用既有权限检查而不是拷贝一份。
- [ ] 类目存在但**为空**（`skills: []`）是「集合为空」的声明：所有 skill 被
      **移除**（§3.2）。这与早先把 `[]` 读作「停止管理但不删除」的规则相反。
- [ ] **删除 manifest（`DELETE`）什么都不删。**这是从 §3.2 推出来的，而不是另一
      条规则：`[]` 是声明（「集合为空」），缺席不是声明（「无意见，别碰」）。
      删掉文档等于没有任何被声明的类目，所以什么都不被覆盖。两个看起来相反的行为，
      其实是同一条规则。
- [ ] 中途失败后记录保持一致：不会记录任何实际没有物化的东西。
- [ ] `dry_run` 不执行任何形式的写入，包括写报告存储。
- [ ] apply 报告只记录凭证**名称**，永不记录值。

**备注。**`script` 放进本项是有意的：它的目标服务已经存在且已加固，这让它成为
「通过既有服务物化」这条路在引入任何拉取之前最便宜的端到端证明。

**规模。**大。与 W1 并列的另一个大件。

**验收标准。**

- [ ] 文件条目通过既有资源服务在一个 workspace 相对的逻辑 `path` 上物化；物理
      落点仍由引擎决定。
- [ ] 目录条目的**收敛单位是整个归档**，但「未变」是拿**已下发的东西**去判定的，
      **不是只看源**。归档没变但树漂移了，这次写入照样要做：如果上次 apply 之后
      有人在 `path` 下加了或改了文件，仅凭源内容就报 `unchanged` 会跳过所有写入、
      把漂移原样留着——这正好击穿下面那条所有权规则，也击穿 §3.2「让 manifest 生效
      就是把声明的那片区域覆盖成声明的样子」这个保证。**这件事没有便宜的绕法，而
      本条 bullet 的上一版声称有。**W11 的记录里只有我们*打算*下发的字节；漂移按
      定义长在 bot 上，所以任何只在我们自己记录里做的比较都看不见它——同尺寸的改动
      尤其看不见。两个诚实的选项：

      1. **每次 apply 都整体替换**（v1 推荐）——下面那条原子的「解包 + 改名」每次都
         跑，§3.2 的保证由构造成立。不读 bot，也就没有漂移这个问题。
      2. **读并哈希已部署的子树**（经 `DeviceFileSystem`），与 W11 的记录比较，有
         差异就替换。只有当读这棵树比重写它更便宜时，它才真的是优化。

      除非 apply 的开销真的成了可测量的问题，否则取 (1)；成了问题再走 (2)。
      **不可用的是「只凭源未变就跳过」。**
- [ ] 目录级所有权：内容变化时，`path` 之下那棵树整体替换——此前存在而新归档里
      没有的文件被移除，包括手工添加的。`path` 之外的一切不碰。
- [ ] **替换只能原子到传输层允许的程度，而传输层做不了改名。**
      `core/devices/services/device_filesystem.py` 暴露的是 `read_file`、
      `write_file`、`delete_file`、`delete_tree`、`list_dir`、`exists`——
      **整个 `core/devices/` 里没有 rename / move / swap**，BaaS 与 teclaw 两条传输
      也都不提供。所以「解包到临时位置，然后改名」**今天根本实现不了**，而本条 bullet
      的上一版还是这么承诺的。

      在既有契约下能做到的是 `delete_tree` 再逐文件写入——这中间有一个真实的窗口，
      `path` 下的树是缺失或半写的，中途失败就会一直停在那个状态。两个选项，本项必须
      选一个，而不是继承那个承诺：

      1. **收窄保证**（v1 推荐）——把这个窗口写进文档，并在下发中途停止时把该条目
         记为 `failed`，让 apply 报告说清楚这棵树处于未知状态。这本来就是 §3.2 已经
         定下的层次：all-or-nothing 的范围是**物化**，v1 明确不回滚类目内中途的下发
         失败。那个改名承诺不只跟传输层矛盾，也跟这条决策矛盾。
      2. **给设备契约加一个原子子树替换**——新增一个 `DeviceFileSystem` 操作，并在
         每条引擎传输上实现。这是实打实的跨团队工作量，也是一个真正的原子性保证
         应有的代价。

      无论选哪个，**平台侧**解包到临时位置这件事都保留：它能保证一次失败的拉取或一个
      坏归档永远到不了 bot，这是我们自己就能守住的那一半。
- [ ] 嵌套禁令在 `PUT` 时强制（W1），并在 apply 时复查。
- [ ] 在 teclaw 上，物化出的树逐文件展开为 `ResourceRef` 条目；
      `BotConfigArtifact` 不变，v1 **不**采用 T5 的子树优化。
- [ ] schema §5 中针对归档的限额生效：单个归档大小、解包后大小、成员数。

**规模。**中偏大。

依赖：我们的 git 宿主不提供只读的 **API** scope，只提供只读的 **Git-over-HTTP**
scope，所以走 API 路线就得在数据库里放一个「对一切可读写」的凭证。选择 git 传输
这条路，让最终的契约**更**可移植而不是更不可移植——§4 里那些具体信息是某一个部署
的实例，不是本项的要求。

**验收标准。**

- [ ] `sources` 声明命名源；`from` 引用其一；`from` 与内联 `source` 互斥；未被
      引用的源在 `PUT` 响应里是警告而不是错误。
- [ ] `auth` 声明在源上，不在使用 `from` 的条目上。
- [ ] **原子的是「解析」，不是「下发」。**改一个 `ref`，在一次 apply 内把所有
      引用该源的条目**解析到同一个 commit**，且该 SHA 只拉取一次、全程复用。这就是
      承诺本身，而且它刻意比「不存在升级到一半的状态」更窄：§2.7 要求一个类目的
      失败绝不牵连另一个，所以 `identity` 可能落地而 `skills` 中止，导致不同类目
      停在不同版本。跨类目的下发原子性需要 apply 级的暂存与回滚，v1 没有。
      **逐类目的 all-or-nothing（§3.2）才是下发真正原子的那一层。**
- [ ] git `ref` 在每个 apply 点被解析为 commit SHA；apply 报告同时记录声明的
      `ref` 与解析出的 SHA。
- [ ] 同一个 `{git, ref}` 每次 apply 只拉取**一次**，并在所有引用它的条目间复用。
- [ ] git 内容经 HTTPS 以**浅层单 ref** fetch 获取（取代设计 §10.5 的归档 API
      方案——见 §4, X1），复用 W2 的受防护传输及其大小、超时、并发上限。
- [ ] 拉取是只读的，绝不执行仓库自带的 hook 或 filter。
- [ ] **W2 的包含性防护同样适用于 git 内容。**git 源不经过解包，所以由构造就绕开了
      归档成员的那套检查——但仓库里能装的正是同一批危险物：形如 `payload -> /etc`
      的符号链接、gitlink/submodule 条目、设备/特殊条目。遍历目标子树的物化器会因此
      读到 checkout 之外的文件，或者把一个逃逸链接下发给 bot。**在 git 内容进入
      W11 的存储或任何下发服务之前**，套用同样的规范化包含性检查与特殊条目拒绝。
- [ ] **受约束的是解开后的 checkout，不只是传输。**W2 的流式字节上限管的是线上的
      字节数；一个很小的 pack 可以展开成一棵巨大的树，而 `--depth` 约束的是**历史**，
      不是选中 commit 的 blob 或 tree。要对**解开后的总字节数、对象/文件个数、单个
      文件大小**都设上限，并在失败时**清理临时 checkout** —— 否则一个已认证的
      manifest 作者就能把后端磁盘撑爆。
- [ ] 被重新指向的 tag 在下一次 apply 收敛到新内容——移动一个 tag 就是改变这份
      声明的含义。
- [ ] 来自 git 源的目录条目不需要 `unpack` 或 `strip_components`。
- [ ] **源的 schema 带上移动 ref 的 `mode`**（§3.2）：`strict` 或 `non_strict`，
      声明在源上——因为持有 `ref` 的是它——缺省 `non_strict`。写在 SHA 形式的 ref 上
      是「接受但无效」：SHA 动不了，两个分支都触发不了。
- [ ] **严格模式在 ref 解析的地方被执行**：解析出的 SHA 与上次 apply 记录的不同时，
      该条目**失败**，bot 继续跑它现在跑的。非严格则应用新内容，并在 apply 报告里
      给该条目记一条告警，写明前后两个 SHA——报告是它唯一的出口，因为第一期是
      pull-only（§2.7）。W8 那条「D2 关于移动 ref 的决定在这里被执行」讲的是
      **apply 时的执行**，它依赖这个字段先存在。

**规模。**中偏大。

每一处 `bcs-cli` 引用都是 singlebox 编排，而且没有任何下发路径处理可执行位。本项
仍按业务优先级推迟，不是因为缺答案。

**类目已摊平：一个条目 = 一个命令 = 一个文件。**`entrypoints` 从 manifest schema
（§3.7）与 artifact 契约里一并删除。一个条目就命名一个可执行文件；压缩包只是**传输
形态**，由 `subpath` 从中选出那一个文件，**包内其余文件不下发**。artifact 条目是
`{name, store, path → 那个文件, md5, version}`，暴露出来的命令名就是 `name`。

**这是把「包内私有可执行文件」这个问题解决掉，而不是推迟，而代价要写明。**被撤销
的那个形状——一个目录加一份 entrypoints 清单——没有任何办法表达「这个文件必须可
执行，但不要变成一条命令」，于是一个 `bin/tk` 去 exec 包内 `libexec/helper` 的 CLI
包会在运行时以 `EACCES` 失败，且从 manifest 层面无法修复。当时的候选答案是加一个
不上 PATH 的 `executables` 列表，或让 POSIX mode 一路穿过平台的拉取/解包/存储链路
（今天没有任何一环这么做，而且重新打开「是否信任归档自带权限位」）。摊平直接删掉了
产生这个问题的形状：**v1 交付自包含的单个可执行文件**，所以需要包内辅助程序或同包
`lib/` 的工具不在范围内，必须打成静态二进制。这一点要写进 schema、用户手册和 teclaw
契约——**限制写出来是范围决策，同一个限制不写出来就是第一个打包 wrapper 的用户提的
缺陷单**。

摊平同时删掉、且不该被无意重新引入的：那一整套**只为约束 entrypoint 取值**而存在的
包含性规则（包内路径穿越、符号链接逃逸、跨工具的 basename 撞名）。唯一性现在是
`name` 的唯一性（W1）。

**验收标准（草案）。****内容相关的 `subpath` 校验在这里，不在 W1** —— 归档解包
之后，选中的 `subpath` 必须存在、必须是**普通文件**、且在符号链接解析之后仍然落在
解包树之内。W1 只拒绝语法那一半（绝对路径、`..` 段、`name` 重名），因为它不做拉取，
`PUT` 时没有目录树可查。然后：平台对最终选中的那个文件计算 **`md5`** 并写进 artifact
条目，让引擎能校验它从 store 取回来的字节（这是我们自己算的哈希，绝不是 store 的
ETag——分片上传的 ETag 不等于内容 MD5）。然后：目标是 `linux/amd64`，每个工具一个
URL（§4, X3）；同时
`${BOT_ARCH}` 在 W1 的白名单里解析为 `amd64`，并校验拉取到的二进制的 ELF 头——
于是架构不匹配会在 apply 报告里失败，而不是变成模型在任务中途撞上的
`exec format error`。然后：`digest` 强制，而**收敛判据是整份与下发相关的声明——
`digest` **与** `subpath` 一起**，不是只看 digest。同一个包、只把
`subpath` 从 `bin/old` 改成 `bin/new`，是一次真实变更：只按 digest 判会报
`unchanged`、什么都不下发，于是旧文件继续挂着，而声明写的是新的那个；
只支持静态二进制与「归档 + `subpath`」
两种形态；一个由平台定义的、在 agent 进程 PATH 上的逻辑工具目录，用户永远看不到
物理路径；在按引擎区分的**默认技能集**里放一个工具用法 skill（`SkillSetService`
已经有这个机制），让模型知道有哪些工具、怎么调用；以及给 teclaw 的 artifact
表达，容器内的放置归他们。

**显式目标：`bcs-cli` 成为它的第一个消费者**，取代那个手工放置它的 singlebox
脚本。否则这个特性会与已经存在的那一套 CLI 机制并存，我们要维护两份——而把它收
进来，还能在任何客户使用之前给这个特性一个真实的内部测试用例。

**规模。**中等。
