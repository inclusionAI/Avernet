A2A 权限传递与授权申请讲解稿

把“好友申请 / 角色申请”和“A2A 消息时鉴权”拆成几张小图讲清楚，避免一张大图承载所有细节。
日期：2026-08-05 类型：会议 briefing HTML 来源：a2a-permission-and-grant-workflow.md 重点：申请流程 + A2A 鉴权流程

0. 先讲一句话

申请流程解决“EdgeGrant 从哪里来”；A2A 鉴权流程解决“已批准的 EdgeGrant 在消息时怎么被安全使用”。
1. 概念拆分ConnectRequest、RoleGrantRequest、EdgeGrant 不是同一个东西。
2. 申请流程加好友第一步；第二步可选申请角色；最终生成 approved EdgeGrant。
3. A2A 鉴权流程BCS 注入瘦引用；Bot 本地用 version-pinned cache 鉴权。
4. 异常与更新cache miss 就拉取；拉不到 deny；role 更新不影响旧 edge。

1. 三个对象先分清楚

给别人讲时先不要进入缓存、digest、版本钉。先把三个对象讲清楚：申请单不是授权事实，真正用于 A2A 鉴权的是 approved EdgeGrant。

ConnectRequest

语义：A 想和 B 建立基础关系。

审批后：通常生成 A→B role=default 的基础 EdgeGrant。

RoleGrantRequest

语义：A 想额外获得 B 的某个角色能力。

审批后：生成对应 role 的 version-pinned EdgeGrant。

EdgeGrant

语义：授权事实，不是申请单。

A2A：只有 approved EdgeGrant 才能进入 active_grants。

2. 申请流程 A：只加好友，不申请角色

这是最简单路径。用户只想先建立基础关系，第二步跳过角色申请。

sequenceDiagram
  participant U as User A
  participant FE as Frontend
  participant BCS as BCS
  participant O as Bot B Owner
  participant DB as BCS DB

  U->>FE: 点击 Connect Bot B
  FE->>U: Step 1 填写好友申请
  U->>FE: 提交 ConnectRequest
  FE->>BCS: Create ConnectRequest(A, B)
  BCS->>DB: 持久化 ConnectRequest(status=pending)
  BCS->>O: 通知 owner 审批
  O->>BCS: Approve Connect
  BCS->>DB: ConnectRequest(status=approved)
  BCS->>DB: 创建 EdgeGrant A→B role=default, status=approved
讲解重点：只加好友也会产生授权边，但这条边通常只是 default 基础角色，不代表拿到所有能力。

3. 申请流程 B：加好友后，可选申请角色

mentor 定下来的产品形态：加好友第一步；第二步出现角色申请，可选，可以跳过。

sequenceDiagram
  participant U as User A
  participant FE as Frontend
  participant BCS as BCS
  participant O as Bot B Owner
  participant DB as BCS DB

  U->>FE: 点击 Connect Bot B
  FE->>U: Step 1 好友申请
  U->>FE: 填写申请说明
  FE->>U: Step 2 展示可申请角色列表

  alt 用户跳过角色申请
    U->>FE: 跳过，只申请好友
    FE->>BCS: Create ConnectRequest(A, B)
  else 用户选择角色
    U->>FE: 勾选 reader / writer 等角色
    FE->>BCS: Create ConnectRequest(A, B)
    FE->>BCS: Create RoleGrantRequests(role_def_ids)
  end

  BCS->>DB: 持久化申请单
  BCS->>O: 合并展示待审批事项
  O->>BCS: 审批 Connect / Role Requests
  BCS->>DB: 通过项生成 approved EdgeGrant

前端可以是一个连续流程

用户感觉上是在一次 Connect 流程里完成好友申请和角色申请，第二步可选。

后端仍然拆成不同申请单

ConnectRequest 和 RoleGrantRequest 分开持久化；审批通过后才生成 EdgeGrant。

4. 申请流程 C：已连接后再申请角色

用户已经是好友后，不需要重新 Connect。直接在 Bot Profile 里申请更多角色。

sequenceDiagram
  participant U as User A
  participant FE as Frontend
  participant BCS as BCS
  participant O as Bot B Owner
  participant DB as BCS DB

  U->>FE: 打开 Bot B Profile
  FE->>BCS: Query Bot B roles
  BCS->>DB: Load role_defs of B
  BCS-->>FE: 返回角色列表和当前拥有状态
  U->>FE: 申请 writer 角色
  FE->>BCS: Create RoleGrantRequest(role_writer@latest)
  BCS->>O: 按 approver_policy 进入审批
  O->>BCS: Approve
  BCS->>DB: Create/Update EdgeGrant A→B role=writer, role_def_version pinned
讲解重点：Connect 是建立关系；Role Request 是增加能力。已连接后新增能力只走 Role Request。

申请单状态 approved ≠ A2A 直接放行 EdgeGrant 也不是包在 A 的消息里发给 B A sends message to B 只是触发运行时鉴权： BCS 查询 approved EdgeGrants → 过滤 status / env / expires_at / originator_policy → 生成 active_grant refs → 再下发给 B 本地鉴权

6. A2A 鉴权流程 A：BCS 只注入 active grant refs

这张图讲“消息里传什么”。关键是：A2A 不传完整 rules，只传 BCS 算出来的瘦引用。

sequenceDiagram
  participant A as Caller A
  participant BCS as BCS Router/Authz
  participant DB as BCS DB
  participant B as Target Bot B

  A->>BCS: Send A2A message to B
  BCS->>BCS: Resolve caller / target / task_id / originator
  BCS->>DB: Query approved A→B edge grants
  DB-->>BCS: Edge grants
  BCS->>BCS: Filter env / status / expires_at / originator_policy
  BCS->>BCS: Build active_grant refs
  BCS->>B: Forward message + AuthzContext(active_grant_refs)

传瘦引用

active_grant_ref = { edge_id, edge_version, edge_digest, role_def_id, role_def_version, platform_guard_version }

不传完整权限

  • 不传完整 role rules
  • 不传完整 edge extra_rules
  • 不信 caller 自声明权限
  • 不把 B 的完整权限集暴露进消息

7. A2A 鉴权流程 B：Bot 本地如何拼出鉴权集

这张图讲“B 收到 refs 后怎么鉴权”。B 用本地 version-pinned cache 拼出 permission_set；缺缓存就拉 BCS，拉不到就拒绝。

8. A2A 鉴权流程 C：缓存 miss / 版本不匹配怎么办

这张图专门讲异常路径。安全闭环不是靠 BCS 主动下发，而是靠按需拉取；拉取失败就 deny。

flowchart TD
  Ref["A2A active_grant_ref"]
  Cache{"本地 cache 命中且版本匹配?"}
  Digest{"digest / 字段校验通过?"}
  Pull["Pull version-pinned snapshot from BCS"]
  PullOk{"拉取成功且校验通过?"}
  Build["Build permission_set"]
  Deny["Deny"]

  Ref --> Cache
  Cache -- Yes --> Digest
  Cache -- No --> Pull
  Digest -- Yes --> Build
  Digest -- No --> Pull
  Pull --> PullOk
  PullOk -- Yes --> Build
  PullOk -- No --> Deny

  classDef ok fill:#e9fbef,stroke:#15803d,stroke-width:2px,color:#14532d
  classDef bad fill:#fff0f0,stroke:#c53030,stroke-width:2px,color:#7f1d1d
  classDef work fill:#eaf1ff,stroke:#2563eb,stroke-width:2px,color:#1e3a8a
  class Build ok
  class Deny bad
  class Ref,Cache,Digest,Pull,PullOk work

拉取是安全闭环

Bot 本地缺少 edge_grant@version、role_def@version 或 platform_guard@version 时，向 BCS 拉取钉住版本。

下发只是性能优化

WebSocket/control channel 可以做预热和失效通知，但通知失败不会越权；下一次 miss 会拉取，拉不到就 deny。

9. 版本钉：owner 改 role 不影响旧 edge

这张图专门讲之前最容易误解的一点：旧 edge 不会自动套用 latest role。

  E13["edge_123@13\npins role_writer@8"]

讲解重点：role 更新只产生新 role_def version；旧 edge 继续钉旧版本。只有显式 reapply / upgrade 后，才产生新的 edge_version。

10. 讲解时建议按这个顺序

顺序讲什么一句话
1概念拆分申请单不是授权事实；approved EdgeGrant 才是事实。
2申请流程加好友第一步，第二步可选申请角色。
3申请到 A2A 的交接审批通过生成 EdgeGrant，A2A 只消费 EdgeGrant。
4A2A 消息里传什么BCS 只注入 active grant refs，不传完整权限。
5Bot 本地怎么鉴权用 edge_grant@version + role_def@version + platform_guard@version 拼权限集。
6异常和更新缺缓存就拉，拉不到 deny；旧 edge 不自动套 latest role。
最终结论：产品上是两步申请；安全运行时是 BCS 算 refs、Bot 本地按版本钉鉴权。两部分通过 approved EdgeGrant 衔接。
