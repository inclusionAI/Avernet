# 工作流修复：审阅、部署与效果验证

日期：2026-10-14。状态：用户已确认整体方案，正在实施。

> 历史方案：2026-10-15 起，以 [精简产品方案与实施交接](2026-10-15-workflow-optimization-product.md) 为当前方向。本文的 Bot 发布主流程、独立确认候选和手动确认效果要求已被取代；精确候选、安全校验及恢复要求保留。本文“现状”仅描述编写时快照，不代表当前代码或部署。

实施计划：[Workflow Repair release flow](../plans/2026-10-14-workflow-repair-release-flow.md)。

## 目标与验收口径

用户能在同一修复任务中看清真实文件改动，确认明确的候选，显式部署该候选，并查看与此次部署绑定的真实运行效果。每一步都有主操作、前置条件、结果和恢复入口。生成成功、确认成功、部署成功、修复有效是四个不同事实。

不会代用户执行线上部署，不将浏览器提供的 YAML/commit 当成可信发布源，不允许从审阅界面悄悄部署最新版草稿。整条动线完成前，不以局部 UI 改动宣称完成。

## 已核对的现状

- Avernet 最新 dev 的 `RepairCapabilities.publication` 仍固定为 false，RepairWorkbenchService 没有确认、部署、验证方法。
- `RepairTaskPanel.tsx` 并排渲染 before/after 全文，没有变更行定位；OCB Git adapter 目前仅用 Git diff 读取变更文件名，再读取两份全文。
- 修复版本已有 review、publishing、published 等阶段，处理项已有 awaiting_verification、verified、ineffective 状态，但没有完整服务动线连接它们。
- ClawMind `deployLatestSnapshot` 从 `saved/<workflowId>` 获取最新保存快照，再经 `handleDeploy` 发布。它不等同于部署当前审阅的 repair candidate commit。
- 运行记录已有 workflow_version 和 workflow_deploy_number，可用于准确分组。未知部署编号的历史运行不能混入效果结论。
- 工作区存在之前“缺少部署基线时提示先部署”的未提交改动，本次实现必须隔离，不能夹带或覆盖。

## 用户动线

生成候选 → 审阅改动 → 确认候选 → 部署候选 → 收集新版本运行 → 确认效果。

页面顶部展示当前步骤及候选版本；底部始终可见当前步骤的操作栏，不把下一步放在长页面底部。一个状态只突出一个主操作。

| 状态 | 主操作 | 次操作与说明 |
| --- | --- | --- |
| 待审阅 | 确认此候选 | 要求修改；查看检查与未覆盖风险 |
| 已确认、未部署 | 部署此候选 | 撤销确认；显示确认版本、目标 Bot/环境及影响范围 |
| 部署处理中 | 查看部署进度 | 禁止重复派发，不显示假成功 |
| 提交结果不确定 | 核对部署状态 | 不盲目再部署，不丢失请求编号 |
| 部署失败 | 重试部署 | 保留候选和失败阶段，不要求取消任务重建 |
| 已部署、待验证 | 查看效果验证 | 显示部署编号、版本、时间和受影响范围 |
| 样本不足 | 刷新验证数据 | 显示已收集样本，继续观察；不会关闭问题 |
| 有效／无效 | 查看验证结论 | 有效关闭对应处理项；无效可反馈生成下一轮 |

历史候选可审阅，但默认不可部署。部署目标必须来自已有工作流授权和真实发布目标，展示后由有发布权限的用户确认，不默认推断另一环境。

## Diff 审阅

- 默认统一逐行 Diff，提供并排切换；行号、删除/新增标记、变更块位置及文件增删统计明确可见。
- 默认每个变更块显示少量上下文，未修改内容折叠，可展开上下文或切换完整文件。打开文件定位第一处变更，提供上一个/下一个变更。
- 并排视图按对应行对齐，单一同步滚动容器；不能再使用两个各自滚动的全文窗口。
- 比较基准明确为“任务冻结基线”或“上一成功候选”，顶部短 SHA 可复制、完整 SHA 可展开。
- 后端从明确的 baseCommit/candidateCommit 生成真实 Git unified diff 与文件统计，分页/按文件读取变更块。前端不对截断的文件全文猜测完整改动。
- 超大、二进制、读取失败与截断分开显示。未读到完整差异不能伪装为无变更；需完整审阅的文件未可用时阻止确认，并提供重试或完整内容读取方式。
- 涉及 Pack 脚本、资源等所有变更文件都在审阅范围内，不能只展示 workflow YAML。

## 确认候选

新增持久化审阅记录，不把“已确认”等同于“已部署”。记录 taskId、revision、candidateCommit、Pack digest、checks digest、任务基线、确认人和时间、明确接受的未覆盖风险。

确认请求只带任务身份、期望版本与幂等请求编号。候选及检查报告从服务端可信来源读取。静态检查失败、结果未完成、unresolved 冲突、候选读取不完整、无修改均不能作为可部署候选。

确认不触发模型、不写线上 spec、不切换 active deployment。新候选生成后旧确认不会自动套用；多人操作使用 stateVersion/候选摘要校验，冲突展示刷新入口。

## 部署：必须发布已确认的精确候选

部署前再次验证权限、候选可用、审阅记录和检查摘要未变化，以及当前线上 deployNumber/基线仍匹配。基线过期明确阻止，给出“基于当前版本重新生成”的恢复入口，不强行覆盖。

采用以下职责边界，不绕过现有完整 Pack 发布流程：

- Avernet：审阅/发布状态机、幂等请求、DB 持久化、权限检查、审计和 UI。
- OCB：选择并派发至明确授权的运行 Bot，组合内部 Git/凭证/部署能力，持久化并核对派发结果。
- ClawMind：增加精确 reviewed candidate 发布入口，读取服务端确认的 commit，将完整 Pack 导出为隔离候选，复用已有语义校验、发布标签、部署历史和运行时激活流程。禁止重新生成修复内容，禁止发布 saved ref 的另一份内容，禁止覆盖 Bot 未保存的本地编辑。
- TaskGuard：仍只负责生成、Git 候选与检查报告，不承担发布；此动线无需把发布职责塞进 AIS。

发布入口使用结构化协议：任务/确认身份、不可变候选 commit、基线部署编号、目标 Bot、请求/执行身份。内部执行端重新读取可信确认并校验实际操作者，不能仅凭浏览器声明放行。

部署结果必须提供精确 release tag、deployNumber、releaseVersion、实际发布内容摘要和目标。服务端核验这些身份后才显示成功、进入待验证，并将本次实际应用的处理项转入 awaiting_verification。

派发前持久化部署请求。超时或连接中断进入“不确定”，按同一请求身份核对已有发布结果；不自动创建第二次发布。失败和重试保留审计记录。存在外部 Git 成功但 DB/激活失败时，保留各阶段事实并提供恢复，不显示整体部署成功。

## 效果验证

本期基于真实运行观察，不自动发起可能有业务副作用的测试运行。

- 对照组只选冻结基线部署编号的运行；实验组只选本次发布部署编号的运行。两组时间窗、样本数及未知身份排除数均可查看。
- 展示成功/失败/超时比例、原问题签名复现数、耗时与 token 消耗，能进入对应运行与证据。
- 部署后无运行、样本不足、目标问题不可判定、指标无法读取分别显示，不用 0% 或“有效”填补缺失数据。
- 用户可按处理项确认“有效”“无效”“继续观察”，附运行证据/理由。系统不因任务完成或部署成功自动关闭原问题。
- 验证结果单独持久化；有效仅关闭已验证的处理项，未覆盖/未应用项继续保留。无效保留当前线上事实并提供下一轮修复入口。
- 回滚复用现有发布历史能力，显示独立确认及结果；不能通过取消修复任务暗中回滚。

## 接口与持久化设计

在既有 repair task 下新增 confirm、revoke-confirmation、deployment、deployment/reconcile、verification 资源，沿用可信 actor 与工作流权限 middleware。目标及效果读取复用现有 Bot、部署历史与运行记录，不创建第二套权威发布历史。

新增审阅记录、部署请求/阶段记录、验证结论三类存储，以现有 repair task/revision 为外键；外部副作用与 DB 使用持久化幂等请求及可恢复的阶段记录协调，而不是宣称跨 Git/运行时存在单一 DB 事务。

capabilities 必须来自实际组合能力和当前权限。缺失时按钮旁显示具体缺少什么，不能只给一个白色不可点按钮。新增契约保持旧生成与重试路径可用，旧任务无审阅记录时回到待审阅，不自动迁移为已确认/已部署。

## 实施与验收

作为一项完整功能交付，内部实现顺序为契约/状态 → 精确部署适配 → 验证数据 → Diff/UI → 全流程验收，不单独交付假下一步按钮。

必须覆盖：

1. 深处变更、增删文件、嵌套代码围栏、长行、无末尾换行、多文件、二进制及截断 Diff。
2. 确认不会部署；部署内容与审阅 commit 完全一致；更新候选使旧确认失效。
3. 未授权、基线过期、检查失败、部分未解决、双击/多人并发、部署超时和部分失败。
4. 失败可恢复，未知结果先核对，同一请求不产生重复发布。
5. 候选脚本和资源一并发布，不只更新 DB YAML；运行时激活实际得到正确 Pack。
6. 验证仅统计目标部署；无样本不判有效；取消不回滚；逐项结论不误关其它问题。
7. 本地真实 Git、数据库、部署端集成测试及浏览器完整点击验收；各受影响包测试、类型检查、Host workspace 边界验证。

最终交付分别报告：实现与测试、PR、合并、宿主部署、运行时上线验收；不把这些状态混为一谈。
