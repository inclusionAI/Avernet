第一部分什么是边权限

1. 一张图说清边权限

边权限不是一张新表、不是一种新机制,它就是 BCS 关系图本身的结构。我们把多 bot 协作的权限关系,画成一张有向图:

  • 点(vertex)只有两种:human、bot。没有第三种点。
  • 有向边(edge)= 一个角色 = 一组权限集合。边 A → B 读作"B 以这条边上的角色运作、为 A 做事"。角色描述的是 B 的姿态(B 用什么权限集干活),不是 A 的管理身份。这个角色就是绑在这条边上的一组 (tool, specifier, allow/deny) 规则。角色不是独立节点,它就是边本身。
  • 同一对 (A,B) 一时刻一条边、一个通道:某角色 / 角色+附带 / 纯自定义权限集。换通道 = 整体替换(非合并),见 §3.2/§4。
  • env 是边键:(from A → to B, env) 唯一,有向图按环境隔离。

2. 点:只有 human 和 bot

图里的点就两类,与 BCS 现有 actor 模型完全一致:

点类型标识说明
humanhuman_{staff_no}人。可以是自己 bot 的 owner,也可以是借用别人 bot 的 caller。
botbot uuidbot。既能被调用(作为边的 to),也能去调用别的 bot(作为边的 from)。
没有"角色节点"。你最初的设计直觉是"边代表角色",我们严格照此:角色就是边,不单独占点。这样图只有两种点,干净;一个角色被多少 caller 共享、能去哪,全画在边上,一目了然。

对齐代码:actor id 见 bcs-domain/src/actor.rs 的 ActorKind{Bot,Human},human 用 human_{staff_no},bot 用 uuid。

3. 边:一条边就是一个角色

3.1 边的两个身份

一条有向边 A → B 同时是两件事,这俩是同一条边:

身份含义承载
关系身份A 和 B 是否有关系(friend / 被owner)边是否存在 + is_creator
权限身份B 凭这条边以什么姿态运作为 A 做、能调哪些 tool绑在边上的 (tool,specifier,allow/deny) 集合
关系身份是门票,权限身份是细度。一条不存在(friend 没有)的边,谈不上权限;一条存在的边,其权限身份回答"B 以这张门票做什么"。friend 管入场,边权限管入场细度。

3.2 边的数据形态:一通道 + role_name 引用 + extra 覆盖

一条边一时刻只挂一个"通道"——某角色 / 角色+附带 / 纯自定义权限集。role_name 只是对角色定义的引用,不把角色 rules 抄进边(角色定义在 bcs_role_defs 另存,见 §6)。边上另挂的 extra_rules 与角色默认 rules 取并集、冲突时 extra 覆盖。

Edge(from A → to B, env) = { edge_id : 自增主键 channel : named_role | role_with_extra | custom ★ 一时刻一个通道, 换通道=整体替换(非合并) role_name : "被owner" | "只读者" | 自定义 | null ★ 对 bcs_role_defs 的引用; channel=custom 时可为 null extra_rules[ ] : 若干 (tool, specifier, allow | deny) ★ 仅 role_with_extra; 与角色默认 rules 取并集, 冲突时 extra 覆盖 如 (Read, ./*, allow) (Edit, /prod/**, deny) custom_rules[ ] : 若干 (tool, specifier, allow|deny) ★ 仅 custom; 不走任何角色, 独立选的一组 // 边的元信息(可选,默认安全) delegation_depth : 0 = 不可再委托给下游; >0 = 可向下传 N 跳 expires_at : 过期时间; null = 永久 grantor : 谁授的这条边 }

3.2.1 求值:通道对应的权限集

对一次 tool call,这条边当前通道求出一个确定的权限集(一个,不是多个合并):

channel = named_role → 权限集 = bcs_role_defs[role_name].rules channel = role_with_extra → 权限集 = bcs_role_defs[role_name].rules ⊕ extra_rules # 冲突 extra 覆盖 channel = custom → 权限集 = custom_rules

这三种通道互斥:边一时刻只走一种。换通道 = 整体替换这条边的权限集(不残留旧 rules),不是把两个权限集合并。

3.2.2 角色 + 附带:唯一允许的叠加(通道内部覆盖)

mentor 稿原写"同 grantor 匿名边自动合并",经讨论判定为错——那等于让 B 一直持有所有被授过的权限合集运作。本稿改为:一时刻一个通道。唯一允许的"叠加"是 role_with_extra 通道里"角色 + 附带"——此时附带的 extra_rules 与角色默认 rules 在同一通道内部取并集,冲突时 extra 覆盖。这不是多权限集合并,而是一个通道的内部覆盖。

# 角色 + 附带(role_with_extra):同一通道内部, extra 冲突覆盖 role 默认 Edge(human_bob → bot2, prod) = { channel : role_with_extra role_name : "只读者" # 引用, 不抄 rules extra_rules: [ (Write, /tmp/**, allow) ] # 只读默认里 Write 是 deny → 这里 extra allow 覆盖 grantor : human_alice } # 求值权限集 = 只读者默认 rules ⊕ extra(Write /tmp→allow 覆盖只读者的 deny) # 对比:换通道(不是合并)——今天 named_role, 明天 want 写活 → 换成 role_with_extra 或 custom # 旧的 named_role 权限集整体失效, 用新通道的权限集, 不是二者并集
为什么删同源合并:A 让 B 办事,B 的权限集就是某一时刻确定的一个。今天走角色 O 通道、改天走角色 P 通道 —— 是换,不是把 O∪P 一直发挥作用。"角色+附带"是给某个通道做临时覆盖(通道内一个权限集),不是两个权限集合并。换通道 = 整体替换,见 §17 改约。

注意 extra_rules / custom_rules 里的元素就是 briefing 的 (tool, specifier, decision) 三元组。一条边一通道 = 一个这种集合(角色定义里那组,或角色+附带的并集,或自定义集)。三元组里 decision 仅二元(allow/deny),贴合 briefing 第一层。

3.3 被owner 边是特例吗?

不是特例。owner 关系天然读作"A 管 B"(A 是管理方),与本图"B 以角色运作、为 A 做事"反着——为统一方向,把它逆转为 被owner 角色:B 被某人拥有、B 以全权运作为 A 做。这样它和 Teacher、只读者同构,都是 B 的姿态。token 简化上 is_creator 标它,图里它和其他角色边同构,只是 rules 是 (* , *, allow)(除了平台守卫)。同一张图、同一套求值器,无特例。

角色边 A → B 读作含义
被ownerB 被 A 拥有、B 以全权运作B 用全权权限集运作;A 是 B 的 owner
TeacherB 以 Teacher 角色运作、为 A 做事B 用 Teacher 权限集运作
只读者B 以只读者权限集运作、为 A 做事B 用只读权限集运作

3.4 角色是这些权限定义的组合:(tool, specifier, decision) 三元组

§3.2 说一条边(角色)的 rules 是"一组 (tool, specifier, decision) 三元组"。那么这三元组究竟长什么样?它从 opencode + claude code 抄底(底座同构,两产品已收敛)。角色不是凭空一个名字,它就是若干三元组的组合——把几条 (tool, specifier, allow/deny) 装进同一条边,这条边就有了角色身份。

三元组格式:(tool, specifier, decision)。decision 三态 allow/ask/deny,但本稿第一层(角色边)只用二元 allow/deny(贴 briefing「第一层无 ask」);ask 归第二层 bot 自身鉴权。所以角色边上的每条 rule 就是 (tool, specifier, allow | deny)。

每个 tool 的 specifier 类型不同(命令 / 路径 / 域名 / 工具名……),通配让组合既能粗(整类)又能细(精确)。下表给出各 tool 的 specifier 类型、危险面、可直接放进角色的示例 rule:

toolspecifier 类型危险面示例 rule(装入角色即一条三元组)
Bash命令模式:*/? 通配;&&/;/| 复合分段,每段子命令独立匹配,任一段 deny → 整条 deny。可按参数限定高 可写/删/部署allow(Bash(git status))、allow(Bash(npm run *))、deny(Bash(rm *))、deny(Bash(git push origin main))
Read路径模式(gitignore 语义:./cwd、~/home、/abs);* 单层、** 递归中 夹带凭证/隐私allow(Read(./docs/**))、deny(Read(./.env))、deny(Read(./**/*.env))

WebFetch域名:domain:<glob>中 出口/外泄allow(WebFetch(domain:github.com))、deny(WebFetch(domain:*.internal.company.com))

角色 = 把若干三元组装进同一条边

"只读者""受限协作者"这些角色名,本质就是上面的三元组组合。举例(与第二部分 §9 Alice 定义的角色一致):

# 角色「只读者」= 这几条三元组的组合 只读者 = [ (Read, ./*, allow), (Grep, ./*, allow), (Edit, *, deny), (Bash, *, deny), ] # 角色「受限协作者」= 另一组组合 受限协作者 = [ (Bash, git *, allow), (Read, ./src/**, allow), (Bash, rm *, deny), # 禁删 (Bash, curl *, deny), # 禁外联 (Edit, /prod/**, deny), # 禁改生产 ]

把上面任一组绑到一条 A→B 边上,这条边就拥有该角色;换通道(§4)就是同一对点随时间换不同的组合。裸名写法如 allow(Bash)=整个 Bash 工具放行,deny(Bash)=把 Bash 从模型上下文移出(更彻底)——这是三元组的边界用法。

平台守卫不是角色边上的三元组。表里的 deny(Bash(rm -rf /)) 在本方案里属于平台守卫层(§5、§16),不是 owner 可配可撤的角色 rule——它最高优先级、不可取消,绕开通道权限集。通道里写的 deny(Bash(rm *)) 才是通道 rule(可被换通道或 extra 覆盖)。
一句话:(tool, specifier, decision) 三元组是权限的最小积木,角色(边)是积木的组合。specifier 的通配/路径/域名/命令模式让组合既能锁整类、又能精确到一条命令;装多少条、装哪些,就决定了这个角色能做什么。

5. 求值:一通道权限集 + 平台守卫兜底

同一对 (A,B) 一时刻只有一条边、一个通道——通道求出一个确定的权限集(§3.2.1,唯一一个,不是多个合并)。求值对这个权限集判。

5.1 三档优先级

对一次 tool call (caller A → bot B, tool, args),按以下顺序判: ① 平台守卫(最高,不可被任何边覆盖) 命中守卫 deny(如 Bash(rm -rf /)) → deny · 熔断 命中守卫 ask(external_directory 等) → 转 bot 第二层审批(本稿不展开) ② A→B 这条边的当前通道权限集(§3.2.1 求出的那一个) 命中 allow → allow 命中 deny → deny 未命中 → 走 ③ ③ bot default 集(owner 配的对任何 caller 默认成立) 命中 allow → allow ; 命中 deny → deny 未命中 → deny(零信任)

5.2 通道权限集命中表

第②档:这条边当前通道权限集对本次 (tool,specifier) 的产出:

通道权限集命中情况终局直觉
命中 allowallow当前通道放行
命中 denydeny当前通道拒绝
未命中落 default → 未命中 deny当前通道不表态,走默认,默认从严
与 mentor 稿差异:mentor 稿是"多边 allow 优先"(同一对点多条边、任一 allow 即放行)。本稿改为"一时刻一通道"——同一对 (A,B) 一时刻只有一个权限集在用,不再"多边合成"。"角色+附带"的覆盖是一通道内部(extra 覆盖 role 默认),不是多边并集。

5.3 两个必须说清的边界

① 想换结果就换通道,不是加边

当前通道权限集 deny 了 Edit(/prod/**),想让 B 能改生产——不是再挂一条 allow 边,而是换通道(换成含 allow(Edit(/prod/**)) 的角色/custom,或 role_with_extra 用 extra 覆盖)。换通道 = 整体替换,旧 rules 不残留。

② 绝对禁止靠平台守卫

普通通道里的 deny(如 deny(Bash(rm -rf /)))是可被换通道绕开的普通 rule。真正"谁都不能做"的兜底交给平台守卫层——最高优先级、不可取消,绕开通道。安全否决权回到该在的地方。

为什么一通道(而非 mentor 多边 allow 优先):协作场景里 A 让 B 办事,B 的权限集就是某一时刻确定的一个。今天走角色 O、改天走角色 P —— 是换通道,不是把 O∪P 一直发挥作用。"角色+附带"是给某通道临时覆盖(通道内一个权限集),不是多权限集合并。换通道 = 整体替换,见 §17 改约。

7. 第一部分小结

边权限 = 点-边图:
① 点只有 human / bot;边就是角色,角色=一组权限集合。
② 一条边既有关系身份(门票)又有权限身份(细度);friend 管入场,边权限管入场细度。
③ 同一对点一时刻一条边一个通道(某角色/角色+附带/自定义集),换通道=整体替换;绝对禁止交给平台守卫层兜底。

12. 环节四:Bob 发起一次调用(图上走 allow/deny)

Bob 让 bot2 "看下 src/main.rs 的鉴权逻辑"。bot2 的 LLM 解析出一个 Read tool call。求值走三档优先级:

若 Bob 改口"顺便把鉴权那段删了重写",触发 Edit:

✓ Read 放行

守卫未命中 → 角色边"只读者" Read(./*) allow 命中 → allow。

✗ Edit 被哪一档挡?

守卫未命中 → 角色边"只读者" Edit(*) deny。Bob→bot2 只这一条边,无其它边给 allow → 终局 deny,在 bot 端细判即拒。

16. 环节八:平台守卫兜底(通道权限集之上的安全闸)

通道权限集里的 deny(如 deny(Bash(rm -rf /)))是可被换通道绕开的普通 rule。若通道换成含 allow(Bash) 的,而 Bob 想跑 rm -rf /——靠通道规则拦不住。这时平台守卫出手:

# 守卫层(最高优先级,先于角色边判) Bash(rm -rf /) → deny 熔断(删根/删家目录,任何边都盖不掉) Bash(rm -rf ~) → deny 熔断 external_directory → 转审批(触工作目录外路径) doom_loop → deny(重复N次)
守卫不是角色边,是独立一层,不归 owner 配、不可取消、最高优先级。它先判,过了才进通道权限集求值。这样把"绝对禁止"(守卫)和"角色放行"(边)分层,各自职责清晰:守卫保安全底线,边做协作灵活。

18. 委托:caller 把自己的部分权限向下传(图上加下游边)

bot2 若想在协作链里把自己部分权限下传给下游 bot3,用边的 delegation_depth。铁律——只能收紧,不可升级(下游 ⊆ 上游):

// 委托时下游边 = 收紧后的上游边 new_allow = 下游_req.allow & 上游.allow // 只能是子集 new_deny = 下游_req.deny | 上游.deny // 只能更严 new_depth = 上游.delegation_depth - 1 // 深度衰减
逐跳 AND + 委托收紧,合力给出一个界:链上任意 bot 能做的事,恒 ⊆ 发起 caller 在第一跳被允许做的事。无需回溯发起者即可得到这个界——这正是 briefing 想要、旧方案做不到的性质。

19. 第二部分小结:图跑了一整圈

从建边到撤销,全程都在图上看边:
① 环节一 被owner 边 + 角色定义(图初态)
② 环节二 friend 建关系边(拿到入场券,无角色)
③ 环节三 给边绑角色(关系边长出权限身份 + 位图回写)
④ 环节四 一次调用三档判(守卫→角色边→default)
⑤ 环节五 role_with_extra(角色+附带,extra 覆盖,换通道非加边)
⑥ 环节六 长链逐跳看边 AND
⑦ 环节七 回环每跳看自己的边,不回溯发起者 → 死结①消除
⑧ 环节八 平台守卫兜底(通道之上的安全闸)
⑨ 环节九 撤销/改约 = 删边/换边,friend 保留
⑩ 委托 只能收紧不可升级 → 全局有界

一句话收尾:把权限画成点-边图——点只有 human/bot,边就是角色、是一组权限集合。一时刻一通道换则替换、不让旧权限残留,平台守卫保安全底线,长链逐跳看边不回溯发起者让回环自然跑通。图是 BCS 现成的关系图,边上的位图已预埋,只待点亮。
