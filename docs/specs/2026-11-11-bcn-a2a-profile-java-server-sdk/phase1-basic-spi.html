BCN A2A Java SDK 第一期：基础版 SPI 实现文档

第一期只交付最简单的一种接入：Agent 实现一个方法，收到一条用户消息、返回一条完整回复。本文是这一期的实现规格，开发按本文实现，测试按本文验收。

状态 实现文档 v0.1日期 2026-11-13上位文档 《BCN A2A Profile 与 Java Server SDK 详细设计》v0.27技术栈 SOFABoot 4 / JDK 17

本文引用的条款编号（P-xx）、决策编号（Dx）和问题编号（Qx）都来自上位的详细设计稿。本文只规定第一期要做什么、怎么做；第一期不涉及的内容以详细设计为准。

1目标与范围

第一期交付详细设计中的消息模式（L0，8.9 节）。一个 Agent 实现 A2aAgentHandler 接口中的 sendMessage 一个方法（其余四个标准方法用默认实现），就能以标准 A2A 服务的形式注册到 BCS，并在 BCN 工作台中被调用。

2与总体设计的关系

第一期是总体设计的一个子集，不是另一套方案。约束如下，保证后续阶段只增加、不修改：

  • A2aAgentHandler 和 BcnCall 的名字、方法签名与详细设计 8.5 节一致，第一期就给出完整的五个方法。后续给 BcnCall 增加的方法都以默认方法加入，已有实现不需要修改。
  • 请求处理流水线和校验按详细设计 8.6 节实现。后续阶段放开 Task 时，只是放宽校验并启用更多方法，流水线不需要重写。
  • 线上格式、错误码、Card 字段与 Profile 一致，第一期接入的 Agent 在后续阶段不需要重新注册。

4SPI

接口

package bcn.a2a.server;

/**
 * Agent 的 SPI。五个方法与 A2A 的五个标准操作一一对应，名字和类型与标准一致。
 * 第一期只需要实现 descriptor 和 sendMessage，其余方法保留默认实现。
 */
public interface A2aAgentHandler {

    /** Agent 的静态描述，SDK 据此生成 AgentCard。启动时调用一次。 */
    AgentDescriptor descriptor();

    /**
     * SendMessage。第一期必须返回一条完整回复（Message），不能返回 Task。
     * 在 SDK 管理的线程上调用，可以阻塞；超时后线程会被中断（第 11 节）。
     * 抛出 A2AError 时按第 9 节返回对应错误；抛出其他异常时，调用方收到内部错误，异常详情只记日志。
     */
    EventKind sendMessage(BcnCall<MessageSendParams> call) throws Exception;

    /**
     * SendStreamingMessage。消息模式下流中只有一条消息，随后关闭（A2A 规范 3.1.2）。
     * 默认调用 sendMessage，把它的回复作为流中唯一的事件；业务通常不需要覆盖。
     */
    default Flow.Publisher<StreamingEventKind> sendStreamingMessage(BcnCall<MessageSendParams> call) throws Exception {
        return Streams.single(sendMessage(call));
    }

    /** GetTask。消息模式没有 Task（P-36）。 */
    default Task getTask(BcnCall<TaskQueryParams> call) {
        throw new TaskNotFoundError();
    }

    /** SubscribeToTask。消息模式没有 Task（P-36）。 */
    default Flow.Publisher<StreamingEventKind> subscribeToTask(BcnCall<TaskIdParams> call) {
        throw new TaskNotFoundError();
    }

    /** CancelTask。消息模式没有 Task（P-36）。 */
    default Task cancelTask(BcnCall<CancelTaskParams> call) {
        throw new TaskNotFoundError();
    }
}

/** SDK 在标准请求外包的一层，带上协议层已经处理好的信息。 */
public interface BcnCall<T> {
    T request();                 // a2a-java 的标准请求对象，已通过校验
    String tenant();             // 本次调用的目标 Agent 标识；单 Agent 部署时为空字符串
    CallerContext caller();      // 调用上下文；调用方未提供时各字段为空
    String requestId();          // SDK 生成的请求标识，用于日志关联
}

public interface CallerContext {
    Optional<String> userId();
    Optional<CallSource> source();
    Optional<String> callerApp();   // 仅 GRPC 绑定可得，来自 SOFARPC 调用上下文
}

public record CallSource(String platform, String app, String botId, String scene) {}

参数和返回值都是 a2a-java 的类型（org.a2aproject.sdk.spec）：MessageSendParams、TaskQueryParams、TaskIdParams、CancelTaskParams；返回的 EventKind 是 Task 和 Message 的共同接口。默认实现抛出的 TaskNotFoundError、UnsupportedOperationError 也是 a2a-java 的错误类型，均为运行时异常。

为什么第一期就给出五个方法。业务从第一期起面对的就是最终的接口，名字和标准一致，读 A2A 规范就能理解。后续阶段需要任务能力时，只需覆盖对应的默认方法，不用换接口。第一期覆盖其余四个方法不会报错，但第一期的校验不允许出现 Task（8.2），所以没有意义。

SDK 另提供几个辅助方法：

public final class Messages {
    /** 取出消息中所有文本 Part，按顺序拼接。 */
    public static String text(Message message);
    /** 构造一条只含一个文本 Part 的 Agent 回复。messageId、role、contextId 由 SDK 补齐。 */
    public static Message agentText(String text);
}

public final class Streams {
    /** 把一个回复包成只有这一个事件的流，供 sendStreamingMessage 的默认实现使用。 */
    public static Flow.Publisher<StreamingEventKind> single(EventKind reply);
}

    .build();

第一期不提供 requireUserId、工具观察、审批、多模态等声明方法，避免声明了却不能用。

完整示例

@Component
public class ExpenseFaqAgent implements A2aAgentHandler {

    private final FaqService faqService;

    public ExpenseFaqAgent(FaqService faqService) {
        this.faqService = faqService;
    }

    @Override
    public AgentDescriptor descriptor() {
        return AgentDescriptor.builder()
                .name("报销问答").description("回答差旅报销政策相关问题").version("1.0.0")
                .skill("expense_faq", "报销政策", "回答报销标准、流程和材料要求", "finance")
                .acceptCallerContext(true)
                .build();
    }

    @Override
    public Message sendMessage(BcnCall<MessageSendParams> call) {
        String question = Messages.text(call.request().message());
        String userId = call.caller().userId().orElse(null);      // 有就按用户回答，没有就回答通用政策
        String contextId = call.request().message().contextId();  // 多轮会话标识，可能为空
        return Messages.agentText(faqService.answer(userId, contextId, question));
    }
}

只实现了 descriptor 和 sendMessage，其余方法用默认实现；声明 streaming(true) 后流式请求也由同一个 sendMessage 回答。返回类型可以收窄为 Message。加上第 12 节的配置，就完成了接入。

5请求处理

5.1 SendMessage 的处理顺序

  1. 绑定层解析请求，得到 protobuf 的 SendMessageRequest，以及版本、扩展协商头、路径中的 tenant、调用方应用名。HTTP 和 JSONRPC 用 protobuf 的 ProtoJSON 解析（忽略未知字段）。
  2. core检查版本：缺省按 1.0 处理；不是 1.0 返回 VERSION_NOT_SUPPORTED。
  3. core确定 tenant 并找到 Agent（5.2）。找不到时返回参数错误，错误信息不透露其他 Agent 是否存在。
  4. core用 ProtoUtils.FromProto.messageSendParams 转成 a2a-java 模型，执行请求校验（8.1）。
  5. core解析调用上下文（5.3）。
  6. core申请执行名额（第 11 节），名额已满返回服务繁忙。
  7. core在执行线程上调用 sendMessage，受超时控制。
  8. core补齐并校验回复（8.2）：补 messageId、role、contextId。
  9. 绑定层用 ProtoUtils.ToProto.message 转回 protobuf，包成 SendMessageResponse（message 分支）返回；HTTP 响应头回显已启用的扩展。

5.2 tenant 与多 Agent

一个进程可以承载多个 A2aAgentHandler Bean，用 tenant 区分。启动时 SDK 收集所有 Bean：

情况处理
只有一个 Agent，且没有设置 tenant所有请求都交给它；Card 不声明 tenant
有多个 Agent每个都必须设置 tenant，且互不相同，否则启动失败
HTTP+JSON、JSONRPCtenant 来自路径 {base-path}/{tenant}/...。请求体里也带了 tenant 且与路径不同时，返回参数错误
GRPC所有 Agent 共用一个接口地址，tenant 来自请求的 tenant 字段（BCS 按 Card 中接口声明的 tenant 填写）

5.3 调用上下文

从 SendMessageRequest.metadata 的 bcn.caller 键读取（详细设计 7.2）。规则：

  • 只有调用方在 A2A-Extensions 中声明了调用上下文扩展的 URI，SDK 才读取；否则忽略这个键，caller() 全部为空。
  • Agent 的描述没有声明 acceptCallerContext(true) 时同样不读取。
  • 格式不对（不是对象、字段类型不对、userId 超过 128 个字符）时返回参数错误，不静默忽略。
  • 未知字段忽略。proof 字段第一期不处理。
  • callerApp 只在 GRPC 绑定下从 SOFARPC 调用上下文读取；HTTP 类绑定下为空。
  • userId 原值不写日志（第 13 节）。

第一期不支持"必须有用户"。BCS 目前还不发送调用上下文（待办 A2A-003，详细设计分期 P3），而且 BCS 遇到 Card 中不认识的 required: true 扩展会拒绝注册。所以第一期只能以 required: false 声明，Agent 自己处理没有用户的情况。

5.4 多轮会话

请求的消息带 contextId 时，回复必须沿用；没带时 SDK 生成一个 UUID 放进回复（P-38）。BCS 会在同一会话的下一轮带回它。会话记忆由 Agent 按 contextId 自己保存，多实例部署时要放在共享存储中，SDK 不管理。

5.5 流式发送

A2A 规范 3.1.2 节规定，流式发送如果返回消息，流中必须正好只有一条消息，然后立即关闭。消息模式没有 Task，所以第一期的流式发送也是"一条完整消息的流"：调用方要等回复生成完才能看到，体验与非流式相同。它的作用是让只会走流式的调用方也能调用这个 Agent，以及在 Card 中声明 streaming: true 后 BCS 走流式通道。

项设计
处理顺序与 5.1 相同：校验、执行 sendStreamingMessage（默认即 sendMessage）、校验回复
何时开始写流拿到并校验完回复之后，才写响应头和这唯一的事件，然后关闭。因此处理过程中的任何错误都以普通错误响应返回，不会出现流写到一半出错的情况
等待期间的连接回复生成期间连接上没有数据。默认 60 秒的执行超时（第 11 节）要小于 MOSN 和负载均衡的空闲超时；需要更长时间的 Agent 应等到支持逐段输出的阶段
Cardstreaming(true) 时 capabilities.streaming 为 true，BCS 改用 SendStreamingMessage；为 false 时 BCS 用 SendMessage。两种情况下 Agent 代码相同
覆盖默认实现允许，但第一期的校验要求流中只有一条消息（8.2），返回 Task 或多个事件都会被拒绝

7.2 JSONRPC

POST {base-path}/{tenant}/jsonrpc，method 为 A2A 操作名（SendMessage 等，与大小写一致），params 为对应请求对象。只支持单个请求，不支持批量。id 原样返回。

{"jsonrpc": "2.0", "id": "req-1", "method": "SendMessage",
 "params": {"message": {"messageId": "run-8f2c", "role": "ROLE_USER", "parts": [{"text": "出差住宿标准是多少？"}]}}}

{"jsonrpc": "2.0", "id": "req-1",
 "result": {"message": {"messageId": "4b1f…", "role": "ROLE_AGENT", "contextId": "c-7d2e…",
                        "parts": [{"text": "一线城市每晚不超过 600 元……"}]}}}

流式发送同样 POST 到这个地址，method 为 SendStreamingMessage，响应为 SSE，唯一的 data 是一个带相同 id 的 JSON-RPC 响应，result 为 {"message": …}。

JSON-RPC 自身的错误：请求体不是合法 JSON 返回 -32700；结构不对返回 -32600；方法名不认识返回 -32601；参数不合法返回 -32602。

7.3 GRPC

  • 实现 A2AServiceGrpc.A2AServiceImplBase，通过 SOFARPC 以 Triple 协议（tri）暴露。Harness 联调时 MOSN 中发布的服务名为 org.a2aproject.sdk.grpc.A2AServiceGrpc$AsyncService:1.0，SDK 沿用同一接口和版本。
  • 版本和扩展协商从 GRPC metadata 的 a2a-version、a2a-extensions 读取。
  • tenant 从请求的 tenant 字段读取。
  • 服务发布、订阅和 MOSN 路由由部署流程完成，SDK 不做（参考 docs/specs/2026-10-28-bcs-a2a-grpc/grpc-mosn-runbook.md）。
  • SendStreamingMessage 是服务端流方法：拿到回复后发出一个 StreamResponse（message 分支），然后正常结束流；出错时直接以错误状态结束，不发任何消息。SubscribeToTask 直接以 NOT_FOUND 状态结束。

带 taskIdTASK_NOT_FOUND（P-36）
contextId 若存在则非空且不超过 64 个字符参数错误
acceptedOutputModes 若存在则必须包含 text/plainCONTENT_TYPE_NOT_SUPPORTED
带推送配置PUSH_NOTIFICATION_NOT_SUPPORTED（P-150）
bcn.caller 格式（仅在已协商时）参数错误

8.2 回复

SDK 先补齐，再校验。补齐：messageId 为空时生成 UUID；role 设为 ROLE_AGENT；contextId 按 5.4 设置，Agent 自己设置了不同的值时以请求的为准并记录告警。

检查不通过时
sendMessage 返回非 null内部错误
返回的是 Message，不是 Task（第一期只支持消息模式）内部错误
parts 非空，且全部为文本 Part（P-05、第一期仅文本）内部错误
文本总长不超过 1 MiB（可配置）内部错误，不截断（P-74）
taskId 为空内部错误
metadata 中没有 bcn. 前缀的键（P-128）去掉这些键并记录告警

回复校验失败说明 Agent 代码有问题。调用方收到内部错误，日志记录违反的检查项和请求标识，指标按检查项计数。

按 A2A 规范 5.4 节。所有 A2A 错误都附带 google.rpc.ErrorInfo：reason 为错误名（大写下划线，不带 Error 后缀），domain 为 a2a-protocol.org。错误信息不包含堆栈、内部地址和其他 Agent 的信息（P-83）。

BCS 对 5xx 和超时的处理。BCS 把 5xx、408、429 和超时都视为"结果未知"，没有协商幂等时不会重发，会报告结果未知（详细设计 P-112）。服务繁忙时请求其实没有执行，但标准里没有表达"确定未执行"的错误，BCS 也无法区分。所以执行名额和超时要按实际负载配置，避免频繁出现这类错误。

11执行、超时与停机

项设计
执行线程有界线程池，大小即并发上限（execution.max-concurrent）。名额不足时立即返回服务繁忙，不排队
RPC 线程只做解析、校验和提交执行，不调用 sendMessage
超时每次 sendMessage 有最长执行时间（execution.timeout，默认 60 秒）。到时中断线程，返回内部错误。调用方的截止时间（GRPC deadline）更短时以它为准
调用方断开HTTP 连接断开或 GRPC 调用被取消时，中断对应的执行线程。消息模式没有任务，断开后结果无处可取，继续执行没有意义
优雅停机收到停机信号后，新请求返回服务繁忙；等待在途请求完成，最多 shutdown.drain（默认 30 秒）；超时后中断剩余执行

管理凭据不要写入代码仓库和日志。provider_bot_ref 要稳定，重启和发布都复用原来的注册，Card 变化时用 PUT 或刷新接口更新。

15.2 BCS 侧的现有行为

以下已对照 BCS 下行代码确认，第一期的实现必须与之一致：

BCS 行为对 SDK 的要求
Card 声明 streaming: false 时，BCS 用 SendMessage（returnImmediately: true）发送SendMessage 返回消息即可，returnImmediately 忽略
Card 声明 streaming: true 时，BCS 用 SendStreamingMessage，流中收到消息即作为最终回复由 5.5 保证
收到消息形式的回复时直接作为最终回复完成本轮回复必须是完整答案
回复的 role 必须是 Agent；contextId 存在时不能为空字符串由 8.2 保证
回复中的 Part 必须全部是文本，否则本轮失败由 8.2 保证
拉取 Card URL 时要求响应类型为 application/json，上限 1 MiB、10 秒由 10.3 保证
遇到不认识的 required: true 扩展会拒绝注册调用上下文扩展只以 required: false 声明（5.3）
GRPC 只经本机 MOSN 调用，Card 中的 GRPC 接口必须与 BCS 配置的路由精确匹配Card 中的 grpc.interface-url 与部署时的 MOSN 路由一致

15.3 联调清单

  1. 注册成功，BCS 返回 bot_id，查询到的 Card 与 SDK 生成的一致。
  2. 工作台单聊：发送问题，收到完整回答。streaming 为 false 和 true 各注册一个 Agent 分别验证。
  3. 同一会话第二轮：Agent 收到第一轮返回的 contextId。
  4. Agent 抛异常、超时：工作台显示失败，不影响下一轮。
  5. 开启的每种绑定各验证一次；GRPC 经 MOSN 验证。
  6. 两个实例：请求分别落到不同实例都能正常回答。
  7. 滚动发布：发布期间的请求要么正常完成，要么明确失败，不出现卡住的会话。
