## 修正

此前真实样本出现结果 Send 已完成、主持人只查普通 status 后等待的情况。代码核对发现：
普通 status 不核验当前 run，显式核验出的恢复动作与顶层阶段提示也可能冲突。
这两处缺口已修正；这不等于已证明历史样本仅由这两处缺口造成。

- 普通 status 对已记录的当前 run 最多执行一次受认证查询。
- 查询仅计算恢复动作，不写入确认、停止标记、已处理集合或重试计数。
- 恢复动作统一生成 `command` 和 `next_action`，优先于本地 RUNNING 提示。
- 真正提交前持锁重新核验，保留两次上限、迟到保护和关联标识确认。
- 清除参考文档中“失败不会唤醒主持人”的旧说明。
- 为满足源文件 1,000 行上限，拆出规则、运行渲染和命令处理；CLI 入口保持原路径。

## 真实故障验收规则

正式批次预先固定十个种子 `2026110101` 至 `2026110110`，发言与真实玩家投票交替。
每次新建独立 Chat 会话，在自然运行的合格玩家节点中随机选择；不选择 `vote_start`，
不暂停其他玩家形成候选窗口。预检与正式批次分开保留，不替换失败样本。

从实际 SIGKILL 时刻 T0 计时。注入器负责重启被结束的玩家，保留重启及上线观测时间；
仅主持人能够根据失败结果调用恢复命令。T4 必须是同会话、同轮次、同常规/PK 和
同发言/投票阶段的新 run 已运行。T0 到 T4 期间不代答人类节点、不发送人类消息或催促。
阶段开始前的人类节点由验收脚本提供固定回答，这属于对局准备条件。

每次复核一条 canonical 结果、一条目标 Send、一个失败事件及实际 Send 终态；对照
本局真实词检查消息和事件，并复算随机选择。结束观测后关闭测试会话；本批不代表十局
自然结束。正常完整对局与同阶段第三次失败停止应单独记录，不混入十次计数。

正式批次 **10/10 通过**，从 kill 到同阶段新 run 为 **6.623–17.511 秒**，中位数
**9.4915 秒**。覆盖五个不同玩家；发言串行，每次 1 个候选；投票每次 5 个候选。
逐次种子复算均一致；每次各一条结果、一条最终 completed 的 Send、一个失败事件；
恢复期间人类消息为 0，结果和事件未出现本局玩家词或已完成节点的完整产物。
