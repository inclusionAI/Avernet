# 主子群任务状态通知优化（最小改动版）

状态：已评审；已实现，验证记录见 implementation.md

版本：0.2

补充：用户-only ledger 状态提示为 best-effort 展示。提示保存或发布失败仅记录服务端
错误日志，不 Send/Inject 给 Manager，不改变已入队/派发/终态回执，不将 coordination
从 Applied 改成 Unknown。任务入队、生命周期事件与 TaskResult 持久化错误仍按原契约处理。
日期：2026-09-22

## 1. 需求

在现有主子群流程上区分“给用户的状态提示”和“需要 manager 处理的通知”：

- 子任务失败或已确认中断时，给 manager 发 Send，让它继续判断重试、重新派发、汇总或报告问题，不停留在等待 Worker 回复的状态。
- 其他任务状态提示只给用户展示，不再 Inject 给 manager。
- 正常成功结果继续走现有 TaskResult/Send，不改变正常协作链路。
- 中断单独显示，不再显示为失败。

本版替代 v0.1 的扩大方案。用户中断单笔子任务也需要通知 manager，不再采用“不唤醒、等下次快照”的方案。

## 2. 范围

本期只修改任务状态映射、状态提示的接收对象，以及异常终态的 manager 通知。

不做：

- 新任务卡片、任务序号、任务中心、前端消息原位更新框架。
- manager 执行前任务快照或新任务查询 MCP。
- 全量任务状态机、系统消息框架或持久化架构重构。
- 自动重试调度器、重试预算、重试工具、重试链建模。
- master 接管修复、SSE 重连、下游终态补偿。
- 改变普通群聊、成员变更等非任务通知。

## 3. 当前实现与修改点

| 位置 | 当前行为 | 本期调整 |
| --- | --- | --- |
| `task_flow.rs::emit_task_ledger_status` | 任务状态汇总通过 GenericNotification 发给用户并 Inject 给 manager | 保留用户展示，取消该提示的 Bot 投递 |
| system-message `producers/generic.rs` | 用户与 Bot 使用同一文案；空 receivers 表示所有 Bot | 为任务提示提供明确的用户-only 通路，不改变旧空列表含义 |
| `queued_task.rs::restore` | Cancelled 与 Failed 合并 | task ledger 增加 Cancelled，展示为已中断/已取消 |
| `queued_task_terminal.rs` | 已有 TaskResult/Send，包含成功、报错、中断回调 | 复用这条链路，简化异常正文，不另发一条 system Send |
| 显式 abort、派发失败等终态入口 | 可能不经过 Worker terminal callback | 检查并补齐异常任务结果通知，避免 manager 漏收 |
| `bot_event/coordination.rs` | 消费 intent 后获得 task_id | 将原派发 intent 引用传入现有 task 元数据，供通知引用 |

以上来自本地实现核对。实施时按目标版本确认调用路径，不能假定所有失败/中断都已覆盖，也不能对已有 Send 重复补发。

## 4. 通知规则

| 场景 | 给用户 | 给 manager |
| --- | --- | --- |
| 已派发、排队、执行中等任务状态提示 | 保持现有展示节奏 | 不 Inject、不 Send |
| 正常完成 | 保持已有 Worker 回复和状态展示 | 保持现有 TaskResult/Send |
| 明确任务失败 | 显示失败及可理解的情况 | TaskResult/Send |
| 已确认中断（包括用户中断单笔子任务） | 显示已中断及已知原因 | TaskResult/Send |
| 排队任务在执行前被取消 | 显示已取消 | TaskResult/Send，说明任务未开始 |
| 已请求停止，但尚未确认 | 按现有方式显示正在停止 | 不以中断终态发送 |
| Unknown / CancelUnknown | 保持结果待确认/停止结果待确认提示 | 不当作失败或已中断发送 |
| Worker 主动进度消息 | 保持现状 | 保持现有任务消息链路，不属于本次清理的状态 Inject |

约束：

1. 此处“其他只展示给用户”针对系统生成的任务状态提示，不取消正常任务结果和 Worker 主动消息。
2. 失败/中断 Send 是原任务的结果通知，不是自动重跑 Worker。
3. 已发送异常 TaskResult 后，不再附加相同事件的 system Send 或 ledger Inject。
4. 单笔 Worker 任务中断不等于停止整个协作。若用户停止的是整个会话/manager，遵守现有停止作用域，不靠子任务通知重新启动已停止的协作。
5. 任务完成与通知送达是两回事；manager 通知失败不得把已完成 Worker 任务改成失败或重新执行。

## 5. manager 通知内容与关联

### 5.1 用原派发 intent 关联，不新增 MCP 工具或返回字段

现有 MCP v2 返回 `intent_id` 与 `status=stored`，保持不变。
后续异常通知携带原始 bcs_assign_task 的完整 intent_id，便于 manager 对应自己的派发请求。

- BCS 内部仍用 task_id 管理任务和通知去重。
- 原派发引用在内部命名为 assignment_intent_id，随现有 task/dispatch 元数据保存和恢复。
- Worker 进度消息自身的 intent_id 不是原派发引用，不得替换。
- 不要求 manager 查询 intent 缓存，不增加独立映射服务或扫描任务。
- legacy/历史任务没有 intent 时，使用现有 task 引用、Worker 和任务摘要，不伪造 intent。
- 存储方式优先扩展已有任务元数据；不得只存在进程内存或依赖 24 小时缓存反查。具体字段由实施时核对现有存储契约后确定。

### 5.2 给模型的是短文本，不是内部事件 JSON

失败示例（权限问题仅在有对应证据时使用）：

```text
[任务失败]
派发引用：bcs_intent_0123456789abcdef0123456789abcdef
Worker：Worker A
任务：检查构建失败原因
情况：读取构建日志时权限不足，未完成检查。
```

中断示例：

```text
[任务中断]
派发引用：bcs_intent_0123456789abcdef0123456789abcdef
Worker：Worker A
任务：检查构建失败原因
情况：用户中断了本次执行，未返回完整结果。
```

文案规则：

- 说明已知事实，不统一套用“执行器异常退出”。
- 仅知道失败时写“任务执行失败，未提供具体原因”，不补造原因。
- 有部分结果时说明“已返回部分内容”，不得错误描述为完全无输出。
- 已中断但原因未知时说明“本次执行已中断，原因未提供”。
- 使用真实任务指令的短摘要，不额外调用模型生成标题；按 UTF-8 安全截断。
- 不将 schema_version、event_id、task_version 等内部字段整份发给 manager。
- 日志、凭据和内部堆栈不进入通知；业务内容与系统说明分开。

### 5.3 manager 后续行为

在已有 manager 协作说明中补充一条简短规则即可：

> 收到子任务失败或中断结果后，不要继续等待该任务的正常回复；结合用户目标和中断原因决定重新派发、调整安排或说明问题。

不在每条通知重复长篇权限声明，也不要求每次都重试。
用户中断原因必须保留，让 manager 能结合用户意图判断，而不是隐去原因机械重试。
manager 可使用已有 bcs_assign_task 重新派发；新调用生成新的 intent/task，旧任务保留失败或中断事实。
本期不扩展工具参数或引入自动重试框架，也不改造整个群任务的收尾协议。

## 6. 用户展示

- 不新增逐任务卡片，不为排队、执行中、完成等每次变化额外插入消息。
- 保留现有任务状态提示的位置和触发频率；本次只调整接收对象与取消文案。
- 原汇总如继续使用“待回复/已回复/失败/超时”，增加“已中断”分类，Cancelled 不再计入失败。
- 优先复用现有错误/中断展示；已有相同提示时不再新增一条。
- 用户侧无需显示长 intent_id；manager 专用通知正文不自动复制成另一条前端消息。
- 本期不彻底解决旧任务与新任务的汇总展示方式；任务详情、稳定编号和卡片另行评审，不作为本次依赖。

## 7. 实施约束：补齐现有链路，不另建一套

### 7.1 用户-only 状态提示

在现有 system-message 通路增加最小且显式的用户-only 表达，可用窄事件分支或局部投递选项实现。
要求用户历史/实时展示仍走现有权限和持久化流程，但不创建 Bot delivery。
不能把 receivers 置空实现用户-only，因为当前空列表代表广播所有 Bot。
不修改 GenericNotification 对其他调用方的默认行为。
仅用户消息不得被该通知通路或自动群路由重新转换成 manager Inject/Send。

### 7.2 异常 TaskResult

复用已有任务结果构建、admission 和发送逻辑：

- Worker error/aborted 回调已产生 TaskResult 时只调整内容/映射，不再发第二次。
- 显式 abort 确认、未发送取消、明确派发失败如果绕过现有 terminal callback，补接同一结果入口。
- 调度器与回调都观察到同一终态时，共用已有 task-result 稳定身份及幂等约束。
- 终态提交与结果通知记录沿用现有事务/恢复约束；存储失败不得吞掉后返回成功。
- 不为网络结果不明的 manager Send 盲目重发；沿用现有 delivery 行为。
- managed 与 legacy 路径都需要验证，不进行全局抽象重写。
- 当前还无法确认的超时/连接错误不伪装成明确失败。现有“已确认任务失败”出口才适用本规则。

### 7.3 最小状态变更

只补 TaskLedgerStatus 的 Cancelled 及所有必要映射、汇总与序列化消费；底层 delivery 已有 Cancelled，不新建全量状态机。
取消请求发出不算已中断，须等现有权威状态确认。
成功与取消竞争继续遵守原状态机/CAS，不允许迟到事件把已确认终态反复改写并重复唤醒。

## 8. 验收标准

| 场景 | 预期 |
| --- | --- |
| 普通任务状态提示 | 用户仍按原流程看到，manager 的新增 Inject/Send 数为 0 |
| Worker 正常完成 | 原 TaskResult/Send 正常，无重复 system Send |
| Worker 明确失败 | manager 收到一份可理解且可关联的失败 Send，可继续调用现有派发工具 |
| 用户中断单笔 Worker 任务并确认 | 展示已中断，manager 收到中断 Send，不再一直等回复 |
| 系统中断或原因未知但已确认停止 | Send 如实说明中断与已知原因，不伪造用户操作 |
| 显式 abort 路径没有 Worker terminal callback | 仍通过已有结果入口补齐 manager 通知 |
| 调度终态和回调重复/重放 | 同一任务异常只产生一个逻辑 TaskResult，不双发 |
| 取消排队任务 | 用户已取消，manager 获知任务未开始 |
| 请求停止未确认、Unknown、CancelUnknown | 不误报已中断或失败，不因此启动重试 |
| 单笔任务结束但整个协作已被停止 | 不绕过原停止范围重新唤醒 manager |
| 同 Worker 多笔任务 | manager 通过各自原派发引用区分，不只靠 Worker 名称 |
| intent 缓存过期/BCS 重启 | 新版本任务仍可从已有持久元数据恢复派发引用 |
| legacy 任务无 intent | 稳定降级展示任务引用，不阻塞异常结果投递 |
| 其他 GenericNotification 空 receivers | 原有广播语义不变 |
| manager 通知投递失败 | Worker 状态不回退、不重做任务，沿用现有错误处理 |

验证包括相关 BCS 单元/契约测试，以及“派发→失败或中断→manager 被唤醒→可再派发”的完整场景。
仅在实际触及前端消费时运行相应前端测试；不因本 spec 主动引入新的前端组件。

## 9. 兼容与交付

- MCP v1/v2 回执不变，不引入新版本工具。
- 新增 Cancelled 消费兼容必须与生产者一起验证，旧端不能把未知状态默认显示为失败。
- 原任务元数据缺少 intent 的历史记录允许降级，不做猜测性全量回填。
- 若实际需要数据库迁移，使用新增迁移，不修改已提交历史迁移；不预设必须新增表。
- 公共 BCS 不引入内部 MCP 实现或私有缓存依赖，契约用本地 fixture 验证。
- 通知接收策略由 BCS 业务层决定，前端/传输 adapter 不根据文案猜测 Send/Inject。
- 本次实施只修改本地代码和测试，不包含线上重试、提交或发布。

## 10. 本轮修订

相对 v0.1：

- 改为失败和已确认中断都通知 manager，包括用户中断单笔子任务。
- 删除执行前快照、任务卡片/序号、完整新状态机及独立通知事件框架要求。
- 不再把用户中断后的不唤醒作为默认行为。
- manager 使用短文本接收异常事实，不接收完整内部 JSON。
- 只清理系统任务状态 Inject，不改变正常成功结果和 Worker 主动消息。
- 重试决策留给被唤醒的 manager，系统不新增重试编排。
