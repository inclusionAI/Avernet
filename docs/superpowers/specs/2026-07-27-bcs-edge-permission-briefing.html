2. 双层模型：第一层看边，第二层先激活边、再鉴权 tool

整体从左往右看：准入层只负责判断 caller 到 target 是否有 friend/owner/approved 边；第二层上层用 originator 找出当前开放的边；第二层下层再用这些边绑定的 role 权限集做 tool 鉴权。

第一层：BCS 准入

只看 caller→target 有没有边。

  • friend / owner 本质上也是边
  • 没有边：直接拒绝，不唤醒 bot
  • 有边：进入第二层

第二层上层：originator 开放边筛选

看哪些边对当前 originator 开放。

  • DirectOnly：只对 caller 自己作为 originator 的直达语境开放
  • OriginatorIn([Alice])：只在 Alice 语境下开放
  • 这一步不看具体 tool

第二层下层：role 权限集

用 active edge 上的 role 判断 tool。

  • 加载 role rules
  • 执行 Read/Edit/Bash 等鉴权
  • 平台守卫仍是最高优先级
EdgeGrant(a → B) = role_name + originator_policy 第一层准入：a→B 有没有边？ 第二层上层：a→B 中哪些边对当前 originator 开放？ 第二层下层：激活后的 role 权限集允许哪些 tool？

通过Bob 管理 bot3

存在 Bob→bot3 边，policy 是 DirectOnly，且 caller=originator=Bob。进入 role 后，管理类 tool 被允许。

拒绝Bob 请求高危操作

边可以激活，但 bot3管理角色 仍不允许高危 Bash / 越权写入等能力，所以在第二层下层或平台守卫处拒绝。

拒绝Bob 没有边

如果没有 approved 的 Bob→bot3 边，第一层直接拒绝，不唤醒 bot3。

通过Alice 经 bot1 调 bot3

bot1→bot3 存在 approved 边，且配置 OriginatorIn([Alice])。在 originator=Alice 语境下，这条边被激活，然后使用 Lark写入角色 做 tool 鉴权。

拒绝Bob 经 bot1 调 bot3

如果 bot1→bot3 只允许 OriginatorIn([Alice])，那么 originator=Bob 时不会激活这条边。

拒绝缺少 bot1→bot3 授权边

即使 Alice 能使用 bot1，也不会自动获得 bot3 的能力。没有 approved 的 bot1→bot3 边时，bot3 不进入后续 role 鉴权。

5. 当前可用线路 C：代理链路 / originator-bound 临时边

这条线路描述的是代理场景：Alice 找 bot1 干活，bot1 无脑代理给 bot2，bot2 发现 bot3 能干并继续代理给 bot3。关键不是“权限传递”，而是整条代理链必须保留 originator=Alice；bot2 到 bot3 这一跳需要向 bot3 申请一个角色权限集，并把这个权限集的上层限定为 originator=Alice，由 bot3 的 owner 审批后生成 bot2→bot3 边。

sequenceDiagram
  participant A as Alice
  participant B1 as bot1
  participant B2 as bot2
  participant B3 as bot3
  participant O as bot3 owner

  A->>B1: 找 bot1 干活
  B1->>B2: 无脑代理，保留 originator=Alice
  B2->>B3: 发现 bot3 能干，继续代理，保留 originator=Alice
  B2->>B3: 申请 bot3 的某个角色权限集
上层限定 originator=Alice
  B3->>O: 提交审批：bot2→bot3 + role + OriginatorIn(Alice)
  O->>B3: 审批通过 / 拒绝
  B3->>B3: 通过后生成 bot2→bot3 边
role + OriginatorIn(Alice) + TTL
  B3->>B3: 使用 bot2→bot3 的 active role 做 tool 鉴权
  B3-->>B2: 返回协作结果
  B2-->>B1: 返回代理结果
  B1-->>A: 返回最终结果

运行态怎么理解？

caller = bot2 target = bot3 originator = Alice EdgeGrant(bot2 → bot3) = { role = bot3 owner 审批开放的角色权限集, originator_policy = OriginatorIn([Alice]), ttl = 短期有效 / 或按审批策略, audit = 必填 }

bot3 最终不是使用 Alice→bot1 的权限，也不是复制 Alice 的权限；它使用的是当前本跳 bot2→bot3 边上、对 originator=Alice 开放的 active role。

为什么不需要 Alice 和 bot3 再沟通？

因为 Alice 已经作为运行态 originator 被带到代理链路里；bot2 申请的是“在 originator=Alice 时可用的 bot3 角色权限集”，审批主体应是 bot3 owner。

也就是说，Alice 不负责给 bot3 增加能力；bot3 owner 决定 bot3 的哪些 role 可以在这条 bot2→bot3 边上、且仅对 Alice 这个 originator 开放。

通过bot3 owner 审批 originator-bound 边

bot2 申请 bot3 的某个 role，并声明上层只对 originator=Alice 开放。bot3 owner 审批通过后，系统生成 bot2→bot3 边。

拒绝Bob 复用 Alice 的边

这条边的上层是 OriginatorIn([Alice])。如果 originator 变成 Bob，即使 caller 仍然是 bot2，这条 bot2→bot3 边也不开放。

拒绝bot2 获得无条件能力

这条边必须带 originator_policy / purpose / audit / 有效期策略。它不是给 bot2 永久扩权，也不是把 Alice 的资源权限传递给 bot2。

需要会议确认：这条线路可以作为代理链路的候选设计，但要明确审批语义：申请方是 bot2，审批方是 bot3 owner；审批对象是 bot2→bot3 的某个角色权限集，且上层限定 OriginatorIn(Alice)。实现上建议称为 originator-bound temporary edge 或 originator-bound approved edge，避免被理解成传统资源权限传递。

下面不是要在本文强行定案，而是把模型边界摆出来，方便开会讨论。

当前模型主要回答“这条边上的 role 是否允许 bot 使用某个 tool”。但真正调用外部系统时还涉及执行身份：用 bot 自己的身份、caller 的身份，还是 originator 的身份？如果考虑用 caller / originator 身份，还需要单独定义用户授权、可见性、审计和撤销，不能出现“我让 bot 干一个活，它就用我的身份做了很多我不知道的事”。

讨论所谓“权限传递”是不是同一个问题？

  R1["另一类问题: 资源 ACL 传递

我们一直说的不是“A 的资源权限传给 B，再传给 C”。本模型的出发点是：一个 bot 在合作前已经确定自己能做什么；owner 再定义一套 tool / specifier / decision 权限体系，决定外部 human / bot / service 让它干活时哪些能力可用、哪些不可用。资源 ACL 传递是另一个角度，需要单独讨论。

7. 会议建议拍板的问题

问题建议默认答案原因
MVP 是否只承诺 ① human 直达 与 ② human 经 bot 中转？ 是 这两条线路的 caller、originator、边激活与 role 鉴权都能讲清楚。
OriginatorIn([ids]) 是否作为中转主推荐？ 是 它能表达“bot1 只能代表 Alice 使用 bot3 的某个角色权限集”。
bot outbound 不带有效 task_id 时怎么处理？ MVP 拒绝 避免 bot 通过省略上下文把链路伪装成 direct/fresh，从而绕过 originator 限制。
bot 自启动时是否允许 originator=bot？ 会议讨论 这会改变 originator 从“源 human”到“源 actor”的含义，需要单独定语义。
service 作为 caller 是否进入本期？ 后期适配 service principal、机器凭证、审计与撤销链路还没定义完整。
bot 真正调用 tool / resource 时使用谁的执行身份？ 会议讨论 鉴权只说明“能不能用这个 tool”，执行身份涉及外部系统授权、用户感知、审计和撤销。
“权限传递”是否要纳入本模型？ 建议拆开 本模型是 bot 能力开放控制；资源 ACL 委托/传递是另一类问题，不应混入当前边权限主线。
代理链路是否采用 originator-bound temporary edge？ 会议讨论 建议将 Alice 的确认解释为“本次代理链路临时开放 bot2→bot3 某个 role”，而不是权限复制。
代理临时边由谁最终批准？Alice、bot3 owner，还是 bot3 的策略流程？ 会议讨论 Alice 可以确认本次代理使用，但 bot3 只能开放自己策略允许的 role；审批边界需要拍板。
推荐会议结论：本期先把 ①② 两条 human 路线闭环；③④ 只保留在模型图里，作为未来适配方向，不阻塞当前设计评审。
