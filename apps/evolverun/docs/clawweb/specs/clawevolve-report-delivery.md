# ClawEvolve Runner 回报重试

## 范围

平台运行时 `_report` 与 Hardening 原生 Handler 共用回报实现，用于候选准备、候选交付、Stage 扩展及使用平台运行时的业务交互。业务 Skill、输入输出业务协议及阶段执行顺序不变。原生阶段中未调用此实现的独立回报脚本不在本次改动范围。

## 传输合同

`POST /api/evolve/internal/tasks/:taskId/steps/:stepId/report` 的 JSON 正文不变。新 Runner 为一次回报生成 UUID，通过 `X-ClawEvolve-Report-Id` 发送；同一次传输重试复用完全相同的标识和正文。

- 502、503、504、连接中断和超时最多发送 5 次，退避 1、2、4、8 秒。
- 单次网络超时上限 20 秒，重试预算 120 秒；这是请求重试预算，不是重新执行 Agent 的期限。
- 4xx、无有效 ACK、协议错误不会盲目重试。仅 400/422 明确拒绝允许原有调用方继续上报失败；不覆盖接受情况未知的结果。
- 重试不重新下载候选、不重新运行业务、不另建 Task/Step。
- `stage_runtime/<stepId>/report-<uuid>.json` 保存原始正文、回报标识、每次状态及确认情况，文件权限 0600，沿用已有任务日志归档。运行日志记录尝试次数及错误类别，不打印正文。

## 服务端去重

`StepReportRepository` 使用现有数据库事务与 Task→Step 锁顺序，在 `ce_steps.ext_json.report_delivery` 中保存正文摘要和回执，不新增表或队列。

1. 首次领取回报后执行现有 report handler；锁只用于领取和写回执，不跨网络派发。
2. handler 完成状态更新和后续调度后，先持久化回执，再向 Runner 返回。相同标识及正文的重试只返回回执，不重建交互或派发下一步。
3. 表单回执只保存交互引用，不重复存储表单正文。HITL 回答、同 Step 恢复、Loop 接受之后仍保留旧回执；迟到的旧回报不能覆盖新状态。
4. 相同标识但不同正文返回 409。Step 终态或等待交互时，新的回报标识不能修改结果。
5. 处理中或处理中断而未保存回执时返回 503，不抢占执行权。有限重试用尽后，Runner 明确报告未确认并保留证据；这不等价于业务失败，也不声称已自动恢复。调查后可通过原有任务重试入口创建新 Step，新 Step 不继承旧传输回执。

无该 Header 的旧调用方保持原处理方式。JSON 正文、数据库 Schema、Host 装配和业务 Skill 均不要求修改。

## 发布与验证

先部署支持回报去重的 CW 后端，再发布包含重试的完整运行包。旧后端会忽略 Header，无法保证 HITL 重试语义，因此不能先发布新 Runner。回滚时同样先停用新 Runner 再回滚后端。

本地验证覆盖：临时错误后恢复、永久错误和预算耗尽、非重试错误、Hardening 复用、业务只执行一次；真实 Express 路由和 SQLite 验证候选准备、HITL、Loop、重复与冲突、跨 Repository 争用、正常任务重试，以及已处理成功后主动断开 HTTP 响应再重发。上线真实环境的网络和数据库行为需在发布后另行验收。
