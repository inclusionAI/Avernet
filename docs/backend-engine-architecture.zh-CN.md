## 1. 骨架：微内核的七个角色

![微内核七角色分层对照](images/arch/01-layers.svg)

Backend 是中心化的多租户服务，Engine 是随 Bot 部署的单机服务。部署形态完全不同，但两者的内部结构是同构的 —— 都落在同一组七个角色上。

### 1.1 七个角色

这套架构有一份成文的规则集（25 条，下称「宪法」），它要求任何模块至少能区分出七种角色，并且**依赖方向必须显式、单向、可被工具检查**：

| 角色 | 职责 | Backend | Engine |
| --- | --- | --- | --- |
| **交付适配** | 把协议翻译成领域调用，不持有领域策略 | 面向租户与前端的 HTTP 表面，40+ 个路由分组 | 面向单个 Bot 的 HTTP + 长连接表面 |
| **服务契约** | 声明「外部可以让内核做什么」 | 115 个服务契约 | 23 个能力域协议 |
| **领域内核** | 全部领域逻辑，不认识任何传输框架 | 55 个领域模块 | 领域模型 + 每引擎一套反腐层 |
| **插件契约** | 声明「内核需要外部提供什么」 | 35 个能力契约 | 每引擎一组原生端口契约 |
| **插件实现** | 契约的具体实现，可整套替换 | 开源 / 本地替身 / 企业，三套 | 每引擎一套传输实现 |
| **底座** | 各层共享的原语，不依赖任何上层 | 生命周期、跨层数据结构 | 线协议信封 |
| **组装根** | 唯一挑选具体实现的地方 | 59 个装配模块，按部署形态选择 | 按引擎组装，每引擎一个 |

层数和依赖方向完全一致，**真正不同的是每一层抽象的对象**：Backend 抽象的是外部基础设施（数据库、缓存、对象存储、身份、审批），Engine 抽象的是异构 Agent 引擎本身。同一套分层方法，套在两类完全不同的「外部世界」上 —— 这个对照是理解这两个模块最省力的入口。

### 1.2 值得单独讲的三个细节

#### （1）一个同名的包，在两个模块里是两个角色

两个模块各有一个顶层包用了同一个名字：在 Backend 它指**服务契约**，在 Engine 它指**交付适配**。

宪法里有一条专门防这个：一个名字在**同一个模块内**必须有唯一明确的角色含义。两个模块各自内部是自洽的，所以严格说没有违规；但跨模块阅读时，这确实是一笔认知成本。

**这一点我们主动提出来，作为评审议题之一**：是统一命名（代价是一次大范围重命名），还是接受「各模块内自洽」并在阅读入口显式说明。两条路都行，但不该默认现状。

#### （2）契约放在哪，是被摩擦决定的，不是被美学决定的

最初的做法是：契约定义在服务契约层，实现放在领域内核。

结果是，每个实现都要反向依赖上层 —— 这违反层序。于是每加一个服务，就要在架构检查里手写一条例外。**那份例外清单只增不减，这本身就是设计出问题的信号。**

现在的做法是：契约和实现都放在领域内核里，实现直接继承同层的契约；服务契约层只负责把名字转出去给外部用。依赖不再倒着走，消费者那边完全无感。**例外清单从此不再增长。**

这个演进过程比结论本身更值得讲：**当你发现某条规则需要不断加例外，通常不是规则错了，是契约放错了地方。**

#### （3）共享原语只能往下沉，不能开例外

Engine 的传输实现是纯粹的叶子节点，规则上**禁止它依赖领域内核**。但传输层产生的线协议信封，恰恰是领域内核要消费的东西。

两边都需要它，谁也不能依赖谁 —— 那就只能把它沉到**两边都够得着的最底层**。底座因此被定义成「不依赖本模块任何其他层」的一层，线协议信封是它的第一个住户。

这是一个通用手法的干净实例：**当两个不能互相依赖的模块需要共享一个类型时，答案永远是往下沉，而不是开一个例外。**

## 2. 契约：两个方向相反的 API

![两类契约的方向性](images/arch/02-two-contracts.svg)

### 2.1 方向是第一性的

宪法里最核心的一条：**服务契约和插件契约是两类不同的东西，必须分开定义、分开记录、分开版本化、分开测试。**

- **服务契约**：外部调内核。定义成独立于交付层的接口。
- **插件契约**：内核调外部。永远为外部能力定义接口。

一个模块可以在不同交互里同时扮演两种角色，但**控制方向必须是明确的**。

### 2.2 方向决定了什么

这不是分类学游戏。方向一旦搞错，下面三件事全错：

| | 服务契约 | 插件契约 |
| --- | --- | --- |
| **谁破坏谁** | 内核改契约 → 所有消费者受影响 | 契约变动 → 所有插件实现受影响 |
| **怎么测** | 一致性测试：实现是否满足契约 | 契约测试 + 替身：内核在各种插件行为下是否正确 |
| **谁可替换** | 内核实现可替换，消费者无感 | 插件实现可替换，内核无感 |

把「注册函数」和「被注册的回调」当成同一个 API 面来描述，是这里最常见的错误 —— 它们的方向恰好相反。

### 2.3 依赖倒置真正落地的样子

图 2 的第二条带子是关键：**没有任何一条箭头从实现指向实现。**

- 消费者依赖服务契约，内核也依赖它；
- 内核依赖插件契约，插件实现也依赖它。

两侧都指向中间的契约。消费者不知道内核里放了什么，内核也不知道插件是谁。

### 2.4 契约的价值来自它描述得有多具体

一份只列了方法名、参数一律写成「随便什么」的契约，挡不住任何东西：形式上它存在，实际约束为零。评审一份契约时真正该问的只有一个问题 —— **它到底约束了什么？**

配套两条工程约定，都是关于「问题在什么时候暴露」：

- 契约与实现之间要能双向找到对方，读代码的人不该先翻一遍装配逻辑才知道谁实现了它；
- 实现没有满足契约，要在**装配的时候**就暴露出来，而不是等到某一次线上调用。

### 2.5 同一份契约，多套实现，由组装根挑选

Backend 侧的 35 个插件契约，每一个都对应多套实现：

| 实现集 | 用途 | 是否随开源分发 |
| --- | --- | --- |
| **开源实现** | 不依赖任何内部 SDK，走通用协议与自带服务 | 是 |
| **本地替身** | 内存实现，单机开发与测试用 | 是 |
| **企业实现** | 对接企业基础设施 | **否** —— 只存在于内部分发 |

挑选发生在**唯一的组装根**，由一个部署形态开关驱动，五档：开源、单机、测试、企业、企业测试。

两个设计细节值得说：

**开关是纯选择器。** 它只回答「哪一档」，不提供任何派生属性。「这一档装配了什么」由**装了哪些模块**回答，而不是由开关上的某个方法回答 —— 否则等于把已经废弃的多维模型重新编码回去。

**开关必须显式。** 未设置或取值未知是启动硬失败，没有静默默认值。一个「猜出来」的部署形态，比启动失败危险得多。

### 2.6 由此得到的分发性质：单一归属

上面那张表的最后一列，是可以当场验证的：开源分发里，企业实现那一套**物理上不存在**。契约文档会提到它的名字，但那份代码不在这棵树里。

这就是**单一归属**：每份代码只存在于一个地方。共享逻辑只有一份，内部分发反向引用它；「同一功能、两种实现」一律表达为「一份契约 + 两套实现 + 按部署形态绑定」，而不是两棵平行维护的代码树。

对评审的意义：**这是开源分发与内部部署同源、零分叉的技术前提。** 开源版能独立启动，内部版跑的是同一份领域内核，两边不需要各自维护一套业务逻辑。

## 3. 引擎：异构接入怎么做到改动可控

![异构引擎反腐层](images/arch/03-engine-acl.svg)

### 3.1 要回答的问题只有一个

**接入一个新引擎，改动面有多大？**

架构好不好，这个问题的答案最能说明问题。Engine 给出的答案是：**只新增该引擎自己的那一套，对外表面和领域内核一行不改。**

| 角色 | 接一个新引擎时 |
| --- | --- |
| 交付适配 | **不动** —— 对外表面与引擎无关 |
| 服务契约（能力域协议） | **不动** —— 领域协议与引擎无关 |
| 反腐层 | **新增一套** —— 领域形状 ⇄ 该引擎原生形状 |
| 插件契约（原生端口） | **新增一套** —— 该引擎的原生接口 |
| 插件实现（传输） | **新增一套** —— 连上去、收发帧 |
| 组装根 | **新增一个** —— 把上面三者拼起来，并声明能力矩阵 |

### 3.2 反腐层的两条关键性质

**性质一：它是领域内核里唯一认识具体引擎的地方。**

这一条让「引擎特异性」有了明确的收纳位置。领域内核里除它之外的任何代码，都不应该出现引擎的名字。

**性质二：它依赖的是端口抽象，不是具体实现。**

反腐层位于领域内核之内，但它只依赖该引擎的**原生端口契约**；具体的传输实现由组装根注入。因此「内核不依赖插件实现」这条约束对**整个内核成立，包括反腐层自己**。

这两条加起来，才使得「引擎可插拔」不只是一句口号。

### 3.3 能力矩阵：声明式，而不是异常驱动

![引擎能力矩阵](images/arch/04-capability-matrix.svg)

每个引擎在自己的组装根声明一份能力矩阵，分三态：

- **原生支持** — 反腐层为它接上了该引擎的原生能力；
- **受限 / 降级** — 支持但有约束，**声明时必须写明原因**；
- **未接入** — 上层不派发，前端直接隐藏功能。

核心规则是：**一个能力存在，当且仅当反腐层真的把它接上了。** 声明与实现的一致性在**装配阶段**交叉校验 —— 声明了却没接上，启动就失败，而不是等到线上第一次调用。

受限项的原因必须具体，例如：建会话在一侧没有独立接口，会话由首条消息落地；工具直调只在一种桥接方式下可用，另一种要绕对话。

**评审时最值得强调的一点：两条链路不是包含关系。**

claude_code 在技能管理和对话交互（澄清提问、模式切换）上更强；openclaw 在 MCP、节点、渠道、Web Shell 上更全。**交集才是领域内核可以无条件依赖的部分**，差集必须走能力判断。

能力名是 Engine、Backend、前端三方之间的稳定契约：**新增是安全的，改名或删除是破坏性变更。**

### 3.4 两条链路的部署差异

| | claude_code | openclaw |
| --- | --- | --- |
| 网关 | 随仓库分发 | 外部部署，不随仓库分发 |
| 桥接方式 | 官方 SDK 或命令行，两种可切 | 自有协议 |
| 开源可跑 | **是** | 否（需自备网关） |

这个差异是有意的：**开源版必须有一条完整可跑的链路**，否则「可插拔」无法被外部验证。claude_code 那条就是这条链路。

## 4. 链路：一次请求怎么穿透两个模块

![端到端请求链路](images/arch/05-end-to-end.svg)

### 4.1 十步，但真正要记住的是中间那条线

以一条公开 API 上的会话消息为例，请求依次经过：

**Backend 侧**：① 调用方 → ② 交付适配（解析、鉴权、协议校验）→ ③ 服务契约（拿到的是契约，不是实现）→ ④ 领域编排（按属主解析 Bot、判定发布态、解析设备上下文）→ ⑤ 出口契约（唯一的跨系统抽象）

**─── 系统边界 ───**

**Engine 侧**：⑥ 统一表面 → ⑦ 能力域协议 → ⑧ 反腐层 → ⑨ 传输实现 → ⑩ 网关 → 模型

回程是流式事件沿同一条链路反向回传。

### 4.2 中间那条线为什么重要

**Engine 没有租户轴。** 它是随 Bot 部署的单机服务，只服务它自己那一个 Bot —— 请求一旦落到设备上，就**没有任何东西再约束它**。

这意味着：**Backend 侧的领域编排，是隔离唯一存在的地方。** 三条不变量都由此推导：

#### 不变量 A · 解析必须先于转发

按属主解析 Bot 必须发生在任何设备操作之前。先转发再解析、或者信任调用方传来的用户标识，隔离就**静默失效** —— 下游不会有任何守卫察觉。

这是最危险的一类缺陷：它不报错、不告警，只是在某一天变成一次越权访问。

#### 不变量 B · 传输成功不等于业务成功

Engine 可以在一次传输层成功的应答里报告业务失败。这里必须把它识别出来，**绝不让它变成一次对外的成功**。同样地，链路故障要在这里收敛成有语义的失败，而不是把设备细节泄漏给调用方。

#### 不变量 C · 发布态走发布绑定

服务型 Bot 必须经由**已发布的运行时绑定**解析（草稿 / 预发 / 线上三态），而不是草稿态 —— 否则线上流量会打到发布前的那台机器上。

### 4.3 一个关于可测性的观察

这条链路上，**唯一不能在测试中真实运行的，是最外面那一跳** —— 因为真实的对端进程不可达。

而它上面的一切 —— Bot 解析、权限判定、发布态选择、响应整形 —— **都是生产代码，都在测试里真实执行**。

这是「可测性由边界位置决定」最好的例证：**把不可测的部分压缩成一个契约，剩下的全部变成可测的**。如果测试里要替换的东西超过一个，通常说明边界画在了错误的地方。

## 5. 治理：架构怎么才能不腐烂

![架构治理闭环](images/arch/06-governance.svg)

### 5.1 门禁针对的四个腐蚀方向

这套规则针对的不是抽象的「架构美感」，而是四个具体的、反复出现的腐蚀方向：

| 腐蚀方向 | 典型表现 | 后果 |
| --- | --- | --- |
| **传输内渗** | 交付层的概念渗进领域逻辑 | 领域逻辑绑死协议，脱离框架就无法独立验证 |
| **实现直连** | 领域逻辑直接依赖某个具体实现 | 失去可替换性，本地与测试环境跑不起来 |
| **环境散落** | 配置读取散落在业务代码各处 | 部署行为不可知，环境差异变成隐性逻辑 |
| **分发泄漏** | 内部实现混进开源分发 | 开源版无法独立启动，分发边界失守 |

四条有一个共同特征：**单看一次改动都很合理，累积起来才致命**。这正是需要机器而不是人来把关的原因。

### 5.2 宪法自己的边界感

25 条规则分三级：

- **不变量** — 必须遵守，违反需要显式豁免；
- **政策** — 强默认，偏离需要说明理由；
- **建议** — 推荐做法，本身不构成结构违规。

更值得注意的是它**明确声明不管什么**：不规定领域建模风格、不规定与架构无关的命名、不规定语言语法细节。

这个自我克制是它能被执行下去的前提。一部什么都想管的宪法，最后只会被整体忽略。

每条规则的结构也是固定的：**规则 → 防止了什么 → 必须检查什么 → 如何解释**。「防止了什么」这一栏是它区别于普通编码规范的地方 —— 规则不是从美学推导出来的，是从事故推导出来的。

### 5.3 五个环节

**① 宪法（25 条）→ ② 模块自描述（87 处）→ ③ 机器校验（53 组）→ ④ CI 门禁（7 类）→ ⑤ 违规出口（2 条路）→ 回到 ①**

### 5.4 模块自描述：让白名单可校验

每个边界显著的模块，在自己的文档里用固定格式声明四件事：

- **职责** —— 一句话说清它负责什么；
- **对外提供什么** —— 公开能力清单；
- **消费哪些外部契约** —— 信息性，不做机器校验；
- **允许依赖哪些内部模块** —— **这是一份白名单，机器校验它**。

关键在最后一项：它不是文档，是断言。模块实际发生的、未被白名单覆盖的依赖，会让架构检查直接失败。

几个设计取舍值得注意：

- **前缀匹配** —— 声明一个范围即覆盖其下所有子模块，避免清单碎片化；
- **声明了但没用不算错** —— 过期条目顺手清理即可，不制造无谓的红灯；
- **反向视图是生成的** —— 「谁依赖了我」由工具反推，不手工维护。

同时明确了几条反模式：把具体实现列进白名单（多半意味着分层已经破了）、把「改动影响」写成文件清单（要写的是**谁会察觉到这个改动**，不是改了哪些文件）。

Backend 75 处 + Engine 12 处，共 87 个模块有这份声明。

### 5.5 机器校验：静态分析，不必把系统跑起来

53 组架构检查（Backend 50 + Engine 3），全部是对代码结构的静态分析 —— 不启动服务、不连依赖，因此可以无条件挂在每一次提交上。它们守的是这些事：

| 守的是什么 |
| --- |
| 领域内核里出现任何交付框架依赖即失败 |
| 底座不得依赖本模块任何其他层 |
| 内核只能依赖插件契约，不得依赖任何具体实现 |
| 真实依赖图 vs 各模块自己声明的白名单，逐条比对 |
| 开源组装根里不得出现内部实现 —— 分发边界也是架构边界 |
| 超大模块预警 —— 单个文件承担多个角色，往往就藏着边界违规 |

这里有一个务实的做法值得单独提：**迁移期允许清单**。规则收紧时，存量违规先进允许清单，新增违规立刻失败，清单条目随迁移逐批删除，**目标是清空**。

这个做法承认现实，但同时锁定了方向 —— 比「一步到位」和「无限期妥协」都更可执行。

### 5.6 违规出口：只有两条路

要么改代码，**要么写一份豁免**：有归属、有负责人、经过评审、有期限。

目前存量豁免 **1 条**。这个数字本身就是一个健康度指标 —— **能被数出来的例外，才是可以管理的例外。**

系统级、难以回退的决策则沉淀为架构决策记录（现 11 条），反过来修订宪法。决策记录的地位高于规格说明和调研文档：**规格和调研是决策的输入，它们不能推翻一份已经接受的决策。**

### 5.7 一条明确的纪律

> 不要为了让改动通过而削弱检查。如果某个检查本身是错的，修检查，并说明为什么。

这句话写在仓库的贡献规范里。它的意义在于：**把「绕过门禁」从一个技术选项，变成一个需要解释的行为。**

## 6. 收口：可迁移的五条经验

不依赖这个仓库的上下文，这五条在任何中大型服务上都成立：

1. **方向比分层重要。** 先问清楚「谁调用谁」，再决定放在哪一层。方向搞错，分层再漂亮也没用 —— 兼容性假设和测试策略会跟着一起错。

2. **契约的位置由摩擦决定，不由美学决定。** 当你发现某条规则需要不断加例外，通常不是规则错了，是契约放错了地方。**例外清单只增不减，本身就是设计信号。**

3. **能力要声明，不要靠异常发现。** 「调用了才知道不支持」是运行期问题；「声明了却没实现」应该是装配期问题。把失败时机往前推。

4. **把不可测的部分压缩成一个契约。** 如果测试里需要替换的东西超过一个，边界多半画错了。可测性不是测试写得好，是边界画得对。

5. **例外要可数。** 允许豁免，但必须有归属、有期限、能被统计。一个说不清自己有多少例外的架构，等于没有架构。

## 附录 A：评审提问预案

> 以下是预计会被追问的问题，以及我们当前的答案。带 ⚠️ 的是我们自己也认为尚未收敛、希望在评审中听意见的。

**Q1：55 个领域模块 + 59 个装配模块，依赖注入是不是过度工程了？**

它的成本集中在组装根，收益分布在每个消费点。真正的判据是：换一套基础设施实现要改多少处？现在是改一处绑定。取消它的话，改动面是所有消费点。规模到了这个量级，这笔账是正的。

**Q2：多套插件实现，测试成本是不是成倍增长？**

不是。各套实现共享同一份契约一致性测试，只有差异部分各自测。而且本地替身那套的存在，恰恰让**上层编排逻辑的测试成本大幅下降** —— 见 §4.3，整条链路只有最外一跳被替换，上面全部跑真实代码。

**Q3：Engine 没有租户轴，安全吗？**

Engine 是随 Bot 部署的单机服务，其边界就是那一个 Bot。隔离在 Backend 侧完成（不变量 A）。风险点不在「Engine 没有租户轴」这个事实，而在「Backend 侧是否真的每次都先解析后转发」—— 所以这条被写进了那个模块的「改动影响」声明里，任何重构都必须保留它。

**Q4：反腐层的翻译会不会成为维护负担？**

会有成本，但它替换的是更贵的东西：没有反腐层的话，引擎的原生形状会直接渗进领域内核，第二个引擎接入时就要大改。反腐层把「引擎差异」这件事的成本**固定在一个可预期的位置**，而不是让它扩散。

**Q5：53 组架构检查会不会拖慢 CI、成为改动阻力？**

全部是静态分析，不启动服务，开销很小。至于「阻力」—— 它确实会挡住一部分改动，这是设计意图。允许清单机制保证了存量不阻塞，只拦新增。

**Q6：为什么 Backend 和 Engine 不合并？**

部署形态不同（中心化多租户 vs 随 Bot 单机）、伸缩维度不同、信任边界不同。合并会让「Engine 没有租户轴」这个简化前提消失，反而增加复杂度。

**Q7：能力矩阵不是超集关系，上层代码怎么写？**

交集部分直接调用；差集部分必须查能力声明后再决定派发、降级还是隐藏。这正是把能力做成**显式声明**而不是「试了才知道」的原因。

**⚠️ Q8：同一个包名在两个模块里是两个角色，要不要统一？**

见 §1.2（1）。两个模块各自内部自洽，但跨模块阅读有认知成本。统一的代价是一次大范围重命名。**希望在评审中定调。**

**⚠️ Q9：能力的装配期交叉校验，目前只覆盖了一部分能力域。**

现在实际比对的是会话、对话、定时这几个有完整插件实现的槽位；其余能力域的协议槽位已经定义，但并非每个引擎都落了实现（openclaw 的 MCP 与技能能力至今由交付层直接服务）。也就是说，「声明了却没接上，启动即失败」这条保证在这几个域上还没有完全生效。这是已知的待收敛项，不是设计意图。

### B.2 我要改 X，应该动哪

| 我要做的事 | 应该动的位置 |
| --- | --- |
| 加一个公开接口 | 交付适配加路由 → 从服务契约层注入契约 |
| 加一个领域能力 | 领域模块内定义契约 + 实现 → 服务契约层转出 |
| 换一个基础设施实现 | 对应实现集里加实现 → 改组装根的一处绑定 |
| 加一个新的外部依赖 | 先定插件契约，再写实现 |
| 接一个新引擎 | 反腐层 + 原生端口契约 + 传输实现 + 组装根，各加一套 |
| 给引擎加一个能力 | 能力域协议定协议 → 各引擎反腐层接上 → 组装根声明 |
| 改一个模块的依赖范围 | 同步改该模块的白名单声明，否则检查失败 |
| 做一个难以回退的系统决策 | 写一份架构决策记录 |
| 确实需要突破某条不变量 | 写豁免 —— 要有负责人和期限 |
