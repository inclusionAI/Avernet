# teclaw 引擎契约增补：`cli_tools`

> **给 teclaw owner 的实现说明。**
>
> 一句话：**下发契约不变，只新增一个 `cli_tools` 段。**其余部分（artifact
> 的组装、投递方式、`{store, path}` 引用形态、`engine_ext` 的不透明约定）
> 全部保持现状，本文档不改动其中任何一条。
>
> 需要 teclaw 侧实现的，只有「把 `cli_tools` 里声明的可执行文件放进容器，并
> 保证它在 agent 进程的 PATH 上」。**具体怎么放、放在哪里、沙箱怎么管，都是你们
> 的实现细节，本文档不过问。**
>
> **状态（2026-08-31）：本文档没有开放问题**，结论见 §8。

---

## 1. 为什么需要这个

平台正在做 **Bot Config Manifest**：用户提交一份声明式配置清单，平台在生命
周期边界上把它落成真实实体（skills / identity / resources / mcp …）。其中一
类是**命令行工具**——用户希望模型能直接调用自己提供的 CLI。

这个能力在仓库里已经有手工版本：singlebox 的编排脚本把 `bcs-cli` 二进制挂到
PATH 上，再配一个 SKILL.md 教模型怎么用。`cli_tools` 是把这套「二进制 +
用法说明」的双件套产品化、声明化。

**ARCA 系**由平台注入 PATH（我们自己实现）。**teclaw** 的容器由你们管理，
平台不进容器，所以这一段需要你们实现——这是本文档存在的唯一原因。

## 3. 契约增补

### 3.1 artifact 顶层新增字段

```jsonc
{
  "schema_version": 4,          // 不升版
  "engine_type": "teclaw",
  "skills": [ … ],              // 不变
  "resources": [ … ],           // 不变
  "identity_files": [ … ],      // 不变
  "mcp": { … },                 // 不变
  "stores": { … },              // 不变
  "engine_ext": { … },          // 不变

  "cli_tools": [                // ★ 新增
    {
      "name": "mycli",
      "store": "bot-data",
      "path": "staff_u1/bot7_42_publish/teclaw/cli/mycli",
      "md5": "9f2c1b7d4e5a60318c2f0ab4d7e9c135",
      "version": "1.4.2"
    }
  ]
}
```

### 3.2 `cli_tools` 条目字段

**一个条目 = 一个命令 = 一个文件。**这是本段最重要的一句话：`path` 指向的不是
一个目录，而是**这个命令的可执行文件本身**。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `name` | string | ✅ | 工具标识符，**同时就是命令名**：落地后 agent 进程按 `name` 调用（`mycli`，不是绝对路径）。不含路径分隔符；平台保证同一 bot 内唯一（§3.3.2） |
| `store` | string | ✅ | 索引到 `stores` 的 key，与 skills / resources 同一机制 |
| `path` | string | ✅ | 相对 `store` 的路径，**指向一个文件**——就是要被置为可执行并暴露成命令的那个文件（§3.3） |
| `md5` | string | ✅ | `path` 所指文件内容的 MD5（32 位小写十六进制），由平台在物化后计算并写入。**用途是变更判据**：同名工具 `md5` 未变即无需重新下载/替换（§3.3.1） |
| `version` | string | ❌ | 元数据，仅用于审计与展示。引擎不需要理解 |

> **为什么没有 `entrypoints`。**早期草案里一个条目是「一个目录 + 一份该目录内
> 要暴露成命令的相对路径清单」。现在这一层被**摊平**了：包在平台侧被解开，取出
> 用户声明的那**一个**可执行文件，artifact 里的 `path` 直接指向它。于是「哪些
> 文件是命令」这个问题在到达你们之前就已经没有了——**数组里有几项，就是几个
> 命令**。随之消失的还有一整套只为约束 `entrypoints` 取值而存在的规则（路径穿越、
> 符号链接逃逸、包内 basename 撞名），见 §3.3.2。

### 3.3 平台保证：下发的一定是「一个可执行文件」

这一条是为了让你们那边尽量简单——**拉取、解包、校验、取文件全部由平台完成**：

- 用户在 manifest 里可以写单个二进制，也可以写 `.tar.gz` / `.zip` 压缩包 **加上
  包内那个可执行文件的路径**。
- 平台负责拉取、**强制校验 `sha256` digest**、（压缩包形态）解包并取出声明的那
  个文件、把**该文件**写入 store、并计算它的 `md5`。
- 所以 artifact 里的 `path` **永远指向一个文件**，两种形态在你们眼里完全一样。

**引擎侧不需要处理压缩包、不需要校验 sha256、不需要判断文件格式、也不需要在一棵
目录树里挑文件。**

> **随之而来的一个真实限制，先讲在前面。**因为下发单位是「一个文件」，**需要同包
> 辅助文件的工具（`bin/tk` 去 exec `libexec/helper`，或运行时要读同包的 `lib/`）
> 在 v1 不被支持**——包里其余文件不会被下发。v1 的口径是：`cli_tools` 交付的是
> **自包含的单个可执行文件**（静态二进制是它的典型形态）。这同时消掉了上一版契约
> 里那个已知问题：「对象存储不保留权限位，所以包内被 exec 的辅助程序会 `EACCES`
> 失败」——现在没有包内辅助程序这回事了。

### 3.3.1 `md5`：变更判据，不是校验门

平台在物化后计算 `path` 所指文件的 MD5，写进 artifact。**这是平台自己算的值，
不是对象存储的 ETag**——分片上传的 ETag 并不等于内容 MD5，所以这个字段是显式
携带的，不要用 ETag 代替它。

**它的用途是让你们省掉重复工作。**收到新 artifact 时，对同名工具比较 `md5`：

- **`md5` 与容器内现有的相同** → 内容没变，**不必重新下载，也不必删了重放**；
- **`md5` 不同** → 内容变了，按新的重新落地（替换掉旧的那个文件）。

`md5` 是**必填**的，因为没有它你们就只能每次都重下。

> **它不是一道拒绝门。**早先的版本把这条写成「不符则拒绝该条目并报错」，那是
> 过度设计：完整性对抗那一半由平台侧对用户声明的 `sha256` 的强校验负责，已经在
> 下发之前完成。要不要额外做一次落地前的一致性检查，由你们自己决定，本契约不
> 作要求。

### 3.3.2 平台保证：命令名唯一

**命令名就是 `name`。**平台在 `PUT` 时保证同一个 bot 的所有 `cli_tools` 条目
`name` 两两不同，且不含路径分隔符。

所以你们不需要处理重名冲突，也不需要定义「谁覆盖谁」的规则——那种情况在到达
你们之前就被拒绝了。

> 上一版契约在这里有一整段关于 basename 撞名的规则（同一个包内 `bin/tool` 与
> `helpers/tool`、两个不同工具各自的 `tool`）。摊平之后这些情况都不存在了：一个
> 条目一个命令，命令名就是这个条目的 `name`。
>
> v1 不提供命令别名（`expose_as` 之类）。要改命令名，改 `name` 即可——它不再与
> 文件名耦合。

### 3.4 需要 teclaw 实现的行为

1. **放置**：把 `path` 指向的**文件**取到容器内的某个位置。**具体落在哪里由
   你们决定**——和 skills / resources 一样，平台不规定物理路径。

2. **判断是否需要重新落地**：比对 `md5`，与容器内现有同名工具相同则跳过（不必
   重下、不必替换），不同则按新的重新落地（§3.3.1）。

3. **可执行位**：这个文件在容器内必须是**可执行**的。这一点平台无法代劳：对象
   存储不保留 POSIX 权限位，所以执行位必须由取下来的一方设置。**每个条目就是一个
   要被置位的文件**，不需要判断「包内哪些文件该置位」。

4. **PATH**：该命令必须能被 **agent 进程**直接按名字调用——即 `mycli` 而不是
   `/some/abs/path/mycli`，**名字取 `name`**。做法由你们决定：放进一个已在 PATH
   上的目录、建软链、或把工具目录追加进 PATH 都可以。

   > 落地文件名与 `name` 不一致时（比如 store 里的路径带版本号），以 `name` 为准
   > ——它就是契约里的命令名。

5. **覆盖语义**：`cli_tools` 与其他类目一样遵循**全量覆盖**——artifact 里这个
   数组就是**完整期望状态**。上一版投递过、这一版不在数组里的工具，应当**移除**
   （命令不再可调用）。数组为空 `[]` 表示「不应有任何 manifest 下发的工具」。

   > 这条与你们现有的重新下发语义一致，不是新规则，只是明确写下来。

### 3.5 一个完整的 artifact 片段

```jsonc
{
  "schema_version": 4,
  "engine_type": "teclaw",
  "version": 7,

  "stores": {
    "bot-data": {
      "type": "oss",
      "bucket": "avernet-prod",
      "base": "teclaw/prod/bolt_data"
    }
  },

  "cli_tools": [
    {
      "name": "mycli",
      "store": "bot-data",
      "path": "staff_u1/bot7_42_publish/teclaw/cli/mycli",
      "md5": "9f2c1b7d4e5a60318c2f0ab4d7e9c135",
      "version": "1.4.2"
    },
    {
      "name": "tk",
      "store": "bot-data",
      "path": "staff_u1/bot7_42_publish/teclaw/cli/tk",
      "md5": "3e7a5c90d1f24b86ae0c7d5619b3f042",
      "version": "0.9.0"
    }
  ],

  "identity_files": [
    {
      "name": "TOOLS.md",
      "store": "bot-data",
      "path": "staff_u1/bot7_42_publish/teclaw/identity/TOOLS.md"
    }
  ]
}
```

解读：

- `mycli` 用户声明的就是一个静态二进制。平台拉取、校验 sha256、写入 store。
  落地后 agent 进程执行 `mycli --version` 应当可用。
- `tk` 用户声明的是一个 `.tar.gz` 包加包内路径 `bin/tk`。**解包和取文件都发生在
  平台侧**，到你们这里它与 `mycli` 没有任何区别——一个文件、一个命令。包内其余
  文件不下发（§3.3 的限制）。
- 两个条目的 `md5` 互不相同，各自是该文件内容的 MD5。
- `TOOLS.md` 是普通 identity 文件，走现有通道。它是用户用来告诉模型「有哪些
  命令、怎么用」的——**用法认知不属于 `cli_tools` 的职责**，`cli_tools` 只保证
  命令在 PATH 上。

## 4. 用例

### 用例 1：单个静态二进制

用户 manifest：

```yaml
manifest:
  cli_tools:
    - name: mycli
      source: https://my-svc.example.com/tools/mycli-linux-amd64
      digest: "sha256:3f7a…"
      version: "1.4.2"
```

平台做的事：拉取 → 校验 digest → 写入 store → 计算 md5。

artifact 里出现：`{name: "mycli", store: "bot-data", path: "…/cli/mycli",
md5: "9f2c…", version: "1.4.2"}`。

**期望结果**：容器内 agent 进程执行 `mycli` 可用。

---

### 用例 2：压缩包里的一个可执行文件

```yaml
manifest:
  cli_tools:
    - name: tk
      source: https://my-svc.example.com/tools/toolkit-0.9.0.tar.gz
      subpath: bin/tk               # 包内哪个文件是这个命令
      digest: "sha256:9b21…"
      version: "0.9.0"
```

平台做的事：拉取 → 校验 digest → 解包 → **取出 `bin/tk` 这一个文件** → 写入
store → 计算 md5。

**期望结果**：`tk` 命令可用。**包内其余文件不会下发**——artifact 里只有这一个
文件（§3.3）。一个包里有两个命令时，用户写**两个条目**，各自指定 `subpath`；
到你们这里就是两个独立的文件。

---

### 用例 3：升级（同名工具换版本）

第一次投递 `mycli` v1.4.2；用户改 manifest 到 v1.5.0，平台重新投递。

artifact 里 `mycli` 的 `path` 变了（新的 stage-scoped 路径），`md5` 与 `version`
也随之改变。

**期望结果**：容器内 `mycli` 是新版本。旧版本不应残留、不应出现两个版本共存。

---

### 用例 4：移除

用户从 manifest 里删掉 `tk`，只留 `mycli`。新 artifact 的 `cli_tools` 只有一项。

**期望结果**：`tk` **不再可调用**，其文件被清理。`mycli` 不受影响。

> 这就是 §3.4 第 5 条的全量覆盖：数组是完整期望状态。

---

### 用例 5：清空

用户写 `cli_tools: []` —— **一个显式的空数组**。

**期望结果**：所有由 manifest 下发的 CLI 工具都不再可调用。

> **注意区分「空数组」与「整个类目缺席」。**只有显式的 `cli_tools: []` 才是「集合
> 为空」这个声明。用户如果是**把 `cli_tools` 这一段整个删掉**，那是「不表态」——
> 平台不会碰这个类目，也不会给你们下发一个空数组。做部分更新的客户端不应该因为
> 没写这一段就丢掉正在用的命令。

> 注意：**只清理 manifest 下发的工具**。容器镜像里自带的命令、你们自己装的
> 工具，都不在这个范围内——平台下发的工具应当落在一个可辨识的位置，正是为了
> 让这次清理有明确边界。

---

### 用例 6：重复投递同一个 artifact（幂等）

同一份 artifact 再投递一次，内容完全没变。

**期望结果**：收敛到同一状态，不产生副作用、不重复堆积。这与你们现有的
convergent re-delivery 语义一致，此处只是确认它对 `cli_tools` 同样成立。

## 5. 不在本次范围内

明确列出，避免过度设计：

| | 说明 |
| --- | --- |
| **多文件工具包** | 一个条目下发一个文件。需要同包辅助程序或运行时读同包 `lib/` 的工具**不在 v1**（§3.3）——请按「自包含的单个可执行文件」理解本契约。真有这种需求，用户当前的出路是把它打成自包含二进制 |
| **包管理器安装**（npm / pip / apt） | 属命令式领域，不进 manifest。ARCA 侧走 startup script；teclaw 不支持 script，因此这类需求在 teclaw 上暂不支持 |
| **沙箱 / 权限策略** | 用户提供的二进制在容器内的权限边界由 teclaw 决定。平台不做规定，但**如果你们有策略上的顾虑，这是需要提出来的地方**——它的能力面与 script 相邻 |
| **架构适配** | v1 只承诺 `linux/amd64`（ARCA 机群已确认）。多架构分发是后续话题 |
| **用法认知** | 模型怎么知道有这些命令、怎么用——走用户自己声明的 identity（如 `TOOLS.md`）或配套 skill，不是 `cli_tools` 的职责 |

## 6. 兼容性

- **`schema_version` 维持 `4`。**本次不升版：`cli_tools` 作为一个新增顶层字段直接
  出现，由**「未知字段忽略而非报错」**承担兼容（`engine-convergence-contract.zh-CN.md`
  A5，你们已同意）。所以不存在「旧引擎读到更高版本号」这回事。
- **字段出现 = 完整期望状态。**一旦平台开始产出这个字段，它与其他类目一样**每次
  都完整出现**：artifact 是从平台实体读出的**全量快照**，不是 manifest 的差分。
  所以 `"cli_tools": []` 的含义就是「这个 bot 没有任何平台下发的工具」，按 §3.4
  第 5 条移除即可——它不是需要特别提防的信号。
- **字段缺席 = 这个平台版本还不产出工具。**在 `cli_tools` 落地之前，平台根本不发
  这个键。缺席意味着「还没有这个功能」，容器内也从来没有过平台下发的工具，因此
  **没有任何东西需要保留或移除**——按 A5 忽略即可。

  > 早先的版本把缺席写成「保持现状，不要动」，并援引 manifest 层「未声明的类目
  > 不碰」作为理由。**那个理由是错的**：manifest 层的「声明 / 未声明」在 artifact
  > 组装之前就已经消解掉了，你们收到的永远是全量状态。这里保留「缺席」这个状态，
  > 纯粹是因为功能尚未上线，不是一种需要你们实现的语义。

## 7. 验收清单

供实现完成后自查，也是平台侧联调时会验证的点：

- [ ] 每个 `cli_tools` 条目，agent 进程可按 **`name`** 直接调用（不是绝对路径）。
- [ ] `path` 被当作**一个文件**处理，且该文件在容器内**可执行**。
- [ ] 同名工具 `md5` 未变时**不重复下载/替换**；`md5` 变化时容器内确实换成了新内容。
- [ ] 落地文件名与 `name` 不一致时，命令名以 **`name`** 为准。
- [ ] 同名工具换版本后，容器内是新版本，无旧版本残留。
- [ ] 上一版有、这一版没有的工具，命令不再可调用。
- [ ] `cli_tools: []` 清空所有 manifest 下发的工具，且**不影响**镜像自带命令。
- [ ] 重复投递同一 artifact 收敛，无副作用堆积。
- [ ] 无 `cli_tools` 字段的旧 artifact 行为不变。

## 8. 已确认的结论（2026-08-31）

本节原本是四个待回答的问题，现已全部关闭，改为记录结论。

| | 结论 |
| --- | --- |
| **落点与 PATH 的具体做法** | ➖ **不问了，由你们决定。**§3.4 的 3、4 两条是**要求**（文件可执行、命令按 `name` 在 agent 进程 PATH 上可调用）；怎么实现是你们的实现细节，平台不需要知道，也不记录 |
| **`md5` 的用途** | ✅ **变更判据，不是校验门。**同名工具 `md5` 未变即无需重新下载/替换；字段**必填**。详见 §3.3.1 |
| **沙箱策略** | ➖ **不问了，由你们决定。**用户提供的二进制在容器内的权限边界属于 teclaw 的自治范围 |
| **`schema_version`** | ✅ **维持 `4`，不升版。**`cli_tools` 直接作为新增字段出现，由「未知字段忽略」保证兼容 |
| **teclaw 不支持 `script`** | ✅ 确认。平台在写入时即拒绝，能力矩阵照此标注 |

**因此本文档对你们没有开放问题**，只有 §3.4 的五条要求和 §7 的自查清单。
