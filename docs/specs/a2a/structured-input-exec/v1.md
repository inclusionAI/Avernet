# Structured Input exec profile v1

Status: implementation in progress. Harness codec, Task continuation, acceptance
persistence and native SDK HTTP tests pass; the demo order-demo Card advertises
this profile. BCS schema/reply/receipt decoding and independent budget/storage
conformance pass. Production BCS interaction delivery and budget wiring are now
connected; real Workbench -> BCS -> Harness -> Ling approve/deny acceptance
passes. The broader A2A implementation still has remaining acceptance gates.

Profile identifier:
`https://github.com/inclusionAI/Avernet/blob/dev/docs/specs/a2a/structured-input-exec/v1.md`

This is the BCS exec business profile of the upstream
[Structured Input draft](https://github.com/a2aproject/experimental-ext-structured-input/blob/ed844541803ad096dc2e12e084a29d761d91b44e/v1/spec.md),
pinned to `ed844541803ad096dc2e12e084a29d761d91b44e`. It does not add an RPC or
replace the Structured Input extension URI:
`https://github.com/a2aproject/experimental-ext-structured-input/tree/main/v1`.
The intended Card declaration uses that URI, `jsonschema_draft: "2020-12"`,
and `bcs_exec_profile` equal to the profile identifier above.
BCS carries full extension parameters to its protocol adapter. Recognizing only
the URI is insufficient: required incompatible draft/profile declarations fail
validation; an optional incompatible declaration remains unnegotiated.

The wire request is a DataPart in the INPUT_REQUIRED status message, with
metadata at the extension URI containing type `input_schema` and a unique
request `id`. Replies tag their DataPart as `structured_input` with the same
`id`, on the same authenticated Task/context. Invalid schema input repeats the
request with a Basic-output `validation_error` part. An identity mismatch is a
correlation rejection, not a claimed schema validation failure.

## Approval data

One pending request covers one Harness confirmation batch. Its schema accepts
an object with exactly one property, `decisions`. That property is an object
with at least one tool-call-ID key. Each known tool accepts the string
`allow_once` or `deny`; unknown tools, extra properties, strings such as
`approve`, booleans and free text are rejected. Not every tool must be present
in one reply: each patch is independently valid against this schema.

The server validates the entire patch before applying any part. Equal repeats
are no-ops; changing an accepted decision is invalid. After a partial reply,
the server retains the same request ID and publishes the updated schema. An
accepted tool uses JSON Schema `const` for its accepted decision. Tools without
a decision retain their two-value enum. The actual Harness ConfirmationInput
is constructed only after all tools have decisions; each tool keeps its exact
Harness tool-call ID and APPROVE/REJECT mapping. The execution owner must resume
this batch once, after confirming cleanup of the preceding advance.

## Business annotations

The root schema's `x-bcs-exec` annotation contains:

- `profile` and integer `version: 1`.
- `expiresAtMs`, an absolute server-supplied approval expiry.
- `tools`, an object keyed by tool-call ID, each holding the name, argument
  snapshot and `argsSha256`.
- `accepted`, the decisions already accepted for this request.

These annotations express exec UI and approval semantics; they are not standard
A2A or general JSON Schema authorization. Other Structured Input clients can
still validate the schema and supply decisions. BCS must recognize the declared
profile before creating exec cards. It checks accepted decisions against the
same request/tool/argument bindings before acknowledging a local resolution.
It never infers approval from ordinary text or a tool-start observation.

Harness snapshots the arguments before publication. The digest is SHA-256 of
UTF-8 JSON with object keys sorted using the pinned Jackson encoder. Clients
retain this digest as an opaque binding rather than reserializing arbitrary
numbers to reproduce it. Changed tool arguments require a new approval request.
Returned schema trees are independent of the authoritative snapshot.

The codec bounds a batch to 64 tools, each argument encoding to 128 KiB and the
complete schema encoding to 240,000 bytes. Oversized input is an explicit
capability failure, never automatic approval. Replies at or after the approval
expiry are rejected. BCS interaction routing, wait/total budgets and queue/Redis
deadline integration are now wired, with cross-language exec acceptance evidence.
The Harness runtime provides cancellation and persisted acceptance.

BCS's decoder accepts the exact profile subset: an object requiring only
`decisions`, a nonempty patch object with no additional properties, and each
known tool's two-value enum or accepted-value const. Validation keywords outside
this subset (including allOf, references and additional required fields) fail
explicitly rather than disappearing from a projected card. Descriptive title
and description annotations are retained. Request/tool/message identifiers are
nonblank and bounded to 4,096 UTF-8 bytes. Numbers must be positive exact safe
JSON integers, including ProtoJSON's integer-valued doubles. Input identity must
match the correlated Task/context. Schema updates may narrow expiry and add
decisions, but may not change tools/argument snapshots/digests or remove/change
accepted decisions. Digest bindings remain opaque across Java/Rust encoders.


## Acceptance persistence

The server records decisions before publishing acceptance or resuming the
engine. Task.metadata at the profile identifier contains `version: 1` and a
`requests` object keyed by input request ID. Each value contains `accepted`,
a tool-call-ID to decision object. The Task retains earlier request decisions
when a later batch appears. Status-message metadata carries the current
`version`, `id` and `accepted` values for streaming clients. Task-level metadata
is authoritative for GetTask calibration after a fast completion.

The Harness Task store reserves this metadata key and preserves its accepted
values against older SDK snapshots. Conflicting decisions cannot overwrite a
prior acceptance. The proof survives completion/reopen, is isolated by Bot and
is published in memory only after the database write succeeds. It proves receipt
of a decision, not successful tool execution. At most 64 batches and 240,000
encoded bytes of acceptance history are supported per Task; exceeding either
limit fails before engine continuation. No token-by-token acceptance writes or
additional acceptance table is introduced.


The native Java SDK HTTP fixture serializes Struct numbers such as the profile
version and minProperties as `1.0`. Consumers must accept integer-valued JSON
numbers without accepting strings such as `"1"` as numeric versions. The Rust
SDK envelope/projection test uses the captured Java fixture and preserves both
the complete schema and UTF-8 tool titles. This wire test does not claim that
BCS already creates/resolves exec interactions.
