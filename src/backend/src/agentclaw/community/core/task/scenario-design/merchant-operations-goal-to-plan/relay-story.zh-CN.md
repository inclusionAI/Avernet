# 一句经营目标如何串行变成经营方案

## 1. 故事的核心

店主不需要预先设计一条多 Bot 工作流，也不需要一开始把所有专家拉进群。

店主只提出经营目标、底线和授权边界。店长 Agent 先判断当前最关键的缺口，再把任务交给相应的专业 Bot。

每个 Bot 都遵循同一个原则：

> 我先完成自己负责的部分；如果结果暴露出一个我无法判断或无法执行的问题，就把“已有背景、已完成的工作、处理不了的问题和交给下家的目标”一起传给下一个职能。

因此，Bot 的加入不是预先编排好的名单，而是由问题自然推动出来的。

## 2. 推荐的最小角色

```text
店主
  ↓
店长 Agent
  ↓
营销方案 Agent
  ↓
会员与服务设计 Agent
  ↓
客流与产能 Agent
  ↓
供应履约 Agent
  ↓
公共风险评审群
    ├── 业务风险 Agent
    └── 舆情与平台风控 Agent
  ↓
店长汇总
  ↓
店主验收
```

条件性角色：

```text
公共风险评审发现缺少系统承接能力
  ↓
执行/研发 Agent
  ↓
回到公共风险评审
```

执行/研发不是每次活动都必须出现。只有当风险评审发现“需要一个当前没有的执行能力”时才被召集。

## 3. 故事背景

一家理发店准备做 18 周年店庆。

店主提出：

> 下个月做 18 周年店庆，第一目标是增加客流，第二目标是提高护理套餐转化。新客推王牌剪发，老客推护理套餐，品质不能下降。

店主随后补充本轮专属决定：

- 活动具体开始日期；
- 商家促销预算上限；
- 备货新增现金占用上限；
- 活动贡献毛利底线；
- 哪些事项店长可以自行决定，哪些必须回到店主审批。

这些内容进入店长的私有经营账本。对外协作只发送脱敏后的目标、公开价格、服务事实和待验证假设。

## 4. 第一跳：店长把目标交给营销方案

店长判断：当前最缺的是一套活动打法，而不是马上计算库存或排班。

店长交给营销方案 Agent：

```text
请基于本轮经营目标，提出周年庆营销方向。
请说明你的判断依据、关键假设，以及当前无法独立判断的问题。
不要接触店主的私有成本、毛利底线和预算上限。
```

营销方案 Agent 产出：

```text
初步方向：

- 新客：王牌剪发体验券；
- 老客：护理套餐和周年庆专属权益；
- 平台侧：通过分阶段投放扩大覆盖。
```

但它发现自己处理不了两个问题：

- 老客不能统一使用同一种权益；
- 护理套餐的服务组合还没有被定义。

所以它不硬写最终方案，而是向下交接：

```text
我已经确定了新客引流和老客护理两个方向，
但当前方案依赖更细的客群和服务定义，这部分超出我的判断范围。

请你基于已有背景继续细化，并返回：
- 你建议采用的客群/服务组合；
- 影响选择的关键依据；
- 仍然无法判断、需要继续向下游求证的问题。
```

## 5. 第二跳：会员与服务设计细化“给谁、卖什么”

会员与服务设计 Agent 输出：

```text
老客建议分为：

- 沉默老客：护理唤醒权益；
- 高频剪发老客：服务升级，不建议直接大幅降价；
- 高价值护理客：预约优先和增值权益；
- 普通老客：限量护理套餐。

护理套餐建议：

- 基础护理 + 头皮护理；
- 单次服务约 90 分钟；
- 必须提前预约；
- 不加入强依赖单个技师的复杂项目。
```

它完成了客群和服务定义，但暴露出新的问题：

> 套餐卖多少、活动券放多少，不能凭营销直觉决定，需要知道门店的真实服务能力。

于是向客流与产能 Agent 交接：

```text
当前方案已经明确了主要客群和服务组合，
但服务数量和投放节奏还没有经过门店能力验证。

请你判断这套方案是否能被门店承接，并指出需要调整的地方。
```

## 6. 第三跳：客流与产能解决“能不能接得住”

客流与产能 Agent 负责：

- 新老客流量基线；
- 预计领券、预约和到店转化；
- 新客剪发与护理服务的分钟数；
- 工作日和周末的差异；
- 工位和员工容量；
- 活动核销量上限。

它可能发现：

```text
- 新客剪发平均占用 45 分钟；
- 护理套餐平均占用 90 分钟；
- 周末自然客流已经占用大部分工位；
- 新客券和护理套餐不能一次性释放。
```

它给出修订建议：

```text
- 新客券先释放 30 份，再根据实际核销分批增加；
- 周末设置每日活动上限；
- 护理套餐采用预约制；
- 未来 7 天预约占用率超过 75% 时暂停新增投放；
- 员工临时减少时，降低次日活动名额。
```

但它无法确认护理耗材是否支持这个数量，也无法确认补货交期，于是继续交接：

```text
当前方案涉及护理服务的首批承诺，
但这些承诺是否有供应和履约事实支撑还不清楚。

请你从供应履约角度判断当前方案能承诺到什么程度，
并提出必要的调整或待确认事项。
```

## 7. 第四跳：供应履约解决“承诺之后有没有东西”

供应履约 Agent 输出：

```text
- 已确认可用库存：30 份；
- 在途库存：20 份，但暂无正式到货回执；
- 首批最多承诺 30 份；
- Plan B 需要确认交期；
- 替代 SKU 需要服务质量确认；
- 在途库存不能直接计入当前可售量。
```

于是候选方案形成：

```text
周年庆方案 V1：

新客：
- 王牌剪发体验券；
- 首批 30 份；
- 分批投放；
- 周末设置上限。

老客：
- 按会员类型差异化触达；
- 护理套餐首批限量 30 份；
- 必须预约。

履约：
- 只使用 30 份已确认库存；
- 在途库存作为 Plan B；
- 预约占用率超过 75% 时暂停新增投放。
```

供应履约 Agent 处理不了的是：

> 我能确认库存、采购和交期，但不能判断活动公开之后是否会引发投诉、差评或平台处罚。

因此方案进入公共风险评审。

## 8. 公共风险评审：允许保留不同意见

公共风险评审不是一个万能的“风险总 Bot”，而是一个由两个具体角色组成的评审群：

```text
业务风险 Agent
舆情与平台风控 Agent
```

二者读取同一份候选方案，但关注点不同，也不要求最终意见完全一致。

### 8.1 业务风险 Agent

它检查：

- 活动和预算是否成立；
- 排班与产能是否接得住；
- 库存和 Plan A/B 是否可信；
- 服务品质是否会下降；
- 首批承诺是否过大；
- 店主私有授权是否被突破。

示例结论：

```text
业务风险：有条件通过

通过：
- 首批 30 份护理套餐有已确认库存支持；
- 新客券采用分批释放；
- 当前服务量未超过测算产能。

待修订：
- 必须写入每日活动上限；
- 预约占用率超过 75% 时暂停放量；
- 员工减少时需要降级规则；
- Plan B 需要正式交期回执。
```

### 8.2 舆情与平台风控 Agent

它检查：

- 原价和折扣是否有依据；
- 活动规则是否透明；
- 有效期和预约限制是否说清；
- 活动用户是否可能感受到服务降级；
- 等待时间增加是否可能造成差评；
- 是否存在薅羊毛、投诉或平台处罚风险。

示例结论：

```text
舆情与平台风控：需修订

问题：
- 护理套餐有效期和预约限制不够明确；
- 不建议使用“全城最低”等无法证明的表达；
- 活动高峰可能造成等待时间增加；
- 当前没有投诉和差评自动监测能力。

建议：
- 在活动页面公开服务内容和预约限制；
- 增加等待时间和客诉处置规则；
- 客诉超过阈值时暂停新增投放；
- 如需自动监测，交给执行/研发职能。
```

注意，评审结果可以是：

```text
业务风险：有条件通过
舆情与平台风控：需修订
```

不要求所有角色都输出 PASS。

## 9. 条件性分支：风险暴露出系统能力缺口

如果舆情与平台风控只要求人工每天查看投诉和预约情况，店长可以把它写入 SOP，直接交给店主验收。

如果店主要求自动监控，或者风险评审认为没有监控就不能放行，则产生一个新的下游任务：

```text
当前缺少活动期投诉、差评和预约占用率的自动监测能力。

请执行/研发职能：
- 接入可用的投诉、差评和预约数据；
- 定义告警阈值；
- 设计暂停投放或转人工复核的动作；
- 输出一个可验收的监控能力或明确的人工兜底方案。
```

执行/研发 Agent 完成后，将结果带着上游方案和风险清单回传，再由公共风险评审复核。

## 10. 店长汇总不是抹平分歧，而是形成可决策版本

店长把评审意见整理为方案 V2：

```text
周年庆方案 V2：

- 新客王牌剪发券分批释放；
- 周末设置每日活动上限；
- 老客按会员类型差异化触达；
- 护理套餐首批限量 30 份并绑定预约；
- 在途库存不计入当前承诺；
- Plan B 需取得交期和品质回执；
- 预约占用率超过 75% 时暂停新增投放；
- 不得使用无法证明的极限宣传词；
- 活动规则、服务内容、有效期和预约限制必须公开；
- 暂时由门店人工查看预约和客诉，或等待自动监控能力补齐。
```

方案中可以保留不同意见：

```text
营销希望扩大投放；
产能希望控制投放；
会员角色希望差异化触达；
供应角色希望等待回执；
舆情角色希望提高公开规则透明度。
```

店长的工作不是让所有人都说“同意”，而是把分歧转成：

- 数量上限；
- 触发条件；
- 版本变更；
- 责任人；
- 人工兜底；
- 需要店主确认的决策。

## 11. 店主最终验收

店主看到的不是“所有 Bot 一致通过”，而是：

```text
当前方案在以下条件下可接受：

- 首批护理套餐最多 30 份；
- 新客券分批释放；
- 预约占用率超过 75% 时暂停投放；
- 活动规则和预约限制公开；
- Plan B 等待供应商回执；
- 舆情和预约暂时人工监控。

尚未完成：
- 平台活动实际上线；
- 采购付款；
- 库存锁定；
- 自动舆情监控。
```

店主可以：

```text
接受当前版本
```

也可以：

```text
只接受新客券，护理套餐暂缓
```

或：

```text
不接受人工监控，先补齐自动监控能力
```

## 12. 最终串行链路

```text
店主目标
→ 店长判断关键抓手
→ 营销方案
→ 营销发现客群/服务组合不够细
→ 会员与服务设计
→ 服务设计发现无法判断承接上限
→ 客流与产能
→ 产能发现无法确认耗材和交期
→ 供应履约
→ 供应发现无法判断公开后的投诉和平台风险
→ 业务风险 + 舆情与平台风控
→ 店长汇总修订
→ 店主验收
```

条件分支：

```text
舆情与平台风控发现缺少自动监测能力
→ 执行/研发 Agent
→ 回到风险评审
```

这条链路的重点不是 Bot 数量，而是每个交接都有一个明确原因：

```text
营销不能决定客群和服务组合；
服务设计不能判断门店接待上限；
产能不能确认库存和交期；
供应不能判断公开后的舆情风险；
舆情发现没有现成系统能力，于是才继续交给执行/研发。
```

## 13. 输入输出不能由上游替下游设计

串行协作最容易犯的错误，是上游把下游的专业检查清单也写进任务里。例如：

```text
请确认库存、预留、安全库存、在途、MOQ、交期、Plan A/B……
```

这意味着上游已经假定自己知道供应履约 Agent 应该检查什么，甚至提前替它定义了工作方法。这样会造成两个问题：

- 下游只是在执行上游的清单，而不是发挥自己的专业判断；
- 上游漏掉的检查项，下游可能也不会主动补充。

更合适的交接方式是：

```text
当前方案涉及护理服务的首批承诺，
但这些承诺是否有供应和履约事实支撑还不清楚。

请你从供应履约角度判断当前方案能承诺到什么程度，
并提出必要的调整或待确认事项。
```

上游传递的是：

```text
背景 + 已完成的判断 + 暴露出的未知问题 + 期望解决的方向
```

下游自己决定：

```text
要查哪些事实 + 使用什么专业方法 + 输出什么结论 + 是否还要继续转交
```

### 13.1 各角色的输入和输出边界

| 角色 | 收到什么 | 自己负责什么 | 输出什么 | 何时继续交接 |
| --- | --- | --- | --- | --- |
| 店长 | 店主目标、底线、授权 | 判断第一关键缺口、控制信息披露 | 目标背景、授权后的公开任务 | 当前问题超出自己的专业能力 |
| 营销方案 | 经营目标、公开事实 | 形成活动方向和候选打法 | 营销方向、关键假设、待解决问题 | 客群、服务、产能等问题不是营销判断 |
| 会员与服务设计 | 营销方向、用户和门店事实 | 决定给谁、卖什么、如何触达 | 客群策略、服务组合、用户路径 | 需要验证实际服务能力或供应能力 |
| 客流与产能 | 客群、服务组合、活动假设 | 判断流量、服务量和门店承接能力 | 产能结论、容量限制、调整建议 | 需要库存、交期或履约事实 |
| 供应履约 | 方案中的服务/商品承诺 | 判断当前能承诺什么、如何补足 | 供应结论、履约条件、替代路径 | 暴露公开风险、规则风险或系统缺口 |
| 业务风险 | 候选方案及各方证据 | 判断经营后果和业务风险 | 风险结论、约束、放行条件 | 风险需要其他专业职能或执行能力处理 |
| 舆情与平台风控 | 同一份公开候选方案 | 判断公开后的信任、投诉和平台风险 | 风险结论、表达约束、处置条件 | 需要实时监控、自动拦截或平台系统能力 |
| 店主 | 最终方案、分歧、条件和未完成事项 | 做授权范围内的最终取舍 | 接受、部分接受、要求修改或拒绝 | 只有要求修改时才回到相应上游节点 |

### 13.2 任务交接的推荐格式

每个 Bot 的交接正文都可以保持四块结构：

```text
背景与目标：我在什么经营背景下工作。

我的产出摘要：我已经判断了什么，形成了什么候选结果。

处理不了的问题：我遇到了什么问题，为什么不属于我的能力边界。

完整正文：支撑下游继续判断所需的事实、假设、证据和分歧。
```

其中“处理不了的问题”不应该写成下游的完整待办清单，而应该写成一个**问题方向**。

例如不建议：

```text
请供应履约确认库存、预留、安全库存、在途、MOQ、交期和 Plan A/B。
```

建议：

```text
护理套餐的首批销售承诺缺少供应事实支撑。
请供应履约判断本轮可承诺范围，并指出影响承诺的关键条件。
```

### 13.3 什么时候可以传递具体字段

具体字段不是绝对不能传，而是要区分两种情况。

如果上游已经有真实事实，应该传事实：

```text
当前候选方案计划首批开放 30 份护理套餐，
这是本轮已经形成的公开候选，不是对供应履约的检查结论。
```

如果上游只是猜测下游要查什么，不应该把猜测伪装成清单：

```text
不要替供应履约预设它一定要查 MOQ、预留和安全库存。
```

下游可能确实会检查这些内容，也可能发现更关键的是：

- 服务耗材的批次品质；
- 供应商是否有正式交期回执；
- 活动承诺和采购授权是否匹配；
- 替代品是否能够维持原服务标准。

这些判断应该属于供应履约 Agent 自己的专业输出。

## 14. 这条链路的真正含义

这不是一条预先写死的“营销、会员、产能、供应、风险”流水线，而是一条由问题推动的 relay：

```text
店长认为当前缺营销打法
→ 营销发现客群和服务定义不足
→ 会员与服务设计发现缺门店承接能力
→ 客流与产能发现缺供应履约事实
→ 供应履约发现公开风险尚未评估
→ 风险评审发现是否存在系统承接缺口
→ 只有确实缺能力时，才继续交给执行/研发
```

如果某个 Agent 已经能够在自己的职责范围内完成判断，就应该直接输出结果，不为了“让更多 Bot 参与”而继续流转。

如果它发现的问题只是参数尚未确定，但自己有权限和能力保守决定，也不一定要交给下一个 Bot；可以在输出中记录假设、条件和失效边界。

只有满足下面的条件，才应该继续 relay：

```text
问题会改变当前方案；
问题需要另一种专业判断；
当前 Agent 没有权限或事实独立解决；
下游能够对这个问题产生新的、可验收的产出。
```
