BCN A2A Profile 与 Java Server SDK 详细设计

公司内 Agent 统一遵循的 A2A 协议标准，以及让 SOFABoot 平台按该标准提供 A2A Server 的 Java SDK。本稿用于内部评审，评审通过后规范性文本落回仓库 Markdown。

状态 评审草案 v0.22日期 2026-11-11范围 协议标准 + Server SDK技术栈 SOFABoot / JDK 17

评审方式。文中三类编号可以直接引用：

  • D1 已确认的决策，评审时只确认后果是否可接受。
  • P-01 Profile 的规范性条款，逐条评审。"必须"表示不满足即不合规。
  • Q1 待确认问题，需要评审给出结论；汇总在第 16 节。

1背景与问题

BCS 现在是公司级的 A2A 注册中心：Agent 把 AgentCard 注册到 BCS，BCS 作为 A2A Client 按 Card 调用 Agent。注册和 Client 侧能力已经具备，问题出在 Agent 一侧。

  • 大量 Agent 没有标准 A2A 接口。它们以各自的 RPC 接口或 HTTP 接口提供服务，要接入就得各自写适配。
  • 适配结果不一致。A2A 标准留了很多自由度（是否返回 Task、文本是追加还是替换、何时算结束、断流后怎么恢复）。BCS 对这些有明确的行为前提，目前只写在接入文档里，没有可检验的标准。
  • BCS 的扩展没有统一实现。工具观察、exec 审批等扩展，目前只有 Harness adapter 一份实现，且不在本仓库。
  • 多实例没有答案。现有文档明确说明内存 TaskStore 不支持多实例，而公司的 SOFABoot 应用默认多实例部署。

现有约定散落在接入指南、接口参考和各扩展文档中。本设计把它们收敛成一份标准，并提供参考实现。

4总体架构

本期的调用方向只有一个：BCS 调 Agent。Agent 不需要知道 BCS 的 Run、Session。唯一的反向调用是可选的推送通知（6.12）：Agent 向调用方指定的地址发送 Task 状态变化的提示，本期只定义语义，不实现。BCS 对外提供 A2A 服务后，Agent 也可以作为调用方，届时由 client SDK 支持，不在本设计范围内。

4.1调用路径：经 BCS 与直连

按 Profile 接入的 Agent 是内网可达、不鉴权的标准 A2A 服务，因此两个 Agent 之间在技术上可以直接调用，不必经过 BCS。BCS 可以只承担控制面（注册、发现、分发 Card、策略），数据面由两端直连。Profile 的条款对两种路径都成立，不假设调用方一定是 BCS。

BCS 在链路中提供的直连时补充手段
发现不受影响调用前向 BCS 查询 Card，之后直连
可见性和访问控制变弱：知道地址即可调用发现时只返回有权看到的 Agent；被调方用 AgentAuthorizer 按来源判断；需要更强保证时由 BCS 在发现阶段签发短期凭证，放入预留的 proof，被调方离线验证
审计和统一观测没有集中记录两端 SDK 输出统一的指标和链路；可异步向 BCS 上报调用摘要，不在调用路径上
用户身份和来源信息由调用方 Agent 填写可信度与经 BCS 时相同，都依赖内网互信（D1）

这样调用方的代码在两种路径下相同，路径策略集中在注册中心，并且所有 Bot 对调用方都表现为标准 A2A 服务。工作台的人机对话不受影响：BCS 自己调用 Agent 时始终使用保存的原始 Card。需要一并确定的问题：

  • 模式由谁决定。按 Agent 类型给默认值，Provider 或平台管理员可以调整。每个 Agent 固定一种，还是可以因调用方而异，待定。
  • 派生 Card 的规则。BCS 保存的原始 Card 不改写；对外提供的是它的一个视图。需要规定哪些字段原样保留、哪些由 BCS 改写。
  • BCN 地址模式不是强制。原生地址在内网可达且不鉴权（D1），知道地址即可绕过 BCS。必须经 BCS 的 Agent 需要配合网络层限制，或启用预留的 proof。
  • 模式切换与缓存。调用方会缓存 Card。需要规定 Card 的有效期；进行中的 Task 不随模式切换而换地址。

直连依赖 client SDK 和 BCS 的发现接口，BCN 地址模式依赖 BCS 对外提供 A2A 服务，都属于后续阶段，本设计不展开。汇总为 Q21。

5已确认的决策

编号决策直接后果被否决的方案
D1调用都在公司内部网络内完成（RPC，或内部域名上的 HTTP），协议不定义额外鉴权。GRPC、HTTP+JSON、JSONRPC 三种绑定都保留，都不鉴权信任边界是公司内部网络。Card 固定 securityRequirements: []。调用上下文的可信度等同于“调用方在内网内”。Bearer 下行凭据；签名的用户断言。成本高，与公司内部服务互信的惯例不一致。另外否决了“只保留 GRPC”。
D2多实例是一等约束SDK 的默认行为必须在多实例下正确；单实例只是特例。要求粘性路由。MOSN 负载均衡下不现实。
D3多实例只提供跨实例存储的 SPI 和参考实现Task 始终在接收它的实例上执行。其他实例只读写共享存储。基于消息队列的事件复制（a2a-java 的 replicated queue manager）。引入额外中间件依赖。
D4接受 D3 带来的三项降级跨实例订阅为轮询合成，粒度约 1 秒；跨实例取消有秒级延迟；审批续交要求引擎状态可从存储恢复。—
D5以进程内 SDK（API + SPI）作为本期唯一的交付形态公司 90% 以上技术栈是 Java。业务引入 starter、实现 SPI、自己运维存储。标准靠窄 SPI、TCK 准入和版本治理保证（8.11）。BCN 托管的协议适配层。多一跳，所有流式流量经过一个中心服务；本期不做，但核心保持可托管。
D6Profile 不包含提交去重扩展标准里没有提交幂等。初始提交结果未知时调用方不重发、报告结果未知。存储只需要一张表和三个原语。没有历史依赖，不需要兼容。保留原 BCS 的提交去重扩展。它要求永久保留占位记录、跨语言一致的请求摘要，并带来“占位成功但未执行”的失败窗口，复杂度与收益不相称。以后确有需要可以作为新扩展加回，不影响现有 Agent。
D7TaskStore 的参考实现只提供分布式缓存Task 记录是短生命周期、高频写入、到期清理的数据，适合缓存。业务接入只需要一个不淘汰数据的缓存实例，不用建表和清理任务。代价是主备切换时可能丢失个别 Task 的最近写入，按 9.8 的规则处理。数据库实现，无论作为默认还是备选。每秒整行更新占用业务库资源，接入要建表和配置清理；公司内的应用都已接入分布式缓存，备选没有使用者，只增加维护成本。

6Profile 规范

6.1定位

合规 Agent 是一个标准的 A2A 1.0 Server，任何标准 A2A Client 都能调用它。Profile 只做三件事：选定子集，收紧行为，规定怎么扩展。BCS 继续兼容不使用 SDK 但符合 Profile 的 Server。

6.2基线

条款内容
P-01接口的 protocolVersion 必须为 "1.0"。对象和绑定细节遵循 A2A 1.0.1 规范。不兼容 0.3 的方法名和字段（message/stream、kind、final）。
P-02必须提供 GRPC、HTTP+JSON、JSONRPC 三种绑定中的至少一种，可以同时提供多种。三种绑定地位相同，BCS 按 Card 中的声明顺序选择。GRPC 的服务为 lf.a2a.v1.A2AService，通过 SOFARPC Triple 暴露，经 MOSN 寻址；普通 Bolt/Hessian 接口不能替代。HTTP+JSON 和 JSONRPC 通过内部域名访问，流式使用 SSE。
P-03三种绑定的对象语义和行为必须一致，都不要求应用层凭据。同一 Task 可以通过任一已声明的绑定查询、订阅和取消。所有端点只能在公司内部网络可达。
P-04必须实现的方法由一致性等级决定（6.3）。Profile 之外的标准方法可以实现，BCS 不调用。
P-05text/plain 是所有 Agent 都必须支持的基线：必须接受纯文本输入，必须能只用文本给出完整结果。其他模态是可选能力，按 6.13 声明和协商。结构化 UI 内容通过已协商的扩展、按内容块规则（7.5）提供。
P-06JSON 使用 A2A 1.0 的 lowerCamelCase（ProtoJSON）。枚举使用全名，例如 ROLE_USER、TASK_STATE_WORKING。

6.12推送通知（可选能力）

A2A 标准有三种跟踪 Task 的方式：流式、轮询、推送通知。BCS 目前只用前两种。推送通知是调用方在提交时给出一个地址，Agent 在 Task 状态变化时主动通知。它适合三类场景：

  • 执行时间很长的 Task（几分钟到几小时），调用方不应一直持有连接或每秒轮询。
  • 非流式 Agent（L0），目前只能靠 1 秒一次的轮询跟踪。
  • 等待人工审批的 Task，等待期间没有输出。

Profile 现在就定义它的语义，否则各业务会按各自的理解实现。实现放在后续阶段。

条款内容
P-150推送通知是可选能力，通过 Card 的 capabilities.pushNotifications: true 声明。未声明的 Agent，四个推送配置方法必须返回 PushNotificationNotSupportedError（标准要求；GRPC 为 FAILED_PRECONDITION，HTTP 为 400）。未声明的 Agent 在 SendMessage 中收到推送配置时返回同一错误，不得静默忽略（标准未规定，这是 Profile 的收紧）。
P-151声明了推送能力的 Agent 必须同时支持两种设置方式：初始提交时的 configuration.taskPushNotificationConfig；以及标准的四个配置方法 CreateTaskPushNotificationConfig、GetTaskPushNotificationConfig、ListTaskPushNotificationConfigs、DeleteTaskPushNotificationConfig。配置随 Task 保存，到 Task 结束或被删除为止。一个 Task 可以有多个配置，Profile 限制为最多 4 个。
P-152只在 Task 进入终态或中断态（INPUT_REQUIRED）时发送，每次状态变化一条。文本增量、过程事件（E4）、内容块更新不发推送。标准只说“Task 状态变化时发送”，没有列出触发事件，这是 Profile 的收紧。
P-153推送是提示，不是事实。负载按标准使用 StreamResponse 格式，Content-Type 为 application/a2a+json；Profile 限定其中只放 statusUpdate（taskId、contextId、当前状态），不放 Artifact 内容和扩展数据。调用方收到后必须用 GetTask 取得结果。
P-154对每个配置至少尝试投递一次（标准要求）。失败时有限次退避重试，单次请求超时 10 到 30 秒（标准的建议值）。接收方以 2xx 确认、校验 Task 标识是自己预期的（标准要求），并能处理重复和乱序。标准不保证推送的顺序。投递失败不影响 Task 的状态。
P-155调用方不得只依赖推送。必须保留低频查询兜底，因为推送可能永远不到。
P-156Agent 必须限制推送地址：只向配置允许的内部域名发送，其他地址在设置时拒绝。这是为了防止调用方利用 Agent 去访问任意内部地址。标准的安全建议是拒绝内网地址，这在公司内网场景不适用，所以改为域名白名单。
P-157调用方在配置的 authentication 中给出 scheme: "Bearer" 和一个每个 Task 随机生成的 credentials。Agent 必须在推送请求的 Authorization 头中原样带回（标准要求）。接收方校验它与 Task 的对应关系。它用于关联和防止误投，不改变“调用 Agent 不鉴权”的决定（D1）。配置中的 token 字段在 1.0 中没有对应的请求头定义，Profile 不使用。凭据不得写入日志，Get 和 List 返回时必须隐去。

与多实例设计的关系

推送由写入该状态的实例发出：正常情况是执行实例，在状态写入存储成功之后发送；执行实例宕机后，由回收该 Task 的实例发送 FAILED。推送配置在 Task 记录中，任何实例都能读到。这与“只提供跨实例存储”（D3）一致，不需要实例之间通信。由于回收是惰性的（9.5），宕机后如果没有任何请求读到这个 Task，就不会有推送，这正是 P-155 要求查询兜底的原因。

6.13多模态输入输出（可选能力）

A2A 标准本身已经定义了多模态：Part 可以是文本、文件字节（raw）、文件地址（url）或结构化数据（data），并带 mediaType 和 filename；Card 和每个技能可以声明支持的输入输出类型；调用方用 acceptedOutputModes 声明能接收的类型。这些不需要扩展。

BCS 目前只处理文本，但标准不应该因此只定义文本，否则各业务的图片、文件能力会各自实现。Profile 沿用标准的多模态定义，只补充企业场景下标准没有规定的部分：文件怎么传、多大、对方不支持时怎么办。

P-102Card 以 required: true 声明本扩展时，未协商或缺少 userId 的请求必须拒绝，不得回退为默认用户或共享用户。
P-103Agent 必须把 userId 与 Task 一起保存。同一 Task 的续交消息如果带有不同的 userId，必须拒绝。
P-104GetTask、SubscribeToTask、CancelTask 不携带上下文，按 Task 关联处理。
P-105userId 不得写入 Artifact、状态消息或工具观察记录。
P-106调用方必须为每次调用填写 source。经 BCS 时，取值来自 BCS 已认证的调用关系（调用 BCN 接口的应用、发起协作的 Bot），不得来自请求体中的自述。直连时，调用方 Agent 填写自己的应用名和 Bot 标识。
P-107是否接受调用由 Agent 决定。Profile 不规定授权规则。Agent 拒绝时必须在创建 Task 之前返回权限错误（GRPC 为 PERMISSION_DENIED，HTTP 为 403），错误信息不得泄露授权规则。
P-108source 是来源声明，不是凭据。它解决"Agent 知道是谁在调用，并据此决定"，不解决"证明调用方没有说谎"。

这是授权的输入，不是认证。Profile 不做应用层鉴权（D1），改为由 BCN 带上来源信息，Agent 通过 SDK 的 AgentAuthorizer（8.5）自己决定是否接受。这对三种绑定都有效，包括拿不到调用方应用名的 HTTP 绑定。

需要评审确认的后果。来源信息没有签名。能直接访问 Agent 端点的内部应用可以绕过 BCS、自己构造 userId 和 source。如果这不可接受，有两条路：在网络层限制只有 BCS 能访问 Agent 端点；或启用预留的 proof 字段，由 BCS 签发、SDK 验证。见 Q8。

7.4扩展模型

前面的平台扩展是逐个定义的。业务方的定制需求主要有三类：请求里带业务参数；响应和 Task 更新里带自定义字段；返回给客户端或前端渲染的 UI 数据。为每个业务逐个写规范、逐个改 BCS 不可持续。

扩展点和扩展是两回事。扩展点由 Profile 固定，业务不能新增或修改，也不需要登记；五个不够用时向 BCN 提需求，通过 Profile 升级增加。扩展是业务自己定义的约定，选用其中几个扩展点来放数据。扩展不需要登记就可以使用，经过 BCS 时也是透明透传（7.6）。

本节定义五个扩展点。每个扩展点规定数据放在哪里、活多久、多大、中间环节怎么处理。业务扩展只需要声明自己用了哪些扩展点，BCS、SDK 和 Client 按扩展点的规则处理，不需要理解数据内容。

7.6经 BCS 透传

业务扩展经过 BCS 时，BCS 透明透传，不需要登记，BCS 也不需要认识这个扩展。这之所以可行，是因为扩展点的设计已经把 BCS 需要知道的事情固定了：

  • 数据属于哪个扩展点，从它所在的位置就能判断，不需要额外的描述。
  • 大小和数量上限按扩展点统一规定，不按扩展分别规定。
  • 每个结构化块都带降级文本，BCS 自己需要文本的地方始终有文本可用。

透传不是无条件的。BCS 只做四项与内容无关的检查：

P-136只透传已协商的扩展。BCS 把上游 Client 声明的扩展 URI 带给 Agent（去掉 Agent 的 Card 中没有声明的）。Agent 返回的数据中，URI 不在这个集合内的一律丢弃。Agent 向上游夹带对方没有要求的数据
P-137按扩展点的统一上限检查大小和数量（7.4、7.5）。超过上限的那一条被丢弃并计数，不影响文本结果和 Task 状态。单个 Agent 占用 BCS 的带宽和存储
P-138只沿本次调用的路径透传。扩展数据不广播给群聊中的其他 Bot，不进入其他 Bot 的上下文。BCS 自己需要内容的地方（会话历史、转发给其他 Bot）使用文本和降级文本。一个业务的私有数据流到不相关的 Bot

7.8群协作与扩展的边界

透明透传只适用于 BCS 不需要理解的数据。群协作不一样：BCS 要决定消息发给谁、谁必须回应、什么时候结束，这些判断依据的信息它必须理解。由此得到一条划分规则：

条款内容
P-126BCS 需要理解才能工作的语义，只能由平台扩展承载。业务扩展的数据 BCS 永远不解释，因此不能用来驱动 BCS 的路由、协作和授权（同 P-125）。
P-127群里的其他 Bot 只能看到文本和降级文本。业务扩展的数据停在本次调用的路径上，不广播（同 P-138）。需要其他 Bot 知道的信息必须写进文本。

这不要求协议把 Agent 分成两类。区分的是扩展的级别，不是 Agent 的种类：同一个 Agent 可以既用业务扩展向自己的前端透传数据，又参与群协作。BCS 按 Agent 声明的能力和 Provider 的设置来决定它能以什么方式入群。

8Java Server SDK

8.1设计原则

  • Profile 约束是默认行为。平台代码不需要知道"先返回 Task""只追加文本""显式终态"，SDK 保证。
  • 平台差异全部走 SPI。SDK 内不判断部署环境；存储、调用方身份、注册都通过配置选择实现。
  • 分两层 SPI。简易层一个接口覆盖 L0 到 L2；完整层按能力拆分，只有需要的平台才实现。
  • 失败要可见。存储写入失败、超限、超时都转成明确的 Task 失败或协议错误，不吞掉。

8.2与官方 a2a-java 的关系

官方 Java SDK（org.a2aproject.sdk，要求 Java 17 以上）提供协议模型、GRPC 生成代码、服务端请求处理和可替换的 TaskStore、QueueManager。它的参考服务端基于 Quarkus，构建中管理了 CDI 和 Jakarta 依赖。它的 extras 中有基于 JPA 的 TaskStore 和基于消息队列复制的 QueueManager。现有 Harness adapter 使用它的 1.4.0.Final。

复用范围spec、spec-grpc、server-common 的请求处理和事件队列只用 spec 和 spec-grpc；请求处理自己实现
优点代码量小；跟随官方修复；Harness adapter 已验证可行无 CDI 依赖；多实例语义（租约、取消标记、轮询订阅）可以直接按第 9 节实现
缺点官方的事件队列以单实例内存或消息队列复制为前提，与 D3 不一致，需要在其上绕行；CDI 与 Spring 的装配需要桥接五个方法的处理逻辑自己维护；需要自己跟进协议变更
升级风险官方内部接口变化会影响 SDK只受模型变化影响

建议采用方案 B。Profile 只有五个方法，处理逻辑有限，而多实例语义是本 SDK 的核心，放在自己的代码里更可控。协议模型和 GRPC 定义继续使用官方库，保证线上格式与标准一致。这一点需要评审确认，见 Q5。无论选哪个方案，对平台暴露的 SPI 不变。

SPI 为什么不是 A2A 的五个方法

A2A 的五个方法是线上协议，由 SDK 实现。SPI 是业务要实现的部分，只包含业务自己才知道怎么做的事。如果让业务直接实现五个方法，Task 生命周期、存储、多实例、文本流规则、断流恢复都要业务自己写，而这些正是 Profile 要统一的部分。官方 a2a-java 也是这种分层，见下方的源码对照。

A2A 方法SDK 做的交给业务的 SPI
SendMessage、SendStreamingMessage（新 Task）校验、协商、授权、创建并持久化 Task、返回首帧、把输出编码成事件、写存储、发终态execute
SendMessage（带 taskId 的审批续交）校验回复、持久化决定、分批处理、跨实例接管执行权execute，request.approval() 带已解析的审批结果
GetTask读存储；租约过期时回收无
SubscribeToTask本实例推送或跨实例轮询合成无
CancelTask本实例中断或写取消标记、等待终态、如实返回cancel

已经有自己的标准 A2A Server 的平台不需要使用 SDK，照 Profile 实现并通过 TCK 即可。

a2a-java本 SDK差异的原因
业务实现的接口AgentExecutor：execute、cancelBcnAgent：execute、cancel；续交同样进入 execute分层和入口都一致。差别在于续交时本 SDK 已把审批回复解析、校验好，放在 request.approval() 中；a2a-java 由业务自己从 RequestContext.getTask() 判断并解析
业务的输出接口AgentEmitter：可以设置任意状态（包括 requiresAuth）、以任意 append 和 lastChunk 组合发 Artifact、发任意事件AgentResponseSink：append、complete、fail，以及扩展通道和文件块本 SDK 故意收窄。Profile 禁止的行为（改写已输出文本、AUTH_REQUIRED、未协商的扩展数据）在接口上就做不出来
五个方法DefaultRequestHandlerserver-core见下一行
存储接口save、get、delete、list，没有版本号和比较并写入get、create、compareAndSet，记录带版本、租约、取消标记9.5 的跨实例协作全部依赖比较并写入，a2a-java 的存储接口提供不了
多实例extras/queue-manager-replicated：通过消息中间件在实例间复制事件队列只通过共享存储协作D3 已否决事件复制

续交和新请求共用 execute。A2A 中审批续交就是带 taskId 的 SendMessage，和新请求是同一个方法，SPI 也保持一个入口，与 a2a-java 一致，平台方不需要多理解一个概念。审批回复的校验规则很细（批次标识、工具标识、参数摘要、过期时间、分批回复、已接受的决定不得改写），这部分仍由 SDK 完成：只有校验通过、决定已持久化、所有工具都有决定并拿到执行权之后，SDK 才调用 execute，并在 request.approval() 中放入已解析的结果。分批回复的中间状态和不合法的回复不会到达业务代码。

后两行是 8.2 建议方案 B（只复用协议模型，请求处理自己实现）的直接依据：复用 DefaultRequestHandler 就要继承它的存储和队列模型，而这两者和本设计的多实例方案不兼容。

@Component
public class OrderAgent implements AdvancedBcnAgent {

    private final OrderEngine engine;          // 业务原有的 Agent 引擎
    private final CheckpointStore checkpoints; // 业务自己的存储，用于跨实例恢复

    @Override
    public AgentDescriptor descriptor() {
        return AgentDescriptor.builder()
                .name("订单助手").description("查询订单、核对发票、办理退款").version("2.1.0")
                .skill("query_order", "查询订单", "根据订单号查询订单状态和物流", "orders")
                .skill("refund", "办理退款", "为订单发起退款，执行前需要用户确认", "orders")
                .inputModes("text/plain", "image/png", "image/jpeg")
                .requireUserId(true)             // L2：调用上下文为必需扩展
                .toolObservation(true)           // L3：声明工具观察扩展
                .execApproval(true)              // L3：声明 exec 审批扩展
                .approvalResumableAcrossInstances(true)
                .businessExtension(OrderUi.URI, OrderUi.CARD_PARAMS)
                .build();
    }

    @Override
    public void execute(AgentRequest request, AgentExecution exec) {
        if (request.approval().isPresent()) {
            continueAfterApproval(request, request.approval().get(), exec);
            return;
        }
        String userId = request.caller().userId().orElseThrow();
        EngineRun run = engine.start(userId, request.contextId(), request.text(), request.attachments());
        drive(run, request, exec);
    }

    /** 审批续交。可能在另一个实例上，所以只依赖存储里的状态。 */
    private void continueAfterApproval(AgentRequest request, ApprovalResult result, AgentExecution exec) {
        Checkpoint cp = checkpoints.take(request.taskId());
        EngineRun run = engine.restore(cp.engineState());
        ToolStep step = cp.pendingTool();

        if (result.decisions().get(step.id()) == Decision.DENY) {
            exec.tools().result(step.id(), step.name(), true, "用户拒绝执行");
            run.feedDenied(step);
        } else {
            invokeTool(step, run, exec);
        }
        drive(run, request, exec);
    }

    /** 把引擎的步骤逐个翻译成 SDK 调用。 */
    private void drive(EngineRun run, AgentRequest request, AgentExecution exec) {
        var ui = exec.extension(OrderUi.URI);

        while (run.hasNext()) {
            if (request.cancelled()) {
                return;                                   // SDK 把 Task 置为 CANCELED
            }
            Step step = run.next();

            if (step instanceof TextStep text) {
                exec.append(text.delta());                // 流式文本

            } else if (step instanceof ToolStep tool && tool.needsApproval() && !exec.approvalAvailable()) {
                // 调用方不支持审批：不执行该工具，告诉引擎被拒绝，由引擎用文本说明
                run.feedDenied(tool);

            } else if (step instanceof ToolStep tool && tool.needsApproval()) {
                // 先保存可恢复的状态，再请求审批，然后立即返回
                checkpoints.save(request.taskId(), new Checkpoint(run.snapshot(), tool));
                exec.requestApproval(new ApprovalRequest(
                        "approval-" + tool.id(),
                        System.currentTimeMillis() + Duration.ofMinutes(10).toMillis(),
                        List.of(new ToolCall(tool.id(), tool.name(), tool.args()))));
                return;                                   // Task 进入 INPUT_REQUIRED，线程释放

            } else if (step instanceof ToolStep tool) {
                invokeTool(tool, run, exec);

            } else if (step instanceof OrderCardStep card) {
                ui.putBlock(card.blockId(), OrderUi.CARD_TYPE, card.json(), card.fallbackText());
                ui.closeBlock(card.blockId());
            }
        }
        ui.setTaskField(run.usageJson());                 // E3：用量统计，随 Task 持久化
        exec.complete();
    }

    private void invokeTool(ToolStep tool, EngineRun run, AgentExecution exec) {
        exec.tools().start(tool.id(), tool.name(), tool.args());
        ToolOutput out = engine.invoke(tool);
        exec.tools().result(tool.id(), tool.name(), out.failed(), out.summary());
        run.feed(tool, out);                              // 工具失败不等于 Task 失败，交给引擎决定下一步
    }

    @Override
    public void cancel(String taskId) {
        engine.abort(taskId);
    }
}
代码中的位置对应的设计

8.6请求处理

初始提交（SendStreamingMessage）

  1. starter收到 GRPC 请求，提取 a2a-version、a2a-extensions、tenant 和 RPC 调用方应用名。
  2. core校验版本和请求结构；通过 AgentResolver 找到 Agent。失败直接返回协议错误，不创建 Task。
  3. core计算协商结果：请求列出的扩展与 Card 声明的交集。必需扩展缺失则返回 EXTENSION_SUPPORT_REQUIRED。
  4. core解析调用上下文扩展，得到 userId 和 source；执行 AgentAuthorizer。拒绝则返回权限错误，不创建 Task。
  5. core生成 taskId、contextId，以 SUBMITTED 状态写入 TaskStore，本实例成为执行实例并写入租约。写入失败返回内部错误。
  6. core向流写出 task 事件，然后把执行提交到执行线程池。线程池已满则 Task 置为 REJECTED。
  7. core执行线程把状态改为 WORKING，调用 BcnAgent.execute。
  8. Agent调用 sink.append。core 更新内存中的累计文本，向本实例的订阅者推送 artifactUpdate，并按节流写入 TaskStore。
  9. core执行结束：写入终态和最终全文，成功后向订阅者推送终态 statusUpdate 并关闭流。

SendMessage 走同一流程。returnImmediately: true 时在第 7 步返回 Task；否则等到第 10 步返回。

8.7线程与背压

项设计
执行线程池SDK 管理的有界线程池，每个 Task 占用一个线程直到 execute 返回。池大小即并发 Task 上限。JDK 21 以上可以配置为虚拟线程。
RPC 线程只做校验、建 Task、写首帧，不执行 Agent 逻辑。
订阅者缓冲每个订阅者一个有界缓冲。客户端读得慢导致缓冲溢出时，SDK 关闭该订阅，不阻塞 Agent 执行。客户端按 GetTask 加 SubscribeToTask 恢复，文本不丢。
存储写入节流写入在独立的调度线程上执行，不阻塞 append。终态写入是同步的：写入成功后才对外发终态。
优雅停机收到停机信号后停止接收新 Task，等待在途 Task 完成（可配置上限）。超时后把剩余 Task 置为 FAILED 并写入存储，不等租约过期。

发布的影响。滚动发布会终止实例。执行时间长于停机等待时间的 Task 会失败。这是 D3"不做执行迁移"的直接后果，需要评审确认可以接受，或确定停机等待时间的默认值（Q9）。支持检查点的引擎可以通过检查点恢复（9.9）在其他实例上继续执行，不再受停机等待时间限制。

8.9Card 生成、发布与注册

  • 生成。starter 根据 AgentDescriptor、配置的接口地址和已装配的能力生成 Card。扩展声明由 SDK 写入：只有对应 SPI 已装配，才声明该扩展。
  • 校验。启动时用 bcn-a2a-spec 的校验器检查 Card。不合规则启动失败，并给出具体条款编号。
  • 发布。开启了 HTTP+JSON 或 JSONRPC 时，在 {base-path}/{tenant}/agent-card.json 提供 Card。只开启 GRPC 时，通过内联 Card 注册。
  • 注册。AgentRegistrar 默认关闭。开启后在启动完成时调用 BCS 的 Provider 管理接口：以 provider_bot_ref 查询，不存在则注册，存在且 Card 有变化则更新。管理凭据从平台的密钥配置读取，不写在应用配置中。注册失败不阻止应用启动，但会告警并重试。

多实例同时启动会并发注册。BCS 对重复的 provider_bot_ref 返回冲突，SDK 收到冲突后改为查询再更新。更新是完整替换且以最后写入为准，各实例的 Card 相同，因此结果一致。动态 Agent（AgentResolver.list() 的结果会变化）的注册时机见 Q10。

8.12推送通知的实现方案（后续阶段）

本期不实现，也不改动任何接口。本期只定义推送的语义（6.12），Task 记录预留 pushConfig 字段，PushSender 只定义不启用。本节说明以后如何在不破坏已有实现的前提下扩展。

难点

推送要求"至少尝试投递一次"，而多实例设计里实例之间不通信、回收是惰性的（9.5）。如果状态写入成功后、推送发出前实例宕机，或执行实例宕机后没有人再查询这个 Task，推送就会丢失。推送存在的意义正是让调用方不必一直查询，所以不能依赖查询来触发。

方案：发件箱加到期队列

  1. core写入状态变化（终态或 INPUT_REQUIRED）时，在同一次比较并写入中，往 Task 记录的发件箱里为每个推送配置追加一条待投递记录，并把这个 Task 放进到期队列，到期时间为当前时间。状态和待投递记录要么一起写入，要么都不写入。
  2. core写入成功后，本实例立即异步投递，不阻塞执行线程。
  3. PushSender按 6.12 发送：负载为只含 statusUpdate 的 StreamResponse，Authorization 头带调用方给的关联凭据，单次超时 10 秒。
  4. core收到 2xx 后，通过比较并写入删除这条待投递记录。失败则记录尝试次数，按退避（例如 5 秒、30 秒、2 分钟、10 分钟）把到期时间推后。达到上限后放弃，计数并记日志。
  5. 任一实例后台每隔几秒从到期队列取出少量已到期的 Task，重新投递其中未完成的记录。到期队列同时登记租约到期时间，所以执行实例宕机后，任一实例都能主动回收该 Task 为 FAILED，并按同样流程推送。

结果是投递"至少一次"：宕机、重启、推送失败都会由其他实例接着重试；重复投递由接收方按 Task 标识加状态去重（P-154）。

9多实例设计

9.1模型

  • 接收初始请求的实例是该 Task 的执行实例。执行权不迁移。例外是审批续交：Task 在 INPUT_REQUIRED 时没有执行实例，接到续交的实例接管；以及支持检查点恢复的 Agent（9.9，提议）。
  • 执行实例是 Task 内容（状态、文本、metadata）的唯一写入者。
  • 其他实例只做三件事：读快照、写取消标记、回收租约过期的 Task。
  • 实例之间不直接通信。所有协作通过 TaskStore 的 CAS 完成。

9.2TaskStore SPI

public interface TaskStore {

    /** 按主键读取。 */
    Optional<TaskRecord> get(String agentKey, String taskId);

    /** 不存在才写入。已存在返回 false。 */

实现约束说明
原子性create 和 compareAndSet 必须是原子的。
读己之写成功写入后，任何实例的读取都必须能看到。不得使用可能读到旧值的从库或缓存。
不淘汰记录在过期时间之前不得被存储主动丢弃。
失败语义存储不可用时抛出异常；不得返回 false 或空来表示故障。
以后的扩展启用推送时会以默认方法的形式增加到期队列两个原语（8.12）。本期的实现不需要为此做任何准备。
不要求的能力发布订阅、分布式锁、范围查询、事务跨多条记录。
一致性测试SDK 提供 TaskStore 的合同测试，自定义实现必须通过。

  • 每次写入都把 leaseExpiresAtMs 更新为当前时间加租约时长（默认 15 秒）。
  • 租约判定加入 5 秒的时钟偏差容忍：当前时间超过 leaseExpiresAtMs 加 5 秒才视为过期。
  • INPUT_REQUIRED 的 Task 没有执行实例，不受租约约束，由 deadlineMs 约束。任何实例读到已过截止时间的 INPUT_REQUIRED Task，都通过 CAS 把它置为 FAILED。

跨实例 SubscribeToTask

  1. 实例 B读取 TaskRecord。不存在返回 TASK_NOT_FOUND；终态返回 UNSUPPORTED_OPERATION。
  2. 实例 BownerInstance 是自己：挂到本地事件源，结束。否则继续。
  3. 实例 B向流写出当前 task 快照，记下每个 Artifact 已发送的文本长度和记录的 version。
  4. 实例 B每秒读取一次记录。version 未变则跳过。
  5. 实例 Bversion 变化：每个 Artifact 的新增后缀作为 artifactUpdate(append: true) 发出；新的 Artifact 以 append: false 发出；状态或状态消息变化作为 statusUpdate 发出。
  6. 实例 B读到终态或 INPUT_REQUIRED：发出对应 statusUpdate，关闭流。
  7. 实例 B读到租约过期：按"宕机回收"处理后发出 FAILED，关闭流。

由于文本只追加（P-70、P-71），快照差异必然是后缀，合成结果与直接推送在文本上等价。差别在于粒度（约 1 秒一批）和工具观察记录可能缺失（两次轮询之间被覆盖的状态消息不可见）。扩展数据遵循同样的规则：E3 和 E5 在存储中，合成订阅能看到，结构化块的变化以整块替换发出；E4 是瞬时的，跨实例订阅看不到。

跨实例 CancelTask

  1. 实例 B读取 TaskRecord。终态返回 TASK_NOT_CANCELABLE。
  2. 实例 B通过 CAS 把 cancelRequested 置为 true。CAS 冲突则重读后重试，最多 3 次。
  3. 实例 A下一次节流写入或续租时 CAS 失败（version 已变），重读记录，看到 cancelRequested。
  4. 实例 A调用 BcnAgent.cancel 并中断执行线程；通过 CAS 写入 CANCELED 和已输出的文本。
  5. 实例 B每 500 毫秒读取一次，直到读到终态或超过 cancel.wait（默认 8 秒）。
  6. 实例 B读到 CANCELED：返回该 Task。读到其他终态（完成与取消竞争）：返回该终态 Task。超时：返回当前非终态 Task。

执行实例最迟在下一次续租（5 秒）时发现取消标记。实际延迟通常在 1 秒内，因为执行中的 Task 在持续写入。已核对 BCS 的处理：响应状态不是 CANCELED 时，BCS 不把该 Run 记为已取消，后续通过 GetTask 核对。BCS 清理路径的取消超时为 15 秒，因此 cancel.wait 默认取 8 秒。

审批续交

  1. 实例 AAgent 调用 requestApproval。core 写入 INPUT_REQUIRED、审批 Schema、deadlineMs，清空 ownerInstance。execute 返回，线程释放。
  2. BCS用户决定后，发送带 taskId 的 SendMessage，可能到达任意实例。
  3. 实例 B读取记录，校验 contextId、审批批次、工具标识、过期时间和 userId 一致性。不合法则返回带校验错误的 INPUT_REQUIRED，不改变已接受的决定。
  4. 实例 B通过 CAS 把决定写入 Task.metadata。仍有工具未决定：保持 INPUT_REQUIRED，返回更新后的 Task。
  5. 实例 B全部已决定：同一次 CAS 把状态改为 WORKING，ownerInstance 设为自己并写入租约。CAS 成功即接管成功。
  6. 实例 B从记录重建本地执行状态：已有的 Artifact 及其文本、块的顺序、E3 字段、协商结果、调用上下文。审批之后的新文本使用新的 artifactId，排在已有块之后（P-140），不改写审批前的输出（P-71）。
  7. 实例 B返回 Task，然后在执行线程上调用 execute。request 由记录重建，内容与 A 上收到的原始请求相同；request.approval() 中为已解析的决定。
  8. Agent从共享存储恢复引擎状态后继续执行。之后的查询、订阅、取消可以落到任意实例，按 9.5 的其他流程处理。

宕机回收

  1. 实例 A进程终止。Task 停在 WORKING，租约不再续期。
  2. 实例 B处理该 Task 的 GetTask、订阅或取消时，读到租约已过期（含 5 秒容忍）。
  3. 实例 B通过 CAS 把状态置为 FAILED，状态消息说明执行中断，保留已写入的文本。
  4. 实例 B按终态继续处理原请求。

回收是惰性的：只有当有人读这个 Task 时才发生。BCS 在跟踪期间会持续查询或订阅，所以在途 Task 会被及时回收。没有人再读的 Task 由保留期清理处理。以后启用推送时，到期队列会让回收变为主动（8.12）。本期不设后台扫描，避免对存储做范围查询。

缓存在主备切换时可能丢失最近的写入。SDK 的处理原则是：可以恢复的就恢复，不能恢复的如实报告，任何情况下都不重复执行。

9.9检查点恢复（提议）

公司内大部分引擎已有检查点机制：执行实例停掉后，另一台机器可以从检查点恢复 Agent 的会话和执行状态。SDK 可以利用它，让被发布或宕机打断的 Task 在其他实例上继续执行，而不是直接失败。这是对 D3"执行权不迁移"的有条件放宽，需要评审确认（Q24）。

核心问题：检查点和 Task 输出的对齐

引擎的检查点和 SDK 的 Task 记录是两份独立写入的状态。恢复时如果两者不在同一个点上，会出两类错：

情况后果
检查点比 Task 记录新：引擎已经越过某一步，但这一步的输出还没写进 Task 记录这段输出永久丢失。恢复后的引擎不会再产出它，调用方看到的结果有缺口
Task 记录比检查点新：输出已写入并展示给了调用方，但检查点还停在之前恢复后的引擎从检查点重做这一步，再产出一遍。大模型的输出不确定，第二遍和第一遍的文字不同，无法按前缀去重；如果这一步调用了工具，工具会被再执行一次

对齐规则

条款内容解决的问题
P-170先输出落盘，后记检查点。引擎把状态存进自己的检查点存储后，调用 exec.checkpoint(ref)。SDK 先把到此为止的输出写入 Task 记录，在同一次比较并写入中记下检查点引用 ref 和输出游标（每个块的长度、块的数量）。Task 记录中的输出永远不落后于它所记录的检查点，第一类错不会发生

恢复的触发

  1. 实例 A优雅停机时，等待时间到了仍未结束的 Task：如果 Agent 支持检查点恢复且记录了检查点，A 不把它置为失败，而是清空执行实例、标记"待恢复"，状态对外仍是 WORKING。A 宕机时，租约过期后效果相同。
  2. 调用方流断开后按 P-113 先 GetTask。请求落到实例 B。
  3. 实例 B读到"待恢复"或租约过期且有检查点：通过比较并写入接管执行权，恢复次数加一。接管不成功说明别的实例已接管，按普通查询处理。
  4. 实例 B按 P-172 关闭游标之后的块，发出恢复说明，返回 Task（WORKING）。调用方随后 SubscribeToTask，由 B 直接推送。
  5. 实例 B调用 execute，request.recovery() 中带检查点引用和恢复次数。引擎按引用加载检查点后继续。

恢复由查询触发，复用了"BCS 断流后必定先查询"这个现有行为，不需要后台扫描。以后有了到期队列（8.12），可以改为主动恢复。

9.10明确不保证的事项

  • 执行实例宕机或被发布终止后，Task 不会在其他实例上继续，结果是 FAILED；支持检查点恢复的 Agent 除外（9.9）。恢复后被打断的那一步可能在新块中重复出现。

  • 跨实例取消不保证在一次调用内确认。
  • Agent 自身的会话记忆（基于 contextId）是否跨实例可用，由 Agent 负责，SDK 不管理。

13安全与信任

主题设计
信任边界公司内部网络。三种绑定的端点都不鉴权，都不得暴露到公网。HTTP 端点只能绑定内部域名，不得挂到对外网关。这是部署要求，SDK 无法在代码层面保证。
HTTP 下的调用方身份GRPC 经 SOFARPC 可以取得调用方应用名。HTTP+JSON 和 JSONRPC 没有等价的可信来源，callerApp() 为空。这两种绑定下的授权只能依据调用上下文扩展中的 source。
授权BCN 在调用上下文扩展中带上来源信息，Agent 通过 AgentAuthorizer 自行决定。Profile 不规定授权规则，默认全部接受。来源信息未签名，可信度依赖内部网络。
用户身份userId 由 BCS 从已认证上下文生成，不验签。能发起 RPC 的内部应用可以构造它。
隔离所有存储访问都带 agentKey。跨 Agent、跨 tenant 的 Task 访问返回未找到。
标识不可猜测taskId 默认随机生成。它不是凭据，但不应可枚举。
数据最小化存储中保存请求文本和输出文本，有保留期。日志不记录文本和 userId 原值。
Card 自声明Card 中的等级、来源分类、提供方信息都不授予权限。归属以 BCS 的 Provider 注册关系为准。
管理凭据自动注册使用的 Provider 管理凭据只用于调用 BCS 管理接口，不进入 Card，不出现在日志。
