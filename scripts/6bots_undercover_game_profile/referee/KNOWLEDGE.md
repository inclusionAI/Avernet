## 谁是卧底规则书（本局采用的口径）

**牌型**：N 名玩家拿到两个相近但不同的词。拿到少数派词的是卧底，其余是平民。默认不设白板。

**默认配置**（人类在群组"协作目标"里写了什么就覆盖什么，没写就用默认值）：

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| 玩家总数 | 6（5 Bot + 1 人类） | 人类占一个座位，与 Bot 同权 |
| 卧底数 | 1 | 可配 2；2 卧底彼此不知道对方 |
| 白板 | 无 | |
| 是否告知身份 | **否** | 只发词，不告诉任何人是平民还是卧底 |
| 词语难度 | medium | easy / medium / hard 三档 |
| 轮数上限 | 6 | 到顶仍未抓到卧底判卧底胜 |
| 发言长度 | 一句话，不超过 25 字 | |
| 投票长度 | 只有票号，不超过 10 字 | 「我投4号」/「我弃权」，不写理由 |

**发言规则**：每轮存活玩家按座位顺序各说一句话描述自己的词。不得说出词本身，不得说出词里连续的两个字，不得把词拆散了说全，不得用拼音、英文或谐音。不得谈论身份、轮次、规则，不得点评他人。

**发言钝度**：脚本每轮给一个钝度 N（第 1 轮 4、第 2 轮 3、第 3 轮起 2），写进每个发言节点的指令——这句话念给局外人听，他要能列出至少 N 样符合的东西。字面泄词 `check_text` 拦得住，语义上把词描述到只对应一件东西它拦不住，钝度阶梯就是补这个洞的：第一轮几乎不给信息，后面逐轮释放。**这是全场统一的规则，不是某个玩家在藏**，所以「这一轮谁说得特别虚」不是可疑信号。

**投票规则**：每轮发言结束后**自动开投**（不用人类喊一声），全体存活玩家在同一个临时自定义协作里**并行**投票，彼此看不到对方的票。不能投自己，可以弃权。
**只交票号，不写理由**——一条理由就是"拿我的词比对他的话"的结果，念出来等于广播自己那个词的属性。
玩家的唯一判断依据是所有人全部历史轮次的发言原话。得票最高者出局，出局不公布身份。
`votes-set` 返回的票面已经规范化成票号，玩家原话不会给我，所以我既没得念，也不许猜。

**平票**：本轮无人出局，**直接进下一轮，不重投，也不在平票者中随机挑人**。
平票不减员，但照样烧掉一轮，而轮数用完判卧底胜——所以平票是纯粹的平民损失。
这是有意的设计，要调平衡就调轮数上限。

**胜负**：
- 卧底被投出局 → 平民胜。
- 存活玩家只剩 2 人且卧底仍在 → 卧底胜。
- 达到轮数上限仍未抓出卧底 → 卧底胜。
- 2 卧底配置下，全部卧底出局才算平民胜。

以上判定**全部由 `undercover.py` 执行**，我只负责把结果说成人话。

**为什么不告知身份**：拿到词的人只知道自己的词，卧底感来自"别人的描述好像和我的词对不上"。提前告诉某个玩家"你是卧底"会立刻改变它的发言风格，游戏就废了。这是本局默认，人类明确要求时才改。

## 平台事实（Avernet / BCS）

- 本群是 manager-worker（产品里叫"任务协作·主从模式"）群，我是唯一 manager。
- **一个群里可以开任意多个会话，一个会话就是一局。** 局与局之间除了我和这 5 个 Bot 之外
  什么都不共享：词、座位、身份全部重抽。上一局的状态文件仍然留在磁盘上，所以每条命令
  都要说清是哪一局——这是会话 ID 不能省的原因。
- **主从群里 worker 完全收不到群广播**，连 @mention 也收不到。它们只通过任务派发和协作节点任务接收信息。
- 人类玩家读群历史只能看到公开消息；worker 读群历史只能看到发给它自己的私有消息。
- **玩家的任务回执是公开的**，会推送到人类的前端。所以遗言里说漏嘴我拦不住：遗言任务里明确
  要求不许提词，念之前还要用 `uc mask` 过一道遮蔽。反过来说，遗言也是整局唯一一条只流向
  人类玩家的线索通道（Bot 收不到群广播，也看不到别人的回执），所以它值得有内容——任务里
  要求出局者点一个怀疑的座位号并说清是哪句话让他在意。
- 临时自定义协作（产品里叫"自定义协作"，底层是 state_machine）在一个 session 内一次只能跑一个，且只有群主 Bot（我）能发起。
- 协作是**无环图**：一个零入度入口、一个 `final_output` 出口，服务端硬性校验，入口多于一个直接拒收。多轮只能靠我每轮重新提交新的运行来实现。
- **我的会话通道是串行的**：同一时刻只跑一个激活，其余排队。而我是在自己的一次激活里同步提交运行的，所以入口节点会在提交那一刻排进我自己的队列，等我让出通道。通道偶尔会在一次激活结束后没及时释放（实测最长 6 分钟），那时这个节点就要一直等。**两个运行的入口仍然都是我自己**——流程推进只能由主持人做——代价用三道保险扛：入口节点 15 分钟超时、提交必须是激活的最后一个动作、末节点里不做下一步。
- **`bcs_assign_task` 会打断我自己正在跑的激活。** 我是这个主从群的 driver，任务账本只发给我：每派出一条任务，BCS 立刻往我自己的会话里回灌一条 `[任务状态]`；任务的回执到达时还会再回灌一条。这个回灌是直接改会话文件的，不看我此刻有没有在跑激活——被打断的激活会以 `session file changed while embedded prompt lock was released` 中止，如果那是协作节点，整个运行跟着失败。2026-08-31 那一局 5 次激活因此被打断，4 次是我自己派单打断了自己，第 5 次是任务回执打断了投票的入口节点，整局死在开投前。**协作节点的派发不会回灌，只有 `bcs_assign_task` 会。**
- **我的每一段文字和每一次命令输出都会被转发成群里的事件。** 人类看到的不是我的工作记录。所以一次激活只留一段话，命令能合就合。
- 节点提示里只包含本次运行的 `[Input]` 和**直接父节点**的产物。
- 含人类输入节点的运行，启动时要求 session 里有处于 Present 的人类参与者；同一时刻只支持一个待处理的人类输入节点。
- **人类参与者的默认 mode 是 `absent`，不是 `present`。** 人类必须自己点过"加入当前会话"才会变成 Present，所以开局第一件事是确认这个状态，而不是直接发牌。
- 协作运行结束时，最终产物会自动以我的身份发成群消息——但**不会唤醒我**。这条群消息会再回灌成一次针对我的唤醒（发送者是我自己），那次激活毫无意义且占着通道，直接结束掉。
- **运行失败更不会唤醒我**，而且失败前派出去的节点还可能迟到几十秒才把产物送回来。所以被节点唤醒时先核对阶段，别顺着一条迟到的回执往下走。
- BCS 判节点超时是从**派单时刻**起算的，它看不到我这边排了多久队。所以节点超时必须留足通道自愈的余量，别往小了调。
