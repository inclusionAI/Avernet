BCN A2A Profile 与 Java Server SDK 详细设计

公司内 Agent 统一遵循的 A2A 协议标准，以及让 SOFABoot 平台按该标准提供 A2A Server 的 Java SDK。本稿用于内部评审，评审通过后规范性文本落回仓库 Markdown。

状态 评审草案 v0.27日期 2026-11-11范围 协议标准 + Server SDK技术栈 SOFABoot / JDK 17

评审方式。文中三类编号可以直接引用：

  • D1 已确认的决策，评审时只确认后果是否可接受。
  • P-01 Profile 的规范性条款，逐条评审。"必须"表示不满足即不合规。
  • Q1 待确认问题，需要评审给出结论；汇总在第 16 节。

1背景与问题

BCS 现在是公司级的 A2A 注册中心：Agent 把 AgentCard 注册到 BCS，BCS 作为 A2A Client 按 Card 调用 Agent。注册和 Client 侧能力已经具备，问题出在 Agent 一侧。

  • 大量 Agent 没有标准 A2A 接口。它们以各自的 RPC 接口或 HTTP 接口提供服务，要接入就得各自写适配。
  • 适配结果不一致。A2A 标准留了很多自由度（是否返回 Task、文本是追加还是替换、何时算结束、断流后怎么恢复）。BCS 对这些有明确的行为前提，目前只写在接入文档里，没有可检验的标准。
  • BCS 的扩展没有统一实现。工具观察、exec 审批等扩展，目前只有 Harness adapter 一份实现，且不在本仓库。
  • 多实例没有答案。现有文档明确说明 Harness adapter 的内存 Task 存储不支持多实例，而公司的 SOFABoot 应用默认多实例部署。

现有约定散落在接入指南、接口参考和各扩展文档中。本设计把它们收敛成一份标准，并提供参考实现。

4总体架构

本期的调用方向只有一个：BCS 调 Agent。Agent 不需要知道 BCS 的 Run、Session。唯一的反向调用是可选的推送通知（6.12）：Agent 向调用方指定的地址发送 Task 状态变化的提示，本期只定义语义，不实现。BCS 对外提供 A2A 服务后，Agent 也可以作为调用方，届时由 client SDK 支持，不在本设计范围内。

4.1调用路径：经 BCS 与直连

按 Profile 接入的 Agent 是内网可达、不鉴权的标准 A2A 服务，因此两个 Agent 之间在技术上可以直接调用，不必经过 BCS。BCS 可以只承担控制面（注册、发现、分发 Card、策略），数据面由两端直连。Profile 的条款对两种路径都成立，不假设调用方一定是 BCS。

BCS 在链路中提供的直连时补充手段
发现不受影响调用前向 BCS 查询 Card，之后直连
可见性和访问控制变弱：知道地址即可调用发现时只返回有权看到的 Agent；被调方用 AgentAuthorizer 按来源判断；需要更强保证时由 BCS 在发现阶段签发短期凭证，放入预留的 proof，被调方离线验证
审计和统一观测没有集中记录两端 SDK 输出统一的指标和链路；可异步向 BCS 上报调用摘要，不在调用路径上
用户身份和来源信息由调用方 Agent 填写可信度与经 BCS 时相同，都依赖内网互信（D1）
会话历史、群聊、同一会话的排队没有需要这些的场景经 BCS

这样调用方的代码在两种路径下相同，路径策略集中在注册中心，并且所有 Bot 对调用方都表现为标准 A2A 服务。工作台的人机对话不受影响：BCS 自己调用 Agent 时始终使用保存的原始 Card。需要一并确定的问题：

  • 模式由谁决定。按 Agent 类型给默认值，Provider 或平台管理员可以调整。每个 Agent 固定一种，还是可以因调用方而异，待定。
  • 派生 Card 的规则。BCS 保存的原始 Card 不改写；对外提供的是它的一个视图。需要规定哪些字段原样保留、哪些由 BCS 改写。
  • BCN 地址模式不是强制。原生地址在内网可达且不鉴权（D1），知道地址即可绕过 BCS。必须经 BCS 的 Agent 需要配合网络层限制，或启用预留的 proof。
  • 模式切换与缓存。调用方会缓存 Card。需要规定 Card 的有效期；进行中的 Task 不随模式切换而换地址。

直连依赖 client SDK 和 BCS 的发现接口，BCN 地址模式依赖 BCS 对外提供 A2A 服务，都属于后续阶段，本设计不展开。汇总为 Q21。

5已确认的决策

编号决策直接后果被否决的方案
D1调用都在公司内部网络内完成（RPC，或内部域名上的 HTTP），协议不定义额外鉴权。GRPC、HTTP+JSON、JSONRPC 三种绑定都保留，都不鉴权信任边界是公司内部网络。Card 固定 securityRequirements: []。调用上下文的可信度等同于“调用方在内网内”。Bearer 下行凭据；签名的用户断言。成本高，与公司内部服务互信的惯例不一致。另外否决了“只保留 GRPC”。
D2多实例是一等约束SDK 的默认行为必须在多实例下正确；单实例只是特例。要求粘性路由。MOSN 负载均衡下不现实。
D3任务状态以引擎的运行记录为唯一来源，SDK 不另存一份（托管模式除外）SDK 是无状态协议层，任意实例把请求转给引擎；对引擎提出 9.2 的要求；业务不需要为 SDK 准备存储。SDK 自有共享存储并承担任务生命周期（v0.22 之前的方案）。两份状态需要对齐，业务要准备缓存实例，SDK 复杂；而且引擎做不到的恢复，SDK 存储也补不上。
D4停机重启后的恢复由引擎保证SDK 不做执行接管和检查点对齐；引擎需满足 R-03、R-04（9.2），9.4 给出实现建议。SDK 侧的检查点对齐和跨实例执行接管。
D5以进程内 SDK（API + SPI）作为本期唯一的交付形态公司 90% 以上技术栈是 Java。业务引入 starter、实现 SPI。标准靠协议层校验、TCK 准入和版本治理保证（8.15）。BCN 托管的协议适配层。多一跳，所有流式流量经过一个中心服务；本期不做，但核心保持可托管。
D6Profile 不包含提交去重扩展标准里没有提交幂等。初始提交结果未知时调用方不重发、报告结果未知。没有历史依赖，不需要兼容。保留原 BCS 的提交去重扩展。它要求永久保留占位记录、跨语言一致的请求摘要，并带来“占位成功但未执行”的失败窗口，复杂度与收益不相称。以后确有需要可以作为新扩展加回，不影响现有 Agent。
D7托管模式的存储只提供分布式缓存实现托管模式的 Task 记录是短生命周期、高频写入、到期清理的数据，适合缓存。只需要一个不淘汰数据的缓存实例。代价是主备切换时可能丢失个别 Task 的最近写入，按 9.5 的规则处理。数据库实现，无论作为默认还是备选。每秒整行更新占用业务库资源，接入要建表和配置清理；公司内的应用都已接入分布式缓存，备选没有使用者，只增加维护成本。
D8引擎模式的 SPI 是 A2A 五个方法的子集接口，参数和返回值使用 a2a-java 的模型类型平台方直接按 A2A 规范理解 SPI，不需要第二套词汇。标准约束由 SDK 在协议层校验和过滤（8.6），扩展编码由工具库提供（8.7）。自定义的执行接口作为唯一 SPI：与 A2A 方法一一对应却换了名字，增加理解成本。直接使用 a2a-java 的 RequestHandler：范围大于标准，演进受官方影响。
D9提供可选的托管模式，给没有运行记录的简单 Agent平台只写输入到输出的逻辑，SDK 代管 Task；不支持 exec 审批，不承诺停机恢复（8.10、9.5）。只提供引擎模式：简单 Agent 要自己实现运行记录，门槛过高。
D10支持只返回消息的消息模式（L0），不支持“有 Task 但不保存”的无状态流式最轻的 Agent 只需实现一个方法，完全符合 A2A 标准，BCS 已支持，多实例天然满足。代价是回答一次性到达、断线后结果丢失、不能取消。需要逐段输出又不想自己存状态的 Agent 使用托管模式。无状态流式：能逐段输出，但换一台机器就查不到 Task，违背“任意实例可查询”；断线、取消都要在标准里开例外，BCS 也要改。
D11调用上下文从等级中拆出，作为任何等级都可以声明的独立能力等级只描述交互形态（消息、非流式任务、流式任务、审批）。L0 的 Agent 也可以拿到用户身份。保留原来“L2 = 调用上下文”的逐级包含：只返回消息的 Agent 需要用户身份时无法达到相应等级。
D12工具观察是尽力投递的过程信息：有 Task 时放在状态消息中（与 v1 相同），没有 Task 时放在回复消息中（v2 新增）；从等级中拆出，作为可选能力符合 A2A 对状态消息和产出物的划分。丢失的记录不补发；需要保存的一方自己保存，BCS 本来就持久化收到的工具调用。L3 只剩 exec 审批（7.9）。放在产出物中：产出物是任务结果，工具调用是过程，语义不对。要求 Agent 把工具记录保存进 Task 历史：增加引擎负担，而 A2A 本来就把过程信息视为可以丢失。移出 A2A、走单独的观测服务：直连的调用方都要另接观测服务，与统一协议的目标相反。
D13扩展标识用 URI，扩展数据的键用短键：BCN 平台扩展统一使用 bcn. 前缀A2A 规范要求扩展以 URI 标识，但 metadata 的键可以是任意字符串，由扩展自己规定。URI 只出现在 Card 和协商头中；每次请求和日志里只有 bcn.caller、bcn.tool、bcn.sdk 这样的短键（P-128）。数据键也用完整 URI：符合官方示例的写法，但又长又难读，对内部系统负担大，且版本信息与 URI 重复。

6Profile 规范

6.1定位

合规 Agent 是一个标准的 A2A 1.0 Server，任何标准 A2A Client 都能调用它。Profile 只做三件事：选定子集，收紧行为，规定怎么扩展。BCS 继续兼容不使用 SDK 但符合 Profile 的 Server。

6.2基线

条款内容
P-01接口的 protocolVersion 必须为 "1.0"。对象和绑定细节遵循 A2A 1.0.1 规范。不兼容 0.3 的方法名和字段（message/stream、kind、final）。
P-02必须提供 GRPC、HTTP+JSON、JSONRPC 三种绑定中的至少一种，可以同时提供多种。三种绑定地位相同，BCS 按 Card 中的声明顺序选择。GRPC 的服务为 lf.a2a.v1.A2AService，通过 SOFARPC Triple 暴露，经 MOSN 寻址；普通 Bolt/Hessian 接口不能替代。HTTP+JSON 和 JSONRPC 通过内部域名访问，流式使用 SSE。
P-03三种绑定的对象语义和行为必须一致，都不要求应用层凭据。同一 Task 可以通过任一已声明的绑定查询、订阅和取消。所有端点只能在公司内部网络可达。
P-04必须实现的方法由一致性等级决定（6.3）。Profile 之外的标准方法可以实现，BCS 不调用。
P-05text/plain 是所有 Agent 都必须支持的基线：必须接受纯文本输入，必须能只用文本给出完整结果。其他模态是可选能力，按 6.13 声明和协商。结构化 UI 内容通过已协商的扩展、按内容块规则（7.5）提供。
P-06JSON 使用 A2A 1.0 的 lowerCamelCase（ProtoJSON）。枚举使用全名，例如 ROLE_USER、TASK_STATE_WORKING。

条款内容
P-20不带 taskId 的消息开启新 Task。Agent 必须分配 id；请求未带 contextId 时必须分配 contextId，带了则必须沿用。
P-21新 Task 必须先持久化，再对外返回或开始执行。

条款内容

6.12推送通知（可选能力）

A2A 标准有三种跟踪 Task 的方式：流式、轮询、推送通知。BCS 目前只用前两种。推送通知是调用方在提交时给出一个地址，Agent 在 Task 状态变化时主动通知。它适合三类场景：

  • 执行时间很长的 Task（几分钟到几小时），调用方不应一直持有连接或每秒轮询。
  • 非流式 Agent（L1），目前只能靠 1 秒一次的轮询跟踪。
  • 等待人工审批的 Task，等待期间没有输出。

Profile 现在就定义它的语义，否则各业务会按各自的理解实现。实现放在后续阶段。

条款内容
P-150推送通知是可选能力，通过 Card 的 capabilities.pushNotifications: true 声明。未声明的 Agent，四个推送配置方法必须返回 PushNotificationNotSupportedError（标准要求；GRPC 为 FAILED_PRECONDITION，HTTP 为 400）。未声明的 Agent 在 SendMessage 中收到推送配置时返回同一错误，不得静默忽略（标准未规定，这是 Profile 的收紧）。
P-151声明了推送能力的 Agent 必须同时支持两种设置方式：初始提交时的 configuration.taskPushNotificationConfig；以及标准的四个配置方法 CreateTaskPushNotificationConfig、GetTaskPushNotificationConfig、ListTaskPushNotificationConfigs、DeleteTaskPushNotificationConfig。配置随 Task 保存，到 Task 结束或被删除为止。一个 Task 可以有多个配置，Profile 限制为最多 4 个。
P-152只在 Task 进入终态或中断态（INPUT_REQUIRED）时发送，每次状态变化一条。文本增量、过程事件（E4）、内容块更新不发推送。标准只说“Task 状态变化时发送”，没有列出触发事件，这是 Profile 的收紧。
P-153推送是提示，不是事实。负载按标准使用 StreamResponse 格式，Content-Type 为 application/a2a+json；Profile 限定其中只放 statusUpdate（taskId、contextId、当前状态），不放 Artifact 内容和扩展数据。调用方收到后必须用 GetTask 取得结果。
P-154对每个配置至少尝试投递一次（标准要求）。失败时有限次退避重试，单次请求超时 10 到 30 秒（标准的建议值）。接收方以 2xx 确认、校验 Task 标识是自己预期的（标准要求），并能处理重复和乱序。标准不保证推送的顺序。投递失败不影响 Task 的状态。
P-155调用方不得只依赖推送。必须保留低频查询兜底，因为推送可能永远不到。
P-156Agent 必须限制推送地址：只向配置允许的内部域名发送，其他地址在设置时拒绝。这是为了防止调用方利用 Agent 去访问任意内部地址。标准的安全建议是拒绝内网地址，这在公司内网场景不适用，所以改为域名白名单。
P-157调用方在配置的 authentication 中给出 scheme: "Bearer" 和一个每个 Task 随机生成的 credentials。Agent 必须在推送请求的 Authorization 头中原样带回（标准要求）。接收方校验它与 Task 的对应关系。它用于关联和防止误投，不改变“调用 Agent 不鉴权”的决定（D1）。配置中的 token 字段在 1.0 中没有对应的请求头定义，Profile 不使用。凭据不得写入日志，Get 和 List 返回时必须隐去。

谁负责投递

引擎模式下由引擎在关键状态变化时投递，至少一次由引擎保证；托管模式下由 SDK 投递（8.16）。无论哪种模式，推送都可能丢失或重复，这正是 P-154、P-155 要求接收方去重并保留查询兜底的原因。

6.13多模态输入输出（可选能力）

A2A 标准本身已经定义了多模态：Part 可以是文本、文件字节（raw）、文件地址（url）或结构化数据（data），并带 mediaType 和 filename；Card 和每个技能可以声明支持的输入输出类型；调用方用 acceptedOutputModes 声明能接收的类型。这些不需要扩展。

BCS 目前只处理文本，但标准不应该因此只定义文本，否则各业务的图片、文件能力会各自实现。Profile 沿用标准的多模态定义，只补充企业场景下标准没有规定的部分：文件怎么传、多大、对方不支持时怎么办。

P-162Agent 只能输出请求的 acceptedOutputModes 中列出的类型。调用方未列出某类型时，Agent 必须用文本给出等价说明（例如文件的名称和摘要），保证纯文本结果完整可读。省略 acceptedOutputModes 等同于只接受 text/plain。
P-163文件默认按引用传递：使用 url，并给出 mediaType 和 filename。内联字节（raw）只用于小文件，单个不超过 256 KB，且整个请求不超过 1 MiB。超过时返回参数错误。
P-164文件地址必须是接收方在公司内部网络内可以直接读取的地址。输出文件的地址有效期不短于 Task 的保留期。地址来源见 Q20。
P-165Agent 读取输入文件地址前必须检查域名在允许范围内，理由同推送地址（P-156）。不得根据 filename 或地址后缀判断类型，以 mediaType 为准。
P-166输出的文件和数据作为独立的内容块，遵循 7.5 的顺序、整块替换、数量上限和 GetTask 规则（P-140、P-141、P-146、P-147）。不对文件块使用 append: true。
P-167每个文件块必须有 name 或 description，供不能展示该类型的调用方显示。
P-168实时音视频流不在 Profile 范围内。音频和视频只能作为完整文件传递。

7.4扩展模型

前面的平台扩展是逐个定义的。业务方的定制需求主要有三类：请求里带业务参数；响应和 Task 更新里带自定义字段；返回给客户端或前端渲染的 UI 数据。为每个业务逐个写规范、逐个改 BCS 不可持续。

扩展点和扩展是两回事。扩展点由 Profile 固定，业务不能新增或修改，也不需要登记；五个不够用时向 BCN 提需求，通过 Profile 升级增加。扩展是业务自己定义的约定，选用其中几个扩展点来放数据。扩展不需要登记就可以使用，经过 BCS 时也是透明透传（7.6）。

本节定义五个扩展点。每个扩展点规定数据放在哪里、活多久、多大、中间环节怎么处理。业务扩展只需要声明自己用了哪些扩展点，BCS、SDK 和 Client 按扩展点的规则处理，不需要理解数据内容。

扩展点用途载体方向生命周期大小上限

7.6经 BCS 透传

业务扩展经过 BCS 时，BCS 透明透传，不需要登记，BCS 也不需要认识这个扩展。这之所以可行，是因为扩展点的设计已经把 BCS 需要知道的事情固定了：

  • 数据属于哪个扩展点，从它所在的位置就能判断，不需要额外的描述。
  • 大小和数量上限按扩展点统一规定，不按扩展分别规定。
  • 每个结构化块都带降级文本，BCS 自己需要文本的地方始终有文本可用。

透传不是无条件的。BCS 只做四项与内容无关的检查：

条款内容防止的问题
P-136只透传已协商的扩展。BCS 把上游 Client 声明的扩展 URI 带给 Agent（去掉 Agent 的 Card 中没有声明的）。Agent 返回的数据中，URI 不在这个集合内的一律丢弃。Agent 向上游夹带对方没有要求的数据
P-137按扩展点的统一上限检查大小和数量（7.4、7.5）。超过上限的那一条被丢弃并计数，不影响文本结果和 Task 状态。单个 Agent 占用 BCS 的带宽和存储
P-138只沿本次调用的路径透传。扩展数据不广播给群聊中的其他 Bot，不进入其他 Bot 的上下文。BCS 自己需要内容的地方（会话历史、转发给其他 Bot）使用文本和降级文本。一个业务的私有数据流到不相关的 Bot
P-139BCS 不解释、不改写扩展数据，日志中只记录 URI 和大小，不记录内容。业务数据进入 BCS 的日志

经过 BCS 时的协商与透传

  1. Client在请求中列出自己实现的扩展。当前阶段的终端是 BCN 工作台，由 BCS 代为声明工作台支持的集合。
  2. BCS向 Agent 协商的集合为：上游声明的扩展中 Agent 的 Card 也声明了的，再加上 BCS 自己处理的平台扩展。
  3. Agent只对协商到的扩展发出数据；其余按降级规则输出文本。
  4. BCSE2 原样下发；E3、E4、E5 原样上送。平台扩展照常由 BCS 处理。

只透传、不登记，剩下的问题

问题影响处理

7.9工具观察（v2）

工具调用是执行过程信息，不是任务的产出（D12）。A2A 规范对此有明确划分：状态消息用于"告知任务进展、请求输入或提供信息性更新"；产出物是"作为任务结果生成的输出"；断线重连时调用方可能收不到全部状态消息，消息不能作为关键信息的可靠投递手段。工具观察按这个划分定位为尽力投递的过程信息：

  • 在线时实时可见，断线、轮询或跨实例订阅时丢失的记录不补发。
  • 需要保存工具调用的一方自己保存。BCS 在群协作和会话历史中本来就持久化收到的工具调用，不依赖 Agent 提供历史。
  • v2 相对 v1 只增加一种载体：没有 Task 的 L0 回复也能带工具记录。

8Java Server SDK

8.1设计原则

  • 任务状态以引擎为唯一来源。SDK 不另存一份任务状态，查询、订阅、取消都交给引擎回答（D3）。只有托管模式由 SDK 代管（8.10）。
  • SPI 就是 A2A 的五个方法。方法名、参数和返回值类型与标准一致，平台方读 A2A 规范就能理解 SPI（D8）。
  • 标准约束靠校验和工具库保证。SDK 在协议层校验和过滤引擎的输出（8.6）；扩展的编码规则由工具库提供（8.7），平台不必自己实现。
  • 平台差异全部走 SPI 和配置。SDK 内不判断部署环境。
  • 失败要可见。校验不通过、超限、引擎报错都转成明确的协议错误或 Task 失败，不吞掉。

8.6请求处理与标准校验

流式发送的处理顺序

  1. starter按绑定解析请求，提取版本、扩展协商头、tenant 和 RPC 调用方应用名。
  2. core校验版本；通过 AgentResolver 找到 handler。新 Task 计算协商结果，必需扩展缺失则返回 EXTENSION_SUPPORT_REQUIRED；续交从 Task 读回初始协商结果。
  3. core检查输入类型（P-161）；解析调用上下文；执行 AgentAuthorizer。失败直接返回协议错误，不调用引擎，不创建 Task。
  4. core组装 BcnCall，调用 handler。
  5. core在 handler 返回的事件流外包一层校验，逐帧检查和过滤后交给绑定层发出。

结构化块带降级文本（P-142）检查块内是否有文本 Part拒绝
输出类型（P-162）检查 Part 的 mediaType 是否在 acceptedOutputModes 中拒绝
大小和数量上限（P-74、P-134、P-147）累计检查拒绝
SDK 保留数据检查 Task.metadata 的 bcn.sdk 键过滤

"过滤"用于去掉数据不影响结果正确性的情况。"拒绝"表示 SDK 无法安全修正：流式响应以协议错误结束，调用方按断流处理（先查询再订阅）；单次响应返回内部错误。两者都记录违反的条款编号。生产环境是否先只记录不拒绝，见 Q25。

校验只覆盖单个请求内能看到的内容。跨请求、跨实例的一致性，例如 A 实例流上输出过的文本在 B 实例的查询快照里是否保留了相同前缀，SDK 看不到，由 TCK 的引擎要求分组验证（第 10 节）。

8.8引擎模式示例

一个订单 Agent，引擎有自己的运行记录。示例展示新请求、审批续交、查询、订阅和取消如何对应到引擎接口。

@Component
public class OrderAgentHandler implements A2aAgentHandler {

    private final OrderEngine engine;   // 业务原有的引擎，运行记录在它自己的共享存储中
    private final RunMapper mapper;     // 业务自己写的映射：运行记录 → A2A Task 和事件

    @Override
    public AgentDescriptor descriptor() {
        return AgentDescriptor.builder()
                .name("订单助手").description("查询订单、办理退款").version("2.1.0")
                .skill("query_order", "查询订单", "根据订单号查询订单状态和物流", "orders")
                .skill("refund", "办理退款", "为订单发起退款，执行前需要用户确认", "orders")
                .streaming(true).requireUserId(true)
                .toolObservation(true).execApproval(true)
                .businessExtension(OrderUi.URI, OrderUi.CARD_PARAMS)
                .build();
    }

    @Override
    public Flow.Publisher<StreamResponse> sendStreamingMessage(BcnCall<SendMessageRequest> call) {
        Message msg = call.request().message();
        RunRecord run = engine.start(call.caller().userId().orElseThrow(), msg.contextId(),
                                     Texts.of(msg), call.taskAttributes());
        return mapper.stream(engine.subscribe(run.id()), call.extensions());
    }

    @Override
    public SendMessageResponse sendMessage(BcnCall<SendMessageRequest> call) {
        Message msg = call.request().message();
        if (msg.taskId() == null) {                          // 非流式的新请求
            RunRecord run = engine.start(call.caller().userId().orElseThrow(), msg.contextId(),
                                         Texts.of(msg), call.taskAttributes());
            return SendMessageResponse.of(mapper.toTask(run, call.extensions()));
        }
        // 审批续交：可能落在任意实例上，只依赖引擎的运行记录
        Task current = mapper.toTask(engine.get(msg.taskId()), call.extensions());
        ApprovalOutcome outcome = Approvals.accept(current, msg);   // 不合法时抛出协议错误
        RunRecord run = engine.confirm(msg.taskId(), outcome.decisions(),
                                       Approvals.receipts(current, outcome));  // 引擎原子地记录并继续（R-06）
        return SendMessageResponse.of(mapper.toTask(run, call.extensions()));
    }

    @Override
    public Task getTask(BcnCall<GetTaskRequest> call) {
        return mapper.toTask(engine.get(call.request().id()), call.extensions());
    }

    @Override
    public Flow.Publisher<StreamResponse> subscribeToTask(BcnCall<SubscribeToTaskRequest> call) {
        return mapper.stream(engine.subscribe(call.request().id()), call.extensions());  // 首帧为快照（R-02）
    }

    @Override
    public Task cancelTask(BcnCall<CancelTaskRequest> call) {
        return mapper.toTask(engine.cancel(call.request().id()), call.extensions());
    }
}

/** 映射必须是确定性的：同一份运行记录在任何实例上都映射出相同的 Task。 */
final class RunMapper {
    StreamResponse toEvent(RunRecord r, RunEvent e, Set<String> ext) {
        return switch (e) {
            case TextDelta t    -> textUpdate(r, "seg-" + t.segmentId(), t.text(), t.isFirst());
            case ToolStarted t  -> StreamResponse.of(ToolRecords.started(task(r), t.callId(), t.name(), t.args()));
            case ToolFinished t -> StreamResponse.of(ToolRecords.finished(task(r), t.callId(), t.name(), t.args(), t.failed(), t.summary()));
            case NeedsConfirm c -> statusUpdate(r, TaskState.TASK_STATE_INPUT_REQUIRED,
                                                Approvals.request(c.batchId(), c.expiresAtMs(), c.calls()));
            case OrderCard c    -> blockUpdate(r, ext.contains(OrderUi.URI)
                                        ? Blocks.structured("card-" + c.id(), OrderUi.URI, OrderUi.CARD_TYPE, c.json(), c.text())
                                        : Blocks.fallback("card-" + c.id(), c.text()));
            case Finished f     -> statusUpdate(r, f.ok() ? TaskState.TASK_STATE_COMPLETED : TaskState.TASK_STATE_FAILED, null);
        };
    }
    // toTask、stream、textUpdate、statusUpdate、blockUpdate 略
}
代码中的位置对应的设计
engine.start(..., call.taskAttributes())引擎把 SDK 保留数据写入 Task 并持久化（8.5、R-05）
Approvals.accept 然后 engine.confirm回复由工具库校验；引擎原子地记录决定，两个实例同时收到同一批回复时只生效一次（R-06）
"seg-" + t.segmentId()块标识由引擎数据推导，保证不同实例映射出相同的 Task
ext.contains(OrderUi.URI)未协商时输出降级文本（P-143）
engine.subscribe首帧快照与后续事件的衔接由引擎保证（R-02）

8.10托管模式

给没有运行记录的简单 Agent 用（D9）。平台只写"输入到输出"的逻辑，Task 的创建、状态、存储、查询、订阅、取消都由 SDK 代管。SDK 把 ManagedAgent 包装成一个 A2aAgentHandler，所以请求处理和校验与引擎模式相同。

8.13Card 生成、发布与注册

  • 生成。starter 根据 AgentDescriptor 和配置的接口地址生成 Card。扩展声明来自 AgentDescriptor 中显式声明的能力。托管模式不允许声明 exec 审批。
  • 校验。启动时用 bcn-a2a-spec 的校验器检查 Card。不合规则启动失败，并给出具体条款编号。
  • 发布。开启了 HTTP+JSON 或 JSONRPC 时，在 {base-path}/{tenant}/agent-card.json 提供 Card。只开启 GRPC 时，通过内联 Card 注册。
  • 注册。AgentRegistrar 默认关闭。开启后在启动完成时调用 BCS 的 Provider 管理接口：以 provider_bot_ref 查询，不存在则注册，存在且 Card 有变化则更新。管理凭据从平台的密钥配置读取，不写在应用配置中。注册失败不阻止应用启动，但会告警并重试。

多实例同时启动会并发注册。BCS 对重复的 provider_bot_ref 返回冲突，SDK 收到冲突后改为查询再更新。更新是完整替换且以最后写入为准，各实例的 Card 相同，因此结果一致。动态 Agent 的注册时机见 Q10。

9多实例设计

9.1模型

消息模式没有 Task，也就没有跨实例的问题。引擎模式下 SDK 是无状态的协议层。任何实例收到任何请求，都在协议层处理完后转给引擎；实例之间不通信，也不共享 SDK 层的状态。多实例下的正确性由引擎满足 9.2 的要求来保证，SDK 不做补救（D3、D4）。托管模式由 SDK 代管任务状态，见 9.5。

9.2对引擎的要求

以下要求适用于引擎模式。它们由 TCK 的引擎要求分组验证：至少两个实例，请求分别发到不同实例，以及终止并重启实例（第 10 节）。

编号要求为什么需要
R-01Task 标识稳定，任意实例都能按标识查询、订阅、取消没有按键路由，后续请求可能落到任何实例
R-02订阅的首帧是当前快照，后续事件与快照衔接，不重复、不遗漏SDK 不再自己合成订阅；断流恢复依赖它（P-40、P-43）
R-03输出只追加，包括停机重启恢复之后。恢复时不得改写已经产出的内容调用方可能已经看到这些内容（P-71）
R-04停机重启后运行可以恢复；不能恢复时置为 FAILED，不得停在非终态停机恢复由引擎保证（D4）；停在非终态会让调用方一直跟踪
R-05Task.metadata 和 Artifact.metadata 原样持久化，包括 SDK 保留键和扩展字段（E3）；结构化块和文件块（E5、6.13）随 Task 持久化SDK 从 Task 读回协商结果和调用上下文（8.5）；断线后查询要能拿到扩展数据
R-06等待审批时，待确认的工具调用、参数快照和已接受的决定随 Task 持久化；记录决定和继续执行是原子的，同一批决定只生效一次审批结果可能落到任意实例，也可能同时到达两个实例
R-07终态在保留期内可查询，保留期不短于 24 小时（6.9）BCS 断流后用查询核对最终结果
R-08会话记忆按 contextId 跨实例可用同一会话的下一轮请求可能落到其他实例
R-09取消可以从任意实例发起，并如实返回结果（P-50 到 P-54）取消请求可能落到不执行该运行的实例

9.4停机与恢复

由引擎保证（D4）。SDK 侧只做两件事：停机时关闭已打开的流；调用方断流后按 P-113 先查询，请求落到其他实例，由引擎回答。

引擎用检查点恢复时，最常见的问题是检查点和已输出内容不在同一个点上：检查点更新而输出没落盘，会丢输出；输出已展示而检查点更旧，恢复后会重做这一步、产出不同的文字，并可能重复执行工具。引擎需要保证 R-03，建议按以下方式实现：

  • 先把输出落盘，再记检查点，并在同一次写入中记下检查点对应的输出位置。
  • 恢复时按引用加载检查点，不加载"最新的"。
  • 检查点之后已经输出的内容不撤回；恢复后的输出另起新块，并发一条"已从检查点恢复"的状态消息。
  • 非幂等的工具已开始但没有结果时，不得直接重做：先查询实际结果，或在审批可用时请求审批，否则以失败结束。
  • 限制每个运行的恢复次数，防止必定崩溃的输入反复恢复。

9.5托管模式的多实例实现

托管模式的 Agent 没有运行记录，由 SDK 把 Task 状态存到分布式缓存（D7）。

模型

  • 接收初始请求的实例是该 Task 的执行实例，执行权不迁移。它是 Task 内容的唯一写入者，并持有一个租约。
  • 其他实例只做三件事：读快照、写取消标记、回收租约过期的 Task。
  • 实例之间不通信，协作全部通过存储的比较并写入完成。
public interface TaskStore {
    Optional<TaskRecord> get(String agentKey, String taskId);
    boolean create(TaskRecord record);                              // 不存在才写入
    boolean compareAndSet(TaskRecord next, long expectedVersion);   // next.version = expectedVersion + 1
}

成本

每个在途 Task 每秒最多一次按键的写入，只写增量；跨实例订阅每秒一次按键的读取。没有扫描，没有事务跨越 Agent 执行。

9.6明确不保证的事项

  • 引擎不满足 9.2 的要求时，SDK 无法补救。TCK 的引擎要求分组用于发现这类问题。
  • SDK 的校验只覆盖单个请求内的输出（8.6）。
  • 托管模式：停机或宕机后在途 Task 失败；跨实例订阅粒度约 1 秒，看不到工具记录和过程事件（E4）；跨实例取消有秒级延迟。
  • 会话记忆由引擎负责，SDK 不管理。

13安全与信任

主题设计
信任边界公司内部网络。三种绑定的端点都不鉴权，都不得暴露到公网。HTTP 端点只能绑定内部域名，不得挂到对外网关。这是部署要求，SDK 无法在代码层面保证。
HTTP 下的调用方身份GRPC 经 SOFARPC 可以取得调用方应用名。HTTP+JSON 和 JSONRPC 没有等价的可信来源，callerApp() 为空。这两种绑定下的授权只能依据调用上下文扩展中的 source。
授权BCN 在调用上下文扩展中带上来源信息，Agent 通过 AgentAuthorizer 自行决定。Profile 不规定授权规则，默认全部接受。来源信息未签名，可信度依赖内部网络。
用户身份userId 由 BCS 从已认证上下文生成，不验签。能发起 RPC 的内部应用可以构造它。
隔离SDK 按 tenant 选择 handler；引擎和托管模式的存储都必须按 Agent 和 tenant 隔离。跨 Agent、跨 tenant 的 Task 访问返回未找到。
标识不可猜测taskId 默认随机生成。它不是凭据，但不应可枚举。
数据最小化Task 中保存请求和输出，有保留期。SDK 保留键中的调用上下文只保存必要字段，并在返回给调用方前去掉。日志不记录文本和 userId 原值。
Card 自声明Card 中的等级、来源分类、提供方信息都不授予权限。归属以 BCS 的 Provider 注册关系为准。
管理凭据自动注册使用的 Provider 管理凭据只用于调用 BCS 管理接口，不进入 Card，不出现在日志。
