# 跨引擎收敛语义契约：应用一份 manifest 会对已经存在的东西做什么

> **给 teclaw owner 与 ARCA 系引擎的双边契约。**
>
> 一句话：**被声明的类目覆盖到等于声明，未声明的类目不碰，`MEMORY.md` 与
> `IDENTITY.md` 永不写、永不删。**
>
> 本文档把规则写成对 **applier** 的**要求**，而不是对平台实现的描述——因为
> 在 teclaw 上，applier 不是我们。

---

## 1. 为什么需要这份契约

平台正在做 **Bot Config Manifest**：用户提交一份声明式配置清单，平台在生命周期
边界上把它落成真实实体（skills / identity / resources / mcp …）。

问题在于「落成」这个动作的最后一步不在同一个地方：

- **BaaS / ARCA 系**——平台自己写文件、自己对齐 skill set，收敛语义归我们；
- **teclaw**——平台把整包 `BotConfigArtifact` 递交过去，容器内怎么应用归你们。

今天没有任何东西让这两侧一致。**而这种不对称在咬到用户之前对用户不可见**：同一份
manifest、同一次修改，在两种 bot 上得到不同结果，用户既没有办法预期，也没有办法
排查。这份契约就是把它变成一件被写下来、被双方同意的事。

**这不是一场谈判。**核心问题已经有答案：**teclaw 的重新下发是全量覆盖**（与
teclaw owner 确认，2026-08-30）。平台侧的收敛策略**正是因此**采纳了同一套语义，
而不是发明第二套再去调和。所以下面每一条，对 teclaw 而言基本都是**对现有行为的
陈述**；真正需要你们确认的是「是不是确实如此」以及「有没有你们不打算实现的部分」。

---

## 2. 谁是 applier

| 引擎系 | applier | 它收到的输入 | 谁实现本契约 |
| --- | --- | --- | --- |
| **BaaS / ARCA 系**（openclaw / claude_code / aicoding / hermes / moltis） | 平台（backend） | manifest 文档本身 | 我们 |
| **teclaw** | teclaw 引擎 | 整包 `BotConfigArtifact` | 你们 |

**「applier」= 把一份声明变成容器内实际状态的那一方。**下文所有 R 条都是对它的
要求，两侧同时成立。

> **下发契约不变。**manifest 特性对 artifact 如何递交、`{store, path}` 的形态、
> `engine_ext` 的不透明约定**不做任何改动**。teclaw 侧唯一的新增是 `cli_tools`
> 段，单独规格见 `teclaw-cli-contract.zh-CN.md`。

---

## 3. 契约

### R1 — 声明即目标：被声明的类目必须覆盖到**恰好**等于声明

applier 收到某个类目的声明时，该类目的**区域**（§4）在应用之后必须**恰好**是声明
描述的样子。区域内其余的一切必须被移除。

不允许「合并」：声明是 `{A, B}` 而区域里原本有 `{B, C}`，结果必须是 `{A, B}`，
`C` 必须消失。**声明获胜，手工漂移被纠正**——这是 GitOps 语义，不是增量更新。

### R2 — 未声明的类目**不得触碰**

manifest 没有对某个类目表态，applier 就不得对该类目做任何事。不是「清空」，不是
「重置为默认」，是**什么都不发生**。

### R3 — 空集合**本身就是**一种声明

`skills: []` 的含义是「**所有** skill 被移除」，而不是「不管 skills」。显式的空
集合与 R1 同解：区域被覆盖成空。

### R4 — 字段**缺席** ≠ 空集合

这是 R2 与 R3 在传输层的落点，**也是最容易出错的一条**：

| 输入 | 含义 |
| --- | --- |
| 字段不存在 | **保持现状，不要动**（R2） |
| `"skills": []` | **清空**（R3） |

> **为什么这条重要。**manifest 只声明了 `skills` 时，因为 skills 变更而下发的
> artifact 里**不会有** `resources` 或 `cli_tools` 字段。若把缺席读成 `[]`，一次
> 与它们无关的变更就会把用户正在用的资源或命令全部清掉。**manifest 层与 artifact
> 层必须在这一点上一致**，否则 R2 在传输过程中被悄悄推翻。

### R5 — 保留名：`MEMORY.md` 与 `IDENTITY.md` 永不写、永不删

**这是 applier 绝不能碰的唯一一件事。**它们是引擎生成的运行期状态，不是配置：

- applier **不得**因为任何声明而写入这两个文件——平台侧在 `PUT` 时就拒绝声明它们，
  所以合法的 manifest 里不会出现；
- applier **不得**因为 R1 的覆盖而删除这两个文件——即使 `identity` 类目被声明、
  即使它们不在声明里。它们**在所有覆盖之外**。

> **这一条取代了一份被撤销的要求。**早先的版本要求 applier「保留新旧两个版本都
> 没声明的所有文件」——那是一个**无界集合**，我们既无法替你们计算，也无法验证。
> 两个具名文件是一份能被同意、也能被检查的契约。

### R6 — 类目是 all-or-nothing 写入的

声明类目里只要有任何一条无法物化，**该类目整个不被覆盖**——关于它的一切保持不变。

**理由是覆盖语义本身让不完整的集合变成破坏性的**：声明是 `{A, B}` 却只写入
`{A}`，在 R1 之下就等于删掉了 `B`。所以类目只能从**完整的目标状态**被写入，一个
瞬时的拉取失败不允许删掉一个正在工作的实体。

平台侧的对应保证：一个类目里的每一条**先全部物化**（拉取、校验、解包、存储）
才发出该类目的任何下发写入，所以 all-or-nothing 的决策是在完整目标状态已经在手时
做出的。

**一个类目的失败绝不牵连另一个类目。**

### R7 — 收敛：应用 N 次 = 应用 1 次

同一份输入重复应用，结果必须相同，且不得有副作用堆积（残留文件、重复条目、
版本堆叠）。重复投递同一个 artifact 是**正常情况**，不是错误。

### R8 — 配置先于就绪

applier 必须在报告 bot **ready 之前**完成整份配置的应用。不允许出现「已经 ready
但配置只应用了一半」的窗口。

> teclaw 已确认满足本条（T1，2026-08-30）：报告 ready 之前会把整个 artifact 应用
> 到 bot 上。

### R9 — 未知字段忽略，不报错

契约会继续演进（例如 `cli_tools` 带来的 `schema_version` 4 → 5）。applier 遇到
不认识的字段应当忽略它，而不是拒绝整份输入。

> 平台侧的对应保证：**在你们支持某个 `schema_version` 之前，我们不下发依赖它的
> 字段。**所以这一条是安全网，不是我们打算依赖的路径。

## 4. 「区域」是逐类目定义的，不是全局的

R1 的覆盖需要一个作用域，而**这个作用域对每个类目并不是同一个形状**。搞错这一点，
一条本意是收敛 skill 列表的规则就会删掉 bot 的工作目录。

| 类目 | 被覆盖的区域 | 备注 |
| --- | --- | --- |
| `skills` | **active skill set** | 它等于声明；未列出的 skill 被移除 |
| `identity` | **identity 文件集合，减去 R5 的保留名** | claude_code 的合法集仅 `CLAUDE.md` |
| `resources` | **仅声明的 `path` 子树** | 见下方警告 |
| `mcp` | **已启用的 server 集合** | |
| `cli_tools` | **由 manifest 下发的命令集合** | 不影响镜像自带命令。详见 `teclaw-cli-contract.zh-CN.md`；teclaw 侧待评审 |
| `script` | `ac_bot_startup_script` 那一行 | **teclaw 不支持**，写入即拒；ARCA 系走 #935 既有启动链 |

> ### ⚠️ `resources` 是绝不能读成「区域 = 整个 workspace」的那一个
>
> 被覆盖的只有**声明的 `path` 那棵子树**，整体替换。声明的 `path` **之外一律不碰**
> ——workspace 是 bot 的工作区，不是 manifest 的。把这个区域读宽一格，就是删掉用户
> 的工作成果。

`engine_config` **不在第一期范围内**（T3），所以本表暂不涉及它。

## 5. 双方各做什么

| | 平台（我们） | applier（BaaS/ARCA 侧是我们；teclaw 侧是你们） |
| --- | --- | --- |
| 拉取源内容 | ✅ 全部平台侧完成 | ❌ 不需要出网 |
| 校验 digest / 解包归档 | ✅ | ❌ |
| 决定哪些类目被声明 | ✅ | ❌ 照收到的输入执行 |
| R6 的 all-or-nothing 判定 | ✅ 只发出完整的目标状态 | — |
| 把区域覆盖成声明（R1–R3） | ✅（BaaS/ARCA） | ✅（teclaw 容器内） |
| 保护保留名（R5） | ✅ | ✅ |
| 收敛与幂等（R7） | ✅ | ✅ |
| 配置先于就绪（R8） | — | ✅ |
| 逐条记录「有没有下发成功」 | ✅ | ❌ |

**关于最后一行的边界，特此写明：**平台的 apply 记录**到「下发」为止**——artifact
递交完成，或逐文件写落地。**引擎之后拿它做什么，是引擎的契约（本文档），不是
apply 的记录。**apply 回答「我们有没有下发」，容器和引擎回答「有没有生效」。

## 7. 自查清单

供实现方自查，也是平台侧联调时会验证的点：

- [ ] 声明了某类目后，该类目区域内**未被声明**的旧内容确实消失了（R1）。
- [ ] **未声明**的类目在同一次应用后**逐字节不变**（R2）。
- [ ] 显式空集合清空了该类目（R3）；**字段缺席**则什么都没发生（R4）。
- [ ] `MEMORY.md` 与 `IDENTITY.md` 在**任何**一次应用之后都还在，内容未被改写（R5）。
- [ ] 特别地：声明了 `identity` 且声明里不含这两个文件时，它们**仍然存在**（R5）。
- [ ] `resources` 的覆盖只影响声明的 `path` 子树，子树之外的工作区文件未被触碰（§4）。
- [ ] 同一份输入连续应用两次，第二次没有产生任何变化，也没有残留（R7）。
- [ ] bot 报告 ready 时，整份配置已经应用完毕（R8）。
- [ ] 含未知字段的输入被接受，未知字段被忽略（R9）。
