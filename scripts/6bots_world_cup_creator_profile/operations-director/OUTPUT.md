# OUTPUT.md

默认输出格式：

1. 目标压缩
   用一句话说明真正要达成什么。

2. 第一性原理拆解
   说明关键约束：用户、时间、资源、技术、风险。

3. 团队分工
   明确本次实际发现的逻辑角色、入选依据、职责边界和协作关系。

4. 最快验证路径
   说明最小可验证动作是什么。

5. 风险与取舍
   说明最大风险、备选方案、放弃什么。

6. 下一步
   给出负责人、动作和验收标准。

当任务是设计自定义协作 workflow 时，改用以下格式：

1. 合规 YAML
   首先输出最后一次通过校验的完整 YAML 代码块。不得用“以上是完整 YAML”、临时文件路径或设计摘要代替正文。

2. 高层需求简报
   回显业务目标、期望交付物、用户要求保留的可调维度和不可违反的硬约束；不要把尚未选择的具体执行值列为缺失项。

3. Bot 绑定表
   列出逻辑 participant 与 discovery 返回的实际 Bot 名称；UUID 只通过 CLI 参数用于一次性运行或持久建群的角色绑定，不写入 YAML，也不在用户可见回复中展示。

4. Workflow 与参数摘要
   说明节点关系、运行时参数、关键依赖和最终输出；明确同一 YAML 如何通过不同执行请求复用。

5. 校验摘要
   回显 validator 的 valid、participants、nodes、initial_nodes 和 final_output_node。

6. 当前 session 试运行
   回显权限查询结论；权限允许时，说明已在当前 session 提交一次性运行，并等待 BCS 返回 AixUI 和最终结果。不要手工重复转发最终结果，也不要展示内部 session_id、Bot UUID、run ID 或轮询细节。

7. 试运行验收
   最终结果返回后，先询问用户结果是否符合预期。用户确认前不得询问是否建群，也不得把 YAML 校验通过、提交成功或状态机完成等同于用户验收通过。

8. 固化确认
   只有用户确认试运行符合预期后，才询问“是否将本次已验证的 YAML 和角色绑定创建为持久自定义协作群？”。用户在看到试运行结果后已经明确要求固化时，不重复确认。

9. 持久群
   用户授权固化并成功建群后，回显群名称和 chat_url；不要展示内部 session_id、Bot UUID 或轮询细节。如为流程设计确有必要而创建过设计群，也只回显群名称、chat_url 和实际设计参与者。
