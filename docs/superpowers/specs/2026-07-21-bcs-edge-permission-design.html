第一部分什么是边权限

1. 一张图说清边权限

边权限不是一张新表、不是一种新机制,它就是 BCS 关系图本身的结构。我们把多 bot 协作的权限关系,画成一张有向图:

  • 点(vertex)有三类:human、bot、service。没有第四种点。
  • 有向边(edge)= 一个角色 = 一组权限集合。边 A → B 表示"A 对 B 的角色",这个角色就是绑在这条边上的一组 (tool, specifier, allow/deny) 规则。角色不是独立节点,它就是边本身。
  • 同一对 (A,B) 可以有多条边(多角色),按 allow 优先合成。
  • env 是边键:(from, to, env) 唯一,有向图按环境隔离。
  • 边可开代理开关:proxy_allowed(默认 false),允许此边代人转发,见 §3.5。

3. 边:一条边就是一个角色

3.1 边的两个身份

一条有向边 A → B 兼具两种身份,但它们是同一条边、不是两件事:

身份含义承载
关系身份A 和 B 是否有关系(熟人 / owner)边是否存在 + is_creator
权限身份A 凭这条边能对 B 做哪些 tool 调用绑在边上的 (tool,specifier,allow/deny) 集合
friend 就是 default 边——模型只有一类边。原来 friend(关系层)与角色边(权限层)两件东西,本方案收敛成一类:friend 即一条 role_name=default 的角色边,其 rules 引用 bot owner 配的 default 规则集。于是"是熟人"= default 边存在,"走默认权限"= default 边参与求值。关系层/权限层之分只是同一条边的两个视角,不是两种结构。三类角色名并立:default(=friend,走默认)/ 具体角色名(只读者 等)/ owner(全权,§3.3)。friend 管入场细度归 default,owner 管归属。

3.2 边的数据形态

一条边是一个 rule 容器——角色名只是这组 rule 的友好标签,不是边的必需组成。一条边可装 1~N 条 rule;只装 1 条 rule 的边就是"单条权限形成的边"。同对点之间多条边,靠 edge_id 区分,不靠角色名(因为可以匿名)。

Edge(A → B, env) = { edge_id : 自增主键 ★ 同对点多边靠它区分,不靠角色名 role_name : "只读者" | "owner" | 自定义 | null ★ 可选; null=匿名边 rules[ ] : 1~N 条,每条 = (tool, specifier, allow | deny) 如 (Read, ./*, allow) (Edit, /prod/**, deny) (Bash, rm *, deny) // 边的元信息(可选,默认安全) delegation_depth : 0 = 不可再委托给下游; >0 = 可向下传 N 跳 expires_at : 过期时间; null = 不过期(默认) ★ 预留扩展:V1 全 null,为将来支持临时授权留口 // 申请-审批(写入流程,见 §3.2.4) status : pending | approved | rejected ★ 只有 approved 参与求值 applicant : 发起申请的 caller approver : 审批的 B 的 owner grantor : 谁授的这条边(= approver,审批通过者) proxy_allowed : false(默认) | true ★ 代理开关:是否允许此边代人转发,见 §3.5 }

3.2.1 单条权限 = 匿名边(角色名可选)

当只要授权一条权限时,不必为它临时造一个角色名。这条权限直接成一条 role_name = null 的匿名边——它就是容器 size=1 的退化,与命名角色边同构:

# 只想给 Bob 单独开 "能往 /tmp 写" 这一条权限 Edge(human_bob → bot2, prod) = { edge_id : 42 role_name : null # 匿名,不起名 rules : [ (Write, /tmp/**, allow) ] # 只一条 grantor : human_alice } # 对比:批量授权"只读者"角色 = 命名边 Edge(human_bob → bot2, prod) = { edge_id : 41 role_name : "只读者" rules : [ (Read,./*,allow), (Edit,*,deny), (Bash,*,deny) ] grantor : human_alice }
角色名是管理便利,不是语义必需。能复用时起名(只读者),临时单权限就不起名(匿名)。两条边在求值时一视同仁——A→B 的所有边展平成一个 rule 池,按 §5 三档求值(守卫→ allow 优先→ default)。命名与否不影响求值,只影响"按角色名批量删/改"的管理便利。

3.2.2 边爆炸的收敛:同源匿名边自动合并

若每条单权限都匿名成独立边,同一对点可能挂几十条小边。这不是错(多边本就是设计意图,删一条不影响其它,见 §17),但为收敛噪声,加一条轻规则:

# 合并规则(写入时触发,对调用方透明) 当给 (A→B) 写一条匿名边时: 若已存在 同一 grantor 的匿名边 → 把新 rule 追加进那条已存在的匿名边(同一容器),不新建边 否则 → 新建一条匿名边 # 即:同对点 + 同 grantor 的零散单权限,归并进同一条匿名边 # 命名角色边不参与合并(它是显式打包的,保持独立)
合并只针对匿名边、只按 grantor 归并。命名角色边(只读者、受限协作者)是 owner 显式打包的语义单元,保持独立、不被并。这样:零散单权限不致边爆炸(自动并进同源匿名边),命名角色仍可整块复用/撤销。合并对调用方透明——求值仍是展平 rule 池,合并与否结果一致。

注意 rules 就是 briefing 的 (tool, specifier, decision) 三元组。一条边 = 一组这种三元组(装 1 条就是单权限,装多条配个名就是角色)。三元组里 decision 仅二元(allow/deny),贴合 briefing 第一层。

3.2.3 过期时间:默认不过期,预留扩展

每条边带一个 expires_at 字段。V1 一律不过期(全 null)——普通授权都是长期有效的。字段保留是为了将来支持临时授权(如"借给同事 7 天只读"、"外包任务 2 小时"等场景),不必到那时再改表结构。

# 过期语义(实现于求值前置,对求值器透明) 读边时,若 expires_at != null 且 now > expires_at: → 此边视为不存在(逻辑失效),不参与 §5 求值 → caller 该对点若无其它有效边 → 退回 bot default 集(同 §17 撤销后行为) → 关系层:是否连 friend 关系一并失效? 默认仅权限身份失效,friend 保留(最小破坏) # 物理清理:过期边可留作审计,或由后台 GC 异步清,不阻塞求值
设计取舍:过期只失效权限身份、不撤 friend 关系(和 §17 撤销边权限但保 friend 同源),最小破坏、最易回溯。物理删除走后台 GC,不进鉴权热路径。expires_at 是扩展字段,V1 全 null 零负担——读边 时一个 null 判断即可,过期功能后续平滑开启。

3.2.4 边的写入:申请-审批(被加者必须同意)

核心安全问题:"加好友即加权限"会让被加方(actor B 的 owner)被动获得一条指向自己的边,产生不安,且给恶意 caller 单方面批量建边留口。本方案规定:指向 B 的边,写入须经 B 的 owner 知情同意。落地为统一的申请-审批流程,所有角色边(含 default/friend)都走这条路。

# 申请-审批流程(申请方=caller,审批方=边指向的 B 的 owner) ① caller 发起申请: "我想要 B 的 [default | 只读者 | 自定义] 边" → 写一条 status=pending 的边(不生效,不参与求值,不进准入) ② B 的 owner 审批: accept → status=approved, 边生效(approver/grantor = owner) reject → status=rejected, 边不落(或留待审记录) ③ 仅 status=approved 的边参与 §5 求值与准入 # 安全闸(协议层硬约束) 指向 B 的边,写入须经 B 的 owner 知情同意。 caller 永远不能在 owner 无任何表示时让指向他人 bot 的边生效。 # 仅有 approved 边生效(本方案不渲染位图,§6): status=pending / rejected → 边不参与求值,不进准入门放行 status=approved → 边生效,rules 参与 §5 求值 # 无位图要同步,准入门/bot 端只认 status 字段,一致性好管
角色边类型写入方式发起方生效条件
default(=friend)申请-审批callerB owner 审批通过
具体角色(只读者 等)申请-审批callerB owner 审批通过
owner(全权)不申请—owner 关系是事实(B 的创建者即 owner),系统初始化时落,无流程
为什么不"owner 直灌":owner 直灌在概念上安全,但实操繁琐——B owner 凭什么知道 caller 要什么角色?会把"我想用你的 bot 做只读"这类协调压成线下 IM/邮件文化。申请-审批把协调搬进系统:caller 在系统内发起,owner 在系统内审批待办,既有安全感(被加方同意)又不繁琐(无需线下)。区别于"单方面建边"——申请不立即生效,要审批才落,所以申请=双向同意的 caller 端发起,不是绕过 owner。

3.2.5 可选加速通道(降摩擦,限低危)

审批流若太严会给高频协作添堵。可选加两条加速通道,都建立在 owner 事先表达过信任的前提下:

  • 预授权白名单:B owner 预先把某些 caller 标"可信",这些 caller 的申请自动 approved(免人工审批)。owner 仍掌控,只是减负。
  • 自助申请角色:B owner 公开某些低危角色"可自助申请",caller 申请即自动落边,owner 事后审计而非事前审批。限低危角色(如只读)。

这两条是可选优化,不是核心。核心流程就是 §3.2.4 的申请-审批。安全闸不变:无论申请还是加速通道,指向 B 的边写入都须经 B owner 知情同意(审批 / 预授权 / 公开模板都是"事先同意"的形态)。

3.3 owner 边是特例吗?

不是特例。owner 关系就是一条权限集合=全权的边。token 简化上 is_creator 标它,图里它和其他角色边同构,只是 rules 是 (* , *, allow)(除了平台守卫)。同一张图、同一套求值器,无特例。

3.4 角色是这些权限定义的组合:(tool, specifier, decision) 三元组

§3.2 说一条边(角色)的 rules 是"一组 (tool, specifier, decision) 三元组"。那么这三元组究竟长什么样?它从 opencode + claude code 抄底(底座同构,两产品已收敛)。角色不是凭空一个名字,它就是若干三元组的组合——把几条 (tool, specifier, allow/deny) 装进同一条边,这条边就有了角色身份。

三元组格式:(tool, specifier, decision)。decision 三态 allow/ask/deny,但本稿第一层(角色边)只用二元 allow/deny(贴 briefing「第一层无 ask」);ask 归第二层 bot 自身鉴权。所以角色边上的每条 rule 就是 (tool, specifier, allow | deny)。

每个 tool 的 specifier 类型不同(命令 / 路径 / 域名 / 工具名……),通配让组合既能粗(整类)又能细(精确)。下表给出各 tool 的 specifier 类型、危险面、可直接放进角色的示例 rule:

"只读者""受限协作者"这些角色名,本质就是上面的三元组组合。举例(与第二部分 §9 Alice 定义的角色一致):

# 角色「只读者」= 这几条三元组的组合 只读者 = [ (Read, ./*, allow), (Grep, ./*, allow), (Edit, *, deny), (Bash, *, deny), ] # 角色「受限协作者」= 另一组组合 受限协作者 = [ (Bash, git *, allow), (Read, ./src/**, allow), (Bash, rm *, deny), # 禁删 (Bash, curl *, deny), # 禁外联 (Edit, /prod/**, deny), # 禁改生产 ]

把上面任一组绑到一条 A→B 边上,这条边就拥有该角色;多边(§4)就是同一对点叠多个这样的组合。裸名写法如 allow(Bash)=整个 Bash 工具放行,deny(Bash)=把 Bash 从模型上下文移出(更彻底)——这是三元组的边界用法。

平台守卫不是角色边上的三元组。表里的 deny(Bash(rm -rf /)) 在本方案里属于平台守卫层(§5、§16),不是 owner 可配可撤的角色 rule——它最高优先级、不可取消,绕开角色边的 allow 优先。owner 在角色边里写的 deny(Bash(rm *)) 才是角色 rule(可被另一条 allow 边压过)。
一句话:(tool, specifier, decision) 三元组是权限的最小积木,角色(边)是积木的组合。specifier 的通配/路径/域名/命令模式让组合既能锁整类、又能精确到一条命令;装多少条、装哪些,就决定了这个角色能做什么。

3.5 代理转发:边上的 proxy_allowed 开关

除了"自己调 bot 干活",还有一种情形:bot1 替一个第三方 caller 把活转给 bot2 做,结果算那第三方 caller 的账。这就是"代理转发"。它不是普通调用,需要一个开关来管控,核心是三个不混的概念:

概念归属含义
original_caller消息(一次调用)上的印章"这次调 bot2 真正算谁调的"——发起者身份。由执行转交的那一方盖、原样往下传、中途不改。
proxy_allowed边上的开关(§3.2)"这条边是否允许代人转发"。默认 false;由被调方 owner 设。
"自用 / 代理"模式调用方运行时选调用方看自己边上的 proxy_allowed 决定本次走哪种模式。

3.5.1 三种调用模式(对照表)

调用场景用哪条边边上 proxy_allowed消息 original_caller结果算谁
普通调用:bot1 找 bot2 干活bot1→bot2 普通授权边false(默认,用不上)无bot1
外包自用:bot1 当甲方外包给 bot2bot1→bot2 普通边false 可无(算 bot1 自己的调用)bot1
代理转发:bot1 替 caller3 转给 bot2bot1→bot2 边(须 proxy_allowed=true)+ caller3→bot2 边true(必须)有,=caller3caller3
普通协作零负担。第一行就是绝大多数情况:bot1 找 bot2 干活,边是普通授权边,proxy_allowed 默认 false 也无所谓(消息没 original_caller,根本走不到代理校验),消息上无 original_caller。proxy / original_caller 只在"代人转发"这个特殊场景才出现,默认完全不碰。

3.5.2 为什么需要 proxy_allowed 开关

"为什么不能让 bot1 自由盖 original_caller、bot2 照单全收?" 三个不可省的理由:

  • 防 bot1 伪造发起者。original_caller 是 bot1 自己盖的,没有门槛则 bot1 能在任意调用谎报"我替 bot某 来的"钻别人权限空子。proxy_allowed 把"bot1 可当代理"做成 owner 预授权的信任缓存——只在 owner 信任的边上,bot1 盖的 original_caller 才被认可。
  • 保证普通边不被代理语义污染。proxy_allowed=false 的边,看到 original_caller 直接拒。普通协作边永远干净,不会误带代理语义——这正是"普通调用零负担"的保证。
  • 代理链可审计的最小信任边界。一次代理调用必须两证齐全:发起者被授权(caller3→bot2 边)+ 代理被信任(bot1→bot2.proxy_allowed),缺一不可。没有 proxy_allowed 就缺了"代理被信任"这一证。

3.5.3 什么时候加 proxy_allowed、什么时候加 original_caller

# proxy_allowed(边属性):由谁、何时加 默认 false —— 所有普通边都是。 当且仅当 bot2 owner 决定"让 bot1 当 bot2 的代理通道"时, 在授权/改约 bot1→bot2 边时主动拨成 true。由被调方(bot2) owner 设; bot1 自己不能为自己开(否则自提权)。 # original_caller(消息印章):由谁、何时加 bot1 运行时,决定"这次调 bot2 用什么模式"时: 读自己 bot1→bot2 边的 proxy_allowed: false → bot1 不能选代理模式,original_caller 一律不带(自用/外包自用) true → bot1 被允许(非命令)选代理: 选"替 caller3 转" → 带 original_caller=caller3 选"自用外包" → 不带 # 关键:proxy_allowed=true 是许可(permissive)不是命令(imperative) # original_caller 的值必须是真实发起者(caller3)身份,从请求追溯,bot1 不能凭空指一个 bot

3.5.4 代理转发的双闸校验(单跳)

bot2 收到带 original_caller=caller3 的代理调用,做两道闸,缺一拒:

caller3 → bot1 → bot2 (bot1 当代理): bot1→bot2 段,bot2 端双闸: 闸A 代理信任: bot1→bot2.proxy_allowed = true (代理被信任) + bot1→bot2 边 rules 对本次 tool call allow (代理者有权限调 bot2 做 X) 闸B 发起者授权: caller3→bot2 边 rules 对本次 tool call allow (发起者被授权做 X) 全 allow → 终局 allow;任一 deny / 边不存在 → 拒(未授权必拦)
回到最初担心的越权:caller3 没被 bot2 授权(闸B 扣除)→ 拦死;bot1 自作主张当代介但边没开 proxy_allowed(闸A 扣除)→ 拦死;两者都齐 → 放行,且这次调用花的是caller3 自己在 bot2 上的权限,不是借道 bot1 的——多级代理不放大权限。

3.5.5 多级代理:信任逐段传、发起者恒定带

允许 N 级代理。整条链靠两样东西传递:

# 链路:caller3 → bot1 → bot1' → bot1'' → bot2 (三段代理) # ① 信任:每条代理边 proxy_allowed=true,由"被调方 owner"逐级预授权 bot1 →bot1' .proxy_allowed = true ← bot1' owner 设 bot1' →bot1''.proxy_allowed = true ← bot1'' owner 设 bot1''→bot2 .proxy_allowed = true ← bot2 owner 设 # 哪段没开,链就断在那段;没有谁一次性授权整条链 # ② 发起者:original_caller 从第一跳盖定,中途原样直传、不改值 bot1→bot1' : original_caller = caller3 bot1'→bot1'': original_caller = caller3 (不改) bot1''→bot2 : original_caller = caller3 (不改) # 中途代理者在变,但发起者恒等于 caller3。不篡改是协议硬约束
跳谁发→谁做判什么
① caller3→bot1发起者调首个代理普通:看 caller3→bot1 边 rules allow?
② ③ ...中间代理跳代理→下一个代理代理闸A:本段代理边 proxy_allowed=true + rules allow?
(中间代理不判发起者授权,只保证"能往下一跳转")
末跳 →bot2末代理→最终执行者闸A + 闸B:本段代理边 allow + caller3→bot2 边 allow?
(发起者核对只在最终执行处一次)
分工:信任逐跳分散(每段独立授权代理边),发起者核对最终集中(只执行者做一次)。每跳只看自己那段 + 一个恒定的 original_caller 常量——不回溯发起者,既消除死结①,又在终点兜住发起者授权。
三个必须钉死的边界:① 链长限:复用 delegation_depth,每过一跳代理 depth-1,到 0 不允许再代理;② original_caller 不可篡改:中途代理若改成自己,就是冒充发起者逃校验,协议层硬禁止;③ 整条链成立 = 每段代理边都 proxy_allowed=true(信任齐) AND caller3→bot2 边 allow(发起者被授权),两条件独立,任一不满足断链——故多级代理不会放大权限。

5. 求值:多边 allow 优先 + 平台守卫兜底

多边必然带来"多条边对同一个 tool 给了不同 decision 怎么办"。本方案定 allow 优先(用户拍板),并配平台守卫做安全兜底。

5.1 两档优先级(守卫 + 角色边 allow 优先)

由于 friend=default 边(§3.1),"走 default"不再是一个单独的退路档——default 就是一条和其他角色边平等参与 allow 优先的角色边。求值从三档塌成两档:

对一次 tool call (caller A → bot B, tool, args),按以下顺序判: ① 平台守卫(最高,不可被任何边覆盖) 命中守卫 deny(如 Bash(rm -rf /)) → deny · 熔断 命中守卫 ask(internal_directory 等) → 转 bot 第二层审批(本稿不展开) ② 角色边(A→B 的所有 approved 边,含 default 边,allow 优先) // 注:若本次消息带 original_caller(代理转发),先按 §3.5.4 双闸处理; // 否则按下方普通求值 任一边(含 default 边) allow → allow 无 allow、有 deny → deny 全未命中(含连 default 边都没有/都没命中) → deny(零信任) # 原"第三档 default 退路"已并入第②档:default 是一条角色边,和其他边一起 allow 优先 # caller 若连 default 边都没建 → 直接 deny(没有熟人关系即无入场)

5.2 allow 优先的真值表

只看第②档(角色边之间),A→B 的所有 approved 边(含 default 边)对本次 (tool,specifier) 的产出。注意:default 不再是独立退路档,它就是表里的一条边,和其他边一起按下方规则参与:

边集合命中情况终局直觉
任一边(含 default 边) = allowallow有人放行就放行
无 allow,有 denydeny没人放行,但有明确拒,则拒
全未命中(含 default 边也没命中)deny没人表态→零信任从严(无独立 default 退路档)
塌档说明:原"第三档 default 退路"已删除——default 是一条角色边,它若 allow 就在第①行放行、若 deny 或未命中就走第②/③行。不存在"落 default"这个独立动作。caller 若连 default 边都没建,则该对点无任何 approved 边,直接落入第③行 deny。

5.3 两个必须说清的边界

① 单条边内部,deny 仍从严

allow 优先是边与边之间。一条边(角色)内部的 deny(Edit(/prod/**)),仍然是"这条边对 Edit(/prod) 投了 deny"。只有当另一条边给了 allow,这条边的 deny 才被压过。即:deny 在"同一角色内"从严,跨角色时被 allow 压过。

② 绝对禁止靠平台守卫

allow 优先下,普通挂一条 deny 边拦不住别人挂的 allow。所以"谁都不能做"的兜底(删根、删家目录、外访内网)交给平台守卫层——它最高优先级,绕开 allow 优先,不归 owner 配、不可取消。安全否决权回到该在的地方,又不破坏"角色边之间 allow 优先"。

为什么 allow 优先(而非 briefing 原版的 deny 优先):协作场景里我们希望 bot 尽量能被放行去干活,多角色叠加时"有一个角色允许就放行"更贴合"尽力服务"。代价是普通 deny 边不能用来收紧,收紧只能靠平台守卫层——这是有意的取舍:把"绝对禁止"和"角色放行"分层,前者守卫、后者角色。

5.4 代理跳的求值(与普通求值的关系)

§5.1~§5.3 讲的是"普通调用/外包自用"的求值。代理转发(§3.5)是另一条路径,两者关系:

调用类型触发求值
普通调用 / 外包自用消息无 original_caller§5.1 两档:守卫→角色边 allow 优先(含 default 边,逐跳看自己边)
代理转发消息有 original_caller§3.5 双闸:代理边(闸A)∧ 发起者→执行者边(闸B),再叠加守卫①
关键:多边 allow 优先(§5.2)是同一对点之间多条角色边的合成;代理双闸(§3.5.4)是不同对点(代理者边 + 发起者边)的合成。两者粒度不同、不冲突:同一对点的 N 条边先内部 allow 优先合成一个跳的 verdict;若是代理跳,再把这个 verdict 与发起者边的 verdict 做 AND。守卫①永远是最高优先级,两类都在其后。

16. 环节八:平台守卫兜底(allow 优先下的安全闸)

allow 优先意味着普通 deny 边拦不住别人挂的 allow。若有人给 bot2 挂了 allow Bash 的边,而 Bob 想跑 rm -rf /——靠角色边拦不住。这时平台守卫出手:

# 守卫层(最高优先级,先于角色边判) Bash(rm -rf /) → deny 熔断(删根/删家目录,任何边都盖不掉) Bash(rm -rf ~) → deny 熔断 external_directory → 转审批(触工作目录外路径) doom_loop → deny(重复N次)
守卫不是角色边,是独立一层,不归 owner 配、不可取消、最高优先级。它先判,过了才进角色边的 allow 优先合成。这样把"绝对禁止"(守卫)和"角色放行"(边)分层,各自职责清晰:守卫保安全底线,边做协作灵活。

逐跳 AND + 委托收紧,合力给出一个界:链上任意 bot 能做的事,恒 ⊆ 发起 caller 在第一跳被允许做的事。无需回溯发起者即可得到这个界——这正是 briefing 想要、旧方案做不到的性质。
