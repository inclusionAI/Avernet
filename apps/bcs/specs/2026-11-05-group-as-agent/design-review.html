BCN Group A2A 方案评审

评审日期：2026-11-12 · 代码核对基线：origin/dev · 9a61798cb7 · 协议：A2A 1.0.1（线上版本字段 1.0） · 状态：待评审

一句话：让外部 Agent 像调用一个 Agent 一样调用 BCN 协作群：发消息、看进度、拿结果、续聊、取消。对外使用标准 A2A 1.0（HTTP+JSON / SSE），群内由 manager 协调成员，或按自定义流程完成工作。群是可复用的 Agent，Session 承接连续对话，Task 记录每一轮执行。

本次评审希望得到的结论：

  1. 对外接口与 A2A 符合性边界：标准内的选择、支持子集、BCN 扩展是否可接受（§4）。
  2. 同 context 并发：本期采用忙碌拒绝（409 / CONTEXT_BUSY），FIFO 排队放下一期待定（§3.2）。
  3. 完成判定：主从群复用 manager 的 task.complete 与 summary，强绑定本轮 Task/activation；先返回受理 ack，再等 manager 退出并收尾，终态提交后才释放占用（§3.1、§3.4、§5.5）。
  4. 收尾有时限：执行有期限，取消后确认停止也有期限；到期仍无法确认旧执行已停止，就先暂停该会话接受新一轮，确认停止后再恢复（§3.5）。
  5. metadata 扩展发布方式：Card 声明可选扩展，请求用 A2A-Extensions 激活；扩展 URI 与 Schema 使用仓库地址（§4.4）。caller / user 的命名和凭据传递方式待定。
  6. 产物持久化与后续范围：Artifact 单独建表持久化，并为非文本类型预留；自由聊天群接入 A2A 留待后续讨论，自然语言建群暂不考虑（§1、§5.4、§5.7）。

逐项记录结论见 §8。

1. 背景与目标

现状与缺口

对象已有缺口
BCN 单 Bot单 Bot 聊天入口、Card 管理、A2A 出站标准 A2A 入站仅为设想，单独排期，不在本期

要解决的问题

第三方 Agent、Fuse 等上游需要把“一个协作群”当作一个可复用的 Agent 使用，而不必知道群里有哪个 manager、哪些成员，或者流程怎么定义。群内的 Session、Run、节点、投递各有自己的状态，需要统一投影成标准的 Task 状态、过程消息和最终结果。

核心要求：对外是标准 A2A 1.0 协议，不是 BCN 私有接口。

  • 标准客户端直接可用：支持 A2A 1.0 HTTP+JSON 绑定的客户端，不需要 BCN 专有 SDK 或群内知识，读取 Agent Card 就能发现、发送、流式订阅、查询和取消。
  • 用标准对象表达群：Group 对外就是一个 Agent，一轮执行对应标准 Task，上下文用 contextId，状态、过程消息和产物都走标准的 Task / Message / Artifact / Part。
  • 偏离有边界且显式声明：只有“支持标准的子集”和“可选扩展（required: false）”两类，不使用扩展也能完成完整调用；详见 §4。

核心模型

Group = Agent

一个 Group 对外发布一个 Agent，Card 发布在 /agent-card.json。上游不传 manager、成员、工作流定义或 provider 参数。

Session = context

contextId 直接使用 Session.id，不新增映射表。同一 context 内连续对话，保留上一轮结果。

一轮执行 = Task

每次独立执行对应一个 Task，绑定一次 Session activation 或一个 Run；每个 Task 保存独立结果，下一轮不覆盖。

3. 调用流程

3.1 一次完整调用

受理、执行和完成流程相同，区别只在客户端如何取回过程与结果。本期 Card 声明 streaming=true、pushNotifications=false，因此有三种取回方式：

调用方式首个响应取回过程与结果适用场景
message:streamSSE 首帧 Task（SUBMITTED，含 taskId / contextId）同一连接持续推送状态、过程消息和产物，终态后关闭；断线后用 subscribe 或 GetTask 恢复需要实时进度
message:send + returnImmediately=true立即返回 Task（SUBMITTED，含 taskId / contextId），不等待执行客户端用 GET /tasks/{taskId} 轮询，直到终态长任务，不便保持长连接（推荐）
message:send（默认 returnImmediately=false）终态或中断态才返回 Task，单次等待最长 60 秒返回即含最终结果；超时返回 504 / SEND_WAIT_TIMEOUT，Task 继续执行，再用 GetTask 取回预期很快完成的短任务

A. 流式（message:stream）。首次发送省略 contextId，BCN 创建 Session 与 Task，并在流的第一帧返回 taskId / contextId。

B. 非流式（message:send + GetTask 轮询）。以 returnImmediately=true 为例：受理后立即返回 Task，执行在后台继续；客户端保存 taskId，按自己的间隔轮询。

3.2 多轮与并发

同一 context 同一时间最多运行一轮。上一轮到达终态并完成收尾后，同 contextId、不带 taskId 的新消息会创建下一个 Task，旧结果保留；运行中到达的新请求被拒绝，不排队。

3.3 受理校验顺序

  1. 验证调用主体、协议版本和输入能力（含 acceptedOutputModes 协商、扩展字段是否已激活）。
  2. 验证目标群及资源归属（group_id、caller_principal、是否为 A2A 创建的 Session）。
  3. 原子查重：同范围同 messageId 且请求指纹一致，复用原 Task；指纹不同报冲突。
  4. 校验 caller/user 来源绑定与 Task / context 状态（空闲 / 忙碌 / 隔离，隔离指暂停接受新一轮，见 §3.5）。
  5. 新受理：原子保存 ID 预留、初始 Task 和 context 占用，然后启动执行。

忙碌、参数错误及来源冲突都发生在预留之前，不预留新的 messageId。错误清单见 §4.5。

3.4 Task 状态与完成判定

群执行事实A2A 状态提交条件

manager 成功提交最终 summary；或 Run 成功且取得指定最终节点输出COMPLETED冻结本轮派发，完成事件投影和结果快照；Artifact 写入 artifacts 表，并与终态在同一事务提交

“完成”只由显式信号触发。普通聊天最后一条消息、Worker 的单项完成、或一段时间没有消息，都不会触发 COMPLETED。主从群要求 task.complete 精确指向本轮 Session / activation / Task，禁止回退到“该群最新 Running Session”。自由聊天群没有这类显式信号，其结束判定和产物定义留待后续讨论，见 §5.7。

接受完成信号后的顺序：① 原子关闭本轮新派发，确认待办与结果回送已完成，固定最终结果和事件边界；② 先向 task.complete 请求返回受理 ack；③ 再等待 manager 当前执行退出并完成本轮清理；④ 提交结果与终态，释放 context 占用。manager 的调用可能发生在其自身执行结束之前，所以不能在收到信号时立即释放（下一轮会与上一轮重叠），也不能在返回 ack 之前等待其退出（会相互等待）。manager 退出或清理超时，进入同一套有界收尾。

REJECTED：本期没有独立的业务拒绝入口，不主动生成该状态；受理前校验失败返回协议错误，受理后启动或执行失败映射为 FAILED。REJECTED 仍是标准终态，取消与订阅的终态规则继续覆盖它。

manager 迟迟不提交完成信号：本轮已无运行中或排队的 manager / Worker 调用、待回送结果、定时重试和尚未确认停止的工作时才开始空闲计时。连续空闲 60 秒仍无 task.complete，向 manager 发一次提交最终汇总的提醒，再给 120 秒宽限；仍未完成则 FAILED，对外原因为“执行未提交最终结果”。每个 Task 最多提醒一次，提醒标记和截止时间持久化；SSE 心跳、普通过程文本和日志不重置计时，Worker 正常执行但没有过程消息不会被判失败。60 / 120 秒为建议值，见 §8.1。

3.5 取消与异常收尾

取消覆盖整轮工作，不只是修改状态：

  1. 持久化取消意图，与完成提交互斥；停止生成新的派发。
  2. 主从群覆盖 manager、Worker 和结果回送；状态机覆盖活动节点、等待节点、定时重试和已派发 Bot 工作。
  3. 对已启动工作发出取消并追踪确认；收尾期限内保持占用。
  4. 确认全部停止并完成收尾后写入 TASK_STATE_CANCELED，释放占用；确认前 CancelTask 返回非终态 Task 并通过 status.message 给出进度。

异常收尾保证 Task 不会长期停在 working，context 也不会无限被占用：

情形Task 与执行context
超过执行期限、Worker 失联、意外等待输入停止派发并发出取消，收尾期限内确认；正常收尾后 FAILED停止确认并保存结果后释放
用户取消，期限内确认停止CANCELED释放，可开始下一轮
收尾期限已过，仍无法确认旧执行是否已停止标记 FAILED，说明“未能确认停止”；不再接收这一轮的新派发和事件，并记下待核实的工作隔离：暂停接受新一轮，查询原 Task 不受影响。同 context 的新消息返回 400 / FAILED_PRECONDITION，reason=CONTEXT_UNAVAILABLE（附原 taskId 与恢复提示）；后台有限次重试核实并告警，确认旧执行已停止后恢复
进程重启读取绝对截止时间、执行代次和已派发关联，不重置预算，不重复启动恢复占用或隔离；旧代次结果无法进入新一轮

举例：Task-1 正在让 Worker 干活，上游发来取消。BCN 通知 Worker 停止，但 Worker 断网没有回应，超过收尾期限仍判断不了它是否还在执行。这时：

  • Task-1 标为 FAILED，让上游不再空等。
  • 这个 context 暂不接受 Task-2，避免与可能仍在运行的 Task-1 同时执行。
  • 后台继续核实；确认旧执行已停止后恢复 context，之后可创建新 Task。FAILED 的 Task-1 保持终态，不会改写。

不采用“占用超时就自动放开”：超时只说明没收到回复，不能证明 Worker 已经停了，放开可能让两轮同时执行。能让旧执行在限定时间内停下，或在停不下来时隔离，是开放 Group A2A 前必须具备的条件。

4. 对外接口（A2A 符合性）

符合性结论

  • 协议绑定：A2A 1.0（规范 1.0.1），HTTP+JSON + SSE；Card 的 supportedInterfaces 声明真实地址、binding 与版本，客户端读 Card 后选择接口。
  • 标准操作：Agent Card、SendMessage、SendStreamingMessage、GetTask、ListTasks、SubscribeToTask、CancelTask 均使用标准路径和标准对象。
  • 标准客户端零改造：不使用任何 BCN 扩展字段，也能完成“发送 → 查询/订阅 → 取消”的完整调用。
  • 偏离只有两类，并在 Card / 错误中声明：支持子集（输入类型、并发、运行中追加），以及可选扩展（required: false）。
  • 本期不支持的标准能力：Push Notification（Card 声明 false）、运行中追加消息（UnsupportedOperationError）；文件输入和 input_required 下一期支持（文件见 §4.7），在此之前文件 Part 返回 ContentTypeNotSupportedError。

4.1 接口一览

基地址：/api/v1/collaboration/a2a/groups/{group_id}。HTTP JSON 请求使用 Content-Type: application/a2a+json 与 A2A-Version: 1.0；流式响应使用 text/event-stream。

接口A2A 操作返回与说明性质

POST /message:sendSendMessage{"task": …}；Group 固定返回 Task标准
POST /message:streamSendStreamingMessageSSE：先 Task，再状态与产物事件，终态后关闭标准

路由实现：当前 axum 0.8.9 / matchit 0.8.4 不允许动态参数后直接拼接 :cancel 等后缀。适配层统一注册 /tasks/{task_action}：GET 把捕获值整体当作 taskId，不拆分；POST 只匹配末尾的 :cancel / :subscribe，去掉后缀后 taskId 必须非空。未知 action 或缺少后缀返回 404；taskId 非法或请求体 id 与路径不一致返回 400；不做重复 URL 解码。对外 URL 仍是上表的标准形式，路由契约测试覆盖两个 action、GET、空 ID、未知后缀和 body 不一致。

SSE 保活：message:stream 与 subscribe 在无业务事件时每 15 秒发送一次 SSE 注释 : keep-alive。它不是 A2A 事件，不写入 Task.history，不受 includeProgress 控制，不延长执行期限或完成宽限，终态后随流停止。适配层及时 flush、部署关闭该路径的代理缓冲，网关空闲超时须大于心跳间隔；网关总时限独立生效。断线重连先取当前 Task 快照，已终态则改用 GetTask，不保证事件逐条重放。

同 context 并发不并行、不排队；忙碌 409。协议并不要求 context 级别的忙碌状态，这是 BCN 的调度选择子集
向 working Task 追加UnsupportedOperationError；协议允许服务端选择不支持子集
metadata 扩展字段includeProgress、caller、user，可选，见 §4.4；caller / user 的命名与凭据传递方式待定扩展
业务错误 reasonCONTEXT_BUSY 等，使用标准错误结构（error.details[] 的 ErrorInfo），reason 由 BCN 定义扩展
同步等待上限单次 HTTP 等待有上限（建议 60 秒），到达后返回 504 / DEADLINE_EXCEEDED，不会成功返回 working Task；业务执行继续扩展
请求体上限建议 1 MiB（含 message / configuration / metadata），网关与适配层都校验；超限返回 HTTP 413，在解析与受理前拒绝，不创建 Task扩展

4.4 BCN 扩展：调用来源与过程消息

已明确的 includeProgress 放在 SendMessageRequest 顶层的 metadata，可省略。来源与用户信息暂称 caller / user，名称、内部结构和凭据载体待联合设计；下表保留讨论候选，接入示例只使用已明确字段。

字段含义规则
includeProgress是否生成并返回过程消息（分工、阶段进展、阶段总结）默认 false；本轮首次受理时固定，续聊可重新选择；所有订阅者看到同一份事件流
caller（命名暂定）调用 BCN 的上游 Agent候选为 {id, name?}；字段名、结构和必填性待定；不作认证键
user（命名暂定）上游 Agent 背后的用户候选为 {id}；字段名、结构、必填性和凭据传递待定

待定项（在 spec 中列为待定）：

  • 字段命名：metadata 里调用来源和用户信息的字段叫什么、内部结构如何，尚未确定；caller / user 只是暂定名。
  • 凭据与认证信息的传递方式：上游的身份凭据放在 metadata、HTTP 头还是其他位置，尚未确定，与认证机制一并联合设计。
  • 不变的约束：无论如何命名，metadata 里的来源信息只是上游自称，不作认证键、不进入去重范围；本期资源归属仍用现有 caller_principal 校验。Schema 在命名确定后定稿。

发现与激活：Card 的 capabilities.extensions 声明一个 required: false 的扩展，params.metadataSchema 描述 Schema；请求使用已定义字段（当前为 includeProgress）时，以 A2A-Extensions 请求头列出扩展 URI。出现已定义字段却没有激活时，在创建 Session/Task 前返回 400 / CALL_METADATA_NOT_ACTIVATED。

来源绑定候选：创建 context 时保存来源，后续省略则继承；显式更换或补绑定返回 400 / FAILED_PRECONDITION · CONTEXT_SOURCE_CONFLICT，另建 context。该规则与来源字段合同一并确认。

为什么 includeProgress 是扩展：A2A 1.0.1 规范里没有用于“是否返回执行过程 / thinking”的标准请求字段，也没有标注“这是思考”的标准类型。SendMessageConfiguration 只有 acceptedOutputModes、taskPushNotificationConfig、historyLength、returnImmediately；其中 historyLength 只裁剪返回的历史条数，不决定过程消息是否生成。规范提供的是承载位置，而不是开关：

层面A2A 标准能力性质
过程内容放在哪TaskStatusUpdateEvent.status.message（Message + Parts）、Task.history、流式 Artifact 分片（append / lastChunk）标准
是否允许附加信息Message、Part、Artifact 均有 metadata；规范明确允许用扩展机制扩展 Message 与 TaskStatus Message，携带任务进展的额外信息标准
客户端是否要求过程消息无标准字段；规范只描述 Agent 可在状态更新中附带 Message，没有让客户端“要求 / 不要”的入口，且不保证全部写入 history需扩展
消息是否为“思考 / 阶段摘要”的类型标记无标准类型，只能由约定的 metadata 表达需扩展

因此本期的做法是：承载用标准结构（过程消息就是普通 status.message，标准客户端看到的是可读文本，不需要识别扩展），开关用 metadata.includeProgress（经 A2A-Extensions 激活）。不使用扩展时，客户端不会收到分工、阶段进展等过程消息，仍能拿到状态、错误和最终结果。若改为“总是发送”，会带来三个问题：不需要的客户端被噪声打扰；Task.history 变大；增加内部信息暴露面（公开内容规则见 §5.6）。

另外，A2A 的设计原则之一是 Opaque Execution：Agent 协作不需要共享内部思考、计划或工具实现。所以 includeProgress 返回的应是经过整理的阶段性公开进展（分工、阶段进展、阶段总结），而不是 manager / Worker 的原始思考或工具输出。

4.5 错误模型

错误使用标准结构（HTTP 状态 + error.details[] 中的 ErrorInfo）。标准错误按 A2A §5.4 映射；大写 reason 由 BCN 定义，不属于标准。HTTP 状态与响应中的 error.code 一致，error.status 使用对应的 gRPC 状态名，reason 放在 ErrorInfo 中。

场景HTTP / status · 错误性质
未知、跨群或不可访问的 Task404 / NOT_FOUND · TaskNotFoundError标准
向 working 或终态 Task 发新消息；订阅已终态 Task400 / FAILED_PRECONDITION · UnsupportedOperationError标准
取消已终态 Task400 / FAILED_PRECONDITION · TaskNotCancelableError标准
输入或输出媒体类型不支持400 / INVALID_ARGUMENT · ContentTypeNotSupportedError标准
同 context 已有执行409 / ABORTED · reason CONTEXT_BUSY（details 含 contextId、activeTaskId）；查询原 Task，结束后重试扩展
旧执行无法确认已停止，context 暂停接受新一轮400 / FAILED_PRECONDITION · reason CONTEXT_UNAVAILABLE；附可见的原 taskId 与恢复提示，不自动重发业务消息扩展
context 来源绑定冲突400 / FAILED_PRECONDITION · reason CONTEXT_SOURCE_CONFLICT；候选绑定规则，与来源合同一起确认扩展
未知、跨群、不可访问或非 A2A 创建的 contextId404 / NOT_FOUND · reason CONTEXT_NOT_FOUND扩展
同 messageId、不同请求内容400 / INVALID_ARGUMENT · reason MESSAGE_ID_CONFLICT扩展
同 messageId，Task 结果已清理404 / NOT_FOUND · reason MESSAGE_RESULT_EXPIRED；预留保留，不再次执行扩展
使用扩展字段但未激活扩展400 / INVALID_ARGUMENT · reason CALL_METADATA_NOT_ACTIVATED扩展
单次同步等待达到上限504 / DEADLINE_EXCEEDED · reason SEND_WAIT_TIMEOUT；可见时 details 带 taskId / contextId，查询或订阅原 Task扩展
请求体超过上限413；在解析与受理前拒绝，不创建 Task扩展

SEND_WAIT_TIMEOUT 由 BCN 定义，A2A 标准错误表没有这一项。网关自行返回的 504 可能没有上述 JSON 结构，上游应按“结果未知”处理，用已知 taskId 查询而不是重发。

5.6 事件投影：轮询与 SSE 共用一份 Task

bcs_events 提供群执行中发生的事实；轮询和 SSE 是上游获取 Task 状态与结果的两种出口，它们读取的是同一份已保存的 Task，两者的状态和结果必须一致。

层次处理内容上游看到什么
群执行与 bcs_events（已有）节点启动、任务完成、manager 消息等业务事实BCN 内部消费
A2A 状态与结果保存（待补齐）关联本轮 Task，更新状态和 history，Artifact 写入 artifacts 表；处理重复和迟到事件一份可查询、可恢复的 Task 快照
GetTask 轮询（待补齐）读取已保存的当前快照（Task 与 artifacts）；查询本身不推进执行请求时的最新状态与结果
message:stream / subscribe（待补齐）先返回 Task 快照，再按顺序发送已保存的变化；artifactUpdate 来自 artifacts 表标准 TaskStatusUpdateEvent / TaskArtifactUpdateEvent

事件里的 task_id 是 BCS 内部任务，需经本轮执行关联找到 A2A taskId；sequence 只在各自 stream 内有序，聚合多个 Worker/Run 时要为本 Task 保存确定的输出顺序和消费位置，并按 event_id 去重。终态提交顺序：关闭本轮派发 → 固定各源 stream 的完成边界 → 投影边界内应公开的过程事件 → 在同一事务中写入 artifacts 表与终态；终态后的迟到回调只进内部追踪，不产生公开事件。

内容来源对外处理
