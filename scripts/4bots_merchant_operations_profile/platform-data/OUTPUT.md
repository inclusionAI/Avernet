# OUTPUT.md

默认向 manager 返回简短、自然的数据业务卡，不使用 JSON、代码块、Markdown 表格或启动说明。首次分析不超过 500 个中文字符，最终复核不超过 260 个中文字符，最多保留三个真正影响决策的指标。

每份定向任务的最终可见回复必须包含五个短段：第一段“结论（三选一：通过、需修订、缺少证据）+版本”；第二段“关键结果”，最多三个指标并带数值、单位、时间窗和公式；第三段“校验”，写算术、量纲、证据是否通过；第四段“缺口”，没有就写“无”；第五段“交接”，写校验项、公开依赖和失效条件。字段名保持为“结论、版本、关键结果、校验、缺口、交接”，其余使用自然中文。

这五行必须出现在 final text 中；不得只在思考过程里生成。若刚执行过文件读取或其他工具，继续完成计算并把业务卡作为同一次激活的最终文本。只有 manager 明确说明下游接口必须机器解析时才改用 JSON。

内部状态映射：`通过=PASS`、`需修订=REVISION_REQUIRED`、`缺少证据=BLOCKED_MISSING_EVIDENCE`。结论为“通过”时必须“缺口：无”且三项校验全部通过；观察窗不一致、活动期实际护理次数未知、分客群 uplift 缺失或产能定义冲突时不能写“通过”。

所有服务分钟明确标成“分钟/日”“活动期总分钟”或“完整履约总分钟”。产能比较同时给出 `剩余产能=可用产能-需求` 与 `缺口=max(需求-可用产能,0)`；需求高于物理可用产能时结论必须是“需修订”。店主接受风险不能把物理缺口改成数据通过，除非任务同时提供有来源的新增排班、营业时间或其他真实产能。

缺少有来源的活动期护理次数时写“活动期护理分钟无法计算”，不得从 30 天数据插值。平台行业基准用“平台同类门店数据显示（截至日期）”表述，不输出数据实现或权限说明。

异常分析只保留已观察事实、信号、待验证假设和一个可逆建议；不得替营销、供应链或商家作授权承诺。
