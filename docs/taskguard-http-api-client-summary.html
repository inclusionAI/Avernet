01

背景与问题

开源版 taskguard 的社区存根 ApiClient 对所有方法返回 { ok: false }——它不实际发出任何 HTTP 请求。 这意味着在纯开源环境下，taskguard 无法与 evolvetrace 通信，所有 API 仓库的操作静默失败。

用户的真实需求：开源版 taskguard 也可以通过 API 请求到 evolvetrace，就像 clawmind 请求 clawweb 一样。

设计约束

当 privateKeyB64 配置时使用 Ed25519 签名；为空时发送无签名请求。

服务端 signatureMiddleware 在 publicKeyB64 为空时是 no-op（接受所有请求）。

API 仓库采用「最佳努力写入」策略：catch 异常返回 false/空，不抛出，与 DB 仓库行为一致。

02

架构设计

CLIENT

HttpApiClient

使用 Node 内置 http/https 模块的真实 HTTP 客户端，替代返回 { ok: false } 的存根。

SIGN

Ed25519 签名

消息格式 ${timestamp}.${JSON.stringify(body)}，通过 crypto.sign() 签名，服务端 crypto.verify() 验证。

EXT

API 扩展点模式

_extensions?.createApiClient → corp 注入；或 new ApiClient(config) → 社区真实实现。

MAP

响应信封映射

服务端返回 { success, data, error }，ApiClient 映射为 { ok, data, status, error }。

请求流程ARCHITECTURE
// taskguard (客户端)
ApiClient.request(method, path, body)
  |  构建 JSON body
  |  if (privateKeyB64)
  |    |  timestamp = Date.now().toString()
  |    |  message  = `${timestamp}.${JSON.stringify(body)}`
  |    |  signature = ed25519.sign(message, privateKey)
  |    +  headers["X-Signature"] = signature
  |       headers["X-Timestamp"] = timestamp
  |  http/https.request(url, { method, headers })
  +  parse response -> { ok, data, status, error }

         v  HTTP

// evolvetrace (服务端)
signatureMiddleware
  |  if (!publicKeyB64) -> next()  // no-op, accept all
  +  verify signature -> next() / 401

routeHandler
  |  business logic
  +  res.json({ success, data, error })

DeployHistory 实现细节

deploy_history 的写入逻辑是分离的：deploy 命令调用 POST /api/workflows/save 时设置 skipDeployHistory: true，然后自己通过 POST /api/internal/deploy-history 写入 deploy_history 记录 （自己计算 version 和 deploy_number）。

deploy-history-api-repository.tsTypeScript
export class DeployHistoryApiRepository {
  constructor(private api: ApiClient) {}

  // 写操作 -> POST /api/internal/deploy-history (签名)
  async insert(input: DeployHistoryInsertBody): Promise<boolean> {
    const resp = await this.api.post("/api/internal/deploy-history", input);
    if (!resp.ok) {
      if (resp.status === 409) return true; // 409 = version exists
      throw new Error(`deploy-history insert failed: ${resp.error}`);
    }
    return true;
  }

  // 读操作 -> GET /api/workflows/:id/history (无签名)
  async getLatestDeploy(packId, workflowId) {
    const resp = await this.api.get(
      `/api/workflows/${workflowId}/history`, { limit: "1" }
    );
    return resp.data.history?.[0] ?? null;
  }
}

泛型参数传了整个响应信封 { success, data }，但 parseResponse 已解包 data 字段。 修复：泛型从 { success: boolean; data: { deleted: number } } → { deleted: number }。

同上原因，同样修复方式。

ERROR 4 — Signature
registry.ts: listAll expects 0 arguments but got 2
listAll(botId, botOwnerId) 传了 2 个参数但方法签名不接受。 修复：增加 botId?: string, botOwnerId?: string 参数。
ERROR 5 — Async Type
index.ts: iamtokenProvider type mismatch
() => string 不兼容 () => Promise<string>。 修复：改为 async () =>。
ERROR 6 — Missing Property

FacadeBindingRow 无 bot_id/bot_owner_id 字段 （facade binding 按 command 绑定，不按 bot）。修复：移除客户端过滤，参数改为 _botId/_botOwnerId 忽略。

17 个存根 API 仓库分析

除了已实现的 6 个核心仓库外，还有 17 个存根 API 仓库。分析结果： 14 个被实际实例化（在 API 模式下 super(null as any) 会在运行时崩溃）， 1 个是死代码，2 个未被实例化。

运行时风险

存根的 super(null as any) 将 db 设为 null。当任何方法被调用时，会尝试访问 this.db.xxx()，导致 Cannot read properties of null 运行时崩溃。

其中 WorkflowSpecApiRepository 最关键——被 5 处引用，走 GET /api/workflows/:id 已有端点，实现成本最低。
