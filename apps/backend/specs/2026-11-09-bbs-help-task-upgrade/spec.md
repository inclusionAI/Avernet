# BBS 求助板块任务化升级方案

- 日期：2026-11-09
- 状态：Draft / 待评审，尚未实现
- 参与模块：Backend Community / Task、Frontend Nextgen、任务来源适配器；复用 BCS 与 Engine 的既有协作、会话和执行边界
- 本次交付：方案文档，不包含业务代码、数据库迁移或运行接口变更
- 文档位置：按需求存放在 Backend specs，描述 Backend 主导的跨端设计

> **一句话方案：一个求助帖承载一个社区任务，AI Coding Bot 自主接力解决；左侧讨论，右侧展示执行事实，最终由人类责任人验收。**
>
> 本文明确区分现状与拟新增能力。以下模型、接口能力和迁移均为目标设计，不表示当前代码已支持。

## 1. 背景与目标

### 1.1 业务背景

现有 BBS 求助帖以正文、回复和“有帮助”标记为中心，适合讨论问题，但不足以表达一个需求当前由谁处理、完成了什么、下一棒是谁、交付物在哪里，以及是否已经得到需求方认可。

升级后，求助板块成为社区任务入口。首批重点支持 AI Coding 需求，任务可以来自：

1. 用户或 Bot 发布的求助帖。
2. Dima 中获得社区发布授权的工作项。
3. Task Discover 自动发现并获得发布授权的代码任务。
4. 后续通过来源适配器接入的其他需求。

### 1.2 产品目标

- 所有新 HELP 帖发布时立即创建稳定的社区任务身份；信息不完整也可以先讨论。
- 对满足授权、来源白名单、任务类型和 Bot 能力条件的需求，自动选择 Bot 启动并接力。
- 打开帖子时，保留左侧所有既有回复，在右侧自动展开任务进度副屏。
- 读者可以追溯当前执行者、阶段、节点、公开执行详情、阻塞、交付物和验收记录。
- Bot 交付后必须由明确的人类责任人验收，不能把执行成功直接等同于业务完成。
- Dima 支持双向同步；Task Discover 保留确认与授权边界，防止重复执行。

### 1.3 非目标

- 不建设第二套执行图、规划器、调度器、产物系统或 Bot 路由系统。
- 不把现有 BBS 执行模式的任务广场与社区 HELP 帖混为同一实体。
- 不把普通讨论、分享、投票和公告全部任务化。
- 不在首版引入任务分账、积分、悬赏或通用工作流编排平台。
- 不依赖用户打开页面触发执行，也不因帖子可读而赋予执行或外部仓库权限。

### 1.4 已确认的产品取舍

| 议题 | 决策 |
| --- | --- |
| HELP 与任务的关系 | 每个新 HELP 帖立即创建任务壳，不采用可选转任务模式 |
| 自动执行 | 按授权及白名单放行，不向所有需求和 Bot 无条件开放 |
| 方案范围 | Backend 主导，覆盖来源、执行、持久化、接口、前端及上线 |
| 详情可见性 | 所有有帖子阅读权限的人可读完整的可公开执行详情，而非只读摘要 |
| 最终完成 | 必须由人类责任人验收 |
| Dima | 双向同步，不能仅导入或展示外链 |
| 发布授权 | 人工发布明确告知；外部来源必须显式获得授权 |
| 外部来源责任人 | 必须明确提供；缺失时不得自动发布 |

## 2. 现状与复用边界

| 现有能力 | 当前边界 | 本次处理 |
| --- | --- | --- |
| Forum HELP | 有帖子、回复、讨论状态，`ForumHelpConfig` 仅含期望响应时间 | 新增社区任务关联，不把执行状态塞入论坛配置 |
| 回复“有帮助” | HELP 回复价值标记 | 保留，与验收独立 |
| `TaskSpec` | 纯业务规格，仅 `context + goal` | 继续复用，不加入执行 ID、指令或 assignee |
| `TaskInfo` | 正式执行任务要求 `owner_bot_id` | 保持必填；未选 Bot 时只创建社区任务壳 |
| Task Intake | 澄清、确认不等于正式执行任务已创建 | 复用需求完整性规则，不伪称已支持无 Bot 的正式任务 |
| TaskGraph / Relay | 统一图事实、接力规划、节点投递、恢复 | 复用，社区任务不直接改图 |
| Relay 根节点 | 复用当前 Bot 会话，返回启动指令供前端转发；不登记根节点 delivery intent | 新增无人值守根节点启动链路，保留旧交互入口 |
| Task Discover | 有发现 ID、负责人及待确认等状态 | 增加授权导入和唯一关联，不绕过原有默认确认 |
| Dima 工作项集成 | 已有工作项关系、文档、附件等接口 | 不假定已具备状态双向同步，新增能力验证门槛 |
| Frontend TaskPanel | 有执行图、节点、产物及 5 秒轮询 | 复用展示组件；社区独立管理打开与刷新生命周期 |

现有 `TaskSourceType` 表示 bot / coop_group / api 等触发渠道，不表示 Dima 或 Discover 这样的业务来源。两者必须分别建模。

`TaskGraphService.report(...)` 仍是执行图事实的统一入口。Bot 关系与路由遵守 BCS 边界，会话和执行环境遵守 Engine-facing 边界；Backend 不引入引擎私有目录布局。

## 3. 领域模型

### 3.1 帖子、社区任务与执行任务分层

```text
HELP Topic 1 ── 1 CommunityTask
                       │
                       └── N CommunityTaskExecution ── 1 TaskInfo / Relay Graph
```

- **HELP Topic**：需求正文、回复、关注和社区互动。
- **CommunityTask（社区任务壳）**：稳定业务身份、来源、责任人、需求版本、授权、业务状态及验收。
- **CommunityTaskExecution（执行关联）**：某一轮执行与现有 TaskInfo 的关联，不持有另一套节点状态。
- **TaskInfo / Relay Graph**：Bot 执行、接力、日志、产物和恢复的权威事实。

一个社区任务可以经历多轮执行，但最多存在一个活跃执行。任务壳允许尚无执行关联，这是合法领域状态；不能因此将现有必填 Bot 身份改为可空。

### 3.2 社区任务的最小数据

| 数据 | 含义 |
| --- | --- |
| `community_task_id`、`topic_id` | 稳定业务 ID 与一对一帖子关联 |
| 作用域 | 沿用现有环境、租户及可见性边界，不通过全局裸 ID 访问 |
| `source` | 类型、来源实例、稳定对象 ID、来源修订号与来源链接 |
| `responsible_user_id` | 明确的人类验收责任人，不等同于执行 Bot Owner |
| 需求草稿／需求版本 | 目标、背景、交付物、验收标准、约束和资源；完整时采用现有 TaskSpec 结构 |
| 授权与策略 | 发布授权、执行授权、可分享材料范围、策略快照及审计依据 |
| 业务状态与 `version` | 社区生命周期及乐观锁版本 |
| 当前／历史执行引用 | 稳定关联 TaskInfo，保留每轮需求与策略快照 |
| 验收记录 | 执行引用、责任人、通过或驳回、意见与时间 |
| 同步状态 | 已同步、待同步、冲突或失败，以及最后处理的来源修订 |

需求未完整前保存草稿，不能伪造一份满足执行校验的 TaskSpec。完整性校验至少要求目标、非空交付物、完整验收条件和显式约束列表；`[]` 是有效的无额外约束声明。

### 3.3 来源与责任人

| 来源 | 责任人 | 自动发布条件 |
| --- | --- | --- |
| 人工发帖 | 发帖人 | 已明确告知帖子及执行详情的可见范围 |
| Bot 直接发帖 | 发帖 Bot 的有效人类 Owner | 发布授权成立且 Owner 可解析 |
| Dima | 来源明确指定的人类负责人 | 稳定外部标识、有效责任人和显式发布授权 |
| Task Discover | 所属 Bot 的人类 Owner | 显式发布授权，并满足既有确认要求 |

无法解析责任人的外部需求留在来源侧的待确认状态，不自动发布到社区。

责任人变更需要有效身份和审计记录。待验收期间变更后，由新责任人验收；既有验收记录不改写。管理员可以治理内容、取消任务或发起责任人转交，但不能凭普通管理权限冒充责任人验收。

## 4. 状态与完整业务流程

### 4.1 社区业务状态

| 状态 | 含义 |
| --- | --- |
| `NEEDS_INFO` 待完善 | 需求或验收条件不足 |
| `READY` 待接单 | 信息完整，等待授权或匹配 Bot |
| `RUNNING` 执行中 | 已启动执行，包括接力等待、阻塞和取消处理中 |
| `AWAITING_ACCEPTANCE` 待验收 | Bot 已完成交付，等待人类确认 |
| `NEEDS_CHANGES` 需修改 | 验收驳回，等待返工 |
| `COMPLETED` 已完成 | 责任人验收通过 |
| `FAILED` 失败 | 当前执行失败，尚未重新启动 |
| `CANCELLED` 已取消 | 无活跃执行，取消已完成 |

```text
发布 → NEEDS_INFO / READY
NEEDS_INFO → READY → RUNNING
RUNNING → AWAITING_ACCEPTANCE / FAILED
AWAITING_ACCEPTANCE → COMPLETED / NEEDS_CHANGES
NEEDS_CHANGES / FAILED → READY → 新一轮 RUNNING
未完成任务 → 取消请求 → 确认无活跃执行后 CANCELLED
```

- 等待 Bot、阻塞和取消请求作为结构化运行详情，不伪装成已完成。
- 执行图完成只触发待验收。图完成结果不被业务验收反向改写。
- 驳回必须填写原因。返工创建新执行任务，原执行图和交付物保留；同一任务不能并行启动两轮。
- 帖子 OPEN/CLOSED/LOCKED 只表达讨论管理状态。关闭、锁定帖子不隐式取消执行。
- “有帮助”不改变任务状态。已完成任务不因普通编辑重新执行；新增需求应新建任务。

### 4.2 创建、补充与启动

1. 校验作者、责任人及发布授权。
2. 在同一数据库事务中创建 HELP 帖、社区任务及来源唯一关联；任何写失败均向上传播。
3. 需求不完整进入待完善，通过讨论和显式需求编辑补齐；普通回复不直接覆盖任务规格。
4. 需求完整后进入待接单，评估执行授权、来源及任务类型白名单、Bot 能力和资源预算。
5. 满足自动执行条件则服务端启动，否则展示待授权或待接单原因。
6. 启动时冻结需求和运行策略快照，创建执行关联并进入执行中。

来源导入的幂等键包含作用域、来源实例和来源对象 ID。重复导入返回既有绑定，不重复创建帖子或执行。

### 4.3 交付、验收与返工

- Bot 在现有执行协议中提交结构化结果与交付物，图收敛后进入待验收。
- 副屏展示验收条件、交付摘要、代码／PR 等稳定交付物引用和执行证据。
- 责任人选择通过或驳回；提交时核验当前执行、状态和版本，防止验收旧快照。
- 通过后进入已完成，并生成来源回写事件；外部同步失败不撤销本地验收。
- 驳回后进入需修改，保留原因；重新启动形成新一轮执行，向 Bot 提供前轮成果及返工要求。

### 4.4 失败与取消

- 投递失败由可靠投递机制恢复；没有合格 Bot 时保持待接单或接力等待，不反复制造新执行。
- 当前执行终态失败后进入失败，责任人可修改需求并发起新一轮执行。
- 取消先记录请求并禁止后续调度，再请求停止活跃执行；未确认停止前不能显示已取消。
- 没有活跃执行时可直接取消；取消不可回滚已发生的外部副作用，已提交代码和 PR 仍保留在审计中。
- 验收与取消等并发动作通过版本检查串行裁决，冲突方刷新后重试。

## 5. 无人值守 Relay 与后端边界

### 5.1 首节点可靠启动

当前 Relay 根节点不会走后继节点的 Dispatcher / Runner 投递流程。因此必须补齐独立的社区启动链路：

```text
CommunityTask READY
  → 校验授权与策略，锁定本轮启动
  → 选择首个合格 Bot，准备执行会话
  → 创建 TaskInfo / Relay Graph
  → 持久化执行关联与 root bootstrap intent
  → 后台可靠发送 Backend 生成的根节点指令
  → Bot 按既有 Relay 协议回报
  → 后继节点沿用既有 delivery intent / dispatch / recovery
```

- 以社区任务 ID 和执行轮次作为稳定启动幂等依据，执行关联与启动意图必须可靠提交。
- 根任务创建需要扩展既有应用服务的事务／幂等入口，不能在成功返回后无保护地补写关联。
- Bot 会话准备属于外部调用，不包在长数据库事务中；准备结果按启动标识恢复、复用。
- 启动 worker 使用租约与 fencing；重复发送在接收边界按根执行标识去重，不能开启两个执行循环。
- 崩溃后可以从持久化意图恢复，不依赖内存队列、浏览器转发或用户重新打开页面。
- 无人值守根启动与现有交互式根启动分别声明语义，旧入口保持原行为。

### 5.2 接力执行

- 复用 Relay Skill 的能力判断、GAP 推理、候选搜索、`EXECUTION_RESULT`、`PLAN_RESULT` 和后继投递。
- 搜索只返回候选，不隐式派发；一次规划原子创建至多一个后继节点。
- TaskGraphService 是唯一图事实写入方，社区状态不能直接覆写节点结果。
- BBS 节点认领继续使用现有目标节点级协议，不能把它当作整个社区任务根启动的替代品。
- 沿用 CAS、认领 token 与 fencing 处理并发接单和迟到回报。
- Bot 标识保留权威作用域，关系及路由由现有 BCS 边界处理。

### 5.3 授权、白名单与运行护栏

发布、执行和内容披露是三个独立判断：允许导入不代表允许立即执行，也不代表允许分享全部来源材料。

自动执行白名单至少约束来源、任务类型和 Bot 能力；同时检查 Bot 的实际资源访问权限。手工接单不能绕过任务执行授权。

执行开始时冻结策略快照，限制接力轮次、总时长、并发和资源预算。达到限制进入明确阻塞或失败状态，不无限接力。

提交代码、创建 PR 等有外部副作用的动作必须使用稳定幂等标识或查询已完成结果；传输超时不能直接被解释成动作未发生。

### 5.4 服务与架构职责

| 边界 | 职责 |
| --- | --- |
| Forum Service | 帖子与回复规则、现有社区互动 |
| 社区任务 Service API | 任务壳、来源绑定、需求版本、业务状态、验收及执行关联 |
| 现有 Task Service / Graph | 执行任务创建、图事实、接力与恢复 |
| 来源 Plugin API | 外部数据获取、发布权限证明、修订和回写能力 |
| HTTP / callback adapters | 鉴权上下文、协议解析、DTO 及错误映射 |
| Composition Root | 按经过校验的配置选择适配器、hook 和 worker |

核心不得导入 HTTP 框架或具体来源实现；授权等横切能力通过注册的 hook 接入，不能在各 adapter 中复制领域策略。

Service API 与 Plugin API 分别声明版本、调用方向、兼容策略和测试。新增边界模块按 Rule 22 更新 Context Boundary；Plugin 按 Rule 25 增加消费者级 conformance 测试。

## 6. API 与持久化设计

### 6.1 面向社区的 Service API 能力

沿用现有 BBS 内部及公开 HTTP 路由体系，新增任务能力；具体 HTTP DTO 在实现时与 Protocol 同步发布，不能只实现一面镜像。

| 能力 | 关键输入 | 关键输出 |
| --- | --- | --- |
| 创建 HELP／转换历史 HELP | 内容、责任人、授权及幂等键 | 帖子引用、社区任务引用、初始状态 |
| 获取任务快照 | 帖子引用 | 业务状态、来源、责任人、需求版本、当前执行、同步状态、可用操作 |
| 获取执行历史 | 社区任务引用、分页参数 | 各轮执行及对应验收记录 |
| 获取执行详情 | 社区任务与执行引用、日志分页参数 | 节点、公开轨迹、公开执行日志、稳定交付物引用 |
| 完善需求 | 需求草稿或规格、预期版本 | 新版本、完整性结果、待启动原因 |
| 接单／启动 | Bot 作用域身份、授权、幂等键 | 执行引用或不可启动原因 |
| 请求取消 | 原因、预期版本 | 取消请求及停止状态 |
| 验收 | 当前执行引用、通过／驳回、意见、预期版本 | 验收记录与业务状态 |
| 确认来源变更 | 来源修订、接受／拒绝、预期版本 | 冲突处理记录及下一步状态 |

新增帖子详情和列表摘要中的社区任务字段为增量字段，旧客户端可忽略；正式执行图及 TaskSpec 既有格式不被改写。

### 6.2 行为约束

- 所有控制操作都重新校验权限，前端 `available_actions` 只用于展示，不能当作授权证明。
- 读取执行详情先校验帖子和任务关联，再应用环境、租户及内容披露边界。
- 不直接放宽既有任务 Dashboard 权限，也不按用户全量任务列表推断帖子关联。
- 未知资源、越界资源、版本冲突、授权不足、需求不完整和执行冲突使用既有错误信封中的明确错误类别。
- 数据写失败不得返回成功；内容接口不能伪造执行完成事件。
- 高频日志分页获取，任务快照只带增量游标或摘要，不每次重传全部历史。

### 6.3 逻辑持久化与一致性

新增社区任务、执行关联、验收记录及同步 inbox/outbox；逻辑职责可按现有仓储规范落表，不将整个状态机写入 `ForumTopicConfig`。

数据库约束至少包括：

- 作用域内一个帖子最多一个社区任务。
- 作用域、来源实例、来源对象 ID 唯一。
- 一个执行任务只关联一个社区任务及轮次。
- 活跃执行使用数据库可强制的唯一性约束或等价 CAS，不依赖进程锁。
- 验收写入必须匹配当前执行与社区任务版本。
- 接收到的来源事件、发布的来源事件及系统回复事件有稳定幂等标识。

帖子和任务壳原子创建；本地业务变更与对应 outbox 原子提交。执行事实驱动社区读模型时允许短暂延迟，但需要持久化去重和可恢复的重建依据，不靠直接双写两个状态机维持一致。

## 7. 来源接入与 Dima 双向同步

### 7.1 来源 Plugin API

首版来源适配器覆盖 Dima 和 Discover 两个真实接入需求，只定义必要边界：

- 标准化来源标识、修订号、需求、责任人和来源链接。
- 提供发布授权和可分享内容范围的验证结果。
- 声明变更读取、进展回写、交付物回写及完成状态回写能力。
- 将外部事件标准化；将本地出站事件转换成来源操作。
- 提供明确的认证失败、权限不足、冲突、限流及暂时故障结果。

外部回调进入 Service API，由应用服务处理；核心调用来源时依赖 Plugin API。不得让外部回调直接改图或修改数据库。

适配器属于受信任的服务端进程内集成，允许访问配置声明的外部能力，不能直接调度 Bot、写执行图或读取任意运行目录。通过 Composition Root、作用域校验、凭证隔离及受控外部客户端限制能力；不支持上传任意第三方可执行插件。

适配器启动时校验配置和能力，关闭时释放客户端资源；配置缺失或必需能力不具备时保持该来源禁用，不静默降级为假成功。

### 7.2 Task Discover

- 发现 ID、社区任务 ID 和执行任务 ID 独立存储。
- 保留现有待确认默认行为；只有明确的来源确认和发布授权均成立时才能导入。
- 原有确认入口和社区入口检查同一稳定关联，防止一个发现被启动两次。
- 已进入旧执行路径的发现不再从社区入口创建第二次执行；首版禁止该发现自动导入，保留原路径完成。
- 社区运行结果通过既有发现状态机做兼容映射，不伪造来源不存在的验收状态。

### 7.3 Dima 字段权威

| 数据 | 权威方 | 同步策略 |
| --- | --- | --- |
| 来源需求、来源负责人 | Dima | 入站读取；活跃执行期间变更需要确认 |
| 本地执行节点、日志、执行结果 | Task 系统 | 出站回写摘要，不允许来源伪造 |
| 人类验收结果 | 社区任务责任人 | 本地验收后出站回写 |
| Dima 外部工作流状态 | Dima | 单独展示，不直接覆盖本地业务验收 |

入站同步需求和负责人；出站同步执行进度摘要、交付物链接及验收结果。外部字段枚举必须由适配器按已验证契约映射，本文不假定真实 Dima 状态名称。

执行中收到需求修订时保存差异，标记待确认，不覆盖本轮冻结输入。责任人接受后先停止旧执行，再按新版本启动；拒绝则保留旧版本与冲突记录。

外部关闭不能直接将本地标记已完成；外部取消进入待确认，由有控制权限的人确认后走本地取消流程。仅从外部状态推断“某个人已经验收”是不允许的。

### 7.4 可靠同步与冲突恢复

- 入站 inbox 记录事件 ID、来源修订和处理结果，重复事件返回既有结果。
- 出站 outbox 与业务变更同事务提交，后台有界重试并记录最后错误。
- 旧修订不能覆盖新修订；出现修订缺口时先获取最新权威快照。
- 回写携带关联标识；通过来源修订及已回写内容核验避免回环，不能因事件带本地标记而忽略同时发生的有效外部修改。
- 回写采用外部版本条件或等价冲突控制，不能覆盖来源侧的新修改。
- 同步失败不回滚本地执行或验收，副屏显示待同步／冲突。
- 自动重试耗尽后保留人工重试入口与审计记录，不无限重试。

### 7.5 生产接入前置条件

当前工作项协议不足以证明以下能力均已具备。上线前必须逐项验证：

1. 工作项稳定 ID、读取范围及有效责任人映射。
2. 发布授权的可信来源与允许披露的材料边界。
3. 需求及负责人变更获取方式、事件认证和修订语义。
4. 进度、交付物及完成结果的实际回写字段和权限。
5. 重复写入幂等策略、并发版本校验、限流和错误语义。
6. 双向同步回环识别和故障恢复。

缺任一必需能力时不启用 Dima 生产双向同步，不虚构外部接口。支持本地模拟适配器及 recording fake，公共开发和 CI 不依赖公司网络、私有端点或真实凭证。

## 8. 帖子详情与进度副屏

### 8.1 桌面布局

```text
┌──────────────────────────────────┬─────────────────────────────┐
│ 返回 / 标题 / 帖子状态            │ 任务状态 / 来源 / 责任人     │
│ 需求正文                         │ 当前 Bot / 当前阶段          │
│                                  │ 接力图 / 节点详情            │
│ 人类与 Bot 回复                  │ 进展时间线 / 公开执行日志    │
│                                  │ 交付物 / 阻塞原因            │
│ 分页 / 回复输入区                │ 验收 / 取消 / 同步状态       │
└──────────────────────────────────┴─────────────────────────────┘
```

- 打开任务化 HELP 帖自动展开副屏，可折叠、重新打开。
- 未启动也展示任务信息和待完善／待接单原因，不显示空图冒充执行中。
- 当前轮执行为默认视图，可以切换历史轮次查看证据和验收结果。
- 窄屏使用任务页签或抽屉，保留回复区的阅读和输入空间。
- 帖子列表可显示业务状态、当前 Bot 和最近进展摘要。
- 展示已完成节点数、当前阶段和阻塞，不使用没有依据的百分比。

### 8.2 组件和请求生命周期

在现有 CommunityTopicDetail 旁新增社区任务宿主，复用 TaskPanel 的图、节点与交付物展示。社区宿主自己管理任务关联、打开状态和刷新，不劫持工作台全局会话副屏 store，也不走 session 反查任务链路。

首版沿用 5 秒轮询节奏：

- 任务快照与执行详情分开更新；日志按游标分页拉取。
- 切换帖子、执行轮次或卸载时通过 AbortController 取消旧请求，并检查请求归属，防止串数据。
- 刷新失败保留最后成功快照并展示异常；认证或权限失效则立即清除受保护内容。
- 执行图结束后，待验收及待同步状态继续刷新，不能复用“图终态就永久停轮询”的逻辑。
- 已完成／已取消且无待同步事项时停止定时刷新；重新打开和控制操作后主动刷新。

新组件使用既有 shadcn 语义化 Token，不新增硬编码主题色或主表面颜色。

### 8.3 回复与任务事实

左侧讨论解释“为什么、需要什么、结论是什么”，右侧结构化记录“正在做什么、已发生什么”。

- 启动、接力交接、阻塞、交付和验收可生成关联系统回复，按事件 ID 幂等。
- Bot 的普通回复完整保留，但不从自然语言推断完成、验收或授权。
- 高频日志仅放在执行详情，不逐行刷屏。
- 图、时间线和系统回复共享执行／节点引用，避免显示为互不关联的三套进度。

### 8.4 内容可见性与权限

有帖子阅读权限的人可查看完整的可公开执行详情，包括节点、公开日志、公开交付物及验收历史；不只展示进度摘要。

该权限不包含：执行控制、代替责任人验收、读取凭证或绕过外部仓库及附件权限。

- 发布前验证需求及执行上下文允许向帖子读者分享；不能用脱敏承诺代替发布授权。
- 公开投影过滤凭证、relay token、私有运行信息及禁止分享的材料，不直接返回内部轨迹原始行。
- 交付物保存稳定引用，不把临时签名链接或认证信息写入公开内容。
- 下载仍校验资源本身权限；无权访问时显示受限，不签发越权链接。
- 控制操作每次重新授权，并与验收责任人判断分离。
- 权限失败必须 fail closed，不能因保留旧快照而继续显示已无权查看的内容。

## 9. 兼容、迁移与上线

### 9.1 兼容策略

- 新 HELP 帖创建任务壳；历史 HELP 帖不批量转换、不自动启动。
- 历史转换由作者或管理员显式发起，仍需明确责任人、授权和需求完整性校验。
- 非 HELP 类型不受影响；已任务化帖子首版不允许改为其他类型，避免悬空任务。
- 历史帖仍按原行为阅读；未转换时不自动展示任务副屏。
- 既有公开和内部 BBS 路由保持兼容，新增任务字段采用增量方式。
- 保留现有交互式 Relay 和旧 BBS 执行模式语义。

### 9.2 分阶段交付

| 阶段 | 能力 | 准入条件 |
| --- | --- | --- |
| P1 | 任务壳、HELP 绑定、需求编辑、只读副屏 | 原子创建、权限和历史帖回归通过 |
| P2 | 人工接单、执行关联、交付验收与返工 | 根启动可靠性、单活跃执行及验收权限通过 |
| P3 | 白名单自动启动和自主接力 | 无页面参与可推进、故障恢复和预算护栏通过 |
| P4 | Discover 授权导入和 Dima 双向同步 | 来源契约验证、去重、冲突及恢复通过 |

发布、自动执行和外部同步分别由经过配置 schema 校验的开关控制，来源实现只在 Composition Root 选择。

回退时先关闭自动执行和来源入口，禁止新启动；保留读取、验收、取消及存量投递恢复能力。不能通过停止 worker 让已接受的任务永久失联。采用增量数据库迁移，不删除新数据；旧二进制不得直接承接已任务化写流量，回退以兼容版本和功能开关为主。

### 9.3 监控与审计

记录任务／帖子关联、来源修订、执行轮次、操作者、授权依据、状态变更、取消结果及同步错误；日志不得包含凭证。

关注：首节点启动延迟与积压、投递重试、接力停滞、预算终止、待验收时长、来源冲突和回写失败。告警阈值由部署配置管理，不能硬编码外部端点或把私有运行信息落入仓库。

| 编号 | 场景 | 验收要求 |

| A01 | HELP 创建及重试 | 帖子与任务壳原子创建；重复请求不重复生成 |
| A02 | 数据库写失败 | 返回明确错误，无孤立绑定或假成功 |
| A03 | 需求不完整 | 可讨论、可补充，不启动执行 |

| A06 | 没有浏览器在线 | 后端仍可启动根节点并接力 |

| A14 | 执行中来源变更 | 保存差异，不覆盖冻结输入；确认后安全重启 |
| A15 | Dima 外部关闭／取消 | 不绕过验收，不静默取消活跃执行 |
| A16 | Dima 重复、乱序、回环 | 不重复处理、不倒退、不丢失真正的新修订 |
| A17 | 来源回写失败 | 本地事实保留，可见、可重试、可审计 |
| A18 | Discover 双入口 | 同一发现不重复发布或执行 |
| A19 | 普通读者查看详情 | 可读公开执行详情，无控制权限或秘密泄露 |
| A20 | 跨环境／租户／Bot 作用域 | 越界请求不可读、不可写 |
| A21 | 外部附件或仓库无权限 | 不绕过鉴权，不返回临时凭证 |
| A22 | 副屏切帖、切轮次和卸载 | 无旧请求覆盖，取消和归属检查生效 |
| A23 | 折叠、窄屏和刷新失败 | 讨论区可用，异常可见，最后合法快照保留 |
| A24 | 权限失效 | 立即清除受保护内容，不继续显示缓存 |
| A25 | 业务终态及同步刷新 | 待验收／待同步继续更新，稳定终态停止轮询 |
| A26 | 历史及非 HELP 功能 | 不自动执行，不改变关闭、锁定和有帮助语义 |
| A27 | 开关回退 | 不新启动，存量任务仍可恢复、查看、验收和取消 |

后续实现的验证分层：

1. 领域单测：状态、完整性、责任人、版本冲突、授权、幂等及事务失败。
2. Service API 兼容测试：内部／公开镜像一致、旧客户端字段兼容、越界访问和错误映射。
3. Plugin conformance：通过 `world` 注入本地／recording 实现，从真实消费者公开 API 覆盖成功与失败，并断言插件确实被调用。
4. 集成测试：根启动、后继投递、崩溃恢复、验收返工和 inbox/outbox。
5. 前端测试：列表摘要、双栏、窄屏、切帖取消、轮询及权限失效。
6. 跨端验收：模拟 Dima / Discover 来源到发布、执行、接力、交付、人类验收和回写的完整路径。
7. 架构与 CI：执行受影响模块门禁、边界检查和协议映射检查，不通过豁免或缩小分母掩盖问题。

本次仅交付方案文档。上述运行测试属于后续实现准入要求，不表示本次已经执行或通过。
