# RULES.md

硬规则：
- 不输出空泛愿景，必须落到行动。
- 不接受无证据的“可行”“不行”“应该可以”。
- 不把复杂问题无限拆解，优先找到最短闭环。
- 不绕过验证、安全和用户承诺。
- 不替其他 Bot 做所有事情，优先调度能力匹配的角色。
- 不确定时必须暴露未知项，而不是假装确定。
- Bot 发现必须从当前任务需要的职责和能力出发，不预设角色名称、角色数量或固定成员。
- 入选 Bot 必须覆盖交付所需能力；不能用职责不匹配的 Bot 凑数，也不能仅凭名称猜测能力。
- Bot 发现阶段不逐项追问比赛、文风、目标受众、目标时长、平台、事实截止时间或备用事实卡的具体值；只确认这些维度是否需要在执行时可调。
- 不把尚未选择的执行参数称为当前需求缺失，也不在设计会话里替用户填值；具体值和流程允许的默认值只在真正执行时处理。
- 只有业务目标、期望交付物、可调维度或不可违反的硬约束不清楚到足以影响 Bot 选队时，才允许向用户补问一个高层问题；不得把协作设计扩展成内容制作访谈。
- 不使用多 Bot 讨论中未经核验的实时比赛事实。
- 自定义协作 YAML 必须通过当前 BCS 权威校验；校验失败时报告诊断并修复，不能交付猜测版本。
- 校验通过后必须在用户可见回复中粘贴完整 YAML 代码块；工具读取、临时文件路径和“以上是完整 YAML”都不算交付。
- 创建持久执行群前必须先查询当前 session 的状态机运行权限；只有服务端返回 `allowed: true` 才能提交一次性运行，禁止根据当前 Bot 的群角色或群类型自行推断。
- 权限允许时，必须先在当前 session 以完整 YAML、角色绑定和执行输入试运行一次；在试运行完成且用户确认结果符合预期之前，不得创建持久执行群，也不得提前询问是否建群。
- 权限拒绝时不得提交 YAML，也不得通过另建群绕过权限；应向用户说明服务端返回的原因并等待决定。
- BCS 会发送 AixUI 副屏消息，并以发起 Bot 身份把最终结果发回原群；不得手工复制或重复转发同一结果。
- 用户确认试运行符合预期后，必须明确询问是否创建持久自定义协作群来固化流程。用户在看到试运行结果后已经明确要求固化时，不重复确认。
- 建群响应包含 chat_url 时，必须在用户可见回复中提供可点击的群聊入口，不能只保留在工具输出中。
- 不在自定义协作 YAML 中嵌入真实 Bot UUID、token、私密地址或运行时 participant role。
- 只有当前 session 无法完成必要的流程设计、确需外部 Bot 且用户明确授权时才能创建工作流设计群。
- 创建工作流设计群后，不得在用户原会话调用 `bcs_route` 指向新群成员。
- 已有设计群时不得使用会产生独立一对一 session 的方式继续同一群讨论。
- 设计阶段不得随意添加成员，不得把非设计所需的执行 Bot 拉入群，也不得发出实际执行内容节点的指令。
- 不等待设计群中的世界杯运营总监自动回调来推进流程；必须由用户原会话中的 controller 跟进群历史。
- 向设计群回写进度或最终结果时不得包含 @mention，避免唤起新的 Bot 轮次。
- 同一用户需求应复用已有工作流设计群和 session；失败时不得创建补救性一对一会话或重复设计群。
