# All-Bot BCN registration on create and desktop plugin routing

## Requirement and acceptance
All successfully persisted Bots attempt BCN provider registration during create, including desktop and provision=False/deferred creation. Engine/template capabilities and the legacy DRM registration switch must not suppress this attempt. Environment/provider credentials remain authoritative; registration is best effort, and failure must not block creation. No deployment, live Bot changes, migration, or merge is authorized in this task.

Across create/start/restart, the independent DesktopBotService.restart, and coding BaaS preparation, openclaw with bot_type personal or desktop uses plugin; all other combinations use existing default gateway/downlink. Preserve desktop lifecycle restrictions and durable restart ordering.

## Existing chain and boundaries
BotService.create_bot inserts the record and initializes capabilities, then desktop/deferred paths return early. Normal creation calls provision_bot -> _provision_created_bot, currently owning gated BCN registration before allocation. Move the registration attempt into the shared successful creation path before early returns, avoiding duplicate attempts when normal/deferred provisioning executes. Existing BcnService owns configured endpoints, credentials, HTTP behavior, idempotency and diagnostic boundary events.

The actual desktop endpoint is a separate chain: desktop/router.py -> DesktopBotService.create_after_authorization -> _execute_creation -> DesktopCreationLifecycle.execute. It inserts its own desktop Bot record and never calls BotService.create_bot. Register a newly inserted desktop Bot in this chain too, through an injected DesktopCreationLifecycleHooks callback. Preserve the existing lifecycle boundary: the focused lifecycle owns insertion/order; the callback delegates BCN policy and registration to the existing application service/helper. No registration side effect belongs in the HTTP router. Existing desktop creation re-entry must retain its idempotent behavior.

Allowed changes: BotService lifecycle registration orchestration and connection mode resolver; the minimal DesktopCreationLifecycle hook, DesktopBotService callback wiring and required dependency-provider wiring for the real desktop creation path; affected tests and scoped specs. These desktop changes are necessary because that path does not call BotService. Avoid introducing a direct circular BotService/DesktopBotService constructor dependency; use the established service-provider pattern where needed. Coding BaaS uses the same resolver, verify by test. Do not modify BCS, schemas, adapters, template capability definitions, unrelated creation behavior, engine runtime or deployment code.

## Methods and model
- create_bot: after successful record persistence and required initialization, call existing best-effort provider helper before any desktop/deferred return; use resolved name, description, actual owner, resolved engine/type, respect_drm=False.
- DesktopCreationLifecycle.execute / DesktopCreationLifecycleHooks: after BaaS handoff and final local binding/ext persistence succeed, invoke registration with the persisted owner/identity and actual engine/type. Retained-record retries repair missing registration; a true success marker skips duplicate registration. Callback failures must remain best effort and not alter BaaS claims or allocation semantics.
- DesktopBotService: wire the lifecycle callback to the existing registration policy/helper using the actual active_engine and bot_type=desktop. Do not duplicate provider HTTP requests, credential checks or success-marker persistence. DesktopBotService.restart reuses this helper after BaaS approval, with skip_registered=False so an existing success marker does not suppress restart registration. The authenticated lookup owner user_id remains authoritative; binding.entity_id may be staff-prefixed and is not the owner work number.
- _resolve_bcn_provider_connection_mode(active_engine,bot_type): return plugin for openclaw + personal/desktop, otherwise None (omit wire field; BCS gateway default).
- _register_bot_to_bcn_as_provider: reuse error handling and persistence of bcn_registered=True on successful/idempotent registration. Eliminate newly orphaned create-only qualification logic/imports if no callers remain.
- Bot fields: bot_id required string stable identity; owner_id required string owning user; active_engine string runtime; bot_type personal/service/desktop; ext.bcn_registered optional bool success marker, not realtime connectivity. No schema/API field changes.
- DesktopCreationLifecycleHooks is an existing internal orchestration dependency value object. Add a required callable for the creation registration operation, receiving Bot identity/owner/engine/name/description and returning no business result. It is not persisted or exposed through HTTP; update hook construction and test fixtures together. No new Bot fields are necessary.
- provider_bot_ref is existing bot_id:owner reference; connection_mode wire values plugin/gateway (omission means gateway). Tokens remain service-owned and absent from logs.
