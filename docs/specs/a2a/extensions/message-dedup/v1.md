# BCS A2A submission deduplication v1

Status: optional BCS client compatibility contract. The default Harness adapter
uses in-memory Task storage and does not advertise or implement this extension.
A host providing it must independently satisfy the durability guarantees below.

URI: `https://github.com/inclusionAI/Avernet/blob/dev/docs/specs/a2a/extensions/message-dedup/v1.md`

This optional Plugin API applies to new-task submissions with a nonempty
messageId of at most 256 characters. Both endpoints must negotiate this URI.
It provides durable at-most-once execution admission, not exactly-once delivery.

Within one authenticated Bot endpoint, the same messageId and equal semantic
SendMessage request identify one Task across HTTP send/stream, concurrent
requests and server restarts. Configuration, context, tenant, metadata and
parts are included in the input fingerprint. Reusing an ID with different
input is an invalid request. Changing send/stream binding alone is allowed.
Extension negotiation must remain unchanged across retries.

The server atomically reserves the messageId and persists its initial Task
before starting the engine. A duplicate returns the existing Task or subscribes
to its current updates; it never invokes the engine again. A completed Task can
be returned as a single stream snapshot. Failed/canceled Tasks are also retained.
Deletion or expiry of a Task must not allow its messageId to start a second
execution. Reservation records are retained for the lifetime of the Bot store.

An interrupted server fails unfinished Tasks on startup. A crash between durable
reservation and execution can therefore produce a failed Task without executing
the request; clients must surface that result, not silently create a replacement.
This is the explicit tradeoff of at-most-once admission.

BCS may retry an uncertain initial submission only when this extension was
advertised and negotiated, reusing exactly the saved messageId and request.
Without negotiation it reports an unknown outcome and does not resubmit.
Continuation messages for Structured Input are outside this version's scope;
their request/decision identity requires its own durable handling.
