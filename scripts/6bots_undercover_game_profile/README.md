# 谁是卧底游戏局

一套 6 Bot 的 OpenClaw profile，用来在 Avernet 的**主从协作群**里玩一整局"谁是卧底"：1 个主持人 Bot + 5 个玩家 Bot + 1 位人类玩家，共 6 名玩家。

一个协作群可以开多个会话，**每个会话就是独立的一局**。

## 角色

| Bot | 角色 | 人格 |
| --- | --- | --- |
| 谁是卧底主持人 | manager / 裁判 | 中立、有仪式感、只推进流程，永不参与推理 |
| 玩家稳健老陈 | worker / 玩家 | 稳健保守，话短、留余地，投票只跟扎实证据 |
| 玩家话痨小满 | worker / 玩家 | 跳跃联想，用生活场景和画面描述 |
| 玩家和事佬阿和 | worker / 玩家 | 共识跟随，措辞温和，倾向跟票 |
| 玩家逻辑控林工 | worker / 玩家 | 属性推理，用条件描述但严格按轮次控制宽窄 |
| 玩家戏精阿浪 | worker / 玩家 | 情绪带节奏，敢第一个指认 |

人格差异是这套 profile 的主要趣味来源：人类玩家唯一能读的"表情"就是这 5 种说话方式。

## 规则默认值

6 人 1 卧底、无白板、**不告知身份**（每人只拿到一个词）、词语难度 medium、最多 6 轮。
发言一句话 ≤25 字，且要满足本轮**钝度**（第 1 轮 4、第 2 轮 3、第 3 轮起 2：这句话念给局外人听，
他要能列出至少这么多样符合的东西）。投票**只交票号**（「我投4号」，≤10 字），不写理由。
平票判本轮无人出局，**直接进下一轮：不重投，也不在平票者中随机挑人**——但那一轮
照样算进轮数上限，所以平票对平民是纯亏。
卧底被投出 → 平民胜；场上只剩 2 人时卧底还在 → 卧底胜。

在建群时的"协作目标"里写别的配置即可覆盖，例如：

```text
谁是卧底 · 6人局（5 Bot + 我）· 卧底1名 · 词语难度 hard · 最多5轮
```

## 启动

先起 BCS 和前端：

```bash
./scripts/singlebox.sh start bcs_frontend
```

再起 6 个 Bot：

```bash
./scripts/singlebox.sh start bots --profile-dir scripts/6bots_undercover_game_profile
```

确认全部就绪：

```bash
./scripts/singlebox.sh status bots --profile-dir scripts/6bots_undercover_game_profile
```

6 个 Bot 都应显示 `Running`。默认端口 30801 起、步长 10。

## 开一局

1. 打开 <http://127.0.0.1:8000/>，进入 Avernet，切换到**人类视角**（不是 Bot 视角）。必要时先点"加入 BCN"。
2. 左侧"拉起协作"，按下面填：
   - 协作群名称：`谁是卧底`
   - 协作目标：`谁是卧底 · 6人局（5 Bot + 我）· 卧底1名 · 词语难度中等`
   - 协作群类型：**任务协作**（主从模式）
   - 成员 Bot：5 个玩家 Bot
   - 群主 Bot：**谁是卧底主持人**
3. 创建后会自动进入一个新会话。**在页面底部找到「用户协作」→「加入当前会话」并确认。** 这一步是必须的：人类参与者的默认状态是 absent，只有变成 Present，主持人才能创建带"用户输入"节点的协作。
4. 主持人会贴出开场白。回复 `开始`，主持人先在群里把**你的词**发给你（忘了随时问它
   "我的词是什么"），紧接着第 1 轮就开始了。

再开一局：在同一个协作群里新建一个会话即可。

## 一轮长什么样

```text
主持人：第二轮。还剩老陈、林工、阿和和你，四个人。这轮老陈先说，你第二个。
   ↓  轮到你时右侧副屏弹出输入框，你的词就在框的最上面
（发言在临时自定义协作里串行进行，主持人是最后一个节点，自动被唤醒）
主持人：四位都说完了。
        老陈（6号）开的头：「用起来得两只手，急不得。」
        …逐条逐字念完，每个人都带着号数…
        🗳️ 看两眼，我这就开投。
   ↓  转述稿回灌把主持人叫醒，它自己去开投，不用你说话
主持人：🗳️ 开投了。你的票箱在右边副屏。
（投票在另一个临时自定义协作里并行进行，所有人同时投、互相看不见）
主持人：🗳️ 票都回来了。老陈（6号）、小满（4号）、阿和（1号）都投了林工（5号）…
        三票对一票，☠️ 林工（5号）出局。身份先不公布。剩下老陈、小满和你。
   ↓  主持人给出局者派了遗言任务，回执把它叫醒开下一轮
        （平票那轮没有这一步：开票稿之后直接就是下一轮的回合开场）
主持人：林工（5号）临走撂了句：「我最不放心 4 号，『软面的边角起毛』那句不是一个路子。」
        好，第三轮。
```

**你每轮只做两件事：在副屏发言、在副屏投票。** 其余全自动——发言念完主持人直接开投。
副屏里属于你的那两个节点都写着「人类玩家」，别点别人的。

## 这套设计为什么是这个形状

### 信道

主从协作群有三条硬事实，整套 profile 都建立在它们之上：

1. **worker 收不到群广播**，连 @ 也收不到。所以聊天时间线天然就是"主持人 ↔ 人类"的私密双人频道 —— 给人类发牌、跟他对话，直接在群里说就行，Bot 一个字也看不到。
2. **发言和投票都在协作节点里**，主持人先看到、人类后看到。所以泄词可以在人类看到之前被遮蔽掉。唯一拦不住的是遗言，因为它是公开的任务回执。
3. **协作运行失败不会唤醒主持人**。所以每一步都必须把"下一次谁来唤醒我"安排好：发言轮由主持人自己作为末节点被唤醒；发言转述稿会回灌把它叫醒一次，那一次去开投（所以人类不用喊"开投"）；投票轮由主持人作为计票节点被唤醒；开票稿会以主持人的身份发成群消息、再回灌把它叫醒一次——**有 Bot 出局就在那一拍派遗言任务，由回执唤醒下一轮；平票或出局的是人类就在那一拍直接开下一轮**。这些唤醒源刚好串成一个环，全程不需要轮询或定时器。运行**失败**时这个环会断，兜底是人类的一句"卡住了"——开场白里会把 5 分钟的时限说清楚。

   **这个环里只剩一处 `bcs_assign_task`（有人出局那一轮的遗言），这是有意压到最少的。** 派任务和它的回执都会让服务端往主持人自己的会话里灌一条 `[任务状态]`，而那条灌入是直接覆盖会话文件的，会把主持人当时正在跑的激活打断（`session file changed while embedded prompt lock was released`）。2026-08-31 那一局 5 次激活因此被打断、白烧 203 秒，最后死在 `vote_open` 上。以前这里还有两条：一条派给已出局玩家的"看门狗"（2026-08-31 拆），一条平票时纯为叫醒自己而派的"预备任务"（本次拆）——后者一次完整的 Bot 激活只换回一句"我准备好了"，而开票稿的回灌本来就能叫醒主持人。

### 两个协作，不是一个

发言图是**传递闭包**而不是链：第 i 个发言者的下游指向它后面的所有人，因为节点提示里只包含直接父节点的产物，链式连接会让后手看不到更早的发言。

投票图是**扇出再汇合**：一个"开投"节点是唯一入口（服务端硬性要求零入度入口只能有一个），扇出给所有投票节点并行执行，最后在计票节点汇合——全场只有主持人能同时看到所有票。

**两个运行的入口节点都是主持人的**：流程推进只由主持人做，玩家 Bot 不当门房，而且入口节点的产物就是那一轮的开场稿——主持人提交完运行不必再说话，人类在提交后几秒就看到"第 N 轮开始"。

代价是一个已知风险：运行是主持人在自己的一次激活里同步提交的，入口节点会在提交那一刻排进主持人自己的会话通道，等主持人让路——通道一旦没及时释放（实测最长泄漏过 6 分钟），节点就一直排在队里。三道保险扛住它：入口节点超时 15 分钟、提交必须是那次激活的最后一个工具调用（所以有 `open-round` / `open-vote` 这两条把查槽位+渲染+提交合成一步的命令，而且"最后一个"是字面意思，`bcs_assign_task` 也算），以及**末节点里不做下一步**。

最后那道是 2026-08-30 补的。两个运行的末节点（发言汇总 / 计票）都是主持人的，而运行要等那次激活结束才算完成、协作槽位才释放。主持人如果在末节点里就去提交下一个运行，就成了「它等槽位、槽位等它」——那一局第 2 轮的发言汇总节点里跑了一次 `open-vote`，之后重试、`sleep`、轮询一路到节点超时，整局无声卡死。所以汇总节点只念转述稿、计票节点只念开票稿，下一步一律等回灌那一拍；脚本也会把这种自锁单独报成 `IN_COLLECT_NODE`，和「上一个运行刚收尾」的普通竞态区分开。

两个协作没有合并成一个，是因为合并之后"发言转述"会变成中间节点的产物，而中间节点的产物只进副屏、不进群聊，人类就看不到了。分开之后，发言转述才能作为第一个运行的最终产物自动发成群消息。

### 玩家 prompt：一条规则只写一处

玩家 Bot 每轮只输出十几二十个字，但 2026-08-31 那一局里每个发言节点平均要 35 秒
（最长 76 秒）才吐出第一个字——从 HTTP 200 到第一个 token 之间全是静默。原因是同一条
硬约束当时被写在四处（节点 instruction、`SKILL.md`、`RULES.md`、`OUTPUT.md`，外加
`HEARTBEAT.md` 的七条自检和 `SKILL.md` 的六条输出前自检），模型每写一句话都要对着四份
副本各验一遍；而钝度自检当时是**开放式**的——"念给局外人，他能列出至少 N 样吗"要求它
先在心里造一批候选物再逐个比对。

所以现在的分工是死的，改 profile 时不要破坏它：

| 内容 | 唯一归属 |
| --- | --- |
| 本次任务的词、座位、轮次、钝度 N、角度表、字数、票号写法、不许出现的字 | **节点 instruction**（`undercover.py` 渲染，带着真词，永远最新） |
| 任务类型判别、发言与投票怎么想 | `skills/undercover-game-player/SKILL.md` |
| 规则常识（几人几卧底、平票、胜负、为什么要钝、为什么不写理由） | `KNOWLEDGE.md` |
| 泄密红线与行为边界 | `RULES.md` / `SAFETY.md` |
| 人格、语气、风格示例 | `SOUL.md` / `OUTPUT.md` / `IDENTITY.md` |

profile 文件**不复述格式**，只说一句"以任务正文为准"。钝度自检也从开放式换成了闭合式：
角度表里挑一个 + 不出现类目名词 + 整句不下定义，这三条一起给出同样的钝度保证，而模型
不需要先把"这句话还能罩住哪些东西"列出来。字面泄词的兜底始终是 `check_text` + `mask`，
不靠模型自己逐字扫描。

### 事实层与表演层

- **事实层**：状态文件 + 协作节点产物 + `undercover.py` 的判定。
- **表演层**：人类看到的每一句话，由主持人用自己的口吻说出来。

主持人**不手写任何玩家的词，也不手算任何游戏状态**。抽词、排座位、分身份、生成协作 YAML、检查泄词、解析投票、计票、判胜负全部由脚本完成。这样"说得像不像人"永远不会影响"判得对不对"。

脚本的输出还天然脱敏：除 `render-*` 和 `reveal` 外，任何命令的输出都不含词和身份；而 `render-*` 把含词的 YAML 写进文件、只打印路径，所以**发言和投票的词一次都不经过主持人的输出通道**。

## 信息边界

| 内容 | 只允许出现在 |
| --- | --- |
| 某个玩家的词 | 它自己协作节点的 `instruction`（由脚本注入） |
| 身份（平民/卧底） | 主持人的状态文件。**任何人都不会被告知自己的身份** |
| 词对 | 终局公布 |

运行输入 `--input` 会出现在每一个节点的提示里，所以里面只有公开的发言史，永远不含任何词语。

**唯一的荣誉制约定**：前端副屏可以点开任意节点的产物详情。平台层不按人过滤节点产物，所以开场白会明确请人类玩家不要去点。

## 主持人在群里说什么、不说什么

Bot 在一次激活里写的**每一段**文字都会被转发成群里的一条独立消息，包括工具调用之间那些"我先看一下状态""确认是……"。人类看到的不是工作记录，是一串不知道该看哪条的碎片。所以整套 profile 反复压同一件事：

- **一次激活只留一段话，就是主持稿**，中间一个字都不写；
- **能一条命令做完的不拆成三条**（`begin` / `open-round` / `open-vote` 就是为此存在的），命令输出默认也压成一行，要详细才加 `--full`；
- 主持稿里**不出现流程术语**：阶段编号、phase 名、"激活/节点/唤醒源/预备任务/状态文件"；
- 有两次激活是**完全不说话**的：提交运行的那次（开场稿归入口节点），和派下一轮唤醒源的那次（开票结果上一条已经说过了）。

## 上手前的人工验收清单

改完 profile 或重启 Bot 后，跑一局最小验证：

- 主持人在人类加入会话前不发牌，而是提示去点"加入当前会话"。
- **同一个群里连开两局**：第二个会话里主持人贴的是开场白，不是"本局已结束"，
  更不会把上一局的词和身份念出来。
- 人类的座位号和身份每局都在变（连开三局，不应固定在同一位置或同一阵营）。
- 回复"开始"之后，群里立刻出现一条"你是 N 号，你的词是【X】"——这条在聊天记录里翻得回去。
- 副屏里属于人类的节点名带着"人类玩家"和座位号，一眼能认出来。
- 第 1 轮发言转述里，每个玩家的句子都不超过 25 字，都没有说出自己的词，每个人后面都标了号数，
  而且**都钝到能同时套在好几样东西上**——第一轮就有人把词描述死，说明钝度阶梯没生效；
  反过来六句全是纯感受、一个属性都没有，也不对。
- 主持人念稿是散文和逐字引语，不是表格，也没有出现 run_id、UUID、节点名或脚本命令。
- 发言念完投票**自动开始**，不需要你说话；开票时只报票向，没有任何人给出理由，主持人也没有替谁编。
- **连着跑完两轮以上**：发言转述和开投之间必须是两条消息、两次激活。转述稿刚发出来主持人就在同一拍里刷一串 `RUN_SLOT_BUSY`，说明末节点纪律又松了。
- 有人出局时，开票结束后主持人自动派出遗言任务，遗言回执之后自动开下一轮；
  **平票那一轮开票稿之后直接就是下一轮的回合开场，中间不该再有任何一条消息**——
  如果那里还冒出一句"某某说他准备好了"，说明预备任务没拆干净。
- 遗言有内容——出局者会点一个怀疑的号码并说清是哪句话让他在意，而不是只喊一句冤。
- 终局同时给出词对、每人的身份和词、关键转折，并结束会话。
- 5 个玩家的发言风格明显可区分，不会都变成同一种通用腔调。

## 已知限制

- 一个会话同时只能跑一个自定义协作，所以发言轮和投票轮严格串行，这是平台约束。
- 运行中任一节点最终失败会让整个运行失败，而主持人作为末节点**不会被唤醒**。因此开场白里会说明"超过 5 分钟没动静就回复 `卡住了`"。
- 目前没有取消运行的 CLI 命令。运行卡死时本局只能作废，新建一个会话重开。
- 同一时刻只支持一个待处理的用户输入节点，所以发言和投票必须分成两个运行。
- 人类中途退出 Present 状态会让下一轮的协作直接失败。
- **遗言是公开的任务回执，主持人来不及遮蔽。** 玩家 profile 里对此有硬规则，但这是唯一拦不住的泄词面。
- 每次任务派发和回复，BCS 会往时间线插一条 `[任务状态] …` 系统消息，profile 层关不掉，而且它会打断主持人当时正在跑的激活。本设计里只有"有 Bot 出局"那一轮会派一次遗言，所以每局大约 2×(出局轮数) 条，平票轮零条。这是 profile 能压到的下限——彻底消除要平台侧改成"driver 有在飞的激活时排队等它结束"。
