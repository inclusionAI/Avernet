# 集群执行器平面 —— 兄弟项目必须提供什么

[English](cross-item-notes.md) · 属于[集群执行器平面设计](design.zh-CN.md)

执行器平面依赖若干它自己不构建的性质。这里把它们列出来,以便每个兄弟项目据此设计。

## 第 2 项 —— 网关层(连接与中继)

网关层(设计 §7)持有所有长连接。第 2 项按以下契约构建它:

- **持有所有连接;不持有任何持久状态。** PA 的流与出站 A2A 流终结在网关上;
  每个供给智能体都是 BCN 拨出访问的 A2A 智能体。执行器一个都不持有。
- **把每个下游事件都发给会话的所有者**(设计 §7.2–7.3):增量每 200 ms 一批,发布到消息队列上该会话所在桶的增量频道,无需确认;控制
  事件(智能体的任务 id、`input-required` / `auth-required`、附拼好输出的最终
  结果)重试直到被确认。区分这两者是网关–执行器契约的一部分。
- **按控制消息逐条查找所有者**(提示缓存 + `NOT_OWNER`);绝不在整个运行期间记住某个所有者。正是
  这一点让会话可以在不碰任何连接的情况下移动。
- **按会话读取,绝不按所有者读取**(设计 §7.4):从最后中继过的条目 id 开始读 S 的 Stream
  (`session:{S}`);在发送 `Submit` 之前就开始读;丢弃围栏令牌比见过的最高令牌更旧的条目。重连时,
  从 Stream 的最新快照条目加上它之后的条目构建快照(设计 §7.5)。扇出的决定属于所有者;网关只中继
  追加给它的内容。
- **保留每个在途派发的输出**,直到所有者确认结果,并在收到 `FetchBuffer` 时交给新所有者
  (设计 §7.2);没有缓冲时,就查询智能体的任务(`GetTask` 或 `SubscribeToTask` 快照)来作答。

## 第 3 项 —— 执行正确性

- **在每个派发记录事务中使用围栏步骤:** 锁住该会话在 `bcs_task_leases`(每个桶一行)中所在桶的
  行并校验令牌。会话没有自己的租约。
- **记录每次派发在哪里执行:** 派发记录写明它的网关(任意健康网关;由接受的网关报告自己的 id),在围栏下写入。该网关死亡时,所有者把派发
  移到另一个网关,由后者按记录的任务 id 对账(读取或重新订阅,绝不盲目重发)。
- **对派发汇报去重**,按 `(dispatch, seq)`:网关会重试控制事件和结果,直到所有者确认。
- **复用同一本投递账本。** 派发意图记录应扩展已有的逐投递账本,而不是另建一本含义
  重叠的账本。
- **立刻记录智能体的任务 id:** 对有副作用的步骤用流式或 `return_immediately = true`
  派发,并要求以 Task 作答(裸 Message 在故障转移后无从查询)。已记录的 Message 响应
  即为终态。
- **把 `messageId` 作为幂等键**(按运行、步骤与尝试确定性生成),这样即使只按
  `messageId` 去重的智能体也能受益。
- **按请求可能在途的最长时间来确定去重窗口大小,而不是按认领阈值。** 暂停或被分区的
  所有者早已发出的请求,可能在后继接管很久之后才到达。窗口必须覆盖单次派发尝试的最长
  生命期(发送超时 × 重试预算 + 最大网络与排队延迟),再加上接管时间(认领阈值)和对账
  时间;发送方也必须强制这一生命期:超过它的尝试绝不再发送或重试。认领阈值只是其中一项。

## 第 4 项 —— BCN A2A 规范

- 关闭连接不得取消任务。
- `SubscribeToTask` 的快照必须包含到目前为止产生的每个 artifact:新的派发网关正是靠它
  找回一个步骤的部分输出。
- 智能体应把进度流式写入任务的 artifacts,这样重新订阅的后继不会看到空档。
- 任务与键已见集合的保留下限。

## 第 5 项 —— 面向个人智能体的接口

- **BCN 对 `SendMessage` 一律以 Task 作答**;调用方使用 `return_immediately = true`
  或流式(阻塞调用会在整个运行期间保持打开)。
- **PA 重试时必须复用 `messageId`。** BCN 在共享存储中按 `(caller, session, messageId)`
  原子去重。没有稳定的客户端键,这一跳不可能做到恰好一次,下游去重也无济于事:重复的
  一轮会变成带新键的新运行。
- **把花钱的步骤设计成对服务端提案的批准**("批准 P-123"),它天然幂等。
- **定义一轮请求在运行进行中到达时意味着什么:** 是该运行的输入、排队,还是以忙碌拒绝。
- **所有传输(gRPC、JSON-RPC、REST、SOFA)共用一套去重实现:** 适配器只负责提取键和
  调用方、对规范化后的请求做哈希以检测冲突,并把结果映射为原生错误。框架重试(gRPC
  对冲、SOFA 故障转移)让并发与跨节点的重复成为常态。
- **重连就是快照加继续:** 任何中断之后,PA 在任意网关上调用 `SubscribeToTask`,先得到当前
  Task,再得到实时事件。故障之后中间输出可能重置;最终结果精确。逐帧精确的 `Last-Event-ID`
  续传是一个可选的 BCN 扩展。
- **向 PA 的 webhook 推送**放在热路径之外(长时间重试、死信),可以走消息队列,也可以走写在
  带围栏提交里的 outbox。
- **"恰好一次"的措辞:** *每一跳都是至少一次投递;对经规范验证的智能体,在去重窗口内
  副作用实际上只发生一次;无法确定的结果会被如实上报,绝不猜测。*
